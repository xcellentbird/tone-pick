# 슬라이스 01 — 회차 생성 + 입장 코드

파일럿 슬라이스. 이 워크플로(시나리오 → 공개 표면 → 테스트 → 구현 → 리뷰)가 실제로 도는지 확인하는 게 목적이다.

`★` 는 프로토타입에서 **실제로 터졌던** 것. 테스트를 반드시 붙인다.

---

## 범위

**만든다** — 운영자 인증, 회차 생성(3스텝), 입장 코드로 회차 찾기, 단계 자동 전환(등록 시작까지).

**안 만든다** — 참가자 등록 폼, 콕, 자리, 발표, 데모 뷰, 참가자 삭제.
이 슬라이스 밖의 화면은 스텁 그대로 둔다. **요청받지 않은 기능을 미리 만들지 마라.**

---

## A. 운영자 인증

### S-A1 운영자 PIN 으로 전체 권한을 얻는다
```
Given  운영자 PIN 이 "1234" 다
When   운영자가 회차 목록 화면에서 "1234" 를 입력한다
Then   scope 는 { kind: "master" } 다
And    회차 목록을 조회할 수 있다
```

### S-A2 ★ 회차별 PIN 은 없다 — 운영자 PIN 하나로 모든 회차를 연다
```
Given  회차 X 와 Y 가 있다
When   회차 X 화면에서 운영자 PIN 을 입력한다 (eventId 를 함께 보내도)
Then   scope 는 언제나 { kind: "master" } 다
And    회차 X·Y 의 콘솔과 회차 목록이 모두 열린다
```

### S-A3 ★ 회차 아이디를 안다고 권한이 생기지 않는다
```
Given  회차 X 가 있고 그 아이디가 알려져 있다
When   아무 번호나 회차 아이디와 함께 보낸다
Then   운영자 PIN 이 아니면 401 이고 세션 쿠키도 나가지 않는다
```
> **왜** — 예전에는 회차마다 PIN 이 있었고, 두 PIN 이 같으면 회차 담당자가 전체 권한을 얻었다.
> `{"회차PIN":"0000","공통PIN":"0000","획득권한":"master","전체회차접근":true}`
> 검사 순서로 막는 대신 **권한을 한 종류로 줄여** 그 사고의 자리를 없앴다 (ADR-12).

### S-A4 틀린 PIN 은 거부한다
```
When   "9999" 를 입력한다
Then   401 이고 메시지는 HOST.pin.wrong 이다
And    응답 어디에도 올바른 PIN 이 들어 있지 않다
```

### S-A5 인증 없이 운영자 API 에 닿을 수 없다
```
Given  세션 쿠키가 없다
When   GET /api/host/events/{X} 를 호출한다
Then   401 이다
```

## B. 회차 생성

### S-B1 기본 설정을 물려받는다
```
Given  기본값이 { maxPre: 1, maxParty: 2, regOpenBeforeD: 6, prevoteBeforeH: 20 } 다
When   위저드를 연다
Then   maxPre=1, maxParty=2 가 채워져 있다
And    등록 시작은 **파티 6일 전**, 사전 투표 시작은 **파티 20시간 전**으로 채워져 있다
And    입장 코드가 자동으로 채워져 있다
```
> 일정 기본값은 전부 **파티 일시에서 거꾸로** 잰다. 운영자가 실제로 아는 건 "언제 모이나" 하나뿐이다.

### S-B2 ★ 회차를 만들 때 회차 PIN 을 받지 않는다
```
When   옛 입력대로 회차 PIN 을 함께 보낸다
Then   회차는 만들어지되, 그 번호로는 아무 문도 열리지 않는다
And    응답에 그 번호가 남지 않는다
```

### S-B3 ★ 입장 코드는 회차 사이에서 유일하다
```
Given  이미 코드 "ABC234" 인 회차가 있다
When   새 회차를 만든다
Then   새 코드는 "ABC234" 가 아니다
And    코드를 직접 "ABC234" 로 지정하면 거부된다
```

### S-B4 '지금 바로' 로 만들면 그 자리에서 등록이 열린다
```
Given  위저드에서 등록 시작을 '지금 바로' 로 둔다
When   생성한다
Then   phase 는 "reg" 다
And    fired.reg 가 채워져 있다
And    그 코드로 즉시 입장할 수 있다
```

### S-B5 예약해서 만들면 준비 중으로 시작한다
```
Given  등록 시작을 1시간 뒤로 예약한다
When   생성한다
Then   phase 는 "prep" 이고 fired.reg 는 비어 있다
When   서버 시각이 예약 시각을 지난다
Then   phase 가 "reg" 로 바뀌고 fired.reg 에 전환 시각이 기록된다
And    한 번 더 조회해도 fired.reg 는 덮어써지지 않는다
```
> **왜** — 예약은 상태가 아니라 **한 번만 울리는 알람**이다. 그래야 나중에 발표를 되돌려도
> 지나간 예약 때문에 즉시 다시 튕기지 않는다.

### S-B6 일정 순서가 뒤집히면 거부한다
```
Given  등록 시작이 14:00 이다
When   사전 투표 시작을 13:00 으로 저장한다
Then   거부된다
```

### S-B7 ★ 생성 요청이 두 번 와도 회차는 하나만 생긴다
```
Given  위저드를 채워둔다
When   생성 요청을 연달아 두 번 보낸다
Then   회차는 하나만 생긴다
And    두 번째 요청은 에러가 아니라 같은 회차를 돌려준다
```
> 프로토타입에서는 버튼 더블클릭으로 `Cannot read properties of null` 이 났다.

### S-B8 '지금 바로' 토글은 값을 잃지 않는다
```
Given  등록 시작을 내일 19:00 으로 지정했다
When   '지금 바로' 를 켰다가 다시 끈다
Then   등록 시작이 다시 내일 19:00 이다     ← 현재 시각으로 남지 않는다
```

### S-B9 기본값 되돌리기는 기존 회차를 건드리지 않는다
```
Given  기본값을 바꾸고 회차를 두 개 만들었다
When   '콕·일정 기본값 되돌리기' 를 실행한다
Then   maxPre/maxParty/오프셋만 초기값으로 돌아간다
And    기존 회차 두 개의 설정은 그대로다
And    로그인도 그대로 된다 — PIN 은 기본 설정이 아니라 배포 시크릿이다
```

## C. 회차 찾기 · 참가 링크

### S-C1 유효한 코드로 회차를 찾는다
```
Given  등록 중인 회차의 코드가 "ABC234" 다
When   GET /api/events/by-code/ABC234
Then   200 이고 회차 이름과 phase 를 받는다
```

### S-C2 ★ 코드 조회 응답에 비밀이 없다
```
When   GET /api/events/by-code/ABC234
Then   응답에 PIN 이 없다
And    참가자 실명·전화번호·인스타가 없다
And    콕 기록이 없다
```
> 이 응답은 **인증 없이** 누구나 받는다. 코드만 알면 되는 화면이다.

### S-C2b ★ 참가 링크 응답에 입장 코드가 없다
```
Given  참가 링크가 /j/<회차id> 다
When   GET /api/events/by-id/<회차id>       ← 인증 없음
Then   회차 이름·단계·파티 일시를 받는다
And    응답 어디에도 입장 코드가 없다
```
> **왜** — 링크는 단톡방에 돌고 스크린샷으로 퍼진다. 링크가 곧 입장이면 운영자가 부르지 않은
> 사람이 명단에 들어온다. 문을 여는 건 운영자가 따로 알려준 6자리다 (ADR-13).

### S-C3 없는 코드는 알려준다
```
When   GET /api/events/by-code/ZZZZZZ
Then   404 이고 메시지는 ENTRY.notFound 다
```

### S-C4 준비 중인 회차는 언제 열리는지 알려준다
```
Given  회차가 준비 중이고 등록 시작이 내일 19:00 이다
When   그 코드로 조회한다
Then   등록 불가로 응답하고 메시지는 ENTRY.notOpenYet("내일 19:00") 이다
```

### S-C5 종료된 회차는 닫혔다고 알려준다
```
Given  회차 phase 가 "done" 이다
When   그 코드로 조회한다
Then   등록 불가로 응답하고 메시지는 ENTRY.finished 다
```

### S-C6 코드는 대소문자를 가리지 않는다
```
Given  코드가 "ABC234" 다
When   "abc234" 로 조회한다
Then   같은 회차를 찾는다
```

## D. 서버 시각

### S-D1 모든 응답이 서버 시각을 싣는다
```
When   아무 /api 응답이나 받는다
Then   x-server-time 헤더에 서버 시각이 들어 있다
```

### S-D2 ★ 클라이언트 시계로는 단계를 못 바꾼다
```
Given  등록 시작이 1시간 뒤로 예약돼 있다
When   클라이언트가 자기 시각을 2시간 뒤로 조작하고 조회한다
Then   phase 는 여전히 "prep" 이다
```

## E. 화면 · 뒤로 가기

### S-E1 위저드 스텝은 뒤로 가기로 돌아간다
```
Given  위저드 2스텝(/host/new/2) 에 있다
When   브라우저 뒤로 가기를 누른다
Then   1스텝(/host/new/1) 이고 입력값이 남아 있다
```

### S-E2 생성이 끝나면 위저드로 돌아가지 못한다
```
Given  회차를 생성해 콘솔(/host/{id}) 에 있다
When   뒤로 가기를 누른다
Then   위저드가 아니라 회차 목록이다        ← replace 로 이동했기 때문
```

### S-E3 PIN 화면도 마찬가지다
```
Given  PIN 을 통과해 콘솔에 있다
When   뒤로 가기를 누른다
Then   PIN 화면이 아니다
```

### S-E4 입장 코드가 틀려도 입력값이 남는다
```
Given  입장 화면에서 "ZZZZZZ" 를 입력했다
When   입장하기를 누른다
Then   ENTRY.notFound 가 입력칸 아래에 뜬다
And    입력칸에는 "ZZZZZZ" 가 그대로 있다
```

## 완료 정의

- 위 26개 시나리오가 테스트로 있고 전부 통과한다
- `npm run check` 통과 — 타입체크(클라이언트+Worker) + `copy.ts` 밖 문구 0건
- 새로 만든 문구가 있다면 `copy.ts` 에 있다
- 참가자에게 나가는 응답을 만드는 곳이 `toPublic()` 하나뿐이다
- 구현이 없는 인터페이스를 만들지 않았다

## 리뷰에서 볼 것 (테스트가 못 잡는 것)

1. 문구를 `copy.ts` 에서 가져왔는가, 지어냈는가
2. 확인 다이얼로그가 무엇이 바뀌는지 보여주는가
3. `docs/DOMAIN.md` 의 설계 결정을 "개선" 하지 않았는가 — 특히 일회성 알람 모델
4. 구현이 하나뿐인데 인터페이스·팩토리를 만들지 않았는가
5. 이 슬라이스 밖의 기능을 미리 만들지 않았는가

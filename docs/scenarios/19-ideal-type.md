# 슬라이스 19 — 이상형 찾기

> **상태** — 구현됨 · 어디까지 나갔나는 `docs/PLAN.md` §6
> **이후 바뀐 것** — ADR-122 (재미 탭의 **두 번째** 카드 — 미션은 운세 카드 안이다 · 벡터는 인식 모델이 아니라 정해진 낱말로 고른 얼굴 속성 ·
> 종이 검증은 페르소나와 눈 가린 판정자로 네 번 돌렸고 운영자가 4차 자산으로 싣기로 정했다). 탭 이름은 `오늘` → `재미` (ADR-20 후기 2)

파티에서 "이상형 연예인 누구예요?" 는 흔한 질문이고 대답하기 어려운 질문이다.
떠오르는 이름이 없어서가 아니라 **말하는 순간 그 이름이 나를 설명해 버려서**다.
그래서 앱이 대신 답을 찾아준다 — 끌리는 얼굴을 세 번 고르면 가장 가까운 연예인이 나온다.

**답을 찾는 건 앱이 하고, 말하는 건 본인이 한다.** 결과는 본인 화면에만 있다.
가림(슬라이스 16)과 같은 자세다 — 앱은 재료를 주고, 언제 누구에게 꺼낼지는 사람이 정한다.

`★` 는 반드시 테스트를 붙이는 것.

## 범위

**만든다**

|                                                            |                                                |
| ---------------------------------------------------------- | ---------------------------------------------- |
| 재미 탭 **두 번째 카드**                                   | 운세 카드 아래. **등록부터.** 재미는 한 자리에 |
| 여·남 중 고르기 → 얼굴 여섯 중 1~3 × 3라운드 → 연예인 셋   | 1분 안에 끝난다                                |
| 결과 아래 **정답 확인 한 번** — 건너뛸 수 있다             | '결과가 취향에 맞나' 를 실전에서 재는 유일한 신호 |
| 결과는 회차 DO 에 1인 1행. **한 번 찾으면 그대로**         | 운세와 같은 규칙, 같은 저장 모양               |
| 계산은 **기기에서**. 서버는 결과만 받는다                  | DO 는 한 번 쓰고 끝. 파티 중 줄이 서지 않는다  |
| 얼굴 자료는 정적 자산. **열 때** 받는다                    | 안 여는 사람은 1바이트도 안 받는다             |

**안 만든다**

- **점수·퍼센트·유사도.** 순서만 있다. 운세에 점수가 없는 이유 그대로다 (ADR-20)
- **남에게 보이는 결과.** 명단·내 카드·프로필 시트 어디에도 없다. 보여주고 싶으면 폰을 보여준다.
  공개를 _본인이 고르게_ 하는 건 다음 슬라이스다 — 이번엔 없다
- **운영자 화면.** 운영에 필요 없는 건 운영자도 안 본다 (ADR-22 와 같은 결)
- **다시 하기.** 라운드 안에서 뒤로 가는 건 된다. 결과를 본 뒤에는 끝이다 —
  '없었어요'(S-C4)도 다시 열지 않는다
- **사진 업로드 · 참가자 얼굴.** 닮은 순위가 생기는 순간 꼴찌가 생긴다 — 이 앱이 없애려던 경험이다
- **고른 얼굴을 취향 자료로 쓰는 것.** `picks` 는 저장하지만 (S-C2 가 다시 그릴 재료)
  쓰는 곳은 그 화면뿐이다 — 지표에도, 추천에도, 어디에도 안 흘린다
- **실시간 신호.** 내 결과는 나만 다시 읽으면 된다. `broadcast()` 를 건드리지 않는다
- **LLM.** 벡터 내적뿐이다. 외부 서비스가 없으니 파티 당일에 죽을 것도 없다

## 정했다 (2026-09-15)

기획에서 열어뒀던 것이 닫혔다. 판단 기준은 하나였다 — **파티 참가자의 경험이 먼저다.**

1. **때 — 등록부터** (S-A2). 등록~파티 사이가 이 앱에서 가장 빈 구간이다 (슬라이스 21 의 발견)
2. **접근 — 재미 탭 두 번째 카드** (S-A1). ADR-20 후기 2 가 탭 이름을 미리 넓혀 뒀다
3. **사진 — 실사. 고르는 것도 결과도** (S-C5). 공개 순간에 얼굴이 있는 쪽을 출처 확보 비용보다 앞에 뒀다
4. **정답 확인 — 이번 슬라이스** (S-C4). 고도화 방향 1 을 승격했다
5. **후보 다양성 — 라운드마다 좁힌다** (고르는 방식). 다양성은 '서로 다른 군집'이, 수렴은 '평균 근처'가 만든다

## A. 자리와 때

### S-A1 재미 탭 두 번째 카드다

```
Then   재미 탭에 운세 카드 아래 두 번째 카드로 있다
```

> 재미는 한 자리에. ADR-20 후기 2 의 다섯 문(본인만 · 한 번이면 그대로 · 점수 없음 ·
> 실패 무해 · 이야깃거리)을 다 지켜서 이 탭에 들어온다.
>
> **고쳤다 (2026-09-27)** — 처음에 `운세 · 미션 아래 세 번째 카드` 로 적었다. 미션은 카드가 아니라
> **운세 카드 안의 한 칸**이다 (UI.md — `카드는 하나다`). ADR-20 후기 2 가 적은 대로 두 번째다.

### S-A2 ★ 등록부터 열린다

```
Given  등록을 마친 참가자
Then   단계와 무관하게 열린다 — 등록 중에도, 사전 투표에도, 파티 중에도, 발표 뒤에도.
       운영자가 단계를 준비로 되돌린 회차에서도 열린다
```

> 남의 데이터를 전혀 쓰지 않으니 명단(ADR-21)처럼 아껴 열 이유가 없다.
> 자산 다운로드도 파티 회선 밖으로 흩어진다.
> 탭의 문이 운세의 문(`canOpenFortune`)을 빌려 쓰던 것을 여기서 끝낸다 — 탭은 등록부터 켜져 있고,
> 운세·미션 카드는 각자의 문을 그대로 지킨다. ADR-20 후기 2 가 예비해 둔 자리다.
> 운세 카드는 그 문을 **자기 안에서** 말한다 — 매력 투표 전에는 생년월일 칸 없이 `FORTUNE.closed` 한 줄이다 (ADR-122).
>
> **고쳤다 (2026-09-27)** — `사전 투표에도, 파티 중에도, 발표 뒤에도` 만 적었다. 이 슬라이스의 과녁인
> **등록 중**이 빠졌고, 운영자가 단계를 되돌리면 등록한 사람이 `준비` 에 있을 수 있다. 문은 조건이 없다 — 서버는 단계를 보지 않는다.

## B. 고르기

### S-B1 처음에 어느 쪽 얼굴을 볼지 고른다

```
Then   '여자' · '남자' 두 버튼이 같은 크기로 있고, 어느 쪽도 미리 눌려 있지 않다
```

> 누구에게 마음이 가는지는 앱이 정할 일이 아니다 (ADR-17). 내 성별의 반대를 미리 골라두지 않는다.

### S-B2 ★ 한 라운드에 얼굴 여섯, 1~3개 고른다. 세 라운드

```
Then   얼굴 6개가 보이고, 1개 이상 골라야 '다음' 이 눌린다. 네 번째는 골라지지 않는다.
       마지막 라운드의 버튼은 '결과 보기' 다
```

> 여섯은 한 화면에 얼굴이 읽히는 크기로 들어가는 수다 (3×2, 한 칸 100px 이상).
> 취향은 하나로 특정돼 있을 수도, 여럿일 수도, 흐릿할 수도 있다 — 그래서 1~3개다. 4개부터는 못 고른다.
> 세 라운드면 1분이다. 파티 테이블에서 폰을 보는 시간으로 그 이상은 길다.
> 세 라운드 만에 부합한 답을 내는 책임은 **고르는 방식**(아래)과 종이 검증이 진다 —
> 여섯이 서로 얼마나 다른가도 화면이 아니라 방식이 정한다. 라운드가 갈수록 좁아진다.

### S-B3 ★ 같은 얼굴이 두 번 나오지 않는다

```
Given  1라운드에 나온 얼굴
Then   2·3라운드에 다시 나오지 않는다
```

> 다시 나오면 고장으로 읽힌다. 고르는 함수가 순수 함수라 이 규칙은 **테스트를 먼저 쓴다**
> (`buildSeating` 과 같은 예외).

### S-B4 뒤로 가면 이전 라운드다. 고른 건 남아 있다

> 라운드마다 push. 뒤로 가기 = 이전 라운드 (등록 스텝과 같다). 잘못 누른 건 여기서 고친다 —
> 그래서 결과 뒤에 '다시 하기' 가 없어도 된다.
> 카드를 닫고 나가면 고르던 건 버려진다. 1분짜리라 이어 하기를 만들지 않는다.
> 앞 라운드를 고쳐 고르면 그 뒤 라운드는 다시 계산한다 — 앞의 선택이 뒤의 후보를 정한다.
> 결과를 본 뒤의 뒤로 가기는 라운드를 되밟지 않고 재미 탭으로 간다 — 결과 보기가 라운드 세 칸을 되감는다 (ADR-122).

### S-B5 고르는 동안 이름이 없다

```
Then   라운드 화면 어디에도 이름이 없다. 사진 파일명도 불투명 id 다 (check:faces 가 잡는다)
```

> 이름을 알고 고르면 끌림이 아니라 팬심으로 고른다. 그리고 옆에서 화면을 본 사람에게
> 취향이 이름으로 읽힌다 — 이 기능이 없애려던 바로 그 노출이다.
> '연예인' 이라는 말도, 이름도 결과 화면에서만 쓴다.

### S-B6 골랐음은 색으로만 말하지 않는다

> 테두리와 함께 ✓ 표시.

## C. 결과

### S-C1 ★ 연예인 셋. 첫 사람이 답이다

```
When   3라운드를 마치면
Then   가장 가까운 순서대로 사진과 이름 셋을 나열한다. 화면에 `%` 가 없다
```

> 첫 이름이 낯설 때 두 번째가 구해준다. **퍼센트는 없다** — 순서만 있다.
> 화면에 `%` 가 없는 것을 테스트로 고정한다 (운세와 같다).

### S-C2 ★ 본 얼굴은 결과에 나오지 않는다. 고른 얼굴은 밑에 따로 보인다

```
Then   결과 셋은 라운드 화면에 나왔던 얼굴이 아니다. 내가 고른 얼굴들은 결과 아래 따로 있다
```

> 방금 고른 얼굴을 그대로 돌려주는 건 답이 아니다 — 그건 본인이 이미 아는 것이다.
> 답은 **안 본 사람 중에서** 나와야 "찾아줬다" 가 된다.
> 골랐던 얼굴도 이상형에 가까운 얼굴들이다 — 버리지 않고 결과 아래에서 되돌아보게 한다.

### S-C3 ★ 한 번 찾으면 그대로 남는다

```
Given  결과를 봤다
When   카드를 다시 연다 · 다시 읽는다 · 다른 기기에서 연다
Then   같은 결과다. 다시 고르는 길이 없다
```

> 두 번 저장돼도 먼저 온 것이 남는다 (`ON CONFLICT DO NOTHING`, 운세와 같다).
> 열 때마다 달라지면 테이블에서 한 말이 거짓말이 된다.
> **시작 화면에서 미리 말한다** — "한 번 찾으면 그대로 남아요".
> 확인창은 따로 띄우지 않는다 — 되돌릴 수 없는 행동이지만 시작 화면이 미리 말했고, 운세도 확인창이 없다.
>
> **고쳤다 (2026-09-27)** — `운세가 뒷면에서 말하는 것과 같다` 고 적었다. **그런 문장은 없다** — 운세 뒷면에는
> 생년월일 칸과 `운세를 읽는 데만 쓰고, 저장하지 않습니다.` 뿐이다. 한 번이면 그대로라고 **미리 말하는 줄은 이것이 처음**이다.

### S-C4 ★ 정답을 한 번 묻는다 — 건너뛸 수 있다

```
Given  결과 셋
Then   그 아래에 "이 중에 진짜 이상형이 있었나요?" — 셋 중 하나를 고르거나 '없었어요'
When   답하면
Then   물음이 답으로 바뀌고 다시 묻지 않는다. 결과는 그대로다 — '없었어요' 도 다시 찾기를 열지 않는다
```

> '결과가 취향에 맞는가' 를 실전에서 재는 유일한 신호다. 종이 검증은 다섯 명이지만 실전은 마흔 명이다.
> 답하지 않아도 아무 일 없다 — 재촉하지 않고, 다음에 결과를 열면 물음이 그대로 있다.
> 남는 곳은 본인 화면과 지표의 **개수**뿐이다 (`v` 별 chosen/none) — 어느 연예인인지는 지표에 없다 (S-D4).
> '없었어요' 는 실패 신고가 아니라 다음 판(`v`+1)의 벡터·규칙을 고치는 재료다.
> 그래서 결과를 바꾸지 않는다 — 바꾸면 S-C3 이 무너진다.

### S-C5 사진은 실사다 — 고르는 것도 결과도

> 공개 순간에 얼굴이 있어야 "찾아줬다" 가 된다. 합성 얼굴안(법적 노출 0)과 견줘
> 참가자 경험을 앞에 뒀다 (정했다 3). **화면에 내보내는 연예인 사진이 이 기능의 법적 노출이다** —
> 사진 출처 확보가 자산 작업의 첫 일이고, 그 전에는 **화면을 열지 않는다** — 문은 빌드가 연다:
> 지금 판의 풀 JSON 이 빌드에 없으면 카드도 주소도 없다 (`lib/faces.ts`, `19-surface.md` 「자산」).
> **남는 노출은 어깨너머다.** 옆에서 화면을 보면 취향이 얼굴로 읽힌다 — 가림(슬라이스 16)이
> 콕에서 막은 그 통로다. 고르는 화면에 이름이 없는 것(S-B5)이 폭을 줄이고,
> 나머지는 알고 고른 대가로 남긴다 (ADR-32 의 '링크를 본 사람' 과 같은 자리였다 — 그 결정은 ADR-75 로 폐기됐고,
> 알고 고른 대가를 적는 자리는 ADR-118 의 `대가` 가 이어 쓴다).

## D. 저장과 공개 범위

### S-D1 ★ 내 결과는 내 응답에만 있다

```
Then   roster 의 PublicPlayer 에 없다 · 프로필 시트에 없다 · HostState 에 없다
```

> `toPublic()` 을 건드리지 않는다. `ParticipantState.ideal` 한 칸이 전부다 — verdict 도 그 안이다.

### S-D2 ★ 참가자를 지우면 결과도 사라진다

> 운세와 같다. 그 사람의 것은 그 사람과 함께 간다. 보낸 콕만 남는다 (ADR-29).
> 회차는 운영자가 지울 때까지 남고(ADR-36), 지우면 DO 하나로 다 사라지는 것은 그대로다.

### S-D3 서버는 id 만 받는다. 계산하지 않는다

> 기기가 고른 결과를 보내고 DO 는 저장만 한다.
> 개발자 도구로 결과를 지어내 보내는 참가자가 있을 수 있다 — **그래서 뭐.** 본인만 보는 본인 결과다.
> 서버가 벡터를 들고 다시 계산하면 워커 번들이 수백 KB 무거워지고,
> 얻는 건 "본인이 본인을 못 속인다" 뿐이다. 이름은 기기가 자산에서 찾는다 — DO 에는 이름이 없다.

### S-D4 회차 DO 밖으로 나가지 않는다

> 지표에 **결과를 넣지 않는다.** "이 파티 이상형 1위" 는 결과 통계다 — 운영 카운터가 아니다.
> 넣는 건 첫 저장·첫 확정의 개수와 `v` 뿐이다. 누가 누구를 골랐는지는 안 된다.
> 자리는 회차를 가리지 않는 집계 `pulse()` 다 (ADR-56) — `{ kind: "ideal"; key: "save" | "chosen" | "none"; v }`,
> 회차 id 도 연예인 id 도 없다. 회차별 카운터(`count()`)는 회차 id 를 인덱스로 달아서 쓰지 않는다 (ADR-122 ③).

## E. 같은 사람, 두 기기

### S-E1 고르던 중간은 이어지지 않는다

> 고르던 값은 그 기기 메모리에만 있다 (S-B4). 서버는 고르는 중간을 모른다 —
> 두 기기에서 같이 열면 각자 고른다.

### S-E2 ★ 먼저 끝낸 쪽이 남는다

```
Given  두 기기가 각자 고르고 있다
When   둘 다 결과를 보낸다
Then   먼저 닿은 것이 남는다. 늦게 보낸 기기에도 저장된 그 행이 그려진다 — 방금 고른 셋이 아닐 수 있다
```

> 서버는 이미 있으면 있던 것을 돌려준다 — 409 로 혼내지 않는다. 늦은 쪽이 잘못한 게 아니다.
> 화면은 응답을 그대로 그린다. 방금 받은 답을 버리고 다시 읽지 않는다 (14 의 `/vote` 와 같은 이유).

## 숫자

|                    | 값                      | 왜                                                    |
| ------------------ | ----------------------- | ----------------------------------------------------- |
| 라운드 M           | 3                       | 1분. 군집 단계와 같다 — 거칠게 → 가늘게 → 낱낱이      |
| 한 라운드의 얼굴 N | 6                       | 한 화면, 읽히는 크기                                  |
| 고르는 수          | 1~3                     | S-B2. 특정된 취향은 하나로 좁고, 갈리는 취향은 셋까지 |
| 결과 J             | 3                       | 답 하나 + 구해주는 둘                                 |
| 풀                 | 성별마다 **200명 이상** | 1·2단계 대표(6·36)를 빼고도 평균 근처가 낱낱이 되는 크기 |

**라운드 수는 고정이다.** 풀이 작으면 라운드를 줄이는 게 아니라 자산을 채워서 온다 —
저장 모양(`picks` 3묶음)과 화면이 라운드 수를 들고 있어서, 이걸 변수로 만들면 전부가 변수가 된다.

**고르는 방식 — 평균을 따라가되, 라운드마다 좁힌다**

```
평균     지금까지 고른 얼굴 벡터 전체의 단순 평균(정규화). 라운드 가중치 없음
1라운드  1단계 대표 6 — 모두에게 같다. "첫 화면에서 누구 골랐어?" 가 된다
2라운드  평균에 가까운 순서로 2단계 대표 6 (본 얼굴 제외) — 대표라서 여섯이 서로 다른 군집이다
3라운드  평균에 가까운 순서로 풀 전체에서 6 (본 얼굴 제외) — 다만 이미 담은 것과
         너무 닮은 후보는 다음 것으로 민다. 닮은꼴 여섯이면 고를 이유가 안 읽힌다
결과     전체 평균에 가장 가까운 연예인 3 (본 얼굴 제외)
```

다양성은 '서로 다른 군집' 이 만들고, 수렴은 '평균 근처' 가 만든다 — 거칠게 → 가늘게 → 낱낱이.
라운드 가중치를 두지 않는 건 정할 값을 하나라도 줄이려는 것이다 — 이 가정 전체를 종이 검증이 재판한다.
**안 고른 얼굴은 쓰지 않는다.** 여섯 중 셋까지만 고를 수 있어 안 고른 것에는 이유가 여럿이다 —
'멀다' 는 보장이 없는 신호를 평균에 넣지 않는다.

가지를 타고 내려가는 방식(고른 군집의 자식만 보여주기)도 검토했다. 둘을 골라 가지가 둘이 되면
어느 쪽 자식을 몇 개 보여줄지가 규칙이 되고, 그 규칙이 결과를 흔든다. 평균을 따라가면 규칙이 하나다 —
**가까운 것부터.** 취향이 둘로 갈리는 사람은 3라운드의 선택이 평균을 한쪽으로 끌고 간다.
계층 군집은 그대로 쓴다 — 단계마다 "얼마나 거친 후보 집합에서 고르나" 를 정하는 게 그 일이다.

## 먼저 확인할 것 — 화면을 만들기 전에

이 기능은 **"고른 얼굴 벡터의 평균에 가까운 연예인 = 내 이상형"** 이라는 가정 위에 서 있다.
얼굴 인식 모델의 벡터는 *누구인가*를 맞추도록 배운 것이지 *끌리는가*를 배운 게 아니다.
같은 사람의 사진은 모이고 다른 사람은 멀어지지만, **"내 취향" 이 그 공간의 한 점인지는 아무도 보장하지 않는다.**

그래서 화면 전에 종이로 잰다.

| 잰다                           | 방법                                                                                     | 판단                                                                            |
| ------------------------------ | ---------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------- |
| 결과가 그럴듯한가              | 성별당 60명짜리 작은 풀로 파이프라인을 돌리고, 다섯 명에게 노트북으로 세 라운드를 시킨다 | **다섯 중 넷**이 "내 취향 맞다" 가 아니면 벡터를 바꾼다 (인식 모델 → CLIP 계열) |
| 1분 안에 끝나나                | 같은 자리에서 잰다                                                                       | 90초를 넘으면 얼굴 크기·흐름을 다시 본다 — 라운드는 줄이지 않는다 (`숫자`)      |
| 첫 라운드 여섯이 충분히 다른가 | 1단계 대표를 나란히 본다                                                                 | 둘이 비슷해 보이면 군집을 다시 본다                                             |

> **후기 (2026-09-27, ADR-122)** — 벡터는 **인식 모델도 CLIP 계열도 아니다.** `gpt-6-luna` 가 사진마다
> 정해진 낱말 목록에서 열다섯 가지 속성(동물상 · 분위기 · 얼굴형 · 눈 … 나이 느낌)을 고르고(다섯 번, 다수결),
> 값마다 `text-embedding-3-large` 로 재어 속성마다 중심을 뺀 68차원으로 옮긴다. 위의 걱정 — *누구인가* 를 배운 공간 —
> 을 비켜 간 것이지 풀어낸 것은 아니다: 여전히 "내 취향이 그 공간의 한 점인가" 는 종이 검증이 본다.
> 종이 검증은 사람 다섯 대신 `gpt-6-luna` 페르소나가 고르고, 눈을 가린 판정자가 무작위 대조군과 견준다.
> 검증 결과는 자산과 함께 적는다 (ADR-122). **통과 기준은 아직 정하지 않았다** — `다섯 중 넷` 은 사람 다섯의 기준이라
> 판정자와 대조군에 그대로 옮겨지지 않는다. 돌리기 전에 ADR-122 `종이 검증` 에 적는다.

종이 검증을 건너뛰고 화면부터 만들면, 화면이 다 된 뒤에 "결과가 이상하다" 를
벡터 탓인지 화면 탓인지 모르게 된다. 슬라이스 01 의 가짜 테스트와 같은 자리다 —
**구현 전에 가정이 참인지 본다.**

> **고쳤다 (2026-09-27)** — 순서가 바뀌었다. **화면은 픽스처 풀**(`test/fixtures/faces/`, 지어낸 벡터)로 먼저 만들었고,
> 종이 검증과 실제 자산은 구현이 아니라 **출시**를 막는다 (`19-surface.md` 「자산」). 위의 걱정 — 벡터 탓인지 화면 탓인지
> 모른다 — 은 픽스처가 반쯤 푼다: 화면 테스트가 지어낸 벡터 위에서 이미 맞으므로, 실제 자산에서 결과가 이상하면 벡터 쪽이다.
> 출시의 문은 코드가 아니라 `qa → main` 이다.

## 문구

`copy.ts` 에 넣는다. 기능 이름은 **이상형 찾기**. "연예인" 은 결과 화면에서만 쓴다.
표는 **뜻**이다 — 문장의 정본은 `copy.ts` 의 `IDEAL` 이다

| 자리          | 뜻                                             |
| ------------- | ---------------------------------------------- |
| 첫 물음       | 어느 쪽 얼굴을 볼까요? — 여자 · 남자           |
| 라운드 안내   | 끌리는 얼굴을 1~3개 골라주세요 · `1 / 3`       |
| 다음 · 마지막 | 다음 · 결과 보기                               |
| 결과 제목     | 내 이상형에 가까운 얼굴 — 최상급은 덜어낸다    |
| 정답 물음     | 이 중에 진짜 이상형이 있었나요? · 없었어요     |
| 자산 못 받음  | 얼굴을 불러오지 못했어요 · 그 자리의 `다시 불러오기` |

`열기` 를 쓰지 않는다 — 운세는 열면 나오지만 이것은 고르는 일이 남아 있다. 같은 말은 같은 무게여야 한다.
`예쁜`·`잘생긴` 을 쓰지 않는다. `끌리는` 이다 — 고르는 건 얼굴의 등급이 아니라 내 쪽의 마음이다.
라운드 안내에 `연예인` 을 쓰지 않는다 — 이름 없이 고르는 화면(S-B5)에서 그 말은 결과의 것이다.

## 남는 물음

1. 외적 이상형이 특정된 사람도, 흐릿한 사람도, 여럿인 사람도 있다 — 1~3개(S-B2)가 받치고,
   갈리는 취향은 3라운드의 선택이 평균을 한쪽으로 끈다. 정말 그런지는 종이 검증과 S-C4 의 답이 말해준다
2. 고르지 않은 연예인을 이상형과 멀다고 읽을 수 있을까 — **읽지 않기로 했다.**
   셋까지만 고를 수 있어 안 고른 것에는 이유가 여럿이다 (고르는 방식)
3. 연예인은 대부분 외모가 뛰어난 편이라 풀이 벡터 공간의 한 구석에 몰려 있을 수 있다 —
   그 안에서도 갈리는지는 종이 검증의 "첫 여섯이 충분히 다른가" 가 본다

## 2. 작업 방식

한 슬라이스를 5단계로 돈다. **테스트를 쓰는 쪽과 통과시키는 쪽을 분리**하는 게 핵심이다.
그래야 "테스트를 고쳐서 통과시키는" 부정행위가 구조적으로 막힌다.

| 단계 | 누가 | 산출물 | 규칙 |
|---|---|---|---|
| 1 시나리오 | 사람 + Claude | `docs/scenarios/NN-*.md` (Given-When-Then) | 여기 없는 건 영원히 안 만들어진다 |
| 2 공개 표면 | Claude | `docs/scenarios/NN-surface.md` | 타입·라우트까지만. **클래스·인터페이스 만들지 않음** |
| 3 테스트 | Claude | `test/NN-*.test.ts` | 공개 표면에만 붙인다. 내부 구조를 알면 안 된다 |
| 4 구현 | Codex | 코드 | 내부 구조는 자유 |
| 5 리뷰 | Claude | 수정 + 기록 | **빠뜨리지 않는다** |

### 왜 5단계가 필수인가

테스트가 통과해도 안 지켜지는 게 있다. 특히 **문구**. 모든 테스트를 통과시키면서
확인창에 "정말 삭제하시겠습니까?"를 쓰는 건 완벽히 가능하다.

리뷰에서 보는 것:

1. 문구를 `copy.ts` 에서 가져왔는가 (`npm run check:copy` 가 1차로 잡는다)
2. 확인 다이얼로그가 무엇이 바뀌는지 숫자로 보여주는가
3. `docs/DOMAIN.md` 의 설계 결정을 "개선" 하지 않았는가 — 특히 **일회성 알람 모델**
4. 구현이 하나뿐인데 인터페이스·팩토리를 만들지 않았는가
5. 슬라이스 밖의 기능을 미리 만들지 않았는가

### 매 슬라이스 시작 전 확인

**구현 전에 통과하는 테스트가 있는지 본다.** 있으면 그 테스트는 가짜다.

슬라이스 01 에서 실제로 두 개 나왔다.
`S-C2`(보안 테스트)는 501 응답에 본문이 없어서 "비밀이 없다"가 저절로 참이 됐고,
`S-B2b`는 생성 실패 시 `continue` 해서 0번 검증했다. 둘 다 **Codex 가 아무것도 안 해도 통과**했을 테스트다.

### 이 환경의 제약

| 작업 | 누가 |
|---|---|
| 코드 편집, 타입체크·빌드·테스트 | Claude (클라우드 컨테이너) |
| `git add` / `commit` | 사람 — Claude 통로는 잠금 파일을 못 지운다 |
| `git push`, `npm install`, `wrangler deploy` | 사람 — Claude 통로에 네트워크가 없다 |

## 4. 파일럿에서 잴 것

슬라이스 01 은 기능이 아니라 **작업 방식**을 검증하는 게 목적이다.

| 지표 | 어떻게 재나 | 판단 |
|---|---|---|
| Codex 왕복 횟수 | 테스트 전부 통과까지 몇 번 주고받았나 | 3회 이하면 좋음 |
| 리뷰 지적 건수 | 5단계에서 잡은 것 | **3건 이하면 워크플로 유지**, 넘으면 조정 |
| 테스트가 놓친 것 | 리뷰에서만 잡힌 항목 | 다음 슬라이스에서 **테스트로 승격** |
| 가짜 테스트 | 구현 전 통과한 개수 | 0 이 목표. 01 은 2건 나왔다 |
| 체감 속도 | Claude 가 직접 짰을 때 대비 | 느리면 역할을 바꾼다 |

**조정 후보** — 리뷰 지적이 많으면 (a) Codex 프롬프트에 규칙을 더 싣거나
(b) Codex 를 구현자가 아니라 **적대적 리뷰어**로 돌린다.
같은 모델이 자기 코드를 검토하면 맹점을 공유하므로, 후자가 더 값어치 있을 수 있다.

## 5. Codex 에 넘길 때

`CLAUDE.md` 를 Codex 가 자동으로 읽지 않는다. 프롬프트에 직접 싣는다.

```
저장소: tone-pick. 슬라이스 01 을 구현해줘.

먼저 읽을 것:
  CLAUDE.md
  docs/scenarios/01-event-create-join.md   (시나리오)
  docs/scenarios/01-surface.md             (계약 — 여기 적힌 것만 계약이다)

목표: npm test 의 22개를 전부 통과시킨다.

지켜야 할 것:
  · 테스트 파일을 수정하지 마라. 규칙이 틀렸다고 생각되면 고치지 말고 말해달라
  · 내부 구조는 자유다. 다만 인터페이스는 구현이 둘 이상일 때만 만든다
  · 사용자에게 보이는 문구는 src/shared/copy.ts 에서 가져온다. 새로 짓지 마라
  · 상태를 바꾸는 건 EventDO 안에서만. Worker 는 인증과 라우팅만 한다
  · 예약은 한 번만 울리는 알람이다. 일반 스케줄러로 "개선" 하지 마라

완료 조건: npm run check 와 npm test 가 모두 통과
```

### 워크플로에서 벗어난 것 (기록)

02~07 은 **시나리오·표면 문서 없이** 구현했다. 한 번에 앱 전체를 끝내달라는 요청이었고,
문서 → 표면 → 테스트 → 구현 왕복을 슬라이스마다 도는 대신 규칙 테스트를 먼저 쓰고 바로 구현했다.

그래서 지금 상태는 이렇다.

- **규칙은 테스트가 지킨다.** 공개 범위·콕 예산·되돌리기·자리 불변식은 전부 테스트에 박혀 있다
- **범위는 문서가 지키지 못한다.** "여기 없는 건 만들지 않는다"의 근거가 01 말고는 없다.
  다음에 기능을 늘릴 때는 `docs/scenarios/NN-*.md` 부터 다시 쓸 것
- 새로 생긴 결정은 ADR-9·10·11 에 남겼다

### 구현하며 드러난 것

| 발견 | 대응 |
|---|---|
| 테스트 격리가 없다 — vitest-pool-workers 0.20 은 테스트마다 스토리지를 되돌리지 않는다 | 테스트를 파일 안에서 상태를 나눠 쓰도록 짰다. 새 테스트도 그 전제로 쓸 것 |
| 확인창이 뜨자마자 스스로 닫혔다 — 히스토리가 갱신되기 전에 "없으면 닫는다"가 돌았다 | 한 번 들어간 걸 본 뒤에만 사라짐을 닫힘으로 해석한다. 화면 테스트가 잡았다 |
| 자리 배정이 100명에 23ms (무료 플랜 10ms 초과) | 안쪽 루프에서 문자열 키를 걷어내고 typed array 로. 3ms |
| 마지막 라운드에서 상호 매칭 쌍이 갈라졌다 (동석률 50%) | 가중치가 아니라 구조로 고정 (ADR-11). 100% |

**QA 환경** — `npm run deploy:qa`. 100명 리허설은 여기서 돈다. 워커가 달라 DO 가 분리되므로
프로덕션 데이터 옆에서 가짜 인원을 만들 일이 없다.

### 100명 리허설 실측 (QA, 2026-08-13)

`MASTER_PIN=0000 npm run rehearsal <QA 주소>` · 100명 · 12테이블 · 실패 0

| 구간 | 결과 |
|---|---|
| 등록 100건 (동시 25) | p50 5.6s |
| 콕 300건 (동시 25) | p50 4.9s |
| **자리 배정** | **261ms** — 무료 플랜 CPU 10ms 관문 통과 |
| 자리 발송 | 230ms · 소켓 99개 |
| 단계 알림 | 99/99 도달 · 첫 도달 213ms |
| 참가자 화면 | 170ms |

**한계는 회차 DO 의 쓰기 처리량, 약 5건/초다.** 근거:

| 요청 | 순차 | 동시 25 |
|---|---|---|
| 정적 자산 / health (DO 없음) | 155ms | 182ms |
| by-code (DO 읽기 1회) | 165ms | 195ms |
| 콕 (DO 쓰기 1회) | 211ms | **4,900ms** |

읽기는 동시성에 거의 영향을 안 받는다. 쓰기만 줄을 선다 — 회차 1개 = DO 1개라서 그렇고,
그 직렬화가 닉네임 유일성과 콕 예산에서 경쟁 조건을 없애주는 바로 그 성질이다. 맞바꾼 값이다.

### 사전 투표 시작 구간 실측 (QA, 50명, 2026-08-19)

읽기 herd 와 쓰기 큐가 겹치는 유일한 구간이라 따로 쟀다.
`PEOPLE=50 WIDTH=25 SPREAD=5 npm run rehearsal <QA 주소>` (콕이 5초에 걸쳐 흩어지는 현실)
와 `--burst`(전원 동시)를 나란히 본 것이다. 콕은 150건(1인 3회 — 기본값의 3배).

| | 현실 (5초 분산) | 버스트 (전원 동시) |
|---|---|---|
| 전환 응답 | 221ms | 217ms |
| 다시 읽기 p50 | 220ms | 227ms |
| **다시 읽기 p95** | **503ms** | **10,011ms** |
| 콕 p50 | 7,376ms | 9,705ms |
| 콕 마지막 | 29.2s | 30.0s |
| 재조회와 겹친 콕 | 10/150 | 99/150 |

**읽기는 쓰기와 독립이 아니다.** 읽기 자체는 가볍지만 같은 DO 를 지나므로,
쓰기 큐가 쌓인 뒤에 도착한 읽기는 그 뒤에 선다 — 버스트에서 재조회 p95 가
0.5초에서 **10초로** 뛴 게 그 값이다. 참가자 눈에는 "화면이 10초 동안 안 바뀐다"로 보인다.

**콕 총 시간은 도착 패턴과 무관하다** (양쪽 다 ~30초 = 150건 ÷ 5건/초).
도착 패턴이 정하는 건 총 시간이 아니라 **누가 기다리는가, 그리고 읽기가 거기 말려드는가**다.

**그래서 분산이 전부다.** 5초만 흩어져도 재조회는 831ms 에 끝나 쓰기 큐가 쌓이기 전에 빠져나간다.
운영에서 "다 같이 지금 누르세요"를 하지 않는 것이 곧 이 구간의 대책이다.

### 저장 알림을 좁힌 효과 (QA, 50명, 전후 비교, 2026-08-19)

ADR-31 의 `toHosts()` 가 실제로 무엇을 줄였나. **같은 스크립트로 코드만 앞뒤로 바꿔** 쟀다
(QA 에 이전 빌드를 잠깐 올렸다 되돌렸다).

| 내 정보 저장 5회 · 소켓 50개 | 이전 | 이후 |
|---|---|---|
| **참가자 재조회** | **250건** | **0건** |
| 저장 쓰기 p50 | 393ms | 191ms |

저장 한 번이 **참가자 수만큼의 읽기**를 부르고 있었다 (5 × 50 = 250).
지금은 운영자 콘솔 하나만 다시 읽는다. 쓰기 자체가 빨라진 건 덤이다 —
출력 게이트가 그 방송까지 붙들고 있었기 때문이다.

**사전 투표 구간은 그대로다** (콕 p50 295ms → 309ms). 그 경로는 손대지 않았으니
차이는 실행마다 흔들리는 폭 안이다. 이 변경이 고친 건 **퍼짐**이지 처리량이 아니다.

> 이 비교는 소켓을 **참가자 세션으로** 붙이고서야 가능했다. 익명 소켓에는
> `toHosts()` 도 닿아서 전후가 똑같이 보였다. 리허설이 `ws` 를 쓰는 이유다.

### 콕 쓰기 반영 속도 실측 (QA, 50명, 15초 분산, 2026-08-19)

쓰기와 읽기가 함께 몰린 상태에서 **콕이 실제로 반영되기까지** 얼마나 걸리나.
콕 응답은 durable commit 이 끝나야 돌아오므로 **응답 시간이 곧 반영 시간**이다.

여기서 처음 같이 잰 것 — **콕 한 건은 쓰기 1 + 읽기 1 이다.**
받은 사람에게 신호가 가고(`toPlayer`), 그 화면은 신호 종류를 가리지 않고 한 벌을 다시 읽는다 (ADR-26).

| 콕 상한 | 쓰기 수 | 도착률 | 콕 p50 | 콕 p95 | 콕이 부른 읽기 p50 | 마지막 |
|---|---|---|---|---|---|---|
| 사전 3 (리허설 기본) | 150건 | 10건/초 | 4,348ms | 6,511ms | 4,150ms | 30.3s |
| **사전 1 (실제 기본값)** | **50건** | **3.3건/초** | **294ms** | **363ms** | **175ms** | 15.2s |

**전부 도착률 하나로 갈린다.** 처리 용량은 약 5건/초이고, 그보다 빠르게 들어오면 큐가 쌓여
지연이 초 단위로 커진다. 느리게 들어오면 큐가 없어 **294ms** — 순차 요청(211ms)과 거의 같다.
같은 인원, 같은 15초인데 상한만 3에서 1로 내리면 **15배** 차이가 난다.

**실제 기본값에서는 최적화할 게 없다.** 50명 · 사전 콕 1회 · 15초 분산이면 3.3건/초로
용량 아래고, 콕도 그것이 부른 읽기도 300ms 안쪽이다. 콕이 느려 보이는 리허설 숫자는
`MAXPRE=3` 이 만든 것이지 코드가 만든 게 아니다.

> 콕 경로 자체는 이미 최소다 — `touch()` 는 전환이 걸릴 때만 쓰고, 예산·받은 수는 색인으로 세고,
> 쓰기는 `INSERT` 하나다. 병목은 JS 가 아니라 durable commit 이라 여기서 더 깎을 것이 없다.
> 올리는 길은 코드가 아니라 **쓰기 수를 줄이거나 도착을 흩는 것**뿐이다.

### 운세 경로의 읽기를 좁혔다 (1.0.0)

`/fortune` 과 `/fortune/mission` 이 `participantState()` 를 부르고 있었다 —
명단 전체를 `toPublic()` 으로 빚고, 콕을 집계하고, 자리를 찾는 읽기다.
정작 필요한 건 **단계·나·저장된 운세 셋**뿐이었다.

파티가 시작되면 이 두 경로가 인원 수만큼 한꺼번에 열리고(1인당 쓰기 2건),
그 일이 전부 **직렬화된 DO 스레드**에서 벌어진다 — 그 시간이 곧 다른 사람의 읽기가
출력 게이트 뒤에서 기다리는 시간이다. 그래서 `fortuneContext()` 로 갈랐다.

> 아직 **재보지 않았다.** 리허설(`scripts/rehearsal.mjs`)이 `오늘` 탭을 지나지 않는다 —
> 유일하게 안 잰 쓰기 경로이고, 하필 파티 시작이라는 이미 붐비는 순간에 들어온다.

### 운세 구간 실측 (QA, 2026-08-20) — 병목이 DO 가 아니었다

`FORTUNE=30 PEOPLE=50 npm run rehearsal <QA 주소>` 로 처음 쟀다.

| 12명이 6초에 걸쳐 운세를 연다 | |
|---|---|
| LLM 호출 (핸들러 안에서 잰 값) | p50 **4,185ms** · 최대 4,606ms |
| 저장 (DO 쓰기) | p50 **30ms** · 최대 32ms |
| **전체 요청** | p50 **23,738ms** · 최대 47,348ms |

**4.2초 + 0.03초인데 전체가 23.7초다.** 나머지 19.5초는 우리 핸들러가 시작되기 전에 간다.

같은 사람들이 **이미 만들어진 운세를 다시 받는** 2차는 같은 동시성에서 **183ms** 다 —
세션 확인도 `fortuneContext` 읽기도 멀쩡하다. 제공자도 멀쩡하다: 같은 키로 6건을
직접 동시에 부르면 2.4초 안에 **병렬로** 끝난다.

→ **요청이 Worker 에 도달하기 전에 줄을 선다.** 앞 요청들이 LLM 을 4초씩 기다리며
자리를 잡고 있어서다. 무료 플랜의 동시 실행 제한이고, **이건 우리 코드로 못 줄인다.**

| 인원 | 흩어진 폭 | 전체 p50 | 최대 |
|---|---|---|---|
| 8 | 8초 | 16.8초 | 31초 |
| 12 | 6초 | 23.7초 | 47초 |
| 24 | 8초 | 52.7초 | 101초 |
| 50 | 30초 | 99초 | 196초 |

처리량은 약 **0.23건/초**. 50명이 운세와 미션을 다 열면 100건이라 **7분**이 든다.
한꺼번에 열면 마지막 사람이 그만큼 기다리고, 15분에 걸쳐 열면 줄이 안 생긴다.

**타임아웃은 이 줄서기를 못 막는다.** `AbortSignal.timeout(12s)` 도, 바깥에
`Promise.race` 로 한 겹 더 두른 것도 한 번도 안 걸렸다 (규칙 문구 0건) —
기다림이 **우리 코드가 실행되기 전**에 일어나므로 우리 타이머가 돌 기회가 없다.
시도했다가 되돌렸다. 코드가 하지 못하는 일을 하는 것처럼 적힌 주석이 더 나쁘다.

**대책은 둘뿐이다.** 콕과 같은 결론이다 —
운영에서 "다 같이 지금 운세 열어보세요" 를 하지 않는 것, 그리고 유료 플랜($5/월) 검토.

### 클라이언트 번들은 건드리지 않았다

414 kB (gzip 132 kB). 운영자 콘솔을 따로 받아오게 갈라 봤더니 386 kB (gzip 125 kB) —
**5%** 였다. 대신 파티 도중 콘솔 덩어리를 못 받아오면 운영자가 단계를 넘기지 못한다.
참가자 5% 를 얻자고 그 실패 모드를 사지 않는다. 콘솔이 더 커지면 다시 본다.

### 읽기가 몰릴 때 실측 (QA, 50명, 1초 창, 2026-08-19)

브로드캐스트가 부르는 재조회 말고, **서버 이벤트 없이** 화면이 스스로 다시 읽는 두 경우다.
`READWINDOW=1` — 읽기 50건이 1초 안에 몰린다.

| 구간 | p50 | p95 | 최대 |
|---|---|---|---|
| **앱 복귀 · 조용할 때** | 164ms | 176ms | 289ms |
| **앱 복귀 · 쓰기가 도는 중** | **8,307ms** | 8,744ms | 8,794ms |
| 소켓 재연결 (50/50 성공) | 475ms | 500ms | 1,068ms |
| 재연결 직후 읽기 | 164ms | 193ms | 500ms |

**읽기 자체는 공짜다.** 50건이 1초 안에 몰려도 164ms — 정적 자산(155ms)과 거의 같다.
소켓 50개가 1초 안에 다시 붙는 것도 실패 0에 500ms 안쪽이라, 재연결 파도 자체는 무해하다.

**문제는 언제나 "그 순간 쓰기 큐가 있는가" 하나다.** 콕 50건이 도는 중에 같은 읽기를 쏘면
164ms 가 8.3초가 된다 — **50배**다. 읽기가 느려진 게 아니라 앞에 선 쓰기가 안 끝난 것이고,
8.3초는 50건 ÷ 5건/초 = 10초에서 1초 뒤에 출발한 값과 정확히 맞는다.

**그래서 시나리오 1·3·4 는 서로 다른 문제가 아니다.** 셋 다 같은 한 문장으로 끝난다 —
읽기는 괜찮다, 쓰기 큐 뒤에 서면 안 될 뿐이다. 대책도 하나다: **쓰기를 흩는 것.**

운영에서 이게 뜻하는 것 —
- "다들 폰 확인하세요" 는 그 자체로는 안전하다. **콕을 재촉하면서** 말할 때만 위험하다
- 파티 중 배포는 재연결 파도를 만든다. 파도는 괜찮지만, 그때 콕이 몰려 있으면 화면이 8초 멈춘다

**현실 부하와의 거리** — 100명이 5분에 걸쳐 등록하면 0.33건/초다. 15배 여유가 있다.
위험한 건 "지금 다 같이 등록하세요" 같은 **동시 버스트**뿐이고, 그때도 실패 없이
20초에 걸쳐 처리된다(개인 최대 6초 대기). 운영에서는 등장 순서대로 자연스럽게 열면 된다.

> 요청당 DO 작업을 줄이는 최적화(등록 왕복 3→1, 콕 집계 색인화, 좌석 N+1 제거)를 먼저 했지만
> 숫자는 거의 그대로였다. 병목이 JS 가 아니라 쓰기 확정이라는 뜻이다. 그래도 되돌리지 않았다 —
> 자료가 늘수록 유리하고, 왕복이 줄면 줄 자체가 짧아진다.

100명 리허설로 WS 연결 수와 DO 지연을 재고, 회차 종료 N일 뒤 개인정보 파기 Cron 을 붙인다.

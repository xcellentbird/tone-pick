# 설계 결정

**바꾸기 전에 반드시 읽는다.** 여기 있는 건 되돌리기 어려운 결정이고, 대부분 사고를 겪고 나온 것이다.
"더 나은 방식"처럼 보이는 게 이미 검토돼 버려진 경우가 많다.

---

## ADR-1 공개 범위는 기능이 아니라 제품의 정체성

**결정** — 일방적으로 받은 콕은 **끝까지 익명**이다. 발표 후에도 상호 매칭만 닉네임이 공개되고,
연락처는 매칭돼도 공개하지 않는다.

**왜** — 이 앱이 없애려는 건 "거절당하는 경험"이다. 누가 나를 안 찔렀는지 알 수 있게 되는 순간
파티의 분위기가 바뀐다.

**따라서** — 설정 가능한 옵션이 아니다. 참가자에게 나가는 응답은 `toPublic()` 한 곳만 거치고,
발표 전에는 콕 발신자(`fromId`)가 응답에 아예 들어가지 않는다.

---

## ADR-2 예약과 수동 진행은 "일회성 알람"으로 공존한다

**문제** — 운영자는 시각을 예약할 수도, 현장에서 버튼으로 진행할 수도 있다. 둘이 섞이면
발표를 되돌렸을 때 지나간 예약 때문에 즉시 다시 튕긴다.

**결정** — 예약 시각은 상태가 아니라 **한 번만 울리는 알람**이다. 실제 전환 시각을 `fired` 에
기록하고, 알람은 `fired` 가 비어 있을 때만 울린다.

```ts
if (phase==="prep" && schedule.regOpenAt && !fired.reg     && now >= schedule.regOpenAt) → "reg"
if (phase==="reg"  && schedule.prevoteAt && !fired.prevote && now >= schedule.prevoteAt) → "prevote"
```

예약이 걸리는 전환은 이 **둘뿐**이다. 사전 투표 마감·파티 시작·발표는 운영자가 누른다 (ADR-14).

**따라오는 규칙 3가지**

1. **예약 값을 지우지 않는다** — "예약은 21:00 이었는데 20:45 에 진행했다"를 보여줄 수 있어야 한다
2. **지나온 항목만 잠근다** — `schedLocked()`. 등록이 시작됐어도 사전 투표 시작은 여전히 수정 가능하다
3. **차이를 알려준다** — 수동 진행 확인창에 `schedDiff()` 한 줄

**버린 대안** — "수동 진행 시 예약을 삭제". 기록이 사라져 운영 회고가 불가능해진다.

> ⚠️ 이걸 일반 스케줄러나 cron 으로 "개선" 하지 마라. 되돌리기가 깨진다.

## ADR-3 회차 PIN 을 공통 PIN 보다 먼저 검사한다 — **폐기됨 (ADR-12)**

**사고** — 두 PIN 이 같은 값일 때 회차 담당자가 자기 PIN 을 넣었는데 master 가 부여됐다.
`{"회차PIN":"0000","공통PIN":"0000","획득권한":"master","전체회차접근":true}`

**당시 결정** — 회차 화면에서는 회차 PIN 을 먼저 비교하고, PIN 을 만드는 모든 지점에서
두 값이 같아지는 걸 막는다.

**지금** — 회차 PIN 자체가 없어졌다 (ADR-12). 검사 순서라는 개념이 사라졌으므로 이 결정은 폐기한다.
남는 교훈은 하나다 — **지켜야 할 순서가 있다면, 그 순서가 필요 없게 만드는 쪽이 낫다.**

## ADR-4 참가자 알림은 저장하지 않고 상태에서 파생시킨다

**결정** — 알림 목록은 `fired` 에서 매번 계산한다. 읽음/안읽음 플래그도, 알림 테이블도 만들지 않는다.

**왜** — 알림을 저장하면 "발표를 되돌렸을 때 이미 보낸 알림을 어떻게 할 것인가"가 곧바로 생긴다.
파생시키면 상태가 하나뿐이라 모순이 없다. 되돌리면 알림도 자동으로 "되돌렸어요"로 바뀐다.

**한계** — "이 알림을 읽었는가"를 알 수 없다. 자리 이동만은 확인이 꼭 필요해서 별도로 `ack` 를 저장한다.

## ADR-5 테이블 수는 설정이 아니라 배정 시점의 입력값

**결정** — 회차 설정에 테이블 수를 두지 않는다. **자리 배정을 누를 때마다** 고르고,
각 배정 결과에 그때 쓴 값을 함께 저장한다.

**왜** — 현장에서 결정되는 값이다. 노쇼가 생기고 지각자가 오고 1부·2부 배치가 다르다.
미리 정해두면 반드시 틀린다.

## ADR-6 되돌릴 수 있는 행동에는 확인을 붙이지 않는다

| 행동 | 확인 | 왜 |
|---|---|---|
| 콕 찌르기 `+` | ✅ | 예산이 줄고 상대에게 알림이 간다 |
| 콕 되돌리기 `−` | ❌ | 다시 찌르면 복구된다. 확인은 마찰만 늘린다 |
| 단계 전환 | ✅ | 참가자 전원의 화면이 바뀐다 |
| 참가자 삭제 | ✅ | 콕·자리 이력이 함께 사라진다 (숫자로 명시) |
| 자리 알림 발송 | ✅ | 참가자 화면을 덮는 확인 화면이 뜬다 |
| 자리 초안 생성 | ❌ | 참가자에게 안 보인다. 몇 번이든 다시 만들 수 있다 |

확인창은 "정말 하시겠습니까?"가 아니라 **무엇이 어떻게 바뀌는지**를 항목별·숫자로 보여준다.

## ADR-7 데모 뷰는 별도 코드가 아니라 컨텍스트 파라미터다

**결정** — 참가자 뷰는 한 벌만 유지하고, 컨텍스트로 "지금 어느 화면을 그리는가"를 결정한다.

**왜** — 데모용 화면을 따로 만들면 두 벌이 갈라져 **데모가 거짓말을 하게 된다.**
컨텍스트만 바꾸면 데모에 보이는 것이 실제 그 화면이다.

**대가** — 모든 뷰·핸들러가 컨텍스트를 받아야 한다. 하나라도 빠뜨리면 다른 화면이 반응한다.
화면 독립성을 테스트로 상시 검사한다.

### 후기 — 데모 뷰 자체를 걷어냈다

이 결정("한 벌만 유지한다")은 옳았지만, **데모 뷰를 운영 앱 안에 둔 것**이 문제였다.
서버 시연 라우트는 `ENV_LABEL` 로 막혀 프로덕션에서 404 였는데, **클라이언트 라우트는 안 막혀서
프로덕션 번들에 화면과 문구가 그대로 실렸다.** "존재 자체를 없앤다" 던 약속이 절반만 지켜진 셈이다.

별도 앱으로 떼는 안도 검토했지만 이 ADR 이 막으려던 **두 벌 갈라짐**이 그대로 돌아온다.
그래서 기능을 걷어냈다. 참가자 뷰는 여전히 한 벌이고, 이제 그 한 벌만 남았다.
부하 리허설은 `scripts/rehearsal.mjs` 가 실제 등록 경로로 대신한다.

## ADR-8 조용한 실패는 테스트로만 잡힌다

**사고** — `새 회차 만들기` 버튼이 아무 반응이 없었다. 함수 이름이 브라우저 내장과 충돌해
**내장 함수가 조용히 호출**됐고, 에러도 남지 않았다.

**결정** — 이름 충돌을 상시 검사한다. 넓게 보면: **에러를 남기지 않는 실패는 사람 눈으로 못 잡는다.**
기계가 잡게 만든다.

같은 이유로 `npm run check:copy` 가 있다 — 문구를 지어내도 에러가 안 나므로.

## ADR-9 회차 목록은 KV 가 아니라 DO 하나가 들고 있다

**결정** — 입장 코드 → 회차 ID 인덱스, 멱등키, 운영자 PIN, 기본 설정을 전부
`RegistryDO` 하나에 둔다. KV 는 쓰지 않는다.

**왜** — 이 네 가지는 모두 "동시에 두 번 눌렀을 때 하나만 만들어져야" 하는 값이다.
KV 는 쓰기 직후 읽기가 보장되지 않아서, 새 회차를 만드는 순간 코드 중복 검사와
멱등키 검사가 **직전에 쓴 값을 못 보고 통과**할 수 있다. 회차가 두 개 생기거나
같은 입장 코드가 두 회차에 붙는다 — 파티 당일에 알아채는 종류의 사고다.

**따라오는 것**

1. 회차 생성은 두 걸음이다. 레지스트리가 신원(아이디·코드·PIN)을 먼저 잡고,
   회차 DO 가 상태를 만든다. `init()` 은 멱등이라 두 번째 요청은 이미 만든 걸 돌려준다
2. 참가자 개인정보는 레지스트리에 올라오지 않는다. 이름·전화·콕은 회차 DO 안에만 있다
3. 배포에 KV 네임스페이스 준비가 필요 없어졌다 — 비밀값 두 개면 나간다

**대가** — 회차 목록을 그릴 때 회차 수만큼 DO 를 호출한다. 한 운영자가 다루는 회차 수는
수십 개 규모라 문제가 되지 않는다. 수백 개가 되면 요약을 레지스트리에 캐시할 것.

## ADR-10 '지금 바로'는 순서 검증의 한쪽이 아니다

**결정** — 회차를 만들 때 `prevoteAt > regOpenAt` 검사는 **운영자가 고른 두 시각 사이에서만** 한다.
등록 시작을 '지금 바로'로 켠 경우에는 사전 투표 시작이 이미 지났더라도 회차를 만든다.

**왜** — '지금 바로'는 시각이 아니라 버튼이다. 서버 시각과 운영자 폰의 시각이 몇 분만 달라도
"방금 고른 시각이 시작보다 앞"이라는 이유로 회차 생성이 막히는데, 운영자는 무엇을 고쳐야 하는지 알 수 없다.

**대신** — 사전 투표 시작이 이미 지난 상태에서는 등록과 사전 투표가 곧바로 이어서 열린다.
운영자가 **두 시각을 직접 고른** 경우에는 그대로 거부한다 — 그건 오타이기 때문이다.

> **폐기 (ADR-38).** 등록 시작을 아예 묻지 않게 되면서 견줄 두 시각이 사라졌다.
> '지금 바로' 토글도, `prevoteAt > regOpenAt` 검사도 없다. 남은 결론은 **"지난 시각을 넣어도
> 회차는 만들어진다"** 하나이고, 그건 이제 예외가 아니라 유일한 동작이다.

## ADR-11 마지막 라운드에서 서로 찌른 쌍은 가중치가 아니라 구조로 지킨다

**사고** — 마지막 라운드의 상호 매칭 보너스(12 × 2.5 = 30)와 나이차 벌점(30)이 정확히 같아서,
가중치 4짜리 I·E 쏠림이 승부를 갈랐다. 서로 찌른 쌍이 갈라져 앉았다 — 동석률 50%.

**결정** — 마지막 라운드에서는 **이미 같은 테이블에 앉은 상호 매칭 쌍을 떼어놓는 맞교환을 시도하지 않는다.**
성비 불변식과 같은 방식이다: 지키려고 노력하는 게 아니라 그렇게 될 방법이 없다.

**원칙** — 어떤 제약이 "가장 중요하다"면 가중치를 키우지 말고 탐색 공간에서 빼라.
가중치는 언제나 다른 가중치의 합에 밀릴 수 있다.

## ADR-12 운영자 PIN 은 하나뿐이다

**배경** — 회차마다 PIN 을 따로 뒀다. 회차 담당자에게 그 회차만 열어주자는 생각이었다.

**실제** — 운영자는 한 명이거나 한 팀이었다. 회차 PIN 을 쓰는 사람이 없었고,
대신 ADR-3 의 사고가 생겼다. **쓰이지 않는 권한 분리가 실제 취약점을 만들었다.**

**결정** — 권한은 `master` 하나다. `AuthScope` 에서 `host` 를 없애고,
회차 PIN·PIN 해시·충돌 검사·자동 생성기를 전부 지웠다.

**따라오는 것**
- `/api/host/pin` 은 `eventId` 를 받아도 무시한다. 회차 단위의 뒷문이 없다는 걸 테스트로 고정했다 (S-A3)
- 회차 설정에서도, 기본 설정에서도 PIN 칸이 사라졌다.
  바꾸는 곳은 배포 시크릿 `MASTER_PIN` **하나뿐**이다 — 바꾸는 자리가 둘이면
  지금 무엇이 맞는 PIN 인지 화면으로는 알 수 없다. 스토리지에 남아 있던 PIN 도 지웠다

**대가** — 회차별로 운영을 나눠 맡길 수 없다. 필요해지면 그때 **역할**로 다시 만든다 —
같은 화면에 번호를 두 개 두는 방식으로는 돌아가지 않는다.

## ADR-13 참가 링크는 회차를 가리킨다 — 문은 따로다

**문제** — 링크에 입장 코드가 들어 있으면(`/j/ABCDEF`) 그 링크가 곧 입장이다.
링크는 단톡방에 돌고 스크린샷으로 퍼진다 — 운영자가 부르지 않은 사람이 명단에 들어온다.

**결정** — 참가 링크는 `/j/<회차id>` 다. 열면 **회차 이름·단계·파티 일시까지만** 보인다.

- `GET /api/events/by-id/:id` 는 인증 없이 열리지만 **입장 코드를 절대 담지 않는다** (S-C2b)
- 문을 여는 방법은 ADR-15 에서 입장 코드 → **초대 명단의 전화번호**로 바뀌었다.
  링크가 문이 아니라는 이 결정은 그대로다

## ADR-14 마감·파티·발표는 예약하지 않는다

**문제** — 사전 투표 마감·파티 시작·발표 시각을 미리 잡아두면, 현장이 그 시각을 따라가야 한다.
사람이 덜 왔는데 마감되고, 이야기가 무르익는 중에 발표가 뜬다.

**결정** — 예약하는 건 **등록 시작과 사전 투표 시작** 둘뿐이다. 파티 당일에 일어나는 세 전환은
운영자가 현황 탭에서 누른다. 시계가 알 수 없는 것(사람이 다 왔는가, 지금 발표해도 되는가)을
시계에게 맡기지 않는다.

**따라오는 것**
- `EventSchedule` 은 `{ partyAt, regOpenAt, prevoteAt }` 이다. `partyAt` 은 **전환을 울리지 않는다** —
  나머지 일정의 기준점이고, 참가자 카운트다운이 향하는 곳이다
- 등록은 발표 전까지 계속 열려 있다. 늦게 온 사람도 파티 중에 합류한다
- 참가자 상단 카운트다운은 **파티 시작**만 센다. 없는 마감을 세어 보여주면 참가자가 그 숫자를 믿는다
- 하루 넘게 남았으면 초를 세지 않는다 (`144:00:00` 은 읽는 사람이 다시 나눠야 한다)

**대가** — 운영자가 제때 누르지 않으면 아무 일도 일어나지 않는다. 그건 사고가 아니라
"아직 안 넘겼다"이고, 현황 탭 맨 위 버튼 하나로 넘어간다.

## ADR-15 파티의 문은 운영자가 미리 받아둔 전화번호다

**문제** — 입장 코드 여섯 자리는 **옮겨 적을 수 있다.** 한 명에게 알려주면 그 사람이
친구에게 알려줄 수 있고, 운영자는 명단에 없는 사람이 들어온 걸 등록이 끝난 뒤에야 안다.

**결정** — 운영자가 회차마다 전화번호 명단을 미리 넣어두고, **그 번호로만** 들어온다.

```
링크(/j/<회차id>) → 전화번호 입력 → 명단에 있으면 통과 → 등록
```

- 통과한 번호는 **서명한 초대 쿠키**에 담는다. 등록 폼은 번호를 받지 않는다 —
  폼에서 받으면 명단에 없는 번호로 바꿔 낼 수 있다 (테스트로 고정)
- **이미 등록한 사람은 명단과 무관하게 통과한다.** 명단은 문이지 자격이 아니다 —
  운영자가 명단을 정리하다 이미 온 사람을 지웠다고 파티 중에 쫓겨나면 안 된다
- 같은 번호로 다시 오면 곧바로 자기 화면으로 간다. 번호가 곧 재접속 키다
- 입장 코드는 남지만 **회차를 가리키는 이름**일 뿐 아무 문도 열지 않는다

#### 후기 2 — **번호를 아는 사람은 그 사람이 될 수 있다** (2026-08-21, 열려 있음)

이 결정이 막는 것은 "명단에 **없는** 사람" 이다. 그건 잘 한다.
막지 못하는 것은 **"명단에 있는 사람이 남의 번호를 쓰는 것"** 이다.

```ts
// participant.ts — 이미 등록을 마친 사람에게는 곧바로 참가자 세션을 준다
const scope = result.registered ? await playerScopeFor(c, id, phone) : ...
```

번호를 아는 것이 곧 **그 사람의 계정 전체**다 — 보낸 콕, 받은 콕 수, 프로필 수정,
그리고 발표 후에는 **그 사람과 서로 찌른 상대의 실명·전화번호·인스타**(`MatchInfo.contact`).
이 앱이 지키기로 한 셋이 한꺼번에 무너진다.

그리고 이건 이론이 아니다 — **같은 파티에 오는 사람들은 서로 번호를 아는 사이다.**
위 결정이 세운 가정("번호는 남이 모른다")이 현실과 어긋나 있었다.

**근본 원인 한 문장: 전화번호는 식별자이지 증명이 아니다.**

살펴본 길과 각각이 포기하는 것 —

| | 막는 것 | 못 막는 것 | 포기하는 것 |
|---|---|---|---|
| **개인별 링크** | 번호만 아는 사람 | 링크를 넘겨받은 사람 | 단톡방에 링크 하나 뿌리기. 1:1 발송 |
| 기기 고정 | 이미 등록한 사람 가로채기 | 피해자보다 먼저 등록하기 | **카톡 인앱 ↔ 크롬 이동** — 국내 기본 동선이라 정상 사용자가 계속 막힌다 |
| 추가 정보(이름 뒤 두 글자 등) | 번호만 아는 남 | **친구** — 문제의 그 사람 | 효과가 거의 없다 |
| **참가자 비밀번호 4자리** | 번호만 아는 사람 **그리고 친구** | 비밀번호를 알려준 사람 · 어깨너머 | 등록 한 단계 · **잊어버린 사람 응대가 파티 당일에 몰린다** |
| IP | — | 전부 | **통신사 CGNAT 뒤에서 수천 명이 한 IP 를 쓴다.** 남과 나를 IP 로는 못 가른다. 게다가 모바일 IP 는 셀·망이 바뀔 때마다 달라져서, 막는 쪽으로 쓰면 정상 사용자가 먼저 걸린다 |
| SMS 인증 | **전부** | — | 문자 비용(파티당 천원 안팎) · 발신번호 사전등록 리드타임 |

**결정 (2026-08-21) — 개인별 링크로 간다. 지금은 아니다.**
SMS 가 유일하게 문제를 닫지만 이 규모의 파티에는 과하다고 봤다.
개인별 링크는 참가자가 할 일이 줄고(번호도 안 친다), 운영자가 1:1 로 보내는 비용만 진다.

**다시 열림 (2026-08-21 저녁) — 비밀번호 줄이 표에 없었다.** 위 결정을 내릴 때
검토한 다섯 줄 중 어느 것도 "참가자가 스스로 정한 비밀번호"가 아니었다. 이건 새 줄이다.

두 길은 **같은 구멍을 막는 서로 다른 답이라 하나만 고른다.** 둘 다 넣으면
개인별 링크가 이미 증명한 신원을 비밀번호로 한 번 더 묻는 셈이다.

| | 개인별 링크 (13) | 참가자 비밀번호 (15) |
|---|---|---|
| 참가자가 할 일 | **없다.** 링크만 연다 | 등록 때 4자리 정하고, 다른 기기에서 친다 |
| **친구를 막나** | 링크가 카톡에 남아 있다 — 폰을 보면 보인다 | **막는다.** 번호를 알아도 못 들어온다 |
| 운영자 부담 | 28명에게 **1:1 발송** | 단톡방에 링크 하나 그대로 |
| 그 부담이 **언제** 오나 | 파티 **전**, 여유 있을 때 | 분실 응대가 **파티 당일**, 가장 바쁠 때 |
| 되돌리기 | 새 링크 뽑아 다시 보낸다 | 운영자가 재설정한다 |

**갈림길은 마지막 두 줄이다** — 막는 힘은 비밀번호가 세지만, 그 비용을 파티 당일에 낸다.

> ⚠️ **그때까지 이 구멍은 열려 있다.** 가장 비싼 유출(연락처)은 **발표 후에만** 열리므로,
> 발표를 현장에서 사람들이 눈앞에 있을 때 누르는 지금 운영이 그나마 완화책이다.
> **표에 없던 줄이 아니면 다시 그리지 마라** — 위 다섯은 이미 검토했다.

**닫혔다 (2026-08-23) → ADR-32.** 개인별 링크(13)로 간다. 15 는 이 결정으로 닫힌다.

#### 후기 — 코드로 회차를 찾는 길까지 닫았다

"아무 문도 열지 않는다" 고 해놓고 **`/api/events/by-code` 가 코드를 회차 아이디로 바꿔주고 있었다.**
그 아이디가 곧 참가 링크다 — 즉 30비트 코드(32^6)를 뚫으면 **64비트 링크(`randomHex(8)`)가
그대로 나왔다.** 링크의 강도가 코드까지 내려가 있던 셈이다.

그래서 셋을 함께 걷었다.

- 뿌리 화면(`/`)의 코드 입력 — 운영자는 보통 링크만 주므로, 링크를 열었다 뒤로 간 참가자가
  **알지도 못하는 코드를 요구받는 막다른 길**이었다. 실제로 겪은 문제다
- `/j/:id` 의 `이전` 버튼 — 그 막다른 길로 보내던 버튼이다. 링크로 온 사람에게는 돌아갈 자리가 없다
- `/api/events/by-code` — 위의 오라클

대신 뿌리 화면은 **세션이 있으면 자기 회차로 보낸다.** 링크를 잃은 사람이 앱 주소만 알아도
자기 파티로 돌아온다 — 다만 **다른 기기에서는 안 되므로**, 링크가 여전히 보편적인 길이다.

**남은 것** — `/ws/:code` 는 여전히 코드로 회차를 찾는다. 다만 그쪽은 아이디를 내주지 않고
"그 코드의 회차가 있는가" 만 새므로 훨씬 약하다. 회차 목록을 훑는 게 걱정되면 그때 닫는다.

**이 문은 인증 없이 열려 있다.** 그래서 제한이 없으면 "이 번호가 이 파티에 있나"를
되묻는 창구가 된다 — 참가 링크를 손에 넣은 사람이 주소록을 통째로 넣어보면
누가 소개팅 파티에 갔는지 알아낼 수 있다. 이 앱이 가장 막아야 하는 유출이다.

- 회차·접속지별로 실패 횟수를 센다 (`ENTRY_TRIES`). 넘으면 잠시 막는다
- 접속지는 **해시로만** 저장한다. 원본 IP 는 어디에도 남기지 않는다
- 실패 문구는 하나뿐이다. "초대되지 않았어요"와 "그런 회차가 없어요"를 구분해 주면
  그 구분 자체가 답을 알려준다

**대가** — 운영자가 번호를 미리 모아야 한다. 명단 편집에는 **더하기와 빼기만** 둔다.

- 한 명씩 — "저도 갈게요" 연락이 파티 전날에 온다
- 붙여넣기 — 처음 명단을 만들 때. 한 명씩으로는 100명을 넣을 수 없다
- **통째로 갈아치우는 길은 없다.** 한 명 추가하려다 손이 미끄러지면 그 파티의 명단이
  전부 날아가고, 되돌릴 방법이 없다. 붙여넣기도 있는 명단에 더한다

**명단이 비어 있으면 아무도 들어올 수 없다.** 그게 기본값이라 운영자가 모르면 파티 당일
문 앞에서 알게 된다 — 참가자 탭 맨 위에서 비어 있음을 경고로 말한다.

## ADR-16 자리 맞교환은 남녀도 바꾼다

**배경** — 좌석 변경을 **같은 성별끼리만** 허용했다. 테이블 성비를 지키기 위해서였다.

**실제** — 현장에서 운영자가 아는 사정(아는 사이라 떼어놔야 한다, 자리를 부탁받았다)은
배정 알고리즘이 모른다. 같은 성별 안에서만 바꿀 수 있으면 그 사정을 못 푼다.

**결정** — 맞교환은 성별을 가리지 않는다. **여전히 맞교환 하나뿐**이다 —
한 명만 옮기는 API 는 만들지 않는다. 그건 테이블 인원이 어긋나는 일이라 성격이 다르다.

바뀐 성비는 자리 화면 테이블 머리의 `남 N / 여 M` 에 곧바로 보인다.
숨기지 않고 보여주는 쪽을 택했다 — 막는 것보다 낫다.

## ADR-17 콕은 성별을 가리지 않는다 (기본값)

**배경** — 처음에는 이성에게만 찌를 수 있었고, 동성 허용은 회차 설정의 선택 항목이었다.

**결정** — 기본이 **모두에게**다. 누구에게 마음이 가는지는 앱이 정할 일이 아니다.
이성만으로 좁히고 싶은 회차에서만 설정에서 좁힌다.

`allowSameGender` 는 그대로 두되 **없으면 모두에게**로 읽는다. 좁혔을 때만 `false` 를 적는다 —
설정을 새 항목으로 갈아엎으면 저장된 옛 모양이 또 화면에 NaN 을 띄운다 (ADR-12 뒤의 사고).

**따라오는 것**
- 참가자 목록의 기본 필터가 '전체'다. 반쪽만 보여주면 찌를 수 있는 사람이 가려진다
- 자리 배정의 남녀 정원은 **어느 쪽이든 그대로**다. 콕과 자리는 다른 규칙이다

## ADR-18 발표 결과는 그 사람이 있는 자리에 나온다

**문제** — 상호 매칭을 '내 정보' 탭에만 보여줬다. 파티장에서는 상대를 눈앞에 두고
다른 탭을 뒤져야 결과를 확인할 수 있었다.

**결정** — 발표 후 참가자 목록에서 **그 사람의 카드가 달라진다.**

- 카드 테두리와 바탕이 강조되고, 매력 자리에 `💘 서로 찔렀어요`가 들어간다
- **색만으로 말하지 않는다.** 글자로 같은 정보를 준다
- 같은 테이블이면 테이블 번호까지 카드에 붙는다
- **목록에서 맨 위로 올라온다.** 스무 명을 훑어 내려가게 두면 다른 탭에 숨긴 것과 같다
- 프로필 시트 맨 위에 매칭 카드가 뜬다
- 홈의 `결과 보기` 는 **참가자 탭**으로 간다
- '내 정보' 탭에는 결과가 없다. 그 탭이 답하는 질문은 "내가 낸 것이 무엇인가" 하나다
- 서로 찌른 상대가 없으면 홈에서 문장으로 말한다. **"0명"이라는 숫자를 꺼내지 않는다**

연락처도 이 자리에서 열린다 (ADR-19).

발표 전에는 `matches` 가 비어 있어서 목록에 아무 표시도 생기지 않는다. 테스트로 고정했다.

## ADR-19 연락처는 서로 찌른 쌍에게, 발표 후에 열린다 — **보관 기간 폐기 (ADR-36)**

**바뀐 것** — 처음에는 "연락처는 매칭돼도 주지 않는다. 앱은 같은 테이블까지만 만든다"였다.
운영자 판단으로 **서로 찌른 쌍에게는 연락처를 연다**로 바꿨다.

**왜 그래도 안전한가** — 이 앱이 없애려는 건 *거절당하는 경험*이지 연락 그 자체가 아니다.
연락처는 **양쪽이 서로를 골랐을 때만** 열린다. 한쪽만 찌른 상대에게는 발표 뒤에도 끝까지 익명이다 —
일방적인 호감이 드러나지 않는다는 첫 번째 기둥은 그대로다.

**통로는 하나뿐이다.** `MatchInfo.contact` 는 `pokeState()` 의 `phase === "done"` 블록,
그것도 `mutual` 에 든 쌍만 지나는 자리에서 채워진다. 세 조건이 구조로 겹쳐 있다.

- 명단(`roster`)은 여전히 `toPublic()` 만 지난다. 예외 없다
- 발표 전에는 `matches` 자체가 비어 있다
- 셋 다 테스트로 고정했다 (발표 후 열림 / 발표 전 없음 / 한쪽만 찌른 경우 없음)

**받을 때 한 약속을 먼저 고쳤다.** 등록 화면은 "연락처는 운영자만 봐요"라고 말하고 있었다.
그 문구를 그대로 둔 채 상대에게 넘기는 건 기능 변경이 아니라 약속을 어기는 일이다.
지금은 등록 전에 이렇게 말한다 — *"연락처는 운영자와, 발표 때 서로 찌른 상대에게만 보여요.
한쪽만 찌른 경우에는 끝까지 공개되지 않고, 파티가 끝나고 3일 뒤에 지워져요."*
(2026-08-16 기본 보관 기간을 7일 → 3일로 줄였고, 회차 설정에서 1~14일로 조정할 수 있게 했다.
등록 화면 문구는 회차의 `retentionDays` 를 그대로 읽었다 — 문구와 파기 판정의 출처가 같았다.
**그 뒤 파기 기한은 등록 문구에서 빠졌고, 지금은 자동 파기 자체가 없다 — ADR-36.**
지금 문구는 *어디까지 가는지* 두 문장만 말한다)

**대가** — 한 번 나간 번호는 되돌릴 수 없다. **우리 쪽 저장소도 저절로 비지 않는다** (ADR-36) —
끝난 회차를 지우는 것이 운영자의 일이 됐다.
그래서 공개 범위를 **양쪽 합의**로 좁혀둔 것이고, 이 조건을 넓히는 변경은
등록 화면 문구를 먼저 고치지 않고는 하지 않는다.

## ADR-20 오늘의 연애운 — 점수를 매기지 않고, 한 번 열면 바뀌지 않는다

**무엇** — 파티가 시작되면 참가자 탭 **맨 오른쪽**에 '오늘' 탭이 생긴다.
카드를 뒤집으면 LLM 이 쓴 오늘의 연애운 한 편(세 문단)과 **오늘의 미션**이 나온다.
이 앱에서 유일하게 기능이 아니라 재미인 자리다.

탭은 끝에 붙인다. 도중에 끼어들면 있던 탭들이 밀려서 손가락이 기억한 자리가 어긋난다.

세 문단은 **오늘 그 파티에서 일어날 법한 일**만 말한다 — 오늘의 결 · 잘 통할 흐름 ·
조심하면 좋을 것. 먼 미래나 인생 전체를 말하지 않는다.
미션은 그 세 문단에서 이어지고, **30분 안에 해볼 수 있고 실패해도 티가 나지 않는 것**이다.
"용기를 내세요" 같은 말은 미션이 아니다.

**미션은 두 칸이다 — 왜(`lead`)와 언제·무엇(`mission`).**
한 줄만 던지면 남이 준 숙제로 읽히고, 숙제는 미뤄진다. 오늘의 운세에서 이어지는 이유가
앞에 서야 내 것이 된다. 그리고 미션 문장에는 **언제 할지**가 들어간다 —
누구에게·무엇을 만 정해주면 그 순간이 오지 않는다. 시계 시간이 아니라 상황으로 적는다
("자리를 옮기고 막 앉았을 때", "대화가 잠깐 멎었을 때").

**무게와 압박은 다르다.** `lead` 는 이유만 말하고 **시키지 않는다** — 시키는 건 미션 한 문장뿐이다.
'꼭'·'반드시'·'해야' 를 쓰지 않는다. 같은 이유로 **"했어요" 체크는 만들지 않는다** —
했다/못 했다가 남으면 그게 곧 점수이고, 이 앱이 없애려던 경험을 앱이 다시 만든다.

`lead` 는 **없이 올 수도 있다.** LLM 이 빼먹었을 때 쓸 만한 미션까지 버리는 건 손해가 더 크다 —
그때는 미션 한 줄만 저장되고 화면도 한 줄로 그린다. 이 칸이 생기기 전에 열어 둔 운세도 마찬가지다.

### 점수를 매기지 않는다

연애운 앱의 기본형은 `82점`인데 여기서는 그게 독이다. 이 앱이 없애려는 게
거절당하는 경험인데 `당신의 오늘 연애운 34점`은 앱이 **직접** 그 경험을 만든다.
파티장에서 옆 사람과 비교하는 순간까지 만든다.

그래서 좋고 나쁨이 아니라 **오늘의 결**을 말한다. 모델에게도 못 박아 둔다 —
점수·등급·순위 금지, 외모 금지, 단정 금지. 화면에 숫자가 없는 것까지 테스트로 고정했다.

### 한 번 열면 바뀌지 않는다

회차 DO 에 1인 1행으로 저장하고, 두 번 저장돼도 **먼저 온 하나**가 남는다
(`ON CONFLICT DO NOTHING`). 다시 열 때마다 달라지면 그 순간 전부 거짓말이 된다.
색과 '말이 잘 통할 결'은 닉네임+MBTI 해시로 정해서 LLM 없이도 같은 값이 나온다.

### LLM 에 보내는 것은 두 입력 함수가 만드는 것뿐이다

호출이 둘이라 **재료도 둘로 갈린다.**

| 호출 | 함수 | 보내는 것 |
|---|---|---|
| ① 오늘의 기운 (사주) | `fortuneInput()` | **실명** · 생년월일 · 성별 · **오늘 날짜** |
| ② 오늘의 미션 | `missionInput()` | **실명** · 닉네임 · MBTI · 매력 3가지 · **방금 나온 운세** |

②가 돌려주는 것은 `{lead, mission}` 두 칸이다.

**미션을 두 번째 호출로 뺀 이유** — 한 호출에서 함께 뽑으면 미션이 본문 마지막 문단을
그대로 옮겨 적었다. 다 읽고 나서 "그래서 오늘 뭘 하지" 를 따로 물으면 겹치지 않는다.

그리고 그 호출은 **참가자가 미션 카드를 뒤집을 때** 나간다. 운세 카드를 뒤집는 것과 같은 의식이다 —
미리 만들어 두고 감췄다 보여주면 "여는 동작이 있어야 오늘 것처럼 읽힌다" 는 이 ADR 의 말과 어긋난다.
안 열어 본 사람 몫을 아예 만들지 않는 것은 덤이다.

**저장이 규칙을 지킨다.** `saveFortune` 의 `ON CONFLICT DO NOTHING` 이 곧 "한 번 연 운세는
바뀌지 않는다" 이고, 미션은 그걸 우회하지 않도록 **`saveMission` 이 따로** 채운다 —
이미 있으면 그대로 돌려주고, 운세 본문은 건드리지 않는다.
(`saveFortune` 로 덮어쓰는 길을 만들면 그 규칙이 조용히 무너진다.)
`parseFortune` 은 `FortuneDraft`(미션 없는 모양)를 돌려준다 — **타입으로 갈라두면
한 호출에서 둘 다 뽑으려는 시도가 컴파일에서 막힌다.**

**읽기는 좁게 한다.** 두 경로 모두 `fortuneContext()` 를 쓴다 — 단계·나·저장된 운세 셋만 꺼낸다.
`participantState()` 를 부르면 명단 전체를 `toPublic()` 으로 빚고 콕을 집계하는데,
파티가 시작되면 이 경로가 인원 수만큼 한꺼번에 열린다. 지금 규모(50명)에서는 그것만으로
줄이 서지 않지만, 필요 없는 일을 인원 수만큼 하지 않는 것은 그 자체로 옳다.

> ⚠️ `fortuneContext()` 의 `me` 에는 **실명이 있다.** LLM 입력을 만드는 데만 쓰고,
> 라우트가 돌려주는 건 `Fortune` 하나여야 한다. 그대로 내보내면 참가자 응답에 이름이 실린다.

**오늘 날짜는 파티가 열리는 지역 기준**이다 (`todayIn`). UTC 로 자르면 자정 넘은 파티가
어제 날짜를 읽는다 — 한국 밤 9시는 UTC 로 같은 날 정오지만, 새벽 1시는 UTC 로 어제다.

**전화번호와 인스타는 어느 쪽에도 가지 않는다.** 이건 그대로다.

**생년월일**은 여는 순간 본인이 직접 넣고(진짜 운세 보는 의식) 별자리·띠로 풀려 실린다.
**전송에만 쓰고 어디에도 저장하지 않는다** — 운세와 함께 남기면 전화번호 옆에 놓이는
가장 무거운 신원 정보가 된다. 라우트가 읽고 그 자리에서 버린다.

#### 개정 — 실명을 운세 호출에만 허용한다

원래는 실명도 금지였다("참가자끼리도 안 주는 걸 외부에 보내는 건 더 나쁘다").
바꾼 이유는 **사주의 재료가 이름과 생년월일**이어서다. 닉네임으로 보는 사주는 사주가 아니다.

대신 예외를 **좁게** 두고 셋을 함께 지킨다. 하나라도 빠지면 예외가 아니라 구멍이다.

1. **오늘의 운세 기능(두 호출)에만.** 그 기능 밖으로는 어떤 이유로도 나가지 않는다 —
   경계가 "기능 하나" 라야 "어디까지 보내도 되나" 를 되묻지 않는다
2. **답변에 이름이 나오지 않는다.** 프롬프트가 못 박고 2인칭으로 쓰게 한다.
   보내는 것보다 **남는 것**이 무겁다 — 답변에 이름이 나오면 저장물에도 화면에도 남는다
3. **저장하지 않는다.** 생년월일과 같다. 전송에만 쓴다

세 가지 전부 테스트가 고정한다 (`test/08-fortune.test.ts`) — 특히 ①은
어필 입력에 실명이 섞이는 순간 깨진다.

**같이 걷어낸 것** — '말이 잘 통할 결'(MBTI 궁합)은 없앴다. 운세 재료가 사주로 좁혀지면서
MBTI 를 보낼 이유가 사라졌고, 그 줄만 살리자고 재료를 넓히는 건 앞뒤가 바뀐 일이다.

'오늘의 어필' 카드도 걷어냈다. 미션과 **같은 말을 두 번** 하고 있었다 —
어필에 미션을 참고로 넘겼더니 그대로 받아 적었다. 두 카드가 서로를 알게 하려던 것이
서로를 베끼게 만들었다. 지금은 미션 하나만 남고, 그게 운세를 읽고 나온다.

### 실패는 정상 경로다

키가 없거나 · 모델 이름이 틀렸거나 · 느리거나(6초) · 형식이 어긋나면 **규칙 문구**로 떨어진다.
그래서 그쪽 문장도 읽을 만하게 썼다 — 본인이 쓴 매력 한 줄을 그대로 안아 쓴다.
파티 당일에 탭 하나가 에러를 뿜는 건 사고다.

**호출은 Worker 에서 한다. DO 안에서 부르지 마라** — DO 는 요청을 한 줄로 처리해서,
응답을 기다리는 몇 초 동안 그 회차의 모든 요청이 뒤에 선다. 파티 중에는 그게 곧 정지다.

**읽는 자리는 `readFortune()` 하나다.** 지금은 1.0.0 이 쓴 모양만 들어 있어 할 일이 없지만,
다음에 모양이 바뀌면 고칠 곳이 여기 하나다 — '오늘의 한 걸음'(`step`)이 '오늘의 미션'(`mission`)이
됐을 때 여기가 그 일을 했다. 그 자료는 1.0.0 기준선에서 사라졌다.
`readFortune()` 이 옛 이름을 받아준다. 저장된 자료는 코드보다 오래 산다 (기본값 NaN 사고와 같은 자리).

**모델은 설정이다** — `LLM_MODEL` · `LLM_BASE_URL` · `OPENAI_API_KEY`.
제공자가 바뀌어도 코드가 아니라 변수가 바뀐다. 모델 이름이 틀리면 규칙 문구로 떨어질 뿐 앱은 돈다.

### 후기 — 문을 둘로 가른다: 운세는 매력 투표부터, 미션은 파티부터 (2026-08-24)

**무엇** — '오늘' 탭이 열리는 시점을 **매력 투표 시작**으로 앞당긴다.
그리고 탭은 **없다가 생기지 않는다** — 처음부터 자리를 지키고 그때 켜진다.

**왜 탭을 미리 세우나.** 이 결정은 "탭은 끝에 붙인다 — 도중에 끼어들면 있던 탭들이 밀린다" 라고
적어뒀는데, 끝에 붙여도 **넷이 넷 폭을 나눠 쓰던 자리가 통째로 다시 나뉜다**(`.tabbar` 는 flex 1).
없앴다 만드는 대신 흐리게(`aria-disabled`) 세워두면 자리가 처음부터 끝까지 그대로다.
꺼진 탭도 **누르면 말한다** — `매력 투표가 시작되면 열려요`. 눌러도 조용하면 고장으로 읽힌다.

**왜 미션만 남기나.** 운세는 읽는 것이라 미리 열려도 잃을 게 없다. 미션은 다르다 —
이 ADR 이 정한 대로 미션 문장에는 **언제 할지**가 들어가고("자리를 옮기고 막 앉았을 때"),
그건 파티장에서만 성립한다. 그런데 매력 투표는 파티 **스무 시간 전**에 열린다
(`DEFAULTS.prevoteBeforeH`). 전날 밤에 뒤집으면 할 수 없는 미션이 **그대로 굳는다** —
"한 번 열면 바뀌지 않는다" 가 여기서는 손해가 된다. 그래서 문을 둘로 가른다
(`canOpenFortune` · `canOpenMission`). 서버가 둘 다 지킨다.

**덤으로 고친 것 — 운세의 `오늘` 은 연 날이 아니라 파티 날이다.** 문이 앞당겨지면서
전날에 연 사람이 어제 날짜로 운세를 받고, 그게 파티 당일까지 남는 길이 생겼다.
세 문단이 말하는 `오늘` 은 **그 파티의 날**이므로 `todayIn(partyAt)` 을 보낸다
(일정 없는 회차만 지금을 쓴다). 기본 일정(파티 20시간 전 = 파티 당일 0시)에서는 원래 같은 날이라
겉으로 달라지는 건 없다 — 운영자가 매력 투표를 더 일찍 잡았을 때만 갈린다.

### 후기 2 — 탭 이름을 `오늘` 에서 `재미` 로, 이모지를 `✨` 에서 `🎲` 로 (2026-08-24)

**무엇** — 탭이 **운세 한 편의 자리에서 재미 카드가 모이는 자리로** 넓어진다.
이름·이모지·주소가 함께 바뀐다: `오늘` → **`재미`**, `✨` → **`🎲`**, `/fortune` → **`/fun`**.
운세 자체(`FORTUNE` 문구 · `/api/fortune` · `canOpenFortune`)는 그대로다 —
**바뀐 것은 그릇의 이름이지 담긴 것이 아니다.**

**왜 이름을.** 이상형 찾기(슬라이스 19)가 이 탭의 두 번째 카드로 들어온다.
`오늘` 은 **날짜에 묶인 이름**이라 그 옆에 설 수 있는 게 "오늘의 무엇" 뿐이었다 —
이상형 연예인은 오늘의 것이 아니다. 이름이 좁으면 **들어올 것을 이름이 먼저 막는다.**

**왜 이모지를.** `✨` 은 매력 투표 버튼이 쓰던 것이다 (`ACT.emoji("pre")`).
같은 이모지를 두 자리에 쓰면 **화면만 보고는 지금 무엇을 하는 자리인지 갈리지 않는다** —
ADR-34 가 `✨`(매력 투표)과 `👉`(콕)을 일부러 가른 것과 같은 규칙인데, 탭이 그 규칙 밖에 있었다.

`🎲` 를 고른 자리는 **탭 안에서도 비어 있어야 했다.** 🔮(운세 오브)·🎯(미션)·🎨(색)은
이미 카드가 쓰고 있고, 그중 하나를 탭 아이콘으로 올리면 **카드 하나가 탭 전체를 대표한다** —
카드가 늘 때마다 아이콘이 거짓말이 되는 자리다. 🪄·🌟 계열은 `✨` 과 다시 붙어서 뺐다.

### 이 탭에 무엇이 들어올 수 있나

이름이 넓어지면 **아무거나 들어올 수 있다는 뜻이 된다.** 그래서 문을 다섯으로 적어둔다.
새 카드는 **다섯을 다 지킬 때만** 여기 들어온다.

| | |
|---|---|
| 본인만 본다 | 운영자 화면에도 남에게도 나가지 않는다 |
| 한 번 열면 그대로 | 열 때마다 달라지면 그 순간 전부 거짓말이 된다 |
| 점수·등급·순위 없음 | 이 앱이 없애려던 경험을 앱이 직접 만드는 일이다 |
| 실패해도 티가 나지 않는다 | 미션 규칙과 같다 |
| 이야깃거리가 된다 | 답은 앱이 찾고, 말할지는 본인이 고른다 |

**'내 정보' 와 겹치지 않는다.** 둘 다 나에 대한 자리지만 방향이 반대다 —
내 정보는 *내가 적어 남에게 보이는 것*, 재미는 *앱이 나에게만 주는 것*이다.

**탭의 문은 가장 먼저 열리는 카드의 문이다.** 지금은 그게 운세라 `canOpenFortune` 이
그대로 탭의 문이고, 꺼진 탭을 누르면 `FORTUNE.closed` 가 나간다. 더 일찍 열리는 카드가
들어오면 **탭의 문을 따로 적는다** — 카드의 문을 빌려 쓰면 문장이 조용히 틀려진다.

**옛 이름은 문서에 그대로 둔다.** ADR 과 시나리오의 `오늘 탭` 은 그때의 기록이다
(매력 투표 개명에서와 같다 — `copy.ts` 머리말). 코드와 `UI.md`·`ROUTES.md` 만 새 이름을 쓴다.

## ADR-21 참가자 명단은 한 번에 다 열리지 않는다

**결정** — 단계마다 보이는 만큼만 보인다.

| 단계 | 보이는 것 |
|---|---|
| 준비 중 · 등록 중 | **아무것도 없다.** 명단도, 인원 수도 |
| 사전 투표 | 닉네임 · 매력 3가지 |
| 파티 시작 후 · 발표 | + 나이 · MBTI |

**왜** — 등록만 하고 기다리는 동안 남의 프로필을 훑는 시간이 길수록,
파티장에서 처음 만나는 순간이 줄어든다. 사전 투표에서 사람을 고를 때 필요한 건
닉네임과 그 사람이 직접 쓴 매력 세 줄이다. 나이와 MBTI 는 그 자리에서 판단을 굳히는 재료라
**눈앞에 사람이 있을 때** 여는 편이 낫다.

**인원 수도 등록 중에는 안 나간다.** 한동안 "기다리는 사람에게 필요한 정보" 라고 보고 내려줬는데,
**인원이 적을수록 그 숫자 하나가 명단만큼 많은 것을 말한다.** 둘이 등록한 회차에서 `2명` 은
"나 말고 한 명" 이고, 그 한 명이 누구인지는 단톡방에서 금방 좁혀진다.

그래서 `ParticipantState.event` 에서 아예 뺐다 — 사전 투표부터는 `roster` 가 대신 말하므로
어느 단계에도 필요 없다. **명단 방송(`roster`)에도 수를 싣지 않는다**: 전원에게 나가는 신호이고,
받는 쪽은 어차피 다시 읽는다 (ADR-26). 화면에서 감추는 것으로는 부족하다 —
개발자 도구를 여는 참가자가 있다.

**성별은 내내 있다.** 이성만 보기와 아바타가 이걸로 그려진다 — 기능이 걸려 있어서 뺄 수 없다.

**화면에서 감추는 게 아니라 응답에 없다.** `toPublic(player, phase)` 한 곳에서 갈린다.
개발자 도구를 여는 참가자가 반드시 있고, 그 사람에게도 없어야 한다.
단계별로 응답 키 목록을 테스트가 고정한다.

**대가** — 등록 직후 참가자 탭이 비어 있다. 왜 비었는지 그 자리에서 말해준다
("사전 투표가 열리면 참가자를 볼 수 있어요"). 아무 말 없이 빈 목록이면
"내 등록이 안 됐나" 싶어진다.

## ADR-22 운영자도 '받은 콕'은 보지 않는다 · 입장 코드는 바꾸지 않는다 · 설정은 확인을 거친다

### 받은 콕을 응답에서 뺀다

현황 탭에서 '아직 콕을 못 받은 사람' 을 뺐던 것과 같은 이유다 —
**알면 그 사람을 다르게 대하게 된다.** 파티를 진행하며 한 사람을 더 챙기거나 덜 챙기게 되고,
그건 이 앱이 없애려던 경험을 운영자 손으로 만드는 일이다.

화면에서 감추는 게 아니라 `HostState` 에서 뺐다. 참가자 삭제 확인창의 숫자에서도 뺐다 —
거기서 새면 감춘 의미가 없다. **사전 투표 1위는 남는다.** 그건 진행 멘트에 실제로 쓴다.

보낸 콕은 남긴다. "누가 아직 아무도 안 찔렀나" 는 운영자가 말을 걸어볼 신호다.

### 입장 코드는 만든 뒤에 바꾸지 않는다

이미 나간 링크·안내와 어긋나고, 바뀐 걸 모르는 사람은 문 앞에서 막힌다.
되돌릴 방법도 없다. 설정 화면에서는 **글자로만** 보여주고, 서버는 `code` 를 받아도 무시한다.
`EventPatch` 에서 아예 지웠다 — 받지 않는 값은 타입에도 두지 않는다.

### 콕 상한은 이미 쓴 횟수 아래로 못 내린다

내리면 그 사람의 남은 횟수가 음수가 되고, 화면은 "−1회 남음" 을 보여준다.
이미 보낸 콕을 되물릴 방법도 없다 — 그래서 **막는 쪽**이 맞다.

두 겹으로 둔다. 화면에서는 `−` 버튼이 그 아래로 내려가지 않고(`pokeUsedMax`),
서버는 같은 규칙으로 409 를 준다. 사람이 고르는 자리와 판정하는 자리를 둘 다 막는다.

### 설정은 확인을 거쳐야 적용된다

이 화면의 저장은 **참가자 전원의 화면**을 바꾼다 — 콕 횟수도, 일정도.
그래서 규칙 4 대로 무엇이 어떻게 바뀌는지 항목으로 보여주고, 바뀐 것만 보여준다.
아무것도 바꾸지 않고 눌렀으면 빈 확인창 대신 그렇다고 말한다.

## ADR-23 커플 자리는 다른 라운드와 화면이 달라야 한다

> ⚠️ **폐기됨 — ADR-51.** 커플 자리 라운드 자체를 걷어냈다. 콕이 매 라운드 자리에 들어가므로
> 쌍만 모으는 전용 라운드가 필요 없어졌고, 못 붙은 쌍은 운영자가 💔 를 보고 맞교환으로 옮긴다.
> **다만 두 가지는 살아서 모든 라운드로 넓어졌다** — 섞어도 붙어 앉은 쌍은 제자리이고,
> 쌍을 떼는 맞교환에는 확인이 붙는다. 아래는 그 규칙들이 왜 생겼는지의 기록이다.

**배경** — 마지막 라운드는 `buildSeating(final: true)` 로 만든다. 이 라운드의 목적은 하나다 —
**서로 찌른 쌍을 같은 테이블에 앉히는 것.** 떼어놓는 맞교환은 아예 시도하지 않는다 (ADR-11).

그런데 화면에는 그게 **하나도 보이지 않았다.** 이름만 늘어놓여 있어서
배정이 제 일을 했는지 눈으로 확인할 방법이 없었고, 제목 한 줄만 달랐다.

### 이름을 바꿨다

`마지막 자리 배정` → **`💘 커플 자리 배정`**.
'마지막' 은 지킬 수 없는 약속이다 — 그 뒤에 한 번 더 배정할 수 있고, 실제로 그럴 일이 있다.
이름은 그 버튼이 **하는 일**을 말해야 한다.

**참가자에게는 이 라운드가 특별하다고 말하지 않는다.** `${round}라운드` 로만 알린다 —
"커플 자리" 라고 알리면 같은 테이블에 앉은 사람 중 누가 나를 찔렀는지 짐작하게 된다.
"마지막 자리" 도 뺐다. 지킬 수 없는 약속이라서.

### 화면에 더한 것 넷

1. **성적표** — `서로 찌른 8쌍 중 7쌍을 같은 테이블에`. 이 라운드가 제 일을 했는지 한 줄로
2. **떨어진 쌍을 이름으로** — 인원 구성상 100% 가 안 될 수 있다 (SEATING.md 기준 90%).
   못 붙인 쌍이 운영자가 맞교환으로 손볼 수 있는 **유일한 신호**다
3. **자리 위의 💘** — 같은 테이블에서 이어진 사람에게 붙는다. 다른 라운드에는 붙이지 않는다.
   그 라운드들은 쌍을 붙이려 하지도 않아서, 표시가 있으면 오해가 된다
4. **쌍을 깨는 맞교환에 확인** — 막지는 않는다. 현장 사정은 운영자가 안다.
   다만 무엇이 깨지는지는 이름으로 말한다

### 섞기가 쌍을 흩어놓던 것을 고쳤다

`shuffleSeating()` 은 남녀 비율만 지키고 쌍은 보지 않았다.
커플 자리에서 누르면 **버튼 하나로 그 라운드가 무의미해졌다.**

커플 자리에서는 붙어 앉은 쌍이 자리를 지키고 나머지만 섞인다.
성비도 그대로다 — 쌍이 제자리에 있으니 각 테이블의 남녀 수는 애초에 변하지 않는다.
버튼은 숨기지 않는다. "이 조합이 마음에 안 든다" 는 커플 자리에서도 일어나는 일이고,
그때 원하는 건 쌍을 푸는 게 아니라 **나머지를 다시 섞는 것**이다.

### 확정해도 배정은 닫히지 않는다 (ADR-28 에서 바뀜)

처음에는 커플 자리를 확정하면 배정을 닫고 `배정 다시 열기` 를 거치게 했다.
지금은 닫지 않는다 — 확인창에는 성적표만 한 번 더 나온다.

## ADR-24 한 사람이 여러 명과 이어질 수 있다

콕이 1인당 여러 번이므로 A–B 와 A–C 가 동시에 성립한다. 막지 않는다 —
두 사람에게 마음이 가는 건 이상한 일이 아니고, 막으려면 "먼저 온 쌍만 인정" 같은
설명할 수 없는 규칙이 필요해진다.

### 참가자에게 보이는 것

**B 는 A 와 이어졌다는 것만 안다.** A 가 C 와도 이어졌다는 건 어디에도 없다.
`matches` 는 본인 기준으로만 만들어지므로 구조가 이미 그렇다 — 테스트로 고정했다.

같은 테이블에 A·B·C 가 앉아도 B 는 눈치챌 수 없다. 자리는 이유를 말하지 않는다.

### 자리 배정

**불가능한 상황이 아니다.** A 가 앉은 테이블에 B 와 C 가 함께 앉으면 두 쌍 다 성공한다.
`seating.ts` 는 처음부터 짝을 **리스트**(`partners: number[][]`)로 들고 있고
`withPartner()` 가 "짝 중 아무나 이 테이블에 있는가"를 본다 — 알고리즘은 이미 맞았다.

정원이 모자라 못 붙이는 경우에만 떨어진 쌍이 된다. 그건 다른 쌍과 똑같이 다룬다.

### 화면 코드에서 실제로 났던 사고

커플 자리 화면(ADR-23)을 만들며 짝을 `Map<string, string>` 으로 뒀다.
`A→B` 를 넣고 `A→C` 를 넣으면 **앞의 것이 덮인다.** 결과는 조용했다 —
A–B 쌍이 성적표에서 빠지고, 💘 가 엉뚱한 사람에게 붙고, 맞교환 경고가 뜨지 않았다.

지금은 이렇게 한다.
- 짝은 `Map<string, Set<string>>` — 사람마다 **여럿**
- 성적표는 사람→짝 지도가 아니라 **쌍 목록**(`mutual`)을 그대로 센다.
  지도에서 세면 쌍 하나가 통째로 빠진다
- 💘 는 같은 테이블의 짝 수를 센다. 둘이면 `💘×2`
- 맞교환 경고는 **떨어지게 되는 쌍을 전부** 이름으로 보여준다. 한 번에 여럿이 깨질 수 있다

**교훈** — "한 사람에 하나" 로 모델링하기 전에 그게 정말 하나인지 본다.
여기서는 아니었고, 틀렸을 때 에러가 나지 않고 조용히 빠졌다.

## ADR-25 여러 쌍 중에서는 콕을 더 많이 주고받은 쪽을 먼저 붙인다

**문제** — A 가 B·C 둘과 이어졌는데 (ADR-24) 정원이 모자라 한 명하고만 앉힐 수 있다.
지금까지는 **목록에 먼저 온 쌍**이 자리를 가져갔고, 그 순서는 Set 순회 순서라 사실상 임의였다.

**결정** — 주고받은 콕 횟수로 정한다. 많이 오간 쪽이 먼저 앉는다.

두 군데에 같은 기준을 넣었다.

1. **자리를 잡는 순서** — 쌍 목록을 세기 순으로 정렬해 강한 쌍부터 앉힌다.
   `buildSeating` 의 ① 단계는 앞의 쌍이 자리를 가져가는 구조라, 정렬만으로 우선순위가 생긴다
2. **벌점** — 붙여 앉히는 보너스가 세기에 비례한다 (`pairWeight`)

**상한을 둔다** — `pairWeight` 는 2를 넘지 않는다. 없으면 30번 주고받은 한 쌍이
나이차 벌점을 통째로 밀어내고 그 테이블만 이상해진다. 가중치가 다른 가중치의 합을
넘으면 안 된다는 건 마지막 라운드에서 이미 겪었다 (ADR-11).

**왜 이 기준인가** — 세 번 주고받은 쌍과 한 번씩 주고받은 쌍 중 하나를 골라야 한다면,
앞의 것이 더 확실한 신호다. 다른 후보(먼저 찌른 순서, 나이차, 무작위)는 설명할 수 없거나
운영자가 손댈 수 없는 값이다. 주고받은 횟수는 두 사람이 스스로 만든 값이다.

**화면도 같은 순서다** — 운영자의 커플 목록이 세기 순으로 읽힌다. 상단이 가장 확실한 쌍이다.

## ADR-26 실시간은 "다시 읽어라" 신호이고, **끊겼던 것도 신호다**

**측정** — QA 에서 재보니 단계 전환 브로드캐스트 +250ms, 콕 +218ms 로 도착한다.
소켓 자체는 잘 돈다. 문제는 **끊긴 동안**이었다.

서버는 놓친 걸 다시 밀어주지 않는다. 콕은 받은 그 순간 한 번만 나가고,
연결이 없으면 그걸로 끝이다. 상태는 서버에 남아 있으니(`receivedCount`)
**다시 읽기만 하면** 되는데, 다시 읽을 계기가 없었다.

파티장에서 폰을 주머니에 넣었다 꺼낸 사람만 옛 화면을 본다 — 조용한 사고다.

**세 가지를 더했다.**

1. **다시 붙으면 한 번 부른다** — `reconnect` 는 서버가 보내는 게 아니라
   클라이언트가 스스로 만드는 신호다. 화면이 스스로 따라잡는다
2. **주기적으로 두드린다** — 25초마다 ping. 죽은 소켓은 `close` 없이 조용히 멈추기도 한다
   (폰이 잠들거나 통신사가 바뀔 때). 70초 동안 아무 소식이 없으면 끊어서 재연결 경로를 태운다
3. **앱으로 돌아오면 따라잡는다** — `visibilitychange`. 폰을 꺼내는 순간이
   사람이 화면을 가장 믿는 순간이다. 소켓이 죽어 있으면 백오프를 기다리지 않고 바로 붙는다

`pong` 으로는 화면을 다시 그리지 않는다. 살아 있다는 뜻일 뿐이다.

**비용** — ping 은 1인당 파티 세 시간에 400여 번이지만 **메시지는 요청으로 세지 않는다.**
WS 는 연결 1건만 요청이다. 이게 애초에 폴링 대신 WS 를 고른 이유다.

**테스트를 쓰지 않았다** — 가짜 소켓을 세워 재연결을 흉내내는 테스트를 써 봤는데,
규칙이 아니라 배관을 검사하고 있었다. 리팩터링에 깨질 뿐 지켜주는 게 없어서 버렸다.
서버 쪽 절반(ping → pong)은 QA 에서 확인했다 (+173ms).

## ADR-27 매력은 사전 투표가 열리기 전까지만 고칠 수 있다 — **대상이 넓어짐 (ADR-31)**

> 지금은 매력만이 아니라 **등록할 때 낸 것 전부**(전화번호 제외)가 이 규칙을 따른다.
> 경계(`phase === "reg"`)와 그 이유는 아래 그대로다.


**왜 열어주나** — 등록 폼 3스텝의 마지막 칸에서 급히 쓴 세 줄이다.
"세 가지 모두 필요해요" 를 채우려고 아무거나 적고 넘어간 사람이 있고,
그 세 줄이 파티에서 자기를 대신 소개한다. 다듬을 시간은 줘야 한다.

**왜 닫나** — 사전 투표가 시작되면 사람들이 그 세 줄을 **보고** 콕을 찌른다.
그 뒤에 바꾸면 누군가 나를 고른 근거가 조용히 사라진다.
찌른 사람은 자기가 무엇을 보고 찔렀는지 다시 확인할 방법도 없다.

**경계는 `phase === "reg"`** — 등록 중에만 열린다.
`prep` 은 등록 자체가 없고, `prevote` 부터는 명단이 열리는 시점과 정확히 같다 (ADR-21).
명단이 열리는 순간과 매력이 잠기는 순간을 같게 뒀다 — 두 개의 경계를 기억하지 않아도 되게.

닫힌 뒤 시도하면 왜 안 되는지 말한다. "저장되지 않았어요" 로 끝내지 않는다.

## ADR-28 커플 자리를 확정해도 배정은 닫히지 않는다 · 테이블 수는 누를 때 묻는다

> ⚠️ **절반 폐기 — ADR-51.** `커플 자리` 라는 라운드가 없어졌다. 이 ADR 의 두 결정은
> 그대로 산다 — **배정은 발표 전까지 닫히지 않고**, 테이블 수는 여전히 누를 때 묻는다.
> `커플 자리` 를 `자리 배정` 으로 읽으면 된다.

### 배정을 닫지 않는다

커플 자리를 확정하면 `seatingClosed` 가 켜지고, 더 배정하려면 `배정 다시 열기` 를 눌러야 했다.
지각자를 막으려는 장치였는데, 실제로는 **한 번 더 자리를 바꾸는 일이 그냥 있다** —
쌍이 떨어졌거나, 테이블이 비었거나, 사람이 더 왔거나.

그때마다 "닫혔습니다 → 다시 열기 → 배정" 세 단계를 지나게 하는 건
막을 이유가 없는 일에 문을 세운 것이다. 플래그·API·화면 분기를 통째로 지웠다.
`자리 재배정`·`커플 자리 배정` 은 발표 전까지 언제나 눌린다.

**발표(`done`)만이 자리를 끝낸다.** 그건 지금도 막혀 있고, 그 하나면 충분하다.

### 테이블 수는 배정을 누를 때 묻는다

`테이블 수` 스테퍼가 화면 맨 위에 상시 떠 있었다. ADR-5 는 **테이블 수는 설정이 아니라
배정 시점의 입력값**이라고 적어뒀는데, 화면은 설정처럼 보였다 — 지금 값이 적용된 건지,
다음에 쓸 값인지 알 수 없다.

이제 배정 버튼을 누르면 시트가 열리고 거기서 고른다. 구조와 화면이 같아진다.

**숫자만 받지 않는다.** 그 숫자가 만드는 자리를 함께 보여준다 —
`테이블당 6명 · 남 3 / 여 3`, 그리고 인원이 모자라거나 넘칠 때의 경고.
없으면 8을 넣어보고 결과를 보고 다시 6으로 되돌리는 일을 반복하게 된다.

- 시작값은 **지난 라운드의 테이블 수**다. 두 번째 라운드에서 같은 수를 다시 고르는 일이 흔하다
- 커플 자리에서는 몇 쌍을 붙이려는 참인지 그 자리에서 말한다
- 시트는 라우트다. 뒤로 가기로 닫힌다 (ROUTES.md)

## ADR-29 참가자를 지워도 그가 보낸 콕은 남는다

**사고가 될 뻔한 것** — 참가자를 지우면서 그 사람이 주고받은 콕을 통째로 지웠다.
그러면 **받은 사람의 숫자가 줄어든다.**

참가자 10명, A 의 받은 콕 3회. 운영자가 C 를 지운다 → A 의 받은 콕이 2회가 된다.
참가자 탭에서 C 가 사라진 것도 **동시에** 보인다. 그 둘을 맞추면 —
**"C 가 나를 찔렀구나."**

받은 콕은 끝까지 익명이어야 한다 (CLAUDE.md 절대 규칙 1). 삭제가 그 문을 열고 있었다.

**결정**
- **보낸 콕은 남긴다.** 받는 쪽 숫자가 흔들리지 않는다.
  남는 건 아무것도 가리키지 않는 아이디뿐이다 — 이름도 번호도 `pokes` 에 없다
- **받은 콕은 지운다.** 보낸 사람의 **예산이 돌아온다**.
  없는 사람에게 쓴 횟수를 물릴 이유가 없다. 새 정보도 아니다 —
  자기가 누구를 찔렀는지는 본인이 알고, 명단이 줄어든 것도 이미 보인다

**따라오는 정리** — 운영자 집계는 **지금 있는 사람만** 센다.
없는 사람의 아이디가 커플 목록에 빈 이름으로 뜨거나, `pokeUsedMax` 를 묶어
콕 상한을 못 내리게 하면 안 된다.

자리 배정과 발표는 이미 방어돼 있었다 — `World` 는 모르는 아이디를 건너뛰고,
`matches` 는 `player()` 가 null 이면 거른다.

**교훈** — "관련된 걸 다 지운다" 는 깔끔해 보이지만, 숫자가 줄어드는 것 자체가 정보다.
지울 것과 남길 것을 **누가 무엇을 알게 되는가**로 갈랐어야 했다.

## ADR-30 화면을 프로토타입 쪽으로 다듬는다 — 가져올 것과 두고 올 것

`reference/poke-party.html` 의 화면을 다시 보고 정리했다. 그 프로토타입은
지금의 공개 범위 결정들 **이전**이라, 형태는 가져오되 규칙은 가져오지 않는다.

### 참가자 카드

| | 전 | 후 |
|---|---|---|
| 아바타 | 🙋‍♀️ 성별 이모지 | **동물 40마리**(닉네임 해시) × **성별 색 2**(남 파랑·여 분홍) |
| 이름 줄 | `닉네임 · 28세 · ENFP` 한 덩어리 | 닉네임 + 나이(작게) + MBTI 배지 |
| 매력 | 첫 줄만 말줄임 | **칩 3개, 한 줄에서 자름** |
| 콕 횟수 | 버튼 **왼쪽** | 버튼 **오른쪽** |

**아바타를 동물로 바꾼 이유** — 성별 이모지는 성별만 알려주고 사람은 구분해주지 못했다.
스무 명 목록에서 같은 이모지가 열두 번 반복되면 눈이 미끄러진다.
첫 글자도 후보였지만 "김" 으로 시작하는 사람이 여럿이면 다시 뭉개진다.
동물은 닉네임 해시로 골라 목록·프로필·자리·현황이 같은 아바타를 쓴다 —
"이 사람 어디 앉았지" 가 눈으로 풀린다.

동물을 고르는 기준 셋 — 귀여울 것(무섭거나 벌레스러운 것은 뺀다. 소개팅 자리의 얼굴이다) ·
같은 종을 두 번 넣지 않을 것(🐶와 🐕가 다른 두 사람이면 구분이라는 목적을 잃는다) ·
사람을 닮은 것·표정이 강한 것은 뺄 것(참가자를 특정 인상으로 대신 말하게 되면 안 된다).

**성별은 링 색이다 (두 번 바뀜).** 처음에는 배경이 해시 색(색=사람), 다음은 성별 그라데이션
채움이었다. 채움은 실제 화면에서 실패했다 — 채도 높은 분홍 위에서 분홍 고래가 뭉개졌다.
이모지는 말풍선 같은 중립 배경용 그림이다. 그래서 바닥은 어두운 틴트로 낮추고
성별의 채도는 **테두리 링**(남 파랑 · 여 분홍, 자리 탭과 같은 단색)이 가져간다.
남녀는 더 또렷해지고 동물은 자기 색으로 뜬다.
역할이 겹치지 않는 게 핵심이다: **동물 = 사람, 링 = 성별.** 하나가 둘을 말하려 하면 둘 다 흐려진다.

동물은 40마리에서 **24마리**로 줄였다 — 전신 동물(🦙🦒🐢🦢)은 21px 에서 형체가 안 읽혔다.
얼굴형 이모지는 작은 크기용 "큰 머리"로 그려져 있어 살아남는다. 겹칠 확률은 올라가지만,
알아볼 수 없는 40마리보다 알아볼 수 있는 24마리가 낫다 — 아바타는 소프트 식별자다.

**매력은 한 줄에서 자른다.** 등록 폼이 "문장으로 써도 좋아요" 라고 권하므로
셋을 다 펼치면 카드 키가 제각각이 되고 목록이 들썩인다. 전문은 프로필 시트에서 본다.

**콕 횟수를 오른쪽으로.** 왼쪽에 두면 찌른 카드만 폭이 좁아져 목록이 들쭉날쭉했다.
오른쪽 자리는 0회일 때도 비워두므로 폭이 흔들리지 않는다.

### 현황 탭 — 받은 콕 순위를 되살린다 (ADR-22 일부 뒤집음)

ADR-22 에서 받은 콕을 운영자에게도 감췄다. 운영자 판단으로 **현황 탭의 순위**로만 되살린다.

**참가자 탭의 개인 행에는 여전히 넣지 않는다.** 두 자리는 성격이 다르다 —
명단은 한 사람씩 훑는 자리고, 현황은 전체 분위기를 읽는 자리다.
목록에서 사람마다 숫자를 달아두면 그 사람을 볼 때마다 숫자가 먼저 읽힌다.

순위는 **TOP 5 다. 5위가 동점이면 그만큼 늘어난다** — 같은 수를 받은 사람을 자르면
순위가 거짓말이 된다. 제목의 N 이 실제로 보여주는 수를 말하고, 동점자는 같은 번호를 단다.

처음에는 0회까지 전원을 보여줬다 — "빼면 빠진 사람이 곧 0회" 라는 이유였다.
TOP 5 로 자른 지금은 반대가 됐다: **빠짐은 "상위권 아님"만 말한다.** 하위권이 오히려 가려진다.
바 길이는 1위 대비 비율이다 — 절대 수보다 "얼마나 몰렸나" 가 눈에 들어온다.

👑 사전 투표 1위는 왕관 카드로, 💘 상호 매칭은 양쪽 아바타 사이에 하트로 바꿨다.
둘 다 진행 중에 가장 자주 보는 것이라 형태가 읽혀야 한다.

**현황 탭의 색** — 왕관은 금색(축하), **매칭은 참가자·운영자 모두 주 색 하나**다
(화면마다 매칭 색이 다르면 색이 뜻을 잃는다). 순위 바는 하트(콕)→주 색(매칭) 그라데이션 —
받은 콕이 쌓여 매칭으로 향한다는 걸 색으로도 말한다. `--heart` 는 콕(보낸 마음)의 색이다.
순위 번호는 **받은 콕이 있는 상위 셋만** 금색 — 전부 칠하면 아무도 돋보이지 않고,
0회에 금색을 주면 금색이 거짓말을 한다.

**MBTI 배지는 네 기질 계열색**이다 (NT 보라 · NF 초록 · SJ 파랑 · SP 노랑 —
16personalities 관행이라 아는 사람에게는 설명 없이 읽힌다). 16가지에 16색을 주면
아무 색도 기억되지 않는다. **참가자용 화면의 명단·프로필 시트에서만** 쓴다 —
운영자 콘솔의 참가자 탭(Players)은 평문 그대로다.
NT 보라가 주 색과 겹치는 건 알고 허용했다: 배지는 글자가 정보를 다 나르고 색은 보조다.

자리 이동 확인율 카드는 현황에서 뺐다 — 자리를 보낸 직후에 보는 숫자라
자리 탭 라운드 카드에 있는 것으로 충분하다. 같은 숫자를 두 곳에 두지 않는다.

### 배경

화면 위 모서리에 아주 옅은 오로라를 깔았다 (`--aurora`).
**옅게** 두는 게 핵심이다 — 진하면 목록을 길게 스크롤할 때 카드 대비가 흔들린다.
스크롤과 함께 흐르지 않도록 화면에 고정한다.

### 가져오지 않은 것

프로토타입 현황에는 `총 콕 26` 같은 집계와 참여율이 있었다.
운영에 쓰이지 않는 숫자라 두고 왔다 — 화면에 있는 숫자는 전부 **누를 이유**가 있어야 한다.

## ADR-31 내 정보는 사전 투표가 열리기 전까지, 한 번에 고친다

**결정** — 등록할 때 낸 것을 참가자가 스스로 고친다. **전화번호만 빼고 전부**,
**사전 투표가 열리기 전까지**, **고치는 버튼 하나로 한꺼번에**.

ADR-27(매력만 고칠 수 있다)의 대상을 넓힌 것이다. 경계는 그대로 `phase === "reg"` 하나다.

### 왜 넓혔나

매력만 고칠 수 있고 닉네임은 못 고치는 상태가 참가자에게 설명되지 않았다.
ADR-27 의 논리는 "남들이 보고 콕을 찔렀으니 근거가 사라지면 안 된다" 인데,
**사전 투표 전에는 어느 필드에도 그게 적용되지 않는다.** 매력만 열려 있던 건
그 필드에 특별한 성질이 있어서가 아니라 그때 그것만 문제로 인식됐기 때문이다.

그리고 복구 경로가 없었다. 오타를 발견한 참가자가 할 수 있는 게 없고
운영자에게도 수정 경로가 없어서(참가자 상세에는 삭제뿐), 유일한 복구가
"운영자가 지우고 참가자가 다시 등록" 이었다. 오타 하나에 그 비용은 과하다.

비용이 가장 큰 오타는 **성별**이다. 토글 하나를 잘못 누르면 자리 배정 풀·`이성만 보기`·
아바타 색이 전부 어긋난다. 못 고치게 두는 건 보수적인 게 아니라 방치다.

### 왜 전화번호만 빼나

파티의 문이 초대 명단의 전화번호다 (ADR-15). 등록 후에 번호를 바꿀 수 있으면
**명단에 없는 번호로 갈아탈 수 있다** — 문을 우회하는 길이 생긴다.

막는 방법은 등록 폼과 같다. **입력 타입(`RegisterInput`)에 phone 키를 두지 않는다.**
들어와도 무시하는 게 아니라 자리가 없고, 저장할 때도 저장돼 있던 값을 그대로 쓴다.
규칙 테스트가 이걸 고정한다.

### 왜 하나로 합쳤나

참가자가 하는 일은 "내가 낸 것을 고친다" 하나다. 버튼이 둘이면
"무엇이 다르길래 둘이지" 를 생각하게 되는데 실제로는 아무 차이도 없다 —
둘 다 사전 투표에 잠기고 둘 다 나만 보는 정보다. 구분할 이유가 없는 걸 화면이 구분하면
사용자는 없는 의미를 찾는다.

잠기는 것도 한 번에 읽힌다. 버튼이 둘이면 잠금 문구를 두 자리에 써야 하고,
한쪽에만 쓰면 어긋난다.

서버도 합치는 쪽이 자연스러웠다. `register()` 의 upsert 가 **매력을 포함해** 전 필드를
갱신하고 있어서, 매력만 따로 UPDATE 하던 `editCharms()` 쪽이 오히려 특수 케이스였다.
지금은 등록과 수정이 `cleanProfile()` → `writeProfile()` 한 길을 같이 지난다.

**저장은 전부 되거나 전부 안 된다.** 닉네임만 실패할 수 있는 필드인데(유일성),
겹치면 같이 보낸 나이도 저장되지 않는다. 화면은 그 칸에 에러를 띄우고 **입력값을 보존한다** —
등록 폼이 `nick_taken` 을 다루는 방식과 같다. 사용자가 잃는 건 저장 버튼 한 번 더다.

### 대가

**늦게 등록한 사람에게는 수정 기회가 처음부터 없다.** 등록은 발표 전까지 열려 있는데
(파티 중 합류) 수정은 사전 투표에서 닫히기 때문이다. 규칙은 어긋나지 않는다 —
그 사람의 정보는 등록 즉시 명단에 보이므로 잠글 이유가 그 순간부터 성립한다.
"등록 후 N분" 같은 개인별 창을 주면 경계가 둘이 되므로 그렇게 하지 않았다.

대신 **화면이 그 사실을 말한다** (`ME.locked`). 버튼만 조용히 사라지면
"내 화면만 이상한가" 가 된다. 매력 하나가 잠길 때는 넘어갔을 수 있지만
내 정보 전체가 잠기면 반드시 눈에 띈다.

**인스타도 함께 잠근다.** 인스타는 발표 전까지 아무도 보지 않으므로 잠글 논리적 근거가
없는 유일한 항목이고, 틀리면 서로 찌른 쌍이 연락할 방법이 사라진다.
그럼에도 함께 잠근 이유는, **이 기능 자체가 그 오타의 완화책**이기 때문이다 —
지금까지는 인스타가 내 정보 탭에서 가려져 있고 고칠 수도 없어 다시 볼 이유가 없었는데,
고치기가 열리면 그 버튼을 누르는 행위가 오타를 발견하는 자리가 된다.
경계를 하나 더 만들 값어치가 그보다 크지 않다.
**실제로 사고가 한 번 나면 인스타만 발표 전까지 여는 것으로 되돌린다.** 그때 이 문단을 지운다.

### 저장 알림은 운영자에게만 간다

처음에는 등록과 똑같이 전원에게 `roster` 를 방송했다. 그런데 고치기가 열려 있는 건
등록 중뿐이고 **그때 참가자에게는 명단이 아예 안 내려간다** (ADR-21). 인원수도 그대로다 —
전원에게 보내면 50명이 **똑같이 그려질 화면**을 다시 읽으려고 줄을 서는 셈이었다.

실시간은 "다시 읽어라" 신호로만 쓰기 때문에(ADR-26) **신호 하나가 곧 N번의 읽기**다.
읽기 자체는 가볍지만 같은 DO 를 지나므로 쓰기 큐가 있으면 그 뒤에 선다 —
50명 리허설에서 재조회 하나가 8초까지 밀린 적이 있다.

그래서 `toHosts()` 로 좁혔다. 참가자 소켓에는 Worker 가 세션 쿠키를 보고 `playerId` 를 붙이므로,
안 붙은 소켓이 운영자 콘솔이다. 바뀐 닉네임이 필요한 건 운영자 명단 하나뿐이다.

> **일반화하지 마라.** 대부분의 변화는 참가자 화면도 바꾸므로 전원에게 가야 한다.
> 이 통로는 "참가자 화면이 똑같이 그려질 변화"에만 쓴다.

### 만들지 않은 것

수정 이력, 운영자에게 가는 수정 알림, 운영자가 참가자 정보를 고치는 길.
사전 투표 전에는 자리도 좌석 칩도 없고 인원·성비 숫자는 어차피 다시 읽히므로
운영자에게 실무상 영향이 없다.

### 후기 — "이렇게 보여요" 는 참가자 탭에 만들었다

처음에는 미리보기도 **만들지 않는 것**에 넣었다. 뒤집은 이유가 둘이다.

**숫자가 이미 어긋나 있었다.** 상단 인원수는 `SELECT COUNT(*)` 라 자기를 포함하는데
명단은 서버에서 자기를 뺀다. 10명인데 9장이었고, 등록 직후 혼자일 때는 "1명" 옆이 빈 화면이었다.

**고칠 수 있게 됐는데 확인할 자리가 없었다.** 매력 세 줄을 다듬고 나서 그게 카드에서
어떻게 읽히는지 볼 방법이 없었고, 단계마다 자기가 어디까지 보이는지도 알 수 없었다.

**내 정보 탭이 아니라 참가자 탭 맨 위**에 뒀다. 다른 카드들 옆에 같은 크기로 있어야
"군중 속의 나" 가 되기 때문이다. 두 탭의 질문은 여전히 갈린다 —
내 정보 탭은 **내가 낸 것**(실명·전화 포함), 이 카드는 **남들이 보는 것**이다.

화면 규칙은 `docs/UI.md`, 범위는 `docs/scenarios/10-my-card.md`.
**서버는 바뀌지 않았다** — 화면이 이미 받은 `me` 를 `toPublic()` 같은 함수로 줄여 그린다.

## ADR-32 참가 링크는 사람마다 다르다 — 번호는 묻지 않는다

**문제** — ADR-15 후기 2 가 연 구멍을 닫는다. **번호를 아는 사람이 그 사람이 될 수 있었다.**
전화번호는 식별자이지 증명이 아닌데, 하필 **같은 파티에 오는 사람들은 서로 번호를 아는 사이다.**

**결정 (2026-08-23)** — 초대 명단의 **한 줄마다 고유 토큰**을 발급한다. 토큰이 곧 신원이고,
**참가자는 전화번호를 치지 않는다.**

```
/j/<회차id>/<토큰>  →  등록 (또는 이미 등록했으면 자기 화면)
```

슬라이스 13 으로 간다. **15(참가자 비밀번호)는 이 결정으로 닫힌다** — 둘은 택일이었다.

### 문은 여전히 초대 명단이다

ADR-15 를 뒤집는 게 아니라 **같은 문의 열쇠를 바꾸는 것**이다. 들어오는 사람은 여전히
운영자가 미리 넣어둔 명단의 그 사람뿐이고, 바뀐 것은 *"명단에 있음"을 무엇으로 보이느냐* 다.

| | 전 (ADR-15) | 후 (여기) |
|---|---|---|
| 참가자가 대는 것 | 전화번호 — **남도 안다** | 링크 토큰 — 그에게만 배달됐다 |
| 링크 | 회차마다 하나, 단톡방에 뿌린다 | **사람마다 하나, 1:1 로 보낸다** |
| 참가자가 할 일 | 번호를 친다 | 없다. 링크를 연다 |

**"이 번호가 이 파티에 있나" 를 되묻는 창구가 사라진다.** ADR-15 가 `ENTRY_TRIES` 로
완화하려던 유출이 구조적으로 없어진다 — 넣어볼 칸 자체가 없다. 제한은 그대로 두되
(문은 여전히 인증 없이 열려 있다), 그것이 막던 일은 이제 일어나지 않는다.

### 왜 `/j/<토큰>` 이 아니라 `/j/<회차id>/<토큰>` 인가

토큰만 담으면 짧아서 당기지만, 그러면 **토큰 → 회차** 를 찾는 색인이 회차 DO 밖에 있어야 한다.
토큰은 **한 사람을 가리키는 값**이라, `metrics.ts` 가 그어둔 선("가리키게 되는 순간
그 보장이 사라진다")을 넘는다. 파기가 DO 하나 지우는 일로 끝나야 한다.

회차 아이디를 앞에 두면 Registry 에 아무것도 쌓이지 않는다. 링크는 길어지지만
**어차피 붙여넣는 것**이라 길이가 비용이 아니다.

**토큰 없는 `/j/<회차id>` 는 없앤다.** 남겨두면 구멍이 그대로다.

**회차 정보 조회도 토큰을 요구한다.** 경로만 없애는 것으로는 모자라다 —
`/api/events/by-id/:id` 가 토큰 없이 파티 이름·일정을 내주면 **회차 아이디만으로 회차가 열린다.**
ADR-15 후기에서 `by-code` 오라클을 걷어낸 것과 같은 종류다. 길을 하나 막으면 옆문도 같이 본다.

### `Join` 화면은 남는다 — 하는 일이 바뀐다

번호 칸이 사라지면 이 화면의 존재 이유가 없어 보이지만, 곧바로 등록 폼으로 넘기지 않는다.

- **등록이 아직 안 열렸을 때 말할 자리가 필요하다.** 안내문은 등록 시작 **전에** 보내므로,
  일찍 연 참가자에게 "언제 열리는지"를 들려주는 화면이 있어야 한다 (지금 하던 일 그대로다)
- 링크를 열자마자 입력 폼이 뜨는 것보다 **파티 이름·일시·장소를 한 번 보여주는 쪽**이 낫다

토큰 검증은 이 화면에 들어올 때 한 번 하고 초대 쿠키를 받는다.
**번호 칸이 있던 자리가 `등록하기` 버튼이 된다.**

### 정한 것

- **토큰은 명단 행에 붙는다** (`invites.token`). 번호를 명단에 넣을 때 `randomHex(16)` 로 만든다.
  회차 아이디가 `randomHex(8)` 인데 토큰이 그보다 약하면 링크의 강도가 거기로 내려간다
- **등록하면 `players` 행에도 복사한다.** 그래야 ADR-15 의 규칙이 살아 있다 —
  운영자가 명단을 정리하다 이미 온 사람을 지워도 그는 자기 링크로 계속 들어온다
- **실패 문구는 여전히 하나뿐이다.** 토큰이 틀렸든, 회차가 없든, 지워졌든 같은 문장.
  구분해 주면 그 구분이 곧 답이 된다
- **번호는 서버가 토큰에서 꺼내 초대 쿠키에 담는다.** `RegisterInput` 에 phone 키를
  두지 않는 방어(ADR-31)는 그대로다 — 이제 폼이 번호를 아예 보지 않는다
- **재발급 경로를 만들지 마라.** 링크를 잃으면 운영자가 안내문을 다시 보내면 된다.
  정 필요하면 명단에서 빼고 다시 넣으면 새 토큰이 나온다.
  "입장 코드는 만든 뒤에 바꾸지 않는다" 와 같은 이유다

### 세션에는 토큰을 담고, 번호를 담지 않는다

세션은 **서명만 하고 암호화하지 않는다** (`auth.ts`) — 서버에 세션 표를 두지 않으려는 선택이고,
그래야 파기가 DO 하나 지우는 일로 끝난다. 대신 **페이로드를 읽을 수 있다.**
HttpOnly 라 JS 로는 못 읽지만 개발자 도구 Application 탭에서는 그대로 보인다.

그래서 초대 쿠키(`tp_inv`)는 **참가 토큰**을 들고, 번호는 회차 DO 안에서만 푼다.
참가자가 번호를 치지 않기로 해놓고 쿠키에 번호를 남기면 그 결정이 브라우저에서 새어 나간다.

**참가자 세션은 30일이다.** 7일이었는데 파티 당일에 딱 걸렸다 —
등록이 파티 6일 전에 열리므로 첫날 등록한 사람은 당일이 7일째다.
끊기면 링크를 다시 찾아야 하고, 그게 하필 파티장에서 일어난다.
늘려도 실질 노출은 안 는다고 봤다 — **회차 파기(3일)가 진짜 상한**이라 세션이 살아 있어도
열리는 게 없다고. **그 상한이 없어졌다** (ADR-36): 자동 파기가 사라져 회차는 운영자가 지울 때까지
남는다. TTL 은 그대로 두되, 끝난 회차를 지우는 것이 그 상한을 대신한다.

**토큰은 주소창에만 있다.** 쿠키에도 `localStorage` 에도 넣지 않는다 —
넣으면 그 기기에서 링크 없이 계속 들어올 수 있어 편하지만, 남의 기기에 남는 값이 하나 더 생긴다.
재발급 화면을 만들지 않기로 한 것과 같은 자세다.

### 한 기기로 여러 회차

참가자 세션은 브라우저에 **하나뿐**이라 다음 회차에 들어가면 앞의 세션이 덮인다.
쿠키를 회차마다 두지 않았다 — 자료가 섞일 길을 늘리는 대신, **되찾는 비용을 링크가 낸다.**

같은 사람이 A·B 에 모두 초대돼도 각자의 링크만 있으면 한 번 누르는 것으로 오간다.
덮인 회차는 그동안 **401 이어야 한다** (S-A9). 링크는 1:1 로 보내져 대화방에 남으므로
되찾는 재료가 사라지지 않는다 — 번호를 묻던 시절보다 오히려 단계가 하나 줄었다.

### 대가 — **링크를 넘겨받은 사람은 못 막는다**

이 결정이 닫는 것은 "번호만 아는 사람" 이다. 닫지 못하는 것은 **"링크를 본 사람"** 이고,
지인 파티에서 그건 대체로 **친구**다 — 링크가 카톡에 남아 있고, 폰을 보면 보인다.
ADR-15 후기 2 의 표가 이미 이렇게 적어뒀고, 그걸 알고 고른 것이다.

15(비밀번호)만이 그 사람까지 막지만, 그 비용을 **분실 응대로 파티 당일에** 낸다.
13 은 부담을 파티 **전**으로 옮기고 참가자가 할 일을 없앤다. 그 교환을 택했다.

> 가장 비싼 유출(연락처)은 **발표 후에만** 열린다. 발표를 현장에서 사람들이 눈앞에 있을 때
> 누르는 운영이 여기서도 완화책으로 남는다.
>
> **사고가 한 번 나면 15 를 다시 연다.** 그때 이 문단을 지우고 표를 다시 그린다.

### 발송 동선 — 이 결정이 요구하는 것

링크가 사람마다 다르면 **단톡방에 하나 뿌리기가 불가능하다.** 그래서 슬라이스 13 은
발송 동선을 같이 만든다 (`PLAN.md` 13).

- 운영자가 **안내 템플릿**을 한 번 쓴다 — `{장소}` `{일시}` 를 치환한다 (`{링크}` 는 뺐다 — 아래 후기).
  기본 문구는 `copy.ts`, 운영자가 고친 것은 자료로 저장한다
- 명단 **행마다 복사 버튼**. 되돌릴 수 있는 행동이라 확인 다이얼로그가 필요 없다
  (행마다 두던 것과 미리보기는 뒤에 걷었다 — 아래 후기)
- ~~**보냄 체크가 필수다.**~~ **걷었다 — 아래 후기.** 명단에 남아 있는 줄이 곧 아직 안 온 사람이다
- 채널은 가리지 않는다 — 인스타 DM·문자·카톡 어디든 붙여넣는다.
  나중에 문자 자동 발송을 붙이더라도 **같은 템플릿을 쓴다**

**회차에 `place` 를 더한다.** 시간은 `schedule` 에 있는데 장소가 없었다.
참가자 응답에는 싣지 않는다 — 안내문으로만 나간다.
**회차 마법사 2단계(일정)에 둔다** — "언제·어디서" 가 한 화면에 있는 게 자연스럽고,
1단계는 이름만 받아 가볍게 시작하는 지금 구조를 지킨다.

#### 후기 — 안내문에서 링크를 뺐고, 보냄 체크를 걷었다 (2026-08-24)

위에서 정한 둘을 뒤집는다. **안내문에 `{링크}` 를 넣는 것**과 **보냄 체크가 필수라는 것**이다.

**① 링크는 안내문 밖으로.** 한 덩어리로 보내면 참가자가 그 글에서 링크만 집어내야 한다.
링크만 온 메시지는 그대로 눌러 열리고, 안 열리면 주소창에 붙여넣을 수 있다.
**장소에 지도 링크를 넣는 회차에서는 한 메시지에 링크가 둘이 된다** — 어느 쪽이 파티인지
받는 사람이 고르게 만드는 셈이다. `{링크}` 자리는 렌더링에서 **지운다**: 남겨두면
전원이 같은 글을 받는다는 전제가 깨지고, 한 사람의 링크가 모두에게 나가는 사고가 거기서 나온다.

**② 안내문 복사는 명단 머리에 하나다.** 링크가 빠지면서 안내문이 **회차당 하나**가 됐다 —
사람마다 다를 것이 없으니 행마다 복사 버튼을 둘 이유가 없다. 행에는 **사람마다 다른 것**만 남긴다.

그 카드에서 **미리보기도 걷었다.** 문구를 고치는 화면이 글을 그대로 띄우고 있어 같은 일을
두 번 하는 자리였다. 남은 건 버튼 둘 — 복사와 고치기. 명단은 계속 보면서 일하는 목록이라,
한 번 확인하면 되는 글이 그 위를 차지하면 안 된다.

복사 실패 문구가 미리보기를 가리키고 있었는데(`아래 미리보기를 그대로 보내주세요`)
그 자리가 없어졌다. **화면의 무엇도 가리키지 않는다** — 없는 곳을 가리키느니
실제로 통하는 길(다른 브라우저)을 말한다.

**③ 보냄 체크를 걷는다.** "한 명씩 복사하는데 어디까지 갔는지 모르면 못 한다" 고 썼는데,
실제로 그 표시가 답하지 못하는 게 둘이었다.

- **복사가 곧 발송이 아니다.** 붙여넣기 전에 창을 닫기도 하고, 보내려던 사람이 바뀌기도 한다.
  복사에 딸려 찍히는 표시는 *복사했다* 를 *보냈다* 로 바꿔 말한다
- **되돌릴 수 있는 표시는 틀렸을 때 아무도 모른다.** 확인창이 없는 게 맞는 표시였지만,
  그래서 잘못 찍힌 것을 알아챌 자리도 없었다

명단이 곧 발송 목록이라는 건 그대로다 — **등록하면 행에서 빠진다.** 남아 있는 줄이
아직 안 온 사람이고, 그게 "어디까지 갔나" 에 답하는 진짜 신호다. 표시는 그 위에 얹은
두 번째 진실이었고, 두 진실이 어긋나면 사람은 둘 다 안 믿는다.

`invites.sent_at` 칸도 지운다 (마이그레이션에서 `DROP COLUMN`). 안 읽는 칸을 들고 다니면
다음 사람이 그게 쓰이는 줄 안다. `invites()` 는 칸을 골라 읽는다 — `SELECT *` 로 두면
칸이 남아 있는 옛 회차에서 그 값이 응답에 딸려 나간다.

#### 후기 2 — `입장 명단` 을 `초대 명단` 으로 고쳤다 (2026-08-24)

**`입장` 이 두 일을 가리키고 있었다.** 파티 당일 문 앞의 일은 참가 상태(`도착`·`미도착`)가
맡는데(ADR-33), 파티 며칠 전에 부를 사람을 정하는 목록이 `입장 명단` 이었다.
한 낱말이 두 일을 가리키면 운영자가 둘을 같은 것으로 읽는다 —
실제로 ADR-33 이 `입장/미입장` 을 버린 이유가 그 겹침이었다.

**이 목록이 실제로 하는 일**은 부를 사람의 번호를 넣는 것이고, 넣는 순간 그 사람의 링크가 생긴다.
아래 목록에 남는 건 **아직 등록하지 않은 사람**이다 — 등록하면 행에서 빠져 카드로 올라간다.
세는 말(`초대 N명`)도, 코드 안의 이름(`invites`)도, `CLAUDE.md` 의 규칙 2("파티의 문은
**초대 명단**이고")도 처음부터 그쪽이었다. **화면만 다른 이름을 쓰고 있었다.**

같이 고친 것 — `전화번호 한 명` → `초대할 사람의 전화번호` · `명단이 비어 있어요 …
들어올 수 없어요` → `아직 초대한 사람이 없어요 — 지금은 아무도 등록할 수 없어요` ·
`이미 명단에 있는 번호예요` → `이미 초대한 번호예요`.

그리고 이름을 훑다가 **틀린 문장 둘**이 나왔다. 둘 다 ADR-32 가 길을 닫은 뒤로 거짓이 됐다.

- 등록 시작 확인창 — `참가 링크나 입장 코드 ABCDEF로 찾아와, 입장 명단에 넣은 번호로 등록합니다`.
  **코드로 찾아오는 길은 닫혔고**(`by-code`), 참가자는 번호도 치지 않는다.
  `초대 명단에 있는 사람이 각자 받은 링크로 들어와 등록합니다` 로 고쳤다.
  이 문장이 `code` 를 쓰던 유일한 자리라 `phaseAction` 의 인자에서도 뺐다
- 참가자 삭제 안내 — `같은 번호로 다시 들어올 수 있어요` → `그 사람의 링크로 다시 들어올 수 있어요`

**문구를 고치다 코드가 틀린 걸 찾았다.** 이름을 훑는 일이 값싼 감사(監査)이기도 하다는 기록으로 남긴다.

## ADR-33 참석 상태 — 문 앞에서 세는 것

**문제** — 파티 당일 운영자가 하는 일은 **누가 왔는지 세는 것**인데, 앱에 그 자리가 없었다.
운영자 한 명이 사람을 맞으면서 명단을 손으로 훑는 건 문 앞에서 줄을 만든다.

`노쇼 체크` 는 "아직 만들지 않는 것" 에 있었다. **연다.** 이유는 하나 —
운영자가 실제로 파티 당일에 하는 일이고, 앱이 그걸 안 하면 종이로 하게 된다.

**결정 (2026-08-24)** — 참가자에게 **참석 상태** 한 칸을 둔다. 그리고 **문 앞 QR** 로 자동으로 찍는다.

### 상태는 셋이고, 칸은 하나다

`players.attendance` — 없음(안 옴) · `arrived` · `left`.

시각을 두 개 두는 대신 칸 하나를 쓴다. **`나감` 은 도착했던 사람만 될 수 있어서** 순서가 있는
한 축이고, 시각 둘(`arrived_at`·`left_at`)로 두면 "나갔는데 온 적 없음" 같은 불가능한 조합이 생긴다.
도착 시각은 아직 아무도 묻지 않았다 — 물으면 그때 칸을 늘린다.

**라벨은 저장하지 않고 단계와 함께 계산한다.**

| 저장된 값 | 파티 시작 **전** | 파티 시작 **후** |
|---|---|---|
| player 없음 (명단만) | `미등록` | `미등록` |
| 없음 | `등록함` | **`미도착`** |
| `arrived` | — | `도착` |
| `left` | — | `나감` |

`등록함` 과 `미도착` 이 **같은 값의 다른 이름**이다. 상태를 하나 더 만들지 않아도 된다.
(`미도착` 은 처음에 `안 옴` 이었다 — 아래 후기에서 바꿨다.)

### 찍는 길은 **하나뿐이다** — 운영자가 누른다

카드 오른쪽의 상태 칩이 곧 버튼이다. 파티가 시작된 뒤에만 눌린다.
되돌릴 수 있어서 확인창이 없다.

**길을 늘리지 않는다.** 참가자가 스스로 누르는 `도착했어요` 버튼도 두지 않는다 —
경로가 둘이면 안내가 둘이 되는데, 애초에 **눌러야 하는지 모르는 참가자**가 있다.
누르지 않은 사람과 안 온 사람이 화면에서 구분되지 않으면 그 숫자는 못 믿는 숫자가 된다.

### 문 앞 QR 을 접었다 — **브라우저가 갈린다**

한동안 "문 앞에 회차 QR 을 붙이고 참가자가 찍으면 자동으로 도착" 으로 설계했다.
찍은 사람이 누구인지는 세션으로 안다고 봤고, 세션이 없으면 체크인 쿠키를 심어
나중에 링크로 들어올 때 반영하기로 했다. **둘 다 통하지 않는다.**

```
등록  :  카톡 링크  →  카카오톡 인앱 브라우저   ← 세션 쿠키가 여기 저장된다
QR    :  기본 카메라 →  Safari / Chrome        ← 여기엔 아무것도 없다
```

QR 스캔은 **폰 기본 브라우저**를 연다. 우리가 고를 수 없다. 그런데 참가자 대부분은
카톡 링크로 등록하므로 세션은 인앱 브라우저에 있다 — 문 앞 QR 은 **세션조차 못 찾는다.**
체크인 쿠키도 같은 이유로 다른 브라우저에 심긴다.

**이 함정은 두 번째다.** ADR-15 후기 2 에서 "기기 고정" 을 버린 이유가 그대로 이것이었다 —
*"카톡 인앱 ↔ 크롬 이동. 국내 기본 동선이라 정상 사용자가 계속 막힌다"*.
표에 적어둔 것을 QR 설계에서 다시 밟았다.

**반쯤 되는 것이 아예 안 되는 것보다 나쁘다.** 통할 때와 안 통할 때가 참가자 눈에
구분되지 않아서, 문 앞에서 "저는 왜 안 돼요" 가 나온다.

**원리적으로 막혀 있다.** 회차 QR 은 찍은 사람이 누구인지 모르고,
개인 QR 은 알지만 참가자가 그걸 **찾아야** 한다 — 찾을 거면 링크를 누르지 QR 을 찍을 이유가 없다.
누구인지 알려면 번호를 물어야 하는데, QR 사진은 단톡방에 도니까
"번호를 아는 사람이 그 사람이 되는" 구멍(ADR-32)이 원격에서 되살아난다.

### 대가

**안 온 사람이 도착으로 남아 있을 수 있다** — 운영자가 안 누른 것과 안 온 것이 같은 값이다.
그래서 파티 시작 **전**에는 그 값을 아예 그리지 않는다 (후기 — 처음에는 `등록함` 이라고 불렀다).
숫자를 믿을 수 있는 건 운영자가 문 앞에서 실제로 누르고 있을 때뿐이고, 그게 이 기능의 전제다.

**남의 참석 상태는 참가자 응답에 나가지 않는다.** 운영자만 본다 (`HostState`).
명단(`roster`)에도, 자기 자신(`me`)에게도 넣지 않는다 — 참가자가 그 값으로 할 일이 없다.

### 아직 안 만든 것

**개인 QR** — 운영자 화면에서 그 사람의 참가 링크를 QR 로 띄워, 링크를 못 찾는 사람이
그 자리에서 찍게 하는 것. 개인 링크는 토큰을 품고 있어 **어느 브라우저에서 열려도 통한다** —
위에서 접은 회차 QR 과 갈리는 지점이 정확히 여기다. 렌더링 라이브러리가 하나 필요해서,
참석 상태가 QA 에서 도는 걸 보고 정한다.

### 후기 — 한 목록을 다시 둘로 나눴다. **축이 아니라 역할로** (2026-08-24)

이 결정은 참석 상태를 열면서 **명단과 참가자를 한 목록으로 합쳤고**,
필터 칩을 성별에서 상태(전체·등록함·미등록·도착·안 옴)로 바꿨다. (그때의 이름은 `안 옴` 이었다.) 참석은 그대로 두고
**그 두 가지를 되돌린다.** 기능이 틀린 게 아니라 한 목록에 두 가지 일이 겹쳐 있었다.

**칩이 두 질문에 동시에 답하려 했다.** `미등록` 은 *등록 전*의 상태고 `안 옴` 은 *등록 후*의
상태인데, 한 줄에 나란히 서 있으면 같은 축으로 읽힌다. 실제로 두 낱말이 섞였다 —
"아직 안 온 사람"(미등록)과 "안 옴"(등록했지만 파티에 안 옴)이 같은 화면에 있었다.

**그래서 축이 아니라 역할로 나눴다.**

| | 맡는 것 |
|---|---|
| 초대 명단 (맨 위 카드 → 시트) | 등록 **전/후** — 더하기 · 안내문 · 아직 등록 안 한 사람 · 빼기 |
| 참가자 카드 (아래) | 등록 **후** — 참석 상태 |

**명단은 시트로 접었다.** 한 화면에 펼쳐 두니 명단 일(더하기·안내문·아직 등록 안 한 사람 N줄)이
당일에 쓰는 카드 목록을 아래로 밀었다. 두 일은 **시간이 다르다** — 명단은 파티 며칠 전에 한 번에,
참석은 문 앞에서. 그래서 탭에는 요약 카드 한 장만 남기고 나머지를 `/players/invites` 시트로 옮겼다
(뒤로 가기로 닫힌다). 카드가 말하는 건 둘뿐이다: 비었나 · 초대/등록 수.
(`아직 안 보낸 사람 N명` 도 있었지만 보냄 체크와 함께 걷었다 — ADR-32 후기.
남은 두 숫자가 이미 "몇 명을 더 불러야 하나" 에 답한다.)

**5번째 탭(명단 탭)도 검토했다가 접었다.** 390px 에서 탭 다섯은 78px씩이라 좁고,
무엇보다 `명단` 과 `참가자` 가 나란히 서면 같은 층위로 읽힌다 — 실제 관계는 상하다
(부를 사람 → 그중 등록한 사람). 파티 당일 문 앞에서 쓰는 탭은 하나여야 급할 때 잘못 누르지 않는다.

**합쳤을 때 얻은 것은 그대로 남는다.** 한 사람은 여전히 한 번만 나온다 —
등록하면 명단 행에서 빠지고 카드로 올라온다. 명단은 파티가 다가올수록 줄고 카드가 그만큼 는다.
합치기 전에 문제였던 "같은 사람이 두 번 나온다" 는 **화면을 갈랐기 때문이 아니라
등록한 사람을 양쪽에 뒀기 때문**이었다.

**칩은 성별로 돌아간다** — 전체 · 남성 · 여성. 칩의 진짜 용도가 "세 숫자를 한 번에 보는 것"
(성비)이었고, 그건 상태 칩으로 대신할 수 없어서 숫자 한 줄로 따로 적어야 했다.
칩이 성비를 도로 나르면 그 줄이 필요 없다 — **같은 숫자를 두 곳에 두지 않는다.**

**참석 상태는 카드 안 맨 오른쪽으로 들어갔다.** 카드 밖 형제 요소로 두니 목록 폭이 들쭉날쭉했고,
누르는 자리가 카드와 따로 놀았다. 안으로 넣으면서 카드가 버튼 하나에서 상자가 됐다 —
버튼 안에 버튼을 넣을 수 없어서 왼쪽(아바타·실명·번호)이 상세를 여는 손잡이,
오른쪽이 참석 칩이다. **한 번 눌러 찍는다는 결정은 그대로다.**

### 후기 2 — `안 옴` 을 `미도착` 으로, 글자를 **상태 배지**로 (2026-08-24)

**이름.** `안 옴` 은 앱이 모르는 것을 아는 척했다. 그 값이 실제로 뜻하는 건
"안 왔다" 가 아니라 **"아직 도착으로 안 찍혔다"** 이고, 이 결정의 `대가` 절이
그걸 이미 적어뒀다 — *운영자가 안 누른 것과 안 온 것이 같은 값이다.*
`미도착` 은 그 사실만 말한다. 덤이 둘 있다: `미등록 · 미도착 · 도착` 이 한 가족이 되고
(`미-` 는 "아직 ~ 아님" 이다), 사람 이름 옆에 붙는 말이 그 사람을 탓하지 않는다.
이 앱은 거절의 경험을 만들지 않으려고 만든 앱이고, 운영자만 보는 화면이라고 말이 거칠어질 이유가 없다.

**같이 검토하고 버린 것** — `불참`(판정 같고 무겁다) · `노쇼`(사람을 라벨로 부른다) ·
`입장/미입장`(당시 `입장` 은 문(초대 링크·`입장 명단`)의 말이라 현장 도착과 겹쳤다.
그 명단은 뒤에 **`초대 명단`** 으로 고쳤지만 — ADR-32 후기 2 — 이 결정은 그대로다:
`입장` 은 파티 당일 문 앞을 가리키는 말이고, 거기서 하는 일은 `도착` 이 더 짧게 부른다) ·
`아직 안 옴`(뜻은 맞지만 칩에 넣기엔 길어 이름줄을 밀어낸다). `도착` 은 그대로 뒀다 —
가장 짧고, 문 앞에서 하는 일을 그대로 부르는 말이다.

#### 후기 — 파티 전에는 배지를 그리지 않는다 (2026-08-24)

`등록함` 을 뺐다. **참가자 탭에 있다는 것이 곧 등록했다는 뜻**이라, 카드마다 붙는 그 배지는
전원에게 같은 말을 한 번씩 더 하고 있었다. 읽을 것만 늘고, 정작 파티 중에 뜨는 참석 상태가
그만큼 덜 도드라진다 — 배지가 **상태값**으로 읽혀야 한다는 아래 결정이 되레 약해졌다.

같은 값을 파티 전후로 다르게 부르던 것(`등록함`/`미도착`)도 함께 사라진다.
파티 전에는 부를 일이 없고, 시작 뒤에는 `미도착` 하나다.

**모양.** 오른쪽 끝을 그냥 글자에서 **상태 배지**로 바꿨다 (`.badge` 와 같은 말투:
알약 · 톤 · 굵은 작은 글자). 도착은 `--ok`, 나감은 `--warn`, 미도착·등록함은 무채색이다.
**톤은 거들 뿐이고 글자가 정보를 다 나른다** — 색만으로 말하지 않는다는 규칙 그대로다.

**크기는 단계가 정한다.** 파티 전에는 전부 작은 배지(아무도 찍을 게 없다),
시작 뒤에는 전부 44px 칩. 처음엔 "누를 수 있는 것만 크게" 로 했는데,
파티 중에 `나감` 한 줄만 작아져서 **덜 중요한 사람처럼 읽혔다.**
누를 수 있나는 크기가 아니라 톤과 눌림이 말한다.

**잃은 것 — 상태별 인원 칩.** `미도착 4` 를 눌러 그 사람들만 보는 길이 없어졌다.
대신 카드 목록 위에 `도착 8 · 미도착 4` 한 줄을 둔다. 세는 건 되고 거르는 건 안 된다 —
스무 명 남짓이라 훑으면 보이고, 거를 만큼 길어지면 그때 다시 연다.

## ADR-34 사전 콕을 매력 투표로 가른다 — 만나기 전은 자리, 만난 뒤는 매칭

**문제** — 사전 콕이 **두 일을 겸했다.** 자리 배정의 재료이면서 매칭의 재료였다.
그런데 그 둘은 성격이 다르다 — 앞은 *"프로필만 보고 고른 것"* 이고 뒤는 *"만나보고 고른 것"* 이다.

첫 회차 숫자가 그 어긋남을 보여준다.

| | 콕 | 매칭으로 | 전환율 |
|---|---|---|---|
| 사전 | 17건 | 4건 | **24%** |
| 파티 | 53건 | 6건 | 11% |

**매칭 5쌍 중 4쌍이 사전 콕에서 출발했다.** 얼굴도 모르고 고른 것이 결과의 대부분을 정한 셈이다.

**결정 (2026-08-24)** — 둘을 가른다.

| | 언제 | 무엇에 쓰이나 | 취소 |
|---|---|---|---|
| **매력 투표** | 운영자가 연 날 → **파티 시작에 마감** | **첫 자리 배정**에만 | 된다 |
| **콕** | 파티 시작 후 | **매칭**과 **둘째 라운드부터의 자리** | 된다 |

개수는 둘 다 회차 설정을 따른다. **매력 투표는 매칭에 들어가지 않는다.**

> 저장값은 `pre` 그대로 둔다. `CHECK (round IN ('pre','party'))` 를 고치는 건 SQLite 에서
> 표를 다시 만드는 일이고, **마이그레이션에서 한 번 데인 뒤라**(ADR-32 후기) 뜻만 바꾼다.
> 뜻은 이 문서가 정한다 — `pre` 는 이제 **매력 투표**다.

### 알림을 없앤다 — 취소와 한 몸이다

**매력 투표도 콕도 참가자에게 아무 알림을 주지 않는다.**
받지 못한 사람에게 나쁜 경험이 되고, 그건 다음 파티에 안 나오는 이유가 된다.
첫 회차에서 **받은 콕 0회가 11명(30%)** 이었고 남성은 36% 였다.
지니 0.51 에 상위 5명이 37% 를 가져갔다 — 알림이 있으면 그 쏠림이 실시간으로 체감된다.

**그리고 이것이 취소를 안전하게 만든다.** 취소만 열면 받은 수가 줄어드는 것을 누가 보고
"방금 누가 취소했다" 에서 발신자를 좁힐 수 있다 — ADR-29 가 막던 유출이다.
알림이 없으면 그 창이 닫힌다. **둘은 한 몸이라 나중에 알림만 되살리면 안 된다.**

### 되돌리기와 알림은 **회차 설정**이다

운영자와 합의되지 않은 것이라 회차마다 정한다. 둘 다 `EventConfig` 에 있고,
**기본은 '되돌릴 수 있다' 와 '알리지 않는다'** 다.

| | 기본 | 없을 때 뜻 |
|---|---|---|
| `allowUndoPre` | 없음 | 매력 투표를 되돌릴 수 있다 |
| `allowUndo` | 없음 | 파티 콕을 되돌릴 수 있다 |
| `pokeNotify` | 없음 | 알리지 않는다. `true` 로 적어야 알린다 |

**되돌리기는 라운드마다 따로 정한다.** 한동안 매력 투표는 언제나 무를 수 있게 뒀는데,
회차마다 판단이 갈리는 값이라 운영자에게 넘긴다.

> **운영자 라벨은 짧게 쓴다.** `할 수 있음`·`못 함`·`보냄`·`안 보냄`.
> 설명이 길면 고르는 자리가 읽는 자리가 된다 — 참가자에게 나가는 문장이 아니다.
> 세 줄이 같은 모양이라 `Toggle` 하나로 그린다.

**알림을 끈 회차에서는 발표 전까지 `receivedCount` 를 응답에 싣지 않는다.**
화면에서 감추는 것으로는 부족하다 — 개발자 도구를 여는 참가자가 있고,
그 숫자 하나가 곧 *"지금까지 몇 명이 나를 골랐나"* 다. 발표 단계에서만 나간다.

**되돌리면 알림이 저절로 사라진다.** 알림은 저장되지 않고 `receivedCount` 에서
파생되므로(`noticesOf`, ADR-4), 무르면 그 줄이 없어져 **받지 않았던 상태로 돌아간다.**
지울 메시지가 애초에 없다.

### 매력 투표에서 '콕' 이라는 말을 쓰지 않는다

둘은 쓰임이 아예 다르다 — 매력 투표는 첫 자리 배정의 재료이고, 콕은 매칭의 재료다.
같은 말로 부르면 참가자가 *"아까 찔렀는데 왜 또?"* 가 된다.

라운드별 이름은 `copy.ts` 의 **`ACT` 한 곳**에서 나온다. 문구를 새로 쓸 때 그걸 거친다.

| | 매력 투표 | 파티 |
|---|---|---|
| 이름 | 매력 투표 | 콕 찌르기 |
| 문장 안 | 투표 | 콕 |
| 버튼 | ✨ | 👉 |

**이모지도 가른다.** 같은 👉 를 두 라운드에 쓰면 화면만 보고는 지금 무엇을 하는지 알 수 없다.

> **서버는 라운드를 모른다.** `pokeMessage` 는 실패 사유만 받으므로
> `anyClosed`·`anyNoBudget` 이라는 **중립 문구**를 따로 둔다.
> 화면이 먼저 막으므로 거기까지 오는 건 단계가 방금 바뀐 경우뿐이다.

### 되돌리기는 **확인창 안**에 둔다

목록 행에 버튼을 하나 더 두면 **카드가 화면 밖으로 밀린다.** 그리고 더 나쁜 게 있다 —
되돌리기는 **찌른 사람 옆에만** 나오므로, 어깨너머 가리기(슬라이스 16)를 켠 동안
그 버튼이 보이면 *"이 사람을 골랐다"* 가 그대로 샌다. 그 슬라이스의 유일한 불변식이
버튼 하나로 깨진다.

확인창은 **이미 숫자를 보여주고 있다**(남은 콕). 거기가 제자리다.
`confirm({ second })` 로 받는다. 이미 보낸 적이 있고 되돌릴 수 있을 때만 나온다.

> **후기 — 줄을 하나로 줄이고, 결과값 대신 변화를 적는다.**
> 처음엔 `보낸 횟수`·`남은 횟수` 두 줄이었고, 둘 다 **누른 뒤의 값**을 현재형 라벨로 적었다.
> 아직 안 찌른 사람 앞에서 `보낸 콕 1회` 가 뜨고, 바로 위 카드가 `남은 콕 3회` 인데
> 창은 `2회` 라고 해서 **한 화면의 두 숫자가 서로 달랐다.** QA 에서 그걸 본 사람은
> 매력 투표가 파티 콕에 합산된 줄로 읽었다 — 서버는 멀쩡했고, 창이 거짓말을 하고 있었다.
>
> 지금은 `남은 콕  3회 → 2회` 한 줄이다. 왼쪽이 카드와 같아서 어긋날 자리가 없고,
> 몇 번째인지는 제목(`한 번 더`)과 그 사람 카드의 숫자가 이미 말한다.
> 이름도 카드와 맞췄다 — `파티 남은 횟수` 가 아니라 `남은 콕` 이다.
> **같은 숫자를 두 이름으로 부르면 다른 숫자로 읽힌다.**

> **후기 2 — 다 쓰면 되돌릴 길이 사라졌다.**
> 되돌리기를 창 안에 둔 대가가 여기서 나왔다. 예산이 0 이 되면 `send()` 의 가드가
> **창이 열리기 전에** 토스트로 끊어서, 되돌리기가 통째로 닿을 수 없게 됐다.
> 하필 **다 쓴 순간이 옮기고 싶은 순간이다** — 셋을 다 쓰고 나서야 넷째 사람을 만난다.
>
> 이제 다 썼어도 **찌른 적 있는 사람에게는 창이 열린다.** 안에는 되돌리기 하나뿐이고
> (보낼 것이 없으니 보내기 버튼을 그릴 수 없다), 항목은 `남은 콕  0회 → 1회` —
> **화살표가 반대인 것이 이 창이 하는 일이다.** 되돌릴 것도 없으면 그때는 토스트가 맞다.
>
> 확인을 한 겹 더 씌운 것은 아니다. 되돌리기는 **전에도 이 창을 열어야 닿았다**(`second`) —
> 걸음 수는 그대로고, 다 쓴 자리에서만 문이 닫혀 있었다.

**자리는 실행 버튼 옆이다.** 둘은 같은 축의 반대 방향이라(한 번 더 / 한 번 물리기)
붙어 있어야 무엇을 고르는 자리인지 읽힌다. **취소는 아래 줄로 내린다** —
아무것도 하지 않고 닫는 것이라 성격이 다르다.

```
[ 되돌리기 ]  [ 매력 투표 ]
[        취소        ]
```

### 보류한 것

첫 기획에는 있었으나 **운영자와 합의되지 않아 이번에 만들지 않는다.**

| | 상태 |
|---|---|
| **둘째 라운드부터의 함께 점수** (50 · 동석 −10 · 콕 +10 · 나이차 −5) | **보류.** 실제 파티에서 재보고 확정한다 |
| **커플 자리 폐지** (ADR-23·28) | ~~보류~~ → **ADR-51 에서 걷어냈다.** 쌍은 운영자가 💘·💔 를 보고 붙인다 |
| 같은 테이블 · 지나온 테이블 보기 | `PLAN.md` 23 |
| 운영자 투표 화면 | `PLAN.md` 24 (서버는 이미 있다) |

자리 배정은 **지금 알고리즘 그대로**다. 매력 투표가 `pre` 라운드에 그대로 들어가므로
첫 자리 배정에 자연히 반영된다 — 바꾼 것은 **매칭이 그것을 세지 않는다**는 한 줄뿐이다.

> **`MatchKind` 를 걷어냈다.** 매칭이 파티 콕만 세므로 `pre`·`crossed` 는 나올 수 없다.
> 남는 길은 *"이 쌍은 매력 투표도 서로 했다"* 로 다시 정의하는 것뿐이었는데,
> **그건 붙일 의미가 없는 사실이다** — 프로필만 보고 서로 골랐다는 게 만나본 뒤의 결과를
> 더 설명해 주지 않는다. 죽은 값을 그리느니 지웠다 (운영자 현황의 네 갈래 카드와 줄마다 붙던 배지).

### 대가

**매칭이 줄어들 수 있다.** 위 표대로면 사전 콕이 만들던 4쌍이 사라진다.
**운영자가 콕 개수를 늘려 맞춘다** — 다음 회차 설정에서, 또는 파티 도중에.
콕이 자리 배정에도 쓰이므로 개수가 늘면 자리도 같이 좋아진다.

**앱을 열 이유가 얇아진다.** 알림이 없어지면 파티 중에 앱을 볼 이유가 콕 하나뿐이다.
같은 테이블 보기와 **운영자 투표**(슬라이스 14 — 서버는 있고 화면이 없다)가 그 자리를 맡는다.
부족하면 테이블 대화 카드·라운드 미션이 대기 중이다 (`PLAN.md` 20·22).

**나이차 −5 는 약한 손잡이다.** 지금은 10살 이상이 한 단이고 콕 하나(+10)가 그것을 덮는다.
`SEATING.md` 에 *3라운드에서 나이차 위반 26쌍* 이 났던 기록이 있으므로,
표본을 재보고 모자라면 값을 올린다. `buildSeating` 은 순수 함수라 숫자를 바꿔가며 잴 수 있다.

### 걸리는 ADR

| | 어떻게 |
|---|---|
| **ADR-21** 명단은 사전 투표부터 열린다 | 기준이 **매력 투표 시작**으로 이름만 바뀐다 |
| **ADR-27·31** 사전 투표 전까지 고칠 수 있다 | 같음 — 경계는 그대로 한 곳이다 |
| **ADR-22·30** 받은 콕 순위 | 운영자 화면은 그대로. 참가자 알림만 사라진다 |
| **ADR-23·28** 커플 자리 | **폐기** (ADR-51 에서 실행). 매 라운드 재계산이 대신한다 |
| **ADR-24** 한 사람이 여러 명과 이어진다 | 그대로. 매칭 규칙은 안 바뀐다 |
| **ADR-25** 여러 쌍 중 콕이 많은 쪽 | **함께 점수에 흡수된다** — 콕 개수가 곧 점수다 |
| **ADR-26** 실시간은 "다시 읽어라" 신호 | 그대로. 콕 알림만 빠진다 |
| **ADR-29** 지운 사람의 콕은 남긴다 | 그대로. 취소가 열려도 알림이 없어 안전하다 |

## ADR-35 규칙과 일정은 콕이 오가기 시작하면 굳는다

**문제** — ADR-34 로 회차 설정이 셋 늘었다 (`allowUndoPre`·`allowUndo`·`pokeNotify`).
셋 다 설정 탭에서 **아무 때나** 바꿀 수 있었다 — `patchMeta` 에 단계 잠금이 없었고,
바꾸면 `broadcast` 가 나가 참가자 화면이 그 자리에서 다시 읽었다. 즉 잘 반영됐다. 그게 문제였다.

**파티 도중에 바뀌면 참가자가 겪는 규칙이 도중에 갈린다.** 가장 나쁜 것이 알림이다.

> 콕은 알림 설정과 무관하게 전부 저장돼 있고, `receivedCount` 는 **읽을 때** 계산된다.
> 파티 중에 알림을 켜면 그때까지 쌓인 콕이 **한 줄씩 N개** 한꺼번에 나타난다.
> 받은 쪽에는 *"방금 다섯 명이 나를 골랐다"* 로 읽히고, 콕에는 시각이 없어(ADR-30)
> 언제 온 것인지 구분할 방법도 없다. **"받은 콕은 한 번에 하나씩"** 이 그 순간 통째로 깨진다.

되돌리기도 마찬가지다. 무를 수 있다고 믿고 누른 사람과 못 무르게 된 뒤에 누른 사람이
같은 회차 안에 생긴다. 콕 대상(`allowSameGender`)은 더 직접적이다 — 이미 찌른 콕이 그대로 남는다.

**결정 (2026-08-24)** — **콕이 오갈 수 있게 된 뒤로는 굳는다.**

| | 굳나 | 왜 |
|---|---|---|
| 콕 대상 `allowSameGender` | **굳는다** | 이미 오간 콕이 새 규칙과 어긋난다 |
| 되돌리기 `allowUndoPre`·`allowUndo` | **굳는다** | 무를 수 있다고 믿고 누른 사람이 생긴다 |
| 알림 `pokeNotify` | **굳는다** | 켜면 쌓인 것이 한꺼번에 터진다 |
| 일정 셋 | **굳는다** | 그 시점에 남은 예약이 없다 |
| 콕 횟수 `maxPre`·`maxParty` | **연다** | 파티 중에 올리는 것이 매칭이 모자랄 때의 손잡이다 (ADR-34) |
| 이름 · 장소 | **연다** | 참가자가 겪는 규칙이 아니다. 장소는 오타가 나기 쉽다 |

> 이 표에 있던 **파기 일수**는 설정에서 사라졌다 (ADR-36) — 자동 파기를 걷어냈다.

판단은 `rulesLocked(fired)` 한 곳에서 한다. `schedLocked` 도 이걸 먼저 본다.

**기준을 `phase` 가 아니라 `fired` 로 잡았다.** 되돌리기로 단계를 뒤로 물려도
이미 오간 콕은 남아 있어서, 거기서 잠금이 풀리면 같은 구멍이 그대로 다시 열린다.
매력 투표를 건너뛰고 파티로 바로 간 회차가 있으므로 `prevote`·`party`·`done` 셋을 다 본다.

**막는 것은 '보냈나' 가 아니라 '달라졌나' 다.** 설정 탭은 저장할 때마다 설정과 일정을
**통째로** 다시 보낸다. 키가 있는지로 재면 굳은 회차에서는 이름조차 못 고친다.

비교는 **뜻으로** 한다. 기본값과 같으면 아예 안 적히는 규약이라(`allowUndo` 없음 = 할 수 있음),
`undefined` 를 그대로 견주면 저장할 때마다 달라 보인다. `frozenRules()` 가 저마다의 기본으로 접는다.

**화면은 잠긴 줄을 지우지 않는다.** 지금 어느 규칙으로 돌아가는 중인지는
파티 도중에 가장 자주 확인하는 값이다. 감추면 확인할 자리가 사라진다 —
버튼만 못 누르게 하고, 그 아래에 이유를 한 줄 둔다. 서버가 거절할 때도 **같은 문장**을 쓴다.

### 보류한 것

**매력 투표 중의 파티 일시 수정.** 파티가 늦어지면 참가자 카운트다운이 틀린 시각을 센다.
잠금을 규칙과 일정으로 갈라 둘로 만들면 살릴 수 있지만, 설정 하나에 판단이 둘 붙는다.
지금은 **한 줄로 둔다** — 늦어지면 운영자가 파티 시작을 누르면 되고, 그 순간 카운트다운은 사라진다.
실제로 걸리면 그때 가른다.

### 곁가지로 고친 것

`PUT /host/events/:id` 가 **`place` 를 DO 로 넘기지 않았다.** 설정 탭은 보내고 있었고
`patchMeta` 는 받을 준비가 돼 있었는데 라우트에서 빠져, **장소 수정이 조용히 무시됐다.**
`allowSameGender` 도 다른 셋과 달리 `?? meta.config` 병합이 없어, 안 보내면 기본으로 되돌아갔다.

## ADR-36 개인정보 자동 파기를 걷어낸다 — **ADR-19 의 보관 기간 폐기**

**바뀐 것** — 회차는 마지막 일정에서 N일(기본 3일, 회차 설정에서 1~14일)이 지나면
Cron 이 DO 를 통째로 지웠다. **그 Cron 과 설정 항목을 함께 걷어냈다.**
이제 회차는 **운영자가 지울 때까지 남는다.**

**왜 반쪽이 아니라 통째로 걷어냈나** — 셋이 한 덩어리라서다.

- **파기 Cron** (`scheduled` · `triggers.crons`) — 하루 한 번 깨어나 회차를 훑던 자리
- **`purgeIfExpired` · `purgeDueAt`** — "가장 나중 자국 + N일" 계산
- **회차 설정의 파기 대기 일수** (`retentionDays` · 설정 탭 `개인정보 파기` 칸)

Cron 만 끄고 설정 칸을 남기면 **운영자가 고른 숫자가 아무 일도 하지 않는다.**
"3일 뒤 삭제" 라고 쓰인 칸이 삭제하지 않는 것은, 그 칸이 없는 것보다 나쁘다.
계산(`purgeDueAt`)만 남겨도 같은 종류다 — 부르는 곳이 없는 판정은 다음 사람에게
*아직 돈다* 고 말한다.

### 등록 화면은 손대지 않았다

**약속을 어기지 않는다.** 등록 폼의 연락처 안내(`REGISTER.contactNote`)는 *어디까지 가는지*
두 문장만 말하고, **파기 기한은 이미 거기 없었다.** 그래서 참가자에게 한 약속과
이 변경은 어긋나지 않는다 — 어긋났다면 문구를 먼저 고쳐야 했다 (ADR-19 의 규칙).

**되살릴 거라면 순서가 있다.** 등록 화면에 "N일 뒤에 지워져요" 를 다시 적는 건
**지우는 코드를 되살린 뒤**다. 문구가 먼저 가면 그 순간부터 거짓말이다.

### 대가 — 무엇이 상한을 잡던 자리였나

| | 전 (ADR-19) | 후 (여기) |
|---|---|---|
| 실명·전화번호 보관 | 마지막 일정 + 3일 | **운영자가 지울 때까지** |
| 참가자 세션 30일 | 회차가 먼저 사라져 열리는 게 없었다 | **회차가 살아 있으면 그대로 열린다** |
| 운영자가 할 일 | 없음 (저절로 사라짐) | **끝난 회차를 지우는 것** |

**참가자 세션(30일)의 근거가 파기였다** (`auth.ts`). "세션이 살아 있어도 열리는 게 없다" 가
성립하지 않으므로, 남의 기기에 남은 쿠키가 회차가 살아 있는 동안 그 참가자 화면을 연다.
TTL 은 건드리지 않았다 — 파티 당일에 세션이 끊기는 사고(ADR-32)가 그 값의 이유이고,
그건 그대로다. **상한을 다시 만드는 길은 끝난 회차를 지우는 것 하나뿐이다.**

지우는 길은 그대로 하나다 — 설정 탭의 `이 회차 삭제하기`. 회차 1개 = DO 1개라
누르면 참가자·연락처·콕이 한 번에 사라진다. 그 매핑은 여전히 지켜야 한다
(개인정보를 회차 DO 밖으로 복사하지 마라).

## ADR-37 연락처를 얼마나 열지는 **본인이 미리 고른다**

**바뀐 것** — ADR-19 이후 발표 때 서로 콕 찌른 쌍에게는 실명·전화번호·인스타가
**자동으로** 열렸다. 이제 참가자가 **등록할 때** 셋 중 하나를 고르고, 그 값이 문을 정한다.

**이름은 고르는 값이 아니다 — 늘 열린다.** 고르는 건 연락 수단 둘이고 **서로 독립**이라,
넷이 나온다.

| 고른 것 | 상대에게 열리는 것 |
|---|---|
| 둘 다 열기 | 이름 · 전화번호 · 인스타 |
| 전화번호만 | 이름 · 전화번호 |
| 인스타만 | 이름 · 인스타 |
| 둘 다 안 열기 | 이름 |

**넷째 조건이다.** ADR-19 의 셋(발표 단계일 것 · 서로 찔렀을 것 · 그 상대의 것일 것)에
*두 사람이 고른 것을 칸마다 겹쳐, 둘 다 허락한 것만* 이 붙는다. **통로는 여전히 하나다**
(`MatchInfo.contact`) — 조이기만 했지 새로 내지 않았다.

### 문제 — 시끄러운 데서 누른 콕이 번호를 넘긴다

콕 자체는 동의로 충분하다. 문제는 **동의의 크기**다. 파티 중에 누른 콕 하나가
전화번호까지 넘기는 건 인스타 아이디가 넘어가는 것과 무게가 다르고,
콕을 누를 때 그 무게를 생각하고 누르는 사람은 많지 않다.

### 왜 발표 **뒤** 수락이 아닌가 — 이게 이 결정의 전부다

가장 먼저 떠오르는 설계는 *발표 때 양쪽이 `수락` 을 눌러야 열린다* 였다. **그걸 안 골랐다.**

> 발표 화면에는 `💘 서로 콕 찔렀어요` 가 이미 떠 있다. 양쪽이 서로를 골랐다는 게 확정된
> 상태에서 내가 수락을 누르고 상대가 안 누르면, **나는 누가 나를 거절했는지 안다.**
> 닉네임도, 아까 같은 테이블에 앉았던 얼굴도.

콕 단계의 거절은 끝까지 익명이다 (ADR-1) — 누가 나를 안 찔렀는지 참가자는 모른다.
수락 단계의 거절은 **이름이 붙는다.** 이 앱이 없애려는 경험을, 앱이 직접, 가장 아픈
형태로 만드는 자리다 (`DOMAIN.md` — "이 앱이 없애려는 건 거절당하는 경험이다").

그리고 `아직` 과 `거절` 은 **구분해서 보여주지 않아도 구분된다.** 그날 밤엔 "아직 안 봤나
보다" 지만 사흘 뒤엔 명백한 거절이다. 시계가 침묵을 답으로 바꾸는 걸 앱이 막을 방법이 없다.

**그래서 고르는 때를 발표 앞으로 당겼다.** 누구와 매칭될지 모르는 상태에서 고르므로,
안 열려도 그건 *나를* 거절한 게 아니라 *그 사람의 방침*이다. 기다림도 없다 —
발표 순간에 이미 정해져 있다.

### 왜 대칭인가 — 각자 제 것만 여는 방식을 안 골랐다

`minShare(a, b)` 가 **칸마다** 둘 다 허락한 것만 남긴다. 각자 자기 것만 여는 비대칭도
가능했지만, 그러면 *"나는 열었는데 못 받았다"* 가 생긴다. 그 비대칭 자체가 상대의 선택을
가리키는 정보이고, 결국 위에서 피한 것과 같은 자리로 돌아간다.
대칭이라서 화면이 **"상대에게도 같은 만큼 보여요"** 라고 쓸 수 있다 — 규칙이 바뀌면 그 문장이 거짓말이 된다.

### 언제 굳는가 — 프로필과 같은 때

**사전 투표가 열리면 잠긴다** (ADR-31 의 잠금을 그대로 쓴다). 별도 편집 경로를 만들지 않았다 —
`Me.tsx` 의 "고치는 길도 하나다" 가 그대로 지켜진다.

⚠️ **발표 뒤에 고치는 길을 만들면 이 ADR 이 통째로 무의미해진다.** 그 순간 이 값은
"이 사람에게 열까" 가 되고, 위에서 피한 이름 붙은 거절이 그대로 돌아온다.
`test/29-contact-share.test.ts` 의 `사전 투표가 열리면 프로필과 함께 굳는다` 가 그 자리를 지킨다.

### 기본값을 두지 않았다

**둘 중 하나라도** 안 고르면 등록이 막힌다. 화면도 서버(`cleanProfile`)도 같은 것을 본다.
안 보낸 것을 열림으로 읽으면 그건 동의가 아니라 동의를 지어낸 것이다.
서버는 `=== true` 가 아니라 **참·거짓인지**를 본다 — 빠진 칸은 `undefined` 라 거기서 걸린다.
어느 쪽도 권하지 않는다 (`추천` 이나 `대부분 이걸 골라요` 를 붙이지 마라).

### 옛 회차의 행에는 이 칸이 없다

`ALTER TABLE players ADD COLUMN contact_share TEXT` 로 붙인다. `parseShare` 가 **세 모양**을
만난다 — `NULL`(칸이 없던 회차) · 사다리 3단이던 시절의 문자열 · 지금의 JSON.
없거나 못 읽는 값은 **둘 다 열림**으로 읽는다. 그때 등록 화면이 한 약속이 *"발표 때 열린다"*
였기 때문이다 — 여기서 조용히 좁히는 것도 약속을 어기는 일이다.
**테스트 DO 는 언제나 새것이라 이 경로를 못 밟는다.** 판단하는 함수만 따로 본다. QA 에서 확인한다.

### 받을 때 한 약속을 먼저 고쳤다

`REGISTER.contactNote` 에 세 번째 줄이 붙었다 — *"무엇까지 열지는 아래에서 고를 수 있어요."*
고르는 자리가 **그 약속 바로 아래**다. 문구와 컨트롤이 같은 화면에 있어야
받을 때 한 약속과 실제 동작이 갈리지 않는다 (ADR-19 의 규칙).

### 남는 것

- **둘 다 닫은 쌍에게는 이름과 `파티장에서 직접 인사해보세요` 가 전부다.**
  그건 ADR-19 이전의 원래 설계라 새 구멍은 아니다
- **없는 줄의 이유를 화면에 적지 않는다.** `상대가 번호를 안 열었어요` 는 상대를 지목하는
  말이고, 멀쩡한 인스타를 실패처럼 보이게 한다. 없는 줄은 그냥 없다
- 회차 설정으로 두지 않았다. 개인정보 규칙은 전부 고정이다 (`DOMAIN.md`) —
  회차마다 다르면 참가자가 이번 파티의 규칙을 매번 새로 배워야 한다

### 후기 (2026-08-24) — 사다리를 걷어내고 **칸 둘**로 바꿨다

처음 판은 사다리 3단이었다 — `전화번호까지` · `인스타까지` · `안 열기`.
**순서를 강요하는 게 문제였다.**

> `인스타는 열되 번호는 닫는다` 는 되는데 **그 반대가 안 됐다.**
> 번호는 줘도 되지만 인스타 계정은 알리고 싶지 않은 사람에게 줄 답이 없었다.
> 사다리는 "얼마나" 를 묻는데, 실제 질문은 **"무엇을"** 이었다.

그리고 `안 열기` 는 **이름까지 닫았다.** 서로 콕 찌른 사이에게 이름조차 안 주면
앱이 해줄 게 없고, 그건 ADR-19 이전으로 돌아가는 것이다. 이름은 신원이지 연락 수단이 아니라
(연락 카드에서도 `연락처` 라벨 **밖에** 둔다) 고르는 값에서 뺐다.

**바뀐 것**

| | 전 (첫 판) | 후 (지금) |
|---|---|---|
| 타입 | `"none" \| "instagram" \| "all"` | `{ phone: boolean; instagram: boolean }` |
| 이름 | `안 열기` 면 안 나감 | **늘 나감** |
| 겹치는 법 | 사다리에서 낮은 쪽 | **칸마다 AND** |
| 저장 | 문자열 | JSON (`writeShare`/`parseShare`) |
| 고르는 화면 | 세로 카드 셋 | 칸마다 `열기`/`안 열기` 알약 한 줄 |

**바뀌지 않은 것이 더 중요하다** — 발표 앞에서 고르는 것, 대칭인 것, 기본값이 없는 것,
사전 투표에 굳는 것. 위에 적은 이유가 전부 그대로다.

⚠️ **사다리 시절 값을 조용히 버리지 마라.** QA 에 그 값으로 등록한 행이 남아 있고,
못 읽어서 기본값으로 떨어뜨리면 그 사람이 좁혀 둔 것이 도로 열린다.
`parseShare` 가 `"all"`·`"instagram"`·`"none"` 을 뜻대로 옮긴다.
**새로 받지는 않는다** — `cleanProfile` 은 참·거짓 둘만 통과시킨다.

## ADR-38 등록은 만드는 순간 열린다 · 장소는 기본값이 된다

**문제 1 — 등록 시작 시각이 답하는 질문이 없어졌다.**

원래 이 칸은 *"아직 문을 열면 안 되는 시기"* 를 위한 것이었다. 입장 코드 시절에는 뜻이 있었다 —
코드가 돌면 누구든 들어올 수 있으니, 문 여는 때를 정해야 했다.

**ADR-32 로 문이 초대 명단이 된 뒤로 그 이유가 사라졌다.** 링크는 사람마다 다르고 1:1 로 보낸다.
운영자가 안내문을 보내기 전에는 아무도 들어올 수 없고, 보낸 뒤에는 늦게 열 이유가 없다.
남은 것은 **운영자가 채워야 하는 칸 하나**와, 그 칸 때문에 필요한 것들이었다 —
'지금 바로' 토글, `regOpenAt: number | "now"` 라는 두 갈래 타입, `prevoteAt > regOpenAt` 순서 검증,
`prep` 단계, 그리고 ADR-10 이라는 예외 규칙 하나.

**결정 (2026-08-24)** — **등록 시작은 묻지 않는다.** 회차를 만들면 그 자리에서 열린다.

| 없앤 것 | 남은 것 |
|---|---|
| 위저드의 등록 시작 칸 · '지금 바로' 토글 | "등록은 회차를 만들면 바로 열려요" 한 줄 |
| `CreateEventInput.regOpenAt` | `schedule.regOpenAt` — **만든 시각이 기록으로** 남는다 |
| `Defaults.regOpenBeforeD` | `prevoteBeforeH` 하나 |
| `prevoteAt > regOpenAt` 순서 검증 · ADR-10 | 없음. 견줄 두 시각이 없다 |

**예약이 걸리는 전환은 이제 매력 투표 시작 하나뿐이다** (ADR-14 의 "둘뿐"이 하나로 줄었다).

`prep` 단계는 **지우지 않았다.** 이 결정 전에 만들어진 회차가 거기 있을 수 있고,
운영자가 단계를 되돌리면 여전히 갈 수 있다. `dueTransition` 의 `prep → reg` 가지와
"N시부터 등록이 열려요" 안내도 그 길을 위해 남는다 — 새 회차가 그 길을 밟지 않을 뿐이다.

> **시각을 지우지 않는 것이 핵심이다.** `schedule.regOpenAt` 에 만든 시각을 적어둔다.
> "지나간 예약을 지우지 마라" 와 같은 이유다 — 언제 문이 열렸는지는 기록이다.

**문제 2 — 장소를 회차마다 다시 친다.**

지인 파티는 대개 **같은 곳에서 열린다.** 그런데 장소는 회차 만들기 화면에만 있어서,
회차를 만들 때마다 같은 가게 이름을 다시 쳤다. 오타가 나면 그 오타가 안내문으로 나간다.

**결정** — `Defaults.place` 를 둔다. 위저드는 **비어 있을 때만** 채운다 —
운영자가 이미 적었으면 기본값이 덮지 않는다. 회차에서 고치면 그 회차만 바뀐다.

빈 값도 뜻이 있다: *"회차마다 다른 곳에서 연다"*. 그래서 빈 문자열을 기본값으로 되돌리지 않고
그대로 저장한다 — 안내문(`inviteTemplate`)이 비면 기본 문구로 되돌리는 것과 반대다.
안내문은 비면 **링크 없는 안내문**이 나가서 고장이지만, 장소는 비어도 안내문이 성립한다.

### 걸리는 ADR

| | 어떻게 |
|---|---|
| **ADR-2** 예약은 한 번만 울린다 | 그대로. 우는 예약이 하나로 줄었을 뿐 |
| **ADR-10** '지금 바로'는 순서 검증의 한쪽이 아니다 | **폐기.** 견줄 두 시각이 없다 |
| **ADR-14** 예약은 둘, 나머지는 손 | **둘 → 하나.** 나머지는 그대로 |
| **ADR-32** 참가 링크는 사람마다 다르다 | 이 결정의 **근거**다. 문이 명단이라 늦게 열 이유가 없다 |
| **ADR-35** 규칙과 일정은 콕이 오가면 굳는다 | 그대로. 등록 시작은 만들 때 이미 `fired` 라 늘 잠겨 있다 |

## ADR-39 매력 투표는 시각으로 닫히고, 자리는 파티 전에 나간다

**문제** — `파티 시작` 버튼 하나가 세 가지를 함께 했다.

**① 매력 투표 마감 · ② 자리 공개 · ③ 콕 열기 (+ 나이·MBTI 공개)**

그래서 **일찍 온 사람을 앉힐 수 없었다.** 자리를 보이게 하려면 ②를 해야 하는데,
그러려면 ①③이 딸려온다 — 아직 안 온 사람의 투표가 마감되고, 빈 테이블에서 콕이 열린다.
반대로 파티 시각까지 기다리면 그때부터 자리를 짜기 시작해야 하는데,
그건 슬라이스 12 가 정확히 피하려던 상황이다.

**결정 (2026-08-24)** — ②를 앞으로 당기고, ①에 시각을 준다.

| | 언제 | 무엇이 정하나 |
|---|---|---|
| **매력 투표 마감** | `voteEndAt` (기본 파티 −1h) | **시각** |
| **자리 공개** | 자리 보내기 | 운영자 |
| **콕 열기 · 나이·MBTI** | 파티 시작 | 운영자 |

### 마감에 시각을 준 것이 ADR-14 예외인 이유

ADR-14 가 막은 건 **현장이 시계를 따라가는 것**이다. 파티 시작과 발표는 현장이 정한다 —
사람이 다 왔나, 지금 발표해도 되나. 시계는 그걸 모른다.

**매력 투표 마감은 현장이 아니라 준비가 쓰는 시각이다.** 마감돼야 자리를 짤 수 있고,
짜는 데 시간이 걸린다. 시각으로 못 박는 쪽이 오히려 운영자에게 **준비 시간을 만들어 준다** —
`voteEndAt` 과 파티 일시 사이가 곧 그 시간이다.

> **전환이 아니라 판정이다.** 알람이 울리지 않고 `phase` 도 그대로 `prevote` 다.
> `canPoke()` 가 서버 시각과 견줘 답할 뿐이다.
> 새 단계를 만들지 않은 이유이기도 하다 — 단계가 여섯이 되면 운영자가 누를 버튼이 하나 는다.
> (뒤에 **마감을 앞당기는 버튼**이 붙었지만 단계는 그대로 다섯이다 — 아래 후기.)

**단계를 넘기지 않는 것이 핵심이다.** 마감이 단계까지 넘기면 나이·MBTI 가 함께 열리고(ADR-21)
콕이 열려서, 아직 아무도 안 온 자리에서 파티가 시작된 것이 된다.

### 자리 게이트를 푼 것

`mySeat()` 이 `phase === "party"` 를 보던 것을 걷어냈다. 슬라이스 12 가 그 게이트를 세운 건
**짜는 동안 새지 않게** 하려던 것인데, 그 일은 지금 **초안**이 맡는다 —
초안은 발행 전까지 `lastPublished()` 에 잡히지 않는다. 즉 방어가 둘이었고 하나면 충분했다.

### 일정 잠금을 규칙 잠금에서 갈랐다

ADR-35 는 규칙 넷과 일정을 `rulesLocked(fired)` 하나로 묶었다. 마감에 시각이 생기면서 깨졌다 —
**파티가 늦어지면 마감도 미뤄야 하는데** `fired.prevote` 하나로 일정 전체를 잠그면 손쓸 방법이 없다.

| | 잠기는 때 |
|---|---|
| `regOpenAt` | 늘 (만들 때 이미 지남) |
| `prevoteAt` | `fired.prevote` |
| `voteEndAt` · `partyAt` | `fired.party` |

규칙 넷(대상·되돌리기 둘·알림)은 그대로 `rulesLocked` 에 묶여 있다.
ADR-35 가 "보류한 것"으로 적어둔 항목이 여기서 풀렸다.

#### 후기 — 마감을 앞당기는 버튼을 뒀다 (2026-08-24)

**"매력 투표 시작 다음에 마감이 나와야 하는데 파티 시작이 나온다"** 는 지적을 받았다.
운영자가 읽는 현황 탭의 버튼은 *다음에 할 일*이고, 매력 투표 다음에 할 일은 마감이다.

위에서 "새 단계를 만들지 않은 이유" 라고 적은 것은 그대로 지킨다 — **단계는 여전히 다섯이다.**
바뀐 건 버튼이 `phase` 를 넘긴다는 전제였다. 다른 단계 버튼과 **같은 뜻**으로 두면 된다:
*예약을 앞당긴다.* 마감의 예약이 `voteEndAt` 이므로, 그 버튼은 그 시각을 앞당길 뿐이다.

| | 누르면 | 단계 |
|---|---|---|
| 매력 투표 시작 | `phase: prevote` | 넘어간다 |
| **매력 투표 마감** | `fired.voteEnd` | **그대로 `prevote`** |
| 파티 시작 | `phase: party` | 넘어간다 |

**단계를 넘기지 않는 것이 핵심이라는 결정은 그대로다.** 마감이 열지 않는 것 —
나이·MBTI(ADR-21)와 파티 콕 — 은 여전히 `파티 시작` 이 연다. 확인창이 그 사실을
**항목으로** 말한다(`VOTE_END`): *"단계 — 매력 투표 그대로예요"*. 마감을 누르면 파티가
시작되는 줄 알고 멈칫하는 자리라, 무엇이 **안** 바뀌는지가 그 창의 일이다.

`fired` 에 짝이 생겼다. 위에서 "`fired` 에 짝이 없다" 고 적은 것은 마감이 시각뿐일 때의
사실이고, 사람이 앞당길 수 있게 된 지금은 **언제 실제로 닫혔는지**를 적을 자리가 필요하다.
`fired.voteEnd` 는 단계 전환이 아니다 — `dueTransition` 은 이 값을 모른다.

**예약은 덮어쓰지 않는다.** `voteEndAt` 을 `now` 로 밀면 "예약은 20시였는데 19시에 닫았다"
를 말할 수 없게 된다 — 지나간 예약은 기록이다(ADR-2와 같은 이유). 닫혔나는
`voteClosed(schedule, fired, now)` 한 곳이 답한다: 시각이 지났거나, 사람이 앞당겼거나.

**파티 시작에도 카운트다운을 붙였다.** 다만 그 숫자만 뜻이 다르다 — 나머지는
"가만히 두면 그때 넘어간다" 이고 이건 그냥 파티 일시다 (ADR-14). 그래서 그 하나에만
안내가 붙는다: *저절로 열리지 않고, 눌러야 시작됩니다.* 넷 다 자동인 줄로 읽히면
**파티가 영영 안 열린다** — `UI.md` 가 일정 화면에서 이미 겪은 함정이다.

### 곁가지 — `validSchedule` 을 없앴다

`prevoteAt > regOpenAt` 검사가 남아 있었는데, ADR-36 이후 `regOpenAt` 이 늘 **회차를 만든 시각**이라
**매력 투표를 지금 당장 열려는 정당한 조작이 거절당했다.** 등록이 늘 열려 있는 지금
"사전 투표가 등록보다 먼저 열렸다" 는 위반 자체가 성립하지 않는다. `schedule_order` 도 함께 뺐다.

### 참가자 화면에 생긴 새 구간

마감 ~ 파티 시작 사이가 **단계 이름으로는 고를 수 없는 칸**이다. 단계는 `prevote` 인데
할 일이 다르다 — 투표는 끝났고 자리를 기다린다. `HOME.todo.voteClosed` 가 그 자리를 맡고,
자리를 이미 보냈으면 자리 카드가 함께 뜬다.

카운트다운은 이제 **다음에 일어날 일**을 세는 규칙이 그대로 한 칸 늘어난다 —
등록 중이면 투표 시작, 투표 중이면 **마감**, 마감 뒤에는 파티 시작. 발표는 여전히 세지 않는다.

### 걸리는 ADR

| | 어떻게 |
|---|---|
| **ADR-14** 예약은 시작뿐, 마감은 손 | **예외 하나.** 마감은 현장이 아니라 준비가 쓴다 |
| **ADR-21** 나이·MBTI 는 파티부터 | 그대로. 마감은 단계를 넘기지 않는다 |
| **ADR-28** 발표만이 자리를 끝낸다 | 그대로. 자리 공개가 앞당겨졌을 뿐 |
| **ADR-34** 매력 투표는 첫 자리에만 | **이 결정이 그 말을 지킨다** — 첫 자리를 짜면 투표는 이미 닫혀 있다 |
| **ADR-35** 규칙과 일정이 함께 굳는다 | **일정을 뗐다.** 규칙 넷은 그대로 |
| **ADR-36** 등록은 만드는 순간 | 그대로. 예약이 걸리는 전환은 여전히 매력 투표 시작 하나 |
| **슬라이스 12** 자리는 파티부터 보인다 | **폐기.** 초안 하나로 충분한 방어였다 |

## ADR-40 자리의 끌림은 표 하나하나가 만든다

**문제** — 두 사람을 붙여 앉히는 힘이 **두 칸**뿐이었다.

| | 값 |
|---|---|
| 서로 찌른 쌍 | −12 × `pairWeight`(1~2) |
| 한쪽만 찌른 쌍 | **−4 (고정)** |

단방향이 고정값인 게 문제다. **한 사람에게 세 번 투표한 것과 한 번 투표한 것이 자리에서는
똑같았다.** 매력 투표 횟수는 회차 설정이고 1~5까지 열려 있는데(`maxPre`),
2표 이상으로 연 회차에서는 그 표들이 자리에 아무 말도 하지 않았다.

한쪽 −4 는 나이차 벌점 30 앞에서 사실상 없는 것과 같다. 그래서 기본값 1표로 도는 회차에서는
1라운드가 **"나이차 최소화 + 서로 투표한 소수를 붙이기"** 였고, 짝사랑 표는 거의 반영되지 않았다.

**결정 (2026-08-24)** — **표당 점수 + 상호 부가 점수.**

```
끌림 = min(4 × 표 수 + (서로 보냈으면 8), 24)
```

| | 값 | | 값 |
|---|---|---|---|
| 한쪽만 1표 | 4 | 상호 1:1 (2표) | 16 |
| 한쪽만 2표 | 8 | 상호 2:1 (3표) | 20 |
| 한쪽만 3표 | 12 | 상호 2:2 (4표) | **24 (상한)** |

**부가 점수를 곱이 아니라 덧셈으로 둔 이유** — 같은 2표라도 *한 사람이 두 번 보낸 것*과
*서로 한 번씩 보낸 것*은 다른 일이다. 곱으로 두면 표가 0에 가까울 때 상호의 뜻이 사라지고,
표가 많을 때는 상호가 과하게 커진다. 덧셈이면 **상호라는 사실 자체에 붙는 값**이 일정하다.

### 상한이 나이차 벌점보다 낮다 — 이게 규칙이다

`PULL_CAP = 24 < SEAT_W.AGE = 30`. 표를 아무리 몰아줘도 **나이차 10살+ 를 이기지 못한다.**

넘게 두면 한 쌍이 나이차를 통째로 밀어내고 그 테이블만 이상해진다 — ADR-11 에서 겪은 일이다.
서로 좋아하는데 나이차가 큰 쌍은 **마지막 라운드**가 붙여준다. 거기서는 가중치가 아니라
구조가 하고(쌍을 떼어놓지 않는다), 상호 쌍끼리는 나이차를 아예 묻지 않는다.

### 따라오는 것

- `pairWeight(exchanged)` → **`pullScore(votes, mutual)`.** 순수 함수라 테스트가 표를 그대로 박는다
- `BuildInput.strength` → **`votes`.** **단방향 쌍에도 채운다** — 이게 이 결정의 전부다.
  예전에는 상호 쌍에만 있어서 단방향의 표 수를 알 방법 자체가 없었다
- `pairs()` 가 쌍마다 오간 표를 합산해 돌려준다. `mutual` 정렬 기준도 그 값이다 (ADR-25 그대로)
- 시드 단계(①)는 **여전히 상호 쌍만** 앉힌다. 단방향은 상대가 고른 게 아니라서
  강제로 붙일 근거가 없다 — 점수로만 끌어당긴다

### 대가

**옛 실측치가 무효가 된다.** `SEATING.md` 의 *"상호 매칭 동석률 무작위 14% → 콕 우선 배치 57%"*
는 두 칸이던 시절의 값이다. 다시 재지 않았다 — 지키려는 불변식(성비 0 · 미배정 0 ·
나이차 무작위 대비 절반)은 테스트가 그대로 붙들고 있다.

**매력 투표를 1표로 두면 달라지는 게 거의 없다.** 이 결정이 값을 하는 건 2표 이상인 회차다.
1표 회차에서 짝사랑 표가 자리에 반영되길 원하면 `maxPre` 를 올리는 것이 실제 손잡이다.

### 걸리는 ADR

| | 어떻게 |
|---|---|
| **ADR-11** 마지막 라운드는 구조로 붙인다 | 그대로. 상한이 그 결정의 이유를 계승한다 |
| **ADR-24** 한 사람이 여러 명과 이어진다 | 그대로 |
| **ADR-25** 여러 쌍 중 콕이 많은 쪽 | **일반화됐다** — 상호끼리의 비교가 모든 쌍으로 넓어졌다 |
| **ADR-34** 매력 투표는 첫 자리의 재료 | 그대로. 그 재료를 **더 잘게** 읽는다 |
| **슬라이스 28** 자리 배정 함께 점수 (보류) | 이 결정이 그 절반을 앞당겼다. 남은 건 둘째 라운드부터의 새 알고리즘 |

## ADR-41 자리에서 빠지는 사람은 `나감` 하나로 정한다

**결정 (2026-08-24)** — 배정 시트의 `이번 라운드에서 뺄 사람` 목록을 걷어낸다.
자리에서 빠지는 건 **참석 상태가 `나감` 인 사람뿐**이고, 그건 **서버가 읽는다**.
요청이 나르는 값은 테이블 수와 커플 자리 여부뿐이다 (`SeatingInput`).

**왜** — 같은 사실을 두 곳에서 말하고 있었다. 가는 사람은 문 앞에서 이미 찍히는데
(ADR-33), 배정할 때 그 목록을 **손으로 한 번 더** 골랐다. 둘이 어긋나면 나중 것이 이긴다 —
그리고 나중 것은 사람이 매번 다시 만드는 쪽이라 틀리기 쉽다.

`뺄 사람` 은 슬라이스 11 후속으로 붙었고, ADR-39 에서 **참석 상태가 그 목록을 미리 채우게**
했다. 채워주는 순간 그 목록은 이미 상태의 사본이었다 — **사본을 지울 때가 된 것이다.**

### `미도착` 은 앉힌다 — 그게 이 결정의 절반이다

ADR-39 의 기본값은 **아직 안 온 사람 전부**를 빼는 것이었다. 그 자리를 좁힌다.

**안 찍은 사람과 안 온 사람이 같은 값이기 때문이다** (ADR-33 — `미도착` 은 저장된 값이 아니라
`없음` 의 다른 이름이다). 운영자가 문 앞에서 바쁘면 도착한 사람도 한동안 `미도착` 이다.
그 사람을 빼면 **온 사람이 조용히 자리를 잃는다.**

| | 빈 자리 | 없는 자리 |
|---|---|---|
| 언제 생기나 | 안 온 사람을 앉혔을 때 | 온 사람을 뺐을 때 |
| 운영자가 아나 | **보인다** — 그 테이블이 비어 있다 | **안 보인다** — 명단을 다시 세야 안다 |
| 고치는 법 | `자리 비우기` 한 번 | 그 사람이 물어봐야 안다 |

둘 중 하나를 고른다면 **보이는 쪽**이다. 늦게 온 사람에게는 이미 자리가 있고,
`앉히기` 로 붙일 일도 없다.

### 화면은 고르는 자리에서 **말해주는 자리**로 바뀐다

접혀 있던 목록 대신 한 줄이 선다 — `1명 배정 · 나감 1명 제외`.
아래 `테이블당 N명` 이 이 인원으로 계산되므로 **왜 줄었는지 같은 화면에서 말해야 한다.**
말하지 않으면 운영자가 자기 눈을 의심하고 명단을 다시 센다.

**나간 사람이 없으면 그 줄은 `N명 배정` 이다.** `나감 0명` 이라고 쓰지 않는다 —
아무 일도 없는 라운드에 없는 일을 알릴 이유가 없다.

되돌릴 곳은 **한 곳뿐이다** — 참가자 탭의 상태 칩. 되돌리면 다음 배정에 다시 들어온다.
`나감` 이 사람에게 붙는 낙인이 되면 안 되고, 잠깐 나갔다 오는 사람이 실제로 있다.

### 걷어낸 것과 남긴 것

| | |
|---|---|
| **걷어냄** | 시트의 뺄 사람 목록 · `SeatingInput.exclude` · `makeSeating(…, exclude)` · 문구 다섯 |
| **남김** | `자리 비우기`(`unseat`) — **이미 짜인 라운드**를 고치는 길이다. 짜는 때와 고치는 때는 다르다 |
| **안 바뀜** | `buildSeating` 은 그대로 순수 함수다. 명단이 짧아질 뿐이다 (`SEATING.md`) |

**서버가 거른다.** 화면이 목록을 보내면 그 목록은 **열어둔 시트만큼 낡는다** —
시트를 열어놓고 문 앞을 보다가 배정을 누르면, 그 사이에 나간 사람이 그대로 앉는다.

### 대가

**FLOWS.md 가 경고하던 것을 안고 간다** — *"사람에게 붙는 플래그는 시간이 지나면 틀리고,
틀린 상태는 다음 라운드에서 사람을 조용히 빠뜨린다."* 그 경고는 참석 상태가 없던 때의 것이고,
ADR-33 이 상태를 만든 순간 이미 절반은 지나간 자리다. 남은 절반은 이렇게 막는다 —
**빠지는 조건은 운영자가 명시적으로 누른 `나감` 하나**이고(안 누른 것은 빠지지 않는다),
**빠진 수는 배정 전에 숫자로 보이며**, 되돌리는 데 한 번 누르면 된다.

## ADR-42 연락처는 참가자에게 나가지 않는다 — **ADR-19 를 되돌리고 ADR-37 을 걷어낸다**

**바뀐 것** — 발표 후 서로 콕 찌른 쌍에게 나가는 것은 **실명 하나**다.
전화번호와 인스타는 **운영자만 본다.** 매칭된 상대에게도 안 나간다.

| | ADR-19 | ADR-37 | **여기** |
|---|---|---|---|
| 매칭 상대에게 | 실명·전화·인스타 자동 | 본인이 고른 만큼 | **실명만** |
| 인스타의 쓰임 | 매칭 상대에게 열리는 연락 수단 | 같음 | **운영자 확인용** |
| 참가자가 고를 것 | 없음 | 칸 둘 | **없음** |

### 왜 되돌렸나

ADR-19 는 *"이 앱이 없애려는 건 거절당하는 경험이지 연락 그 자체가 아니다"* 라고 적고
연락처를 열었다. 그 판단이 틀렸다는 게 아니라, **앱이 그 일을 할 필요가 없다는 것**이다.

> 서로 마음이 맞았다는 것과 **그게 누구인지**를 알려주면 앱의 일은 끝난다.
> 두 사람은 **같은 방에 있다.** 이름을 알고 얼굴을 알면 연락은 그 자리에서 직접 한다.
> 앱이 번호를 옮겨주는 건 편의지 필요가 아니었고, 그 편의의 값으로
> **참가자 응답에 전화번호가 실리는 구조**를 계속 지켜야 했다.

ADR-37 은 그 값을 참가자가 조절하게 해서 문제를 풀려 했다. 조건이 셋에서 넷이 됐고,
등록 화면에 칸이 둘 늘었고, 저장 형식과 옛 값 읽기가 생겼다. **문제를 옮겼을 뿐이다** —
새어나갈 수 있는 필드가 있는 한 조건이 몇 개든 지켜야 할 것이 남는다.

### 지금의 방어는 조건이 아니라 **타입**이다

`MatchInfo` 에 `phone`·`instagram` 을 **담을 자리가 없다.** 조건을 지키는 코드가 아니라
값을 담을 곳이 없는 구조라, 되살리려면 타입부터 고쳐야 한다 —
그리고 그건 등록 화면이 한 약속을 바꾸는 일이라 눈에 띈다.

- `MatchInfo.contact` 객체가 사라지고 `realName: string` 한 칸이 됐다
- `ContactShare`·`minShare`·`parseShare`·`writeShare`·`SHARE_KEYS`·`ShareChoice.tsx` 를 걷었다
- `players.contact_share` **칸은 남긴다.** `DROP COLUMN` 은 옛 회차의 표를 건드리는 일이고
  (`CLAUDE.md` 의 `CREATE TABLE IF NOT EXISTS` 함정과 같은 자리), 남은 값은 참·거짓 둘뿐이라
  개인정보도 아니다. **읽지도 쓰지도 않는다**

> **후기 (2.0.0)** — `CREATE TABLE` 에서는 뺐다. **새로 만드는 회차에는 안 생긴다.**
> `DROP COLUMN` 은 여전히 하지 않는다 — 이미 그 칸을 가진 표는 그대로 두고,
> 읽는 코드가 없으니 있든 없든 같다.

### 실명은 왜 남기나

**연락 수단이 아니라 신원이다.** 닉네임만으로는 파티장에서 서로를 못 찾는다 —
`💘 서로 찔렀어요` 를 보고도 그게 누구인지 모르면 앱이 아무 일도 안 한 것이 된다.
연락 카드에서도 `연락처` 라벨 **밖에** 뒀던 이유가 그것이고, 그 구분이 여기서 살아남았다.
한쪽만 찌른 상대에게는 발표 뒤에도 끝까지 나가지 않는다 (ADR-19 의 규칙 그대로).

⚠️ 화면 라벨을 **`연락처` 라고 쓰지 마라.** 그렇게 쓰면 뒤에 뭔가 더 있어야 하는 칸이 되고,
빈 채로 남으면 고장 난 화면으로 읽힌다. `이름` 이라고 쓴다.

그 아래 한 줄은 **다음에 뭘 하면 되는지**만 말한다 — *"더 친해지고 싶다면 인스타를 나눠보세요."*
처음에는 `연락처는 서로에게 보이지 않아요` 라고 **없는 것을 설명**했는데 뺐다.
앱이 안 하는 일을 굳이 알릴 이유가 없고, 그 문장이 있으면 **못 받은 것**이 먼저 읽힌다.
나누는 건 두 사람이지 앱이 아니라서 `인스타가 열려요` 처럼 쓰지 않는다 —
그건 화면 어디에도 없는 것을 찾아 헤매게 만든다.

### 받을 때 한 약속을 먼저 고쳤다

등록 화면(`REGISTER.contactNote`)이 **좁아진 쪽으로** 바뀌었다.

> 전화번호와 인스타는 운영자만 봐요. 다른 참가자에게는 보이지 않아요.
> 발표 때 서로 콕 찌른 상대에게는 이름만 보여요.

**좁히는 변경이라 이미 등록한 사람에게 안전하다** — 더 주겠다고 한 적은 있어도
덜 주는 것으로 약속을 어기지는 않는다. 반대 방향이었다면 문구가 먼저였어야 한다.

인스타 칸 아래에는 **왜 받는지** 한 줄을 붙였다(`REGISTER.instaWhy` — *"운영자가 참가자를
확인할 때만 써요"*). 이 줄이 없으면 참가자가 `연락 수단으로 쓰이겠구나` 로 읽는데,
그건 이제 사실이 아니다. **등록 폼과 내 정보 수정 폼이 같은 말을 쓴다.**

### 남는 것

- **매칭된 두 사람이 그날 인사를 못 하면 앱이 해줄 게 없다.** 그게 이 결정의 값이다 —
  ADR-19 이전의 원래 설계이고, 새 구멍은 아니다
- 인스타는 여전히 **필수**다. 쓰임이 바뀌었을 뿐 운영자에게는 그대로 필요하다
- `players.contact_share` 에 남은 값은 아무 일도 하지 않는다. 다음 사람이 보고
  *아직 쓰이나* 하지 않도록 `SCHEMA` 주석에 적어 뒀다

## ADR-43 커플 발표를 예약한다 — **파티가 시작된 뒤에만 울린다**

**바뀐 것** 둘.

1. **커플 발표에 예약 시각이 생겼다** (`revealAt`, 기본 파티 **3시간 뒤**)
2. **알림이 라운드마다 따로가 됐다** (`preNotify` · `pokeNotify`)

### 1. 발표 예약 — ADR-14 를 어디까지 지켰나

ADR-14 는 마감·파티·발표를 예약하지 않기로 했다. 막으려던 건 **현장이 시계를 따라가는 것**이다.

> 사람이 덜 왔는데 마감되고, 이야기가 무르익는 중에 발표가 뜬다.

그중 **가장 나쁜 건 아무도 안 온 자리에서 발표가 뜨는 것**이다. 콕이 열린 적도 없으니
매칭 0으로 파티가 끝난 것이 된다. 그래서 예약을 붙이되 조건 하나를 걸었다.

```ts
if (phase === "party" && schedule.revealAt && !fired.done && now >= schedule.revealAt) return "done";
//  ^^^^^^^^^^^^^^^^^ 이 한 줄이 ADR-14 와의 약속이다
```

**운영자가 `파티 시작` 을 안 눌렀으면 시각이 지나도 아무 일이 없다.** 시계가 혼자 파티를
끝내지 못한다. 남은 걱정 — *이야기가 무르익는 중에 발표가 뜬다* — 은 **미룰 수 있게** 풀었다.

| | |
|---|---|
| 먼저 발표하고 싶다 | 그냥 누른다. `fired.done` 이 서서 예약은 울리지 않는다 |
| 파티가 길어졌다 | 설정 탭에서 **미룬다**. 발표 시각만 파티 시작 뒤에도 열려 있다 |
| 잘못 발표됐다 | **되돌릴 수 없다** (ADR-50). 누르기 전에 확인창이 무엇이 열리는지 보여준다 |

**일정 잠금에 예외가 하나 더 생겼다.** ADR-39 가 `voteEndAt` 에서 겪은 것과 같은 자리다 —
파티가 늦어지면 미뤄야 하는데 파티 시작에 잠그면 손쓸 방법이 없다.
`schedLocked` 에서 `revealAt` 만 `fired.done` 을 본다.

**참가자 카운트다운에는 넣지 않았다.** 시각이 생겼으니 셀 수는 있지만, 파티 중에
`발표까지 1시간 12분` 이 보이면 남은 시간을 재며 서두르게 된다 —
이 앱이 만들려는 자리가 아니다. 카운트다운은 그대로 **다음에 일어날 일**만 센다.

### 2. 알림을 라운드마다 갈랐다

되돌리기는 이미 라운드마다 따로였는데(`allowUndoPre`·`allowUndo`) 알림만 하나였다.
**둘은 성격이 다르다.**

> 파티 콕은 **몇 시간** 안에 오간다. 매력 투표는 **며칠**에 걸쳐 쌓인다 —
> 그동안 숫자가 실시간으로 보이면 **파티 전에 이미 순위가 생긴다.**
> 만나기도 전에 자기 자리를 알고 오는 사람이 생기는 것이다.

⚠️ **끄는 건 화면에서 감추는 일이 아니다.** `receivedCount` 에서 빠져야 한다 —
그 숫자 하나가 곧 "지금까지 몇 명이 나를 골랐나" 다 (ADR-34).
`visibleReceived()` 가 **켜진 라운드만** 더한다. 총합을 그대로 내려보내면
매력 투표 알림을 끈 회차에서 **파티가 시작되는 순간 그때까지 쌓인 표가 얹힌다.**

발표 뒤에는 전부 센다 — 그때는 매칭까지 열리므로 감출 것이 없다.
그리고 알림 둘 다 `rulesLocked` 에 든다. 파티 도중에 켜면 쌓인 것이 한꺼번에
나타나서 "받은 콕은 한 번에 하나씩" 이 통째로 깨진다 (ADR-35).

### 굳는 규칙 다섯을 위저드에 모았다

`allowSameGender`(콕 대상)만 위저드에 없고 설정 탭에만 있었다. **그게 문제였다** —
이 다섯은 콕이 오가기 시작하면 함께 굳으므로(ADR-35) **만들 때가 사실상 유일한 기회**다.
만든 뒤에 설정 탭을 따로 찾아 들어가야 한다는 건, 못 찾으면 영영 못 고친다는 뜻이다.

두 화면의 **순서도 같게** 맞췄다 — 대상 → 되돌리기(매력 투표·콕) → 알림(매력 투표·콕).
다르면 운영자가 매번 다시 찾는다.

그리고 `validConfig` 가 `allowSameGender` 를 안 보고 있었다. `"false"` 라는 **글자**가
들어오면 `=== false` 가 아니라서 조용히 `모두에게` 가 된다 — 운영자는 좁힌 줄 알고 파티를 연다.
**접지 말고 거절한다.** 굳는 규칙 다섯이 다 그 검사에 있어야 하는 이유다.

### 후기 — 위저드 세 스텝을 **성격으로** 나눴다 (2026-08-24)

칸이 늘면서 2스텝이 `파티 일시 · 장소 · 투표 시작 · 투표 마감 · 발표` 로 뒤섞였다.
성격으로 갈랐다.

| 스텝 | 성격 |
|---|---|
| 1 | **기본 정보** — 회차 이름 · 장소 |
| 2 | **예약** — 매력 투표 시작 → 마감 → 파티 시작 → 커플 발표 (**시간 순**) |
| 3 | **콕 설정** — 횟수 둘 · 대상 · 되돌리기 둘 · 알림 둘 |

**장소가 1스텝으로 갔다.** 시각이 아닌 유일한 칸이 시각 넷 사이에 끼면 그 목록이
시간 순으로 안 읽힌다. 머리글도 `2/3 · 예약` 으로 성격을 말한다 —
참가자 등록(`REGISTER.steps`)과 같은 꼴이다.

⚠️ **넷 중 파티 시작만 예약이 아니다** (ADR-14). 그래서 `manualNote` 를 목록 아래에서
**그 칸으로** 옮겼다(`partyHint`). 아래에 떠 있으면 어느 칸 이야기인지 알 수 없고,
넷 다 저절로 넘어가는 줄로 읽으면 운영자가 아무것도 안 눌러서 **파티가 영영 안 열린다.**

`파티 일시` 라는 라벨도 `파티 시작` 으로 바꿨다 — 나머지 셋과 나란히 서는 자리라
혼자 다른 꼴이면 같은 종류로 안 읽힌다.

**화면 순서와 계산 순서는 다른 이야기다.** `partyAt` 은 셋째 자리에 있어도 여전히 기준점이고,
기본값은 거기서 거꾸로 잰다 (`changeParty`).

### 설정 탭도 같은 묶음으로 접었다

위저드를 나누고 나니 설정 탭이 한 두루마리로 남았다 — 칸이 스무 개 가까이라 무엇이 어디
있는지 못 찾는다. **같은 이름·같은 순서**로 접었다: 기본 정보 · 예약 · 콕 설정, 그리고 `삭제`.

`삭제` 는 만들 때 없는 일이라 짝이 없다. **다른 묶음에 끼워 넣지 않았다** —
되돌릴 수 없는 버튼은 다른 걸 고치다 손이 닿는 자리에 두지 않는다.

⚠️ **묶음은 라우트가 아니라 화면 상태다.** 여는 게 아니라 거르는 것이라 뒤로 가기로 닫을 것이
없다 (`CLAUDE.md` 5번은 모달·시트 이야기다). 폼 하나를 나눠 보는 것뿐이라 입력값은 전부
살아 있고 `적용` 은 세 묶음을 한꺼번에 저장한다.

**그래서 접힌 자리의 변경이 안 보이는 게 유일한 위험이다.** 확인창과 알약의 점을
**한 곳에서**(`pending()`) 만든다 — 따로 세면 점은 켜졌는데 확인창은 비어 있는 일이 생긴다.

### 새 칸을 더할 때 함께 보는 곳

발표 예약처럼 **전환을 거는** 값은 두 곳이 짝이다.

- `dueTransition()` — 판정. 요청이 들어올 때 본다
- `nextDue()` — 알람. `storage.setAlarm` 이 걸 시각을 준다

**조건이 같아야 한다.** `nextDue` 를 빼면 아무도 안 두드릴 때 안 울리고,
`dueTransition` 을 빼면 울려도 아무 일이 없다.

### 남는 것

- **`revealAt` 은 필수다.** "예약 안 함" 을 만들지 않았다 — 안 누르면 안 넘어가는 건
  그대로고(파티를 시작해야 울린다), 미루는 길이 있어서 끄고 싶을 이유가 적다.
  정 필요해지면 그때 비울 수 있게 연다
- 회차를 만들 때 **발표가 파티보다 앞이면 거절한다.** 파티가 시작되자마자 끝난다
- 위저드가 서버 기본값에 **빠진 칸이 있으면 코드 기본값으로 메운다.**
  안 그러면 `undefined * HOUR` 가 `NaN` 이 되어 시각 칸이 빈 채로 뜬다 —
  새 칸이 붙은 직후에 실제로 만나는 상황이다

## ADR-44 세션은 탭마다 갈린다 — 링크가 사람마다 달라도 쿠키가 하나면 소용없다

**문제** — 개인 링크(ADR-32)로 사람마다 문을 나눴는데, **한 브라우저에서는 여전히 참가자가
하나뿐이었다.** 두 번째 탭에서 다른 사람의 링크를 열면 주소창이 `/e/<코드>` 로 바뀌면서
**첫 번째 탭의 사람 화면이 떴다.**

원인이 둘이었고, 둘 다 고쳐야 했다.

**① 쿠키는 탭이 아니라 브라우저 단위다.** `tp_play` 하나에 마지막으로 들어온 사람이 담긴다.

**② `/j/:id/:token` 이 토큰을 보기도 전에 답을 정하고 있었다.**

```ts
// 옛 Join.tsx — 첫 줄이 하는 일
api<ParticipantState>(`/me?event=${id}`)          // ← "이 브라우저에 세션이 있나"
  .then((state) => navigate(`/e/${state.event.code}`, { replace: true }))
```

토큰이 유효하든 말든 공용 쿠키가 "너는 A다" 라고 답하면 그대로 넘어갔다.
**링크를 아무리 잘 나눠도, 판정을 쿠키에게 물으면 나눈 의미가 사라진다.**

**결정 — 링크는 지목, 쿠키는 증명. 그리고 쿠키를 사람마다 따로 둔다.**

```
서버   Set-Cookie: tp_play_<이름표>=…   (HttpOnly) + 이름표 없는 tp_play
탭     sessionStorage["tp.ref"] = 이름표    ← sessionStorage 는 탭마다 별개다
요청   x-tp-ref: <이름표>  →  서버가 tp_play_<이름표> 를 읽는다
소켓   /ws/:code?ref=<이름표>             ← 브라우저 WS 는 헤더를 못 싣는다
```

**이름표는 비밀이 아니다.** 브라우저가 든 여러 쿠키 중 어느 것을 읽을지 고르는 값일 뿐이라,
훔쳐도 그 HttpOnly 쿠키가 없으면 아무 문도 열리지 않는다. 그래서 JS 가 읽는 곳(sessionStorage)에
둬도 되고, 주소나 로그에 실려도 무해하다. **증명은 끝까지 HttpOnly 쿠키 안에 있다.**

그리고 **"이미 등록했나" 는 토큰이 답한다.** 회차 조회(`/events/by-id/:id?t=`)가 이미
그 토큰의 `registered` 를 돌려주고 있었다 — 화면은 그것만 보면 됐다. `/me` 를 부르던 자리를 걷었다.

**따라오는 것**

- 이름표 없는 **기본 쿠키를 함께 심는다.** 없으면 링크를 닫고 앱 주소만 다시 연 참가자가
  로그인을 잃고, 기본값만 있으면 탭이 서로를 덮는다 — 둘 다 필요하다
- 이름표는 쿠키 **이름**에 붙으므로 요청에서 온 값을 그대로 쓰면 `;` 하나로 남의 속성이 붙는다.
  16진수만 통과시키고, 통과 못 한 값은 **이름표 없음**으로 되돌아가 기본 쿠키를 읽을 뿐이다
- 등록(`/register`)은 **들어온 이름표를 그대로 쓴다.** 새로 만들면 이 탭이 방금 만든 세션을
  놓치고 기본 쿠키만 남아 다른 탭을 덮는다
- 회차 DO 는 세션을 모른다. `checkEntry` 는 `EntryOutcome`(이름표 없는 판정)을 돌려주고,
  이름표는 Worker 가 붙인다 — 설계 경계 그대로다

**왜 QA 전용으로 만들지 않았나** — 이 요청은 "QA 에서 탭마다 다른 참가자로 보고 싶다" 에서
시작했다. 게이트를 두면 **연습용이 프로덕션과 다른 코드를 돌리게 되고, 거기서 통과한 것이
프로덕션을 보증하지 못한다.** 게다가 이건 QA 만의 문제가 아니다 — 가족이 폰 하나를 같이 쓰면
현장에서 같은 일이 난다. 그래서 분기 없이 한 코드로 간다.

**대가**

- 쿠키가 사람 수만큼 쌓인다. 실제 참가자는 한둘이고, QA 도 브라우저 한도(도메인당 ~180개)
  근처에 가지 않는다
- **이름표가 없는 탭은 여전히 기본 세션을 읽는다.** 링크를 거치지 않고 앱 주소만 연 탭,
  그리고 `sessionStorage` 가 막힌 사파리 프라이빗 창이 그렇다. 그 탭에는 자기 신원이 없으므로
  이건 못 고치는 게 아니라 **정의상 그렇다**
- 탭 복제(Duplicate tab)로 연 탭은 `sessionStorage` 가 복사돼 같은 참가자다. 의도한 동작이다

## ADR-45 참석 상태를 걷어내고, 뺄 사람은 배정할 때 고른다 — **ADR-33 과 ADR-41 을 되돌린다**

**결정 (2026-08-24)** — 앱은 **누가 왔는지 세지 않는다.** 문 앞에서 세는 건 사람이 한다.
자리에서 빠지는 사람은 **배정할 때 그 라운드에만** 고른다.

| | ADR-33·41 | **여기** |
|---|---|---|
| 참석 상태 | `미도착`·`도착`·`나감` 을 저장 | **없다** |
| 자리에서 빼는 조건 | 저장된 `나감` (서버가 읽음) | 배정 요청의 `exclude` (그 라운드에만) |
| 고르는 순서 | 없음 — 테이블 수만 | **뺄 사람 → 테이블 수**, 두 걸음 |

### 왜 되돌렸나

**`FLOWS.md` 의 경고가 결국 맞았다.**

> *사람에게 붙는 플래그는 시간이 지나면 틀리고, 틀린 상태는 다음 라운드에서 사람을 조용히 빠뜨린다.*

ADR-41 은 그 경고를 알면서 안고 갔다 — "명시적으로 누른 것 하나로 좁혔으니 괜찮다" 는 판단이었다.
좁히는 것으로는 부족했다. **문제는 정확도가 아니라 두 곳에 진실이 생기는 것**이다.
운영자는 문 앞에서 사람을 맞으면서 화면도 눌러야 했고, 둘이 어긋나는 순간
**화면의 값과 눈앞의 사람 중 무엇을 믿을지**가 매번 새 판단이 됐다.

**앱이 모르는 것을 아는 척하지 않는다.** 누가 와 있는지는 운영자가 눈으로 안다.
그 앎을 앱에 옮겨 적게 만드는 대신, **필요한 그 순간에 한 번 묻는다** — 자리를 짤 때.

### 뺄 사람은 테이블 수보다 **먼저** 온다

두 걸음의 순서가 이 결정의 절반이다. 둘째 걸음의 `테이블당 N명` 이 첫 걸음에서 남은
인원으로 계산되므로, 순서가 뒤집히면 **운영자가 방금 읽은 숫자가 곧바로 틀린 것이 된다.**

걸음은 주소가 정한다 (`/seats/:mode` → `/seats/:mode/tables`). 뒤로 가기가 곧 `이전` 이고
한 번 더 누르면 닫힌다 — 시트는 라우트다 (규칙 5).

### 저장하지 않는 것이 요점이다

`exclude` 는 **요청에만 있고 어디에도 쓰이지 않는다.** 다음 배정은 언제나 전원으로 시작한다.

- 노쇼는 다음 라운드에 나타날 수 있고, 온 사람이 잠깐 빠질 수도 있다
- 저장하지 않으므로 **낡을 수가 없다.** ADR-41 이 안고 갔던 위험이 여기서 사라진다
- 시트를 새로 열면 고른 것이 비워진다 — 지난 라운드의 선택이 따라오지 않는다

ADR-41 이 걱정한 것("화면이 보낸 목록은 시트를 열어둔 만큼 낡는다")은 남는다.
다만 그건 **몇 초짜리 낡음**이고, 그 사이 사정은 운영자가 눈앞에서 보고 있다 —
며칠 전에 찍힌 상태가 낡는 것과는 다른 종류다.

### 걷어낸 것과 남긴 것

| | |
|---|---|
| **걷어냄** | `Attendance` 타입 · `HostState.attendance` · `POST /players/:pid/attendance` · `setAttendance` · `leftIds()` · 카드의 상태 배지와 상세의 3단 선택 · `도착 N · 미도착 N` 한 줄 · `HOST_UI.status` |
| **되살림** | `SeatingInput.exclude` · `makeSeating(…, exclude)` · 뺄 사람 고르기 화면 (이번엔 **접힌 목록이 아니라 제 걸음**이다) |
| **남김** | `players.attendance` 칸 — 읽지도 쓰지도 않는다. `DROP COLUMN` 은 옛 회차의 표를 건드리는 일이고, 남은 값은 개인정보도 아니다 (ADR-42 가 `contact_share` 에 한 것과 같다). **2.0.0 에서 `CREATE TABLE` 에서만 뺐다** — 새 회차에는 안 생기고, 옛 표는 그대로다 |
| **안 바뀜** | `buildSeating` 은 그대로 순수 함수다. 명단이 짧아질 뿐이다 (`SEATING.md`) · `자리 비우기`(`unseat`) — **이미 짜인 라운드**를 고치는 길이라 짜는 때와 다른 일이다 |

### 대가

- **운영자가 매 라운드 목록을 다시 고른다.** 그게 이 결정이 산 것이다 — 매번 새로 고르는 값은
  낡지 않는다. 대부분의 라운드는 아무도 안 빼므로 그대로 다음을 누른다
- **누가 왔는지 앱이 모른다.** 현황 탭의 인원 숫자는 등록 기준이지 참석 기준이 아니다.
  파티 당일 "몇 명 왔나" 를 앱에서 볼 수 없다 — 알고 고른 것이고, 다시 필요해지면
  **저장하지 않는 방식**부터 찾는다

## ADR-46 현황 탭의 순위는 라운드마다 따로 센다 — 왕관 카드를 걷어낸다

**문제** — 운영자 현황 탭의 `🔥 받은 콕 TOP` 이 **매력 투표 표까지 합쳐서** 세고 있었다.
파티에서 한 번도 안 찔린 사람이 며칠 치 매력 투표 표만으로 그 순위 1위에 서 있었다.

합쳐 세던 것은 라운드가 하나뿐이던 시절의 잔재다. ADR-34 가 매력 투표와 콕을 갈라놓은 뒤로
**둘은 쓰임이 다르다** — 매력 투표 표는 **자리의 재료**고(ADR-40), 파티 콕은 **매칭의 재료**다.
운영자가 이 순위를 읽는 목적도 다르다.

| 보는 것 | 무엇에 쓰나 |
|---|---|
| ✨ 매력 투표 TOP | 자리를 짤 때 — 표가 어디로 몰렸나 |
| 🔥 받은 콕 TOP | 파티 중에 — 지금 이 자리에서 누가 오가고 있나 |

합쳐 두면 **뒤쪽을 못 읽는다.** 며칠 치 표가 얹혀 있어서, 파티 30분 만에 콕이 두어 개 오간 것이
숫자에 묻힌다. 앞쪽도 못 읽는다 — 파티가 시작되면 그 순간부터 표와 콕이 섞여서
"매력 투표는 이렇게 끝났다" 를 다시 볼 방법이 없다.

**결정**

`HostState.received` 를 `Record<라운드, Record<참가자, 수>>` 로 **가른다.** 서버가 합계를 만들지 않는다.

```ts
/** ⚠️ 다시 합치지 마라. 합계가 필요하면 쓰는 쪽에서 더한다 */
received: Record<PokeRound, Record<string, number>>;
```

현황 탭은 같은 `Ranking` 을 **두 번** 그린다. 제목·빈 문구만 다르다.

**그리고 순서가 단계를 따른다 — 지금 쓰이는 것이 위로 온다.**

| 단계 | 위에서 아래로 |
|---|---|
| 등록 · 매력 투표 | ✨ 매력 투표 TOP 5 **하나뿐** |
| 파티 · 발표 | 💘 상호 매칭 → 🔥 받은 콕 TOP 5 → ✨ 매력 투표 TOP 5 |

파티 전에 매칭과 콕 TOP 을 **그리지 않는다.** 둘 다 그전에는 **있을 수가 없다** (ADR-34) —
빈 카드를 세워두면 자리만 차지하고, 운영자는 매번 그게 정상인지 한 번 더 확인한다.
그때 볼 것은 표가 어디로 몰렸나 하나뿐이고, 그건 자리를 짜는 재료다 (ADR-40).

파티가 시작되면 **매칭이 맨 위다** — 자리를 붙일지 판단하는 게 그 시점의 일이라서.
매력 투표는 끝난 라운드라 기록으로 맨 아래에 남는다. 지우지는 않는다 — 자리를 짜다 되돌아볼 일이 있다.

`done` 도 파티와 같다. 발표가 끝나도 그 결과를 계속 본다.

**왕관 카드(`👑 사전 투표 1위`)는 걷어낸다.** 남녀 1위를 크게 보여주던 카드인데,
매력 투표가 자리의 재료가 된 뒤로 **1등이라는 사실이 운영에 쓰이지 않는다** —
쓰이는 건 *누가 위쪽인가* 이고 그건 TOP 5 가 이미 말한다. 그 자리를 매력 투표 TOP 5 가 대신한다.
1위만 보여주면 2·3위가 조용히 가려지는데, 자리를 짤 때 필요한 건 그 2·3위다.

**따라오는 것**

- **바 길이는 각 순위 안의 1위 대비다.** 두 순위를 한 척도로 맞추면 파티 초반의
  콕 두어 개가 며칠 치 표 옆에서 보이지 않는 선이 된다
- **빈 문구가 라운드마다 다르다** — 매력 투표는 `아직 받은 표가 없어요`, 파티는 `아직 받은 콕이 없어요`.
  매력 투표 자리에서 `콕` 이라고 하면 운영자가 읽는 것과 참가자가 겪는 것이 갈린다 (ADR-34).
  참가자는 그 단계에서 콕을 찌른 적이 없다
- `rankNote` 에서 `전체 라운드 합계` 를 뺐다. 이제 제목이 어느 라운드인지 말한다
- `prevoteRank`(왕관이 쓰던 남녀 1위 목록)를 응답에서 지웠다. 죽은 값을 내려보내지 않는다

~~**참가자에게 가는 것은 그대로다.**~~ **뒤집었다 — 아래 후기.** 당시에는 참가자가 보는
`receivedCount` 를 알림이 켜진 라운드만 합친 **한 수**로 두었다(ADR-43).
거기서 라운드를 가르면 *어느 단계에서 받았나* 가 드러나 발신자가 좁혀진다고 봤다.

**대가** — 순위가 둘이라 현황 탭이 길어진다. 매칭 쌍이 많은 회차에서는 스크롤이 늘지만,
단계 컨트롤은 맨 위 그대로라 가장 자주 하는 일은 여전히 첫 화면에 있다.

#### 후기 — 참가자 쪽도 갈랐다 (2026-08-24)

위에서 "참가자에게 가는 것은 그대로다" 라고 적은 것을 뒤집는다. `MyPokeState.receivedCount`
한 수를 `received: Record<PokeRound, number>` 로 가른다.

**합쳐 두니 소식 줄이 거짓말을 했다.** 매력 투표 중에 표를 받았는데 화면은
`누군가 콕! 찔렀어요` 라고 했다 — 그 단계에서 **참가자는 콕을 찌른 적이 없다.**
줄마다 라운드를 모르니 목록 전체를 한 이름으로 부를 수밖에 없었고, 어느 이름을 골라도
절반이 틀리는 자리가 남았다. `copy.ts` 가 스스로 "매력 투표에서 '콕' 이라는 말을 쓰지 마라"
고 적어둔 규칙을, 데이터 모양 때문에 지킬 수가 없었다.

**대가는 그대로 값이다.** 어느 줄이 어느 라운드에서 왔는지가 드러난다. 그러면
*그 단계에 누가 있었나* 와 맞춰 발신자를 좁힐 수 있다 — 시각을 붙이지 않는 규칙과 같은 가족이다.
다만 **좁혀지는 폭이 다르다**: 시각은 몇 분으로 좁히고, 라운드는 *며칠짜리 매력 투표*와
*몇 시간짜리 파티* 둘 중 하나로만 가른다. 파티 라운드가 참가자를 온 사람들로 좁히긴 하지만,
그건 참가자가 그 자리에 있어서 이미 아는 사실이다.

**바꾸지 않은 것** — 꺼둔 라운드는 여전히 **0으로 나간다** (ADR-43). 가른 것은 켜진 수를
어떻게 담느냐이지, 무엇을 보여줄지가 아니다. 발표 뒤에 전부 세는 것도 그대로다.

**여전히 하지 마라** — 받은 것에 **시각**을 붙이는 일. 그건 이 결정과 다르다.
라운드는 두 칸이고 시각은 분 단위다.

## ADR-47 내 정보 탭에서 연락처를 걷어내고, 가리기 토글을 없앤다

**문제** — `내 정보` 탭이 전화번호와 인스타를 줄로 보여주고, 그 아래에 `다시 가리기` 토글이 있었다.
토글은 슬라이스 16 시절의 것이다. 그때는 **매칭되면 상대에게 연락처가 열렸고**(ADR-19),
파티장에서 어깨너머로 보일 값이라 기본으로 가려뒀다.

ADR-42 가 그 쓰임을 없앴다. 연락처는 이제 **운영자만 본다** — 매칭된 상대에게도 실명까지다.
그러자 이 탭의 두 줄은 *누구에게도 나가지 않는 값을 나에게만 되보여주는 것*이 됐다.

**결정 하나 — 두 줄을 걷는다.**

이 탭이 답하는 질문은 하나다: **내가 낸 것이 무엇인가.** 두 값 다 그 답이 아니다.

| 값 | 왜 여기 없나 |
|---|---|
| 전화번호 | **참가자가 낸 값이 아니다.** 초대 명단에서 왔고 참가자는 치지도 않는다 (ADR-32) |
| 인스타 | 받는 이유가 **운영자 확인 하나**다 (ADR-42). 되보여줄 자리가 아니다 |

**실명은 남는다** — 내가 적은 값이고, 발표 때 매칭된 상대에게 나가는 것도 이것이다.
가릴 이유가 없어졌으므로 **늘 보인다.**

**인스타는 고치는 칸으로만 남는다.** 칸까지 없애면 오타를 낸 사람이 영영 못 고치고,
그 오타는 운영자가 사람을 확인할 때 그대로 걸린다. **읽기 화면에는 없고 폼에는 있다** —
같은 값이지만 하는 일이 다르다.

**결정 둘 — 번호는 응답에서 뺀다.**

화면에서만 지우면 개발자 도구에 그대로 남는다. `ParticipantState.me` 를 `Player` 에서
`MyProfile`(`Omit<Player, "phone">`)로 좁히고, `toPublic` 과 같은 규율의 `toMe()` 를 통과시킨다 —
**빼는 게 아니라 고른다.** `Player` 에 칸이 하나 늘면 `toMe` 가 컴파일에서 걸리고,
그때 하는 일은 한 줄 더 적는 게 아니라 *이 값이 본인에게 가도 되나* 를 정하는 것이다.

조회(`GET /me`)와 수정(`PUT /me`) **둘 다** 좁혔다. 수정 응답도 참가자에게 그대로 간다.

**인스타는 응답에 남는다.** 고치는 폼이 그 값을 칸에 다시 채워야 한다 —
없으면 폼을 열 때마다 빈 칸이고, 저장하면 멀쩡하던 값이 지워진다.

**결정 셋 — 가리기 토글을 없앤다.**

가릴 값이 사라졌는데 토글만 남으면 **아무 일도 안 하면서 "여기 감춘 게 있다" 고 말한다.**
문구 넷(`hidden`·`show`·`hide`·`hideNote`)과 `phoneFixed` 를 함께 걷었다 —
번호 칸이 없으니 *왜 못 고치는지* 를 말할 자리도 없다. 없는 칸을 가리키는 줄이 된다.

⚠️ **참가자 탭의 어깨너머 가리기(`ROSTER.cover`·`uncover`, 슬라이스 16)는 다른 기능이다.**
그건 콕 버튼을 덮어 *내가 누구를 고르는지* 를 가린다 — 가릴 것이 그대로 있으므로 그대로 뒀다.
이름이 비슷해 함께 걷기 쉬우니 조심할 것.

**따라오는 것**

- `ME.labels.phone`·`labels.instagram` 은 **남는다** — 운영자 참가자 탭이 쓴다.
  걷은 건 참가자 쪽 화면이지 라벨이 아니다
- 전화번호를 못 고친다는 규칙(ADR-15)은 그대로다. **말할 자리가 없어졌을 뿐이다** —
  고칠 칸도 없고 보여줄 값도 없어서, 참가자가 그 규칙을 마주칠 일 자체가 사라졌다
- "번호가 안 바뀌었다" 를 참가자 응답으로는 더 이상 확인할 수 없다.
  규칙 테스트는 **운영자 상태**에서 본다 — 번호를 볼 수 있는 유일한 자리다 (ADR-42)

**대가** — 참가자가 자기 번호를 앱에서 확인할 수 없다. 초대 링크를 받은 본인의 번호라
모르는 값이 아니고, 다르다고 느끼면 운영자에게 묻는 게 맞는 경로다 — 명단을 고치는 것도 운영자다.

## ADR-48 소식 칸은 위가 늘 최신이다 — 콕에 **시각 없이** 차례를 준다

**문제** — 홈 탭 `지금까지의 소식` 에서 방금 받은 콕이 **며칠 전 단계 알림 아래**에 깔렸다.

```
04:26  파티가 시작됐어요
04:23  매력 투표가 시작됐어요
  —    누군가 콕! 찔렀어요      ← 파티 중에 받은 것인데 맨 아래
```

시각이 있는 알림은 처음부터 최신순이었다 (`b.at - a.at`). 문제는 받은 콕이
`at: 0` 으로 들어가 **언제 왔든 항상 맨 아래**였다는 것이다.

**왜 `at: 0` 이었나** — 받은 콕에 시각을 붙이면 *그때 누가 있었는지* 와 맞춰
발신자를 좁힐 수 있다. 익명은 이름을 가리는 것만으로 지켜지지 않는다.
그래서 시각을 아예 안 실었고, 그 대가로 차례도 잃었다.

**결정 — 보여줄 시각과 세울 차례를 가른다.**

`Notice` 에 `order` 를 더한다. 화면에 그리는 것은 여전히 `at` 이고, **콕의 `at` 은 0 그대로다.**

| | `at` (보여줄 시각) | `order` (세울 차례) |
|---|---|---|
| 단계 알림 | `fired.<단계>` | 같은 값 |
| 받은 콕 | **0 — 안 보여준다** | 그 라운드가 열린 순간 `+1` |

`+1` 이라 같은 라운드의 시작 알림 **바로 위**에 선다. 그래서:

```
  —    누군가 콕! 찔렀어요       ← 파티 콕
  —    누군가 콕! 찔렀어요
04:26  파티가 시작됐어요
  —    누군가 나에게 투표했어요   ← 매력 투표 표
04:23  매력 투표가 시작됐어요
```

**위가 늘 최신이다.** 그리고 콕에는 여전히 시각이 없다.

**왜 진짜 도착 시각을 쓰지 않았나**

`order` 에 실제 도착 시각을 넣으면 정확해진다. 그리고 **그 순간 시각을 보여준 것과 같아진다** —
콕 카드가 `04:23` 과 `04:26` 사이에 서면, 보여주지 않아도 *그 3분 사이에 왔다* 를 읽어낼 수 있다.
자리가 곧 시각이다. 서버가 콕 하나하나의 시각을 안 보내는 것이 그 방어이고, 그대로 둔다.

**라운드까지가 우리가 말하는 전부다.** 그건 이미 열려 있다 (ADR-46 후기) —
줄마다 `누군가 나에게 투표했어요` / `콕! 찔렀어요` 로 달리 불리므로 라운드는 화면에 이미 있다.
차례를 라운드로 잡는 것은 **새로 여는 것이 없다.**

**따라오는 것**

- `order` 를 화면에 그리지 마라. 그리는 값은 `at` 이고 콕의 `at` 은 0 이다
- 배너(`bannerOf`)는 그대로 `at` 을 본다 — 콕은 `bannerable: false` 라 영향이 없다
- **단계 알림 사이에 시각 있는 알림이 늘어나면 이 결정을 다시 봐야 한다.**
  슬라이스 14(운영자 공지)가 파티 중에 여러 번 울리면 콕이 서는 칸이 그만큼 좁아지고,
  좁아진 칸은 다시 시각에 가까워진다. 그때는 **콕을 라운드 묶음으로 모으는 쪽**이 맞다

**대가** — 같은 라운드 안에서는 콕끼리 차례가 없다. 받은 순서대로 쌓일 뿐이고
그중 어느 것이 더 최근인지는 말하지 않는다. 말할 수 있는 값을 안 가지고 있고,
가지려면 시각을 실어야 한다. **그건 이 결정이 지키려는 것 자체다.**

## ADR-49 발행된 자리는 **잠겨 있다** — 최신 라운드만, `수정하기` 를 눌러야 열린다

**문제 셋이 한 화면에 있었다.**

1. **지난 라운드도 고칠 수 있었다.** 3라운드가 진행 중인데 1라운드 카드에서 두 사람을
   맞바꿀 수 있었다. 사람들은 이미 3라운드 자리에 앉아 있어서 **아무 데도 반영되지 않는다** —
   고쳤다는 사실만 남고, 운영자는 바꿨다고 믿는다
2. **늘 열려 있었다.** 이 카드는 대부분 *누가 어디 앉았나* 를 읽으러 여는 자리다.
   그런데 아무 때나 사람을 누르면 골라지고, 한 번 더 누르면 **말없이 바뀐다.**
   파티장에서 한 손에 폰을 들고 스크롤하다 스치기 좋은 크기다
3. **설명이 자리를 다 먹었다.** 안내문 두 줄이 늘 떠 있었고, 둘 다 두 줄로 감겨서
   **테이블보다 넓은 자리**를 차지했다. 정작 보러 온 자리 배치는 그 아래로 밀렸다

**결정 — 문을 만든다.**

라운드 카드 머리줄에 `수정하기` 를 둔다. 누르기 전까지 **자리는 눌러도 아무 일이 없다**(`locked`).
누르면 열리고, `완료` 로 닫는다. 닫을 때 고르던 사람도 함께 놓는다 —
남겨두면 다시 열었을 때 옛 선택이 살아 있어서 엉뚱한 맞교환이 된다.

**그 버튼은 가장 최신 라운드에만 붙는다.** 목록이 최신순이라 맨 위 카드 하나다.
발표 뒤에는 그것도 사라진다 (ADR-28) — 서버도 같은 문을 닫아둔다.

**`완료` 는 저장이 아니다.** 맞바꾸는 순간 이미 서버에 들어가 있다.
그래서 `저장`·`확정` 이라 쓰지 않았다 — 그렇게 쓰면 **누르기 전까지 안 바뀐 줄 안다.**
모아뒀다 한 번에 보내는 쪽도 생각했지만 걷었다: 화면에만 있는 자리가 생기고,
그건 ADR-26 이 막으려던 *화면과 서버가 조용히 어긋나는* 자리 그대로다.
탭을 닫으면 조용히 사라지는 것도 나쁘다.

**설명은 넷에서 하나로.** 고치는 동안에만 서고, 남긴 것은 **눌러서는 알 수 없는 것**뿐이다.

| 걷은 줄 | 왜 |
|---|---|
| `남녀도 바꿀 수 있어요` | 눌러 보면 그대로 된다 |
| `한 명만 옮기는 건 없습니다` | **화면에 그 버튼이 없다** — 없는 기능을 설명하고 있었다 |
| `확인 화면이 뜨지 않으니` | 뒤쪽 절반만 남겼다 (아래) |

남긴 한 줄 — `두 명을 고르면 맞바꿔요 · 바뀐 자리는 본인에게 말해주세요`.
뒤 절반이 중요하다: **참가자에게 알림이 가지 않는다.** 앱이 말해주는 줄 알고 그냥 두면
그 사람은 옛 테이블에 앉아 있다. 사람을 고르면 이 줄이 `pickedOne` 으로 바뀌고
맞바꾼 뒤 다시 돌아온다 — **그 경고를 다시 읽는 자리가 그때**다.

**따라오는 것**

- **자리 이동 확인 수는 머리줄에 그대로 남는다.** 고치는 문이 열려도 사라지지 않는다 —
  지금 사람들이 답하고 있는 라운드가 바로 그 카드다
- 초안(`draft`)은 이 문의 대상이 아니다. 아직 아무에게도 안 나갔고, 그 카드는
  **고치라고 여는 자리**라서 잠글 이유가 없다
- 서버는 그대로다. 발행된 라운드의 `swap`·`seat`·`unseat` 는 원래 열려 있었고
  **이 결정은 화면에서 문을 만든 것**이다. 지난 라운드를 고치는 API 를 막지는 않았다 —
  막으면 발표 뒤 되돌리기 같은 운영 경로가 함께 막힌다

**대가** — 고치려면 한 번 더 눌러야 한다. 그 대신 읽으러 온 사람이 실수로 바꾸지 않고,
카드 위쪽이 설명이 아니라 자리로 채워진다. 자리를 자주 고치는 회차라면
`완료` 를 누르지 않고 계속 열어둘 수 있다 — 문은 카드마다 따로 기억한다.

### 후기 — `자리가 없는 사람` 은 경고가 아니었다

같은 카드에서 **`이 라운드에 자리가 없는 사람`** 이 `--warn`(주황빨강)으로 떠 있었다.
`--warn` 은 잘못된 상태에 쓰는 색이라(테이블당 인원이 모자람, 초대 명단이 빔)
**정상인 것을 고장처럼** 보이게 했다. 이 목록에 서는 사람은 셋 중 하나다 —
발행 뒤에 등록했거나, 배정할 때 뺐거나(ADR-45), 운영자가 자리를 비웠거나. 전부 정상이다.

- **문구** → `아직 앉지 않은 사람`. `없는` 은 없는 것을 세는 말이라 잘못된 상태처럼 읽힌다.
  대부분은 아직 안 앉혔을 뿐이고, 운영자가 할 일은 눌러서 앉히는 것 하나다.
  `이 라운드에` 도 뺐다 — 라운드 카드 안이라 이미 말해져 있다
- **색** → `--accent`. 경고가 아니라 **할 일**이라 바로 아래 칩 버튼과 같은 색으로 묶었다.
  `--dim` 은 너무 조용하다 (앉히지 않으면 그 사람은 서 있게 된다)

**안내문도 한 가지를 더 말한다.** `이름을 누르면 자리에 앉혀요.` 를
`이름을 누르면 성비를 맞춰 앉혀요.` 로 바꿨다 — 운영자가 실제로 물은 것이
*그럼 테이블은 어떻게 고르나* 였다. **테이블은 서버가 고른다** (`SEATING.md`):
그 성별이 가장 적은 테이블, 같으면 인원이 적은 쪽. 고르게 하면 그게 곧 단일 이동이고
테이블 인원이 어긋난다. 옮기려면 앉힌 **뒤에** 맞교환한다.
어느 테이블인지는 앉힌 뒤 토스트(`seatedAt`)가 말한다 — 안내문은 약속하지 않는다.

### 후기 2 — 낱말이 하는 일을 말하지 않고 있었다

운영자 화면을 훑다 나온 것 넷. 앞의 둘은 **덜어냄**, 뒤의 둘은 **정확함**이다.

**현황 탭 머리줄의 `실시간 · 운영자만`·`운영자만` 을 걷었다.** 세 묶음 머리에 같은 말이
세 번 서 있었는데, 이 탭은 통째로 운영자 것이고 숫자는 늘 지금 것이라 **아무것도 가르지 않는 말**이었다.
되붙이지 마라.

**빈 순위가 아래 간격을 벌리고 있었다.** 순위 행을 담는 `stack` 이 자식 없이도 그려져서,
그것도 flex 항목이라 부모의 `gap` 을 한 번 더 먹었다 — 받은 콕이 없는 회차에서
**콕 TOP 아래만 넓어져** 묶음마다 간격이 달랐다. 눈에는 "여기만 뭔가 빠졌나" 로 읽힌다.
⚠️ **빈 `stack` 을 남기지 마라.**

**`링크 복사` → `참가 링크 복사`.** 그냥 `링크` 면 안내문 링크인지 지도인지 회차 주소인지
알 수 없다. 이건 **그 사람만의 참가 링크**고(ADR-32), 잘못 보내면 남의 신원이 된다.
앱이 이 링크를 부르는 이름(`ENTRY.linkOnly`)과 같은 말로 맞췄다.

**`삭제하기` → `내보내기`** (참가자 상세). 지우는 건 데이터가 아니라 **이 파티에서의 자리**고,
그가 보낸 표·콕은 실제로 남는다 (ADR-29). 게다가 `삭제하기` 는 회차 삭제(`DELETE_EVENT`)와
**같은 낱말**이라, 사람 하나를 빼는 일과 회차를 통째로 지우는 일이 구분되지 않았다.
`BTN.delete` 를 그대로 쓰지 말고 `DELETE_PLAYER.btn` 을 쓴다 — 회차 삭제는 여전히 `삭제하기` 다.

## ADR-50 발표는 **되돌릴 수 없다** — 현황 탭의 `발표 되돌리기` 를 걷어낸다

`done` 에서 `party` 로 물리는 버튼이 현황 탭에 있었다. 확인창까지 갖춘 정식 경로였고,
운영 지침(ADR-43 표)에도 *잘못 발표됐다 → 되돌린다* 로 적혀 있었다. **걷어낸다.**

### 왜

**되돌려지지 않는 것을 되돌린다고 말하고 있었다.**

발표가 여는 것은 화면이 아니라 **사실**이다. 서로 콕 찌른 쌍에게 상대의 실명이 나가고,
그걸 읽은 사람은 읽은 채로 남는다. 되돌리기가 하는 일은 *다음에 여는 사람에게만* 감추는 것이라,
누른 순간 참가자는 **본 사람과 못 본 사람**으로 갈린다. 그 뒤에 오는 질문 —
*나는 봤는데 왜 없어졌나* · *쟤는 봤다는데 나는 왜 못 봤나* — 에 앱이 답할 말이 없다.

옛 확인창도 그 사실을 알고 있었다. 세 줄 중 하나가 `이미 본 사람 — 되돌릴 수 없어요` 였다.
**되돌리기 버튼이 스스로 되돌릴 수 없다고 적어둔 것**이, 이 기능이 무엇이었는지 그대로 말한다.

### 대신 무엇이 그 자리를 맡나

**누르기 전**이다. 발표 확인창은 원래부터 무엇이 열리는지 항목으로 보여준다 (규칙 4).
거기 있던 되돌리기 줄을 `발표한 뒤에는 되돌릴 수 없습니다` 로 바꿨다 —
없는 기능을 설명하던 자리가 **마지막 경고**가 됐다.

일찍 눌러 곤란한 경우는 이미 다른 길이 있다. 파티가 길어지면 **발표 시각을 미룬다**
(ADR-43, `revealAt` 은 파티 시작 뒤에도 열려 있다). 시계가 혼자 발표하지도 않는다 —
파티가 시작돼야 예약이 운다.

### 문은 서버가 잠근다

화면에서 버튼만 걷으면 요청은 그대로 통한다. `EventDO.setPhase` 가 `done` 에서 나가는
전환을 거절한다. 운영자 콘솔은 인증을 지나온 자리라 더더욱 — **눌러서 되는 일은 언젠가 눌린다.**

**`done` → `done` 은 통과시킨다.** 두 번 눌린 발표를 실패로 답하면 운영자는 안 된 줄 알고
다시 누른다. 앞으로 가는 전환이 아니라 `fired.done` 은 처음 발표한 시각 그대로 남는다.

### 함께 걷어낸 것

| 걷은 것 | 왜 |
|---|---|
| `NOTICE.unrevealed` (`운영자가 발표를 되돌렸어요`) | 그 일이 일어나지 않는다 |
| 배너의 `warn` 갈래 | 되돌림 알림 하나만 쓰던 색이다 |
| `noticesOf` 의 단계 분기 | `fired.done` 이 섰으면 단계는 언제나 `done` 이다 |

**옛 회차 하나는 남는다** — 이 결정 전에 되돌려둔 회차는 `fired.done` 이 선 채로 파티 진행에
서 있다. 그 화면에 `결과가 발표됐어요` 를 띄우면 참가자 탭에는 아무것도 없으므로,
`noticesOf` 가 `phase` 를 함께 본다. 다시 발표하면(파티 → 발표) 정상으로 돌아온다.

### 대가

**잘못 눌렀을 때 손쓸 방법이 없다.** 이것이 이 결정의 값이고, 그래서 확인창이 남는다.
정말로 결과를 물려야 하는 사고라면 앱이 아니라 사람이 수습할 일이다 —
운영자가 참가자에게 직접 말하는 쪽이, 화면이 조용히 달라져 있는 쪽보다 낫다.
## ADR-51 커플 자리 배정을 걷어낸다 — **ADR-23·28 을 폐기하고, 쌍은 운영자가 붙인다**

ADR-34 가 **보류**로 남겨뒀던 것이다 (`보류한 것` 표: *커플 자리 폐지 — 지금 규칙 그대로 둔다*).
같은 ADR 의 `걸리는 ADR` 표는 이미 *폐기. 매 라운드 재계산이 대신한다* 라고 적어뒀는데,
운영자와 합의가 안 돼 코드를 건드리지 않았다. 그 합의가 됐다.

**왜**

자리 배정 버튼이 둘이었다 — `자리 배정` 과 `💘 커플 자리 배정`.
뒤엣것은 **서로 찌른 쌍을 구조로 붙이는** 전용 라운드였다 (나이차 면제 · 끌림 ×2.5 ·
붙은 쌍은 맞교환 대상에서 제외).

그런데 지금은 **콕이 매 라운드 자리에 들어간다** (ADR-40).

- 첫 배정은 매력 투표 결과가 확률적으로 정한다
- 둘째부터는 오간 콕이 계속 자리에 반영된다

즉 쌍을 모으는 일은 **이미 모든 라운드가 조금씩 하고 있다.**
그것만 하는 라운드를 따로 두면, 운영자는 매번 *"이번이 그 라운드인가"* 를 정해야 하고
그 판단은 앱이 도와줄 수 있는 게 아니다. **버튼은 하나면 된다.**

**대신 짚어준다**

전용 라운드가 하던 일이 사라지는 게 아니라 **운영자의 손으로 옮겨온다.**
그래서 자리 검토 화면이 쌍을 짚어준다 —

| | 뜻 |
|---|---|
| `💘` (`💘×N`) | 짝과 **같은 테이블**이다 |
| `💔` | 짝이 **다른 테이블**에 있다 — 맞교환으로 옮길 수 있다 |
| 없음 | 이 라운드에 자리가 있는 짝이 없다 |

**💔 이 이 화면의 요점이다.** 붙은 것을 확인해 주는 표시는 할 일을 만들지 않는다.
그림만으로 말하지 않는다 — 칩의 아랫줄이 `짝과 함께` · `짝 따로` 로 같은 것을 글자로 준다.
떨어진 쌍은 카드 머리에서 **이름으로도** 말한다 (`⚠️ 떨어진 쌍: 가 ↔ 나`) — 그게 작업 목록이다.

쌍 성적표(`PairReport`)와 짝 표시는 **초안과 발행된 라운드 모두**에서 보인다.
발행 뒤에도 고칠 수 있으므로(슬라이스 11) 거기서도 짚어줘야 한다.

**남긴 것**

- **섞어도 붙어 앉은 쌍은 제자리다** (ADR-23 의 그 규칙). 커플 자리에서만 그랬던 것을
  **모든 라운드로 넓혔다** — 운영자가 손으로 붙여둔 쌍을 섞기가 흩어놓으면
  버튼 하나로 그 손이 헛일이 된다
- **쌍을 떼는 맞교환에는 확인이 붙는다.** 이것도 모든 라운드로 넓혔다.
  막지는 않는다 — 현장 사정은 운영자가 안다. 다만 무엇이 떨어지는지 이름으로 말한다
- 자리 배정을 확정해도 배정은 닫히지 않는다 (ADR-28 의 그 부분). 발표만이 자리를 끝낸다

**걷어낸 것**

- `BuildInput.final` 과 그에 딸린 분기 넷 — 나이차 면제 · `FINAL_MUTUAL_BOOST` ·
  재회 면제의 `!final` 조건 · `optimize` 의 `withPartner` 제외
- `SeatingRound.final` · `SeatingInput.final` · `MySeat.final`
  (**마지막 것은 참가자 응답에 실려 있었다.** 화면에 그리지는 않았지만 개발자 도구에는 보였고,
  *이번이 커플 자리다* 는 곧 *누가 나를 찔렀나* 의 힌트다)
- 문구 `💘 커플 자리 배정` · `finalNote` · `roundTitle` 의 `final` 갈래
- 라우트 `seats/:mode` → `seats/new` (길이 하나뿐이라 파라미터가 뜻을 잃었다)

**DB 의 `seatings.final` 칸은 남긴다.** `DROP COLUMN` 은 옛 회차의 표를 건드리는 일이고,
`NOT NULL DEFAULT 0` 이라 안 적어도 들어간다. `contact_share`·`attendance` 와 같은 자리다.

> **후기 (2.0.0)** — `CREATE TABLE` 에서는 뺐다. **새로 만드는 회차에는 안 생긴다.**
> `DROP COLUMN` 은 여전히 하지 않는다 — 이미 그 칸을 가진 표는 그대로 두고,
> 읽는 코드가 없으니 있든 없든 같다.

**대가 — 나이차가 큰 쌍은 알고리즘이 못 붙인다**

끌림의 상한(24)이 나이차 벌점(30)보다 낮다 (ADR-11). 전용 라운드는 그 벽을 면제로 넘었는데
이제 넘을 방법이 없다. 실측(12남12녀 · 4테이블 · 상호 8쌍)으로 **8쌍 중 6쌍**이 붙고,
**떨어지는 둘은 나이차가 가장 큰 두 쌍**이다 (14살 · 9살). 무작위가 아니라 설명되는 실패다.

나머지 둘은 운영자가 💔 를 보고 맞교환으로 붙인다. 그게 이 ADR 의 거래다 —
**가중치를 올려 자동으로 붙이면 그 테이블의 나이 구성이 통째로 무너진다** (ADR-11 에서 겪었다).
`test/05-seating.test.ts` 의 `서로 찌른 쌍` 이 이 숫자와 그 이유를 함께 지킨다.

## ADR-52 도움말이 회차 설정을 따라가고, **연락처가 열린다고 말하지 않는다**

**발단** — 도움말을 다시 읽다가 발표 칸에서 이 줄을 봤다.

> 서로 콕 찌른 사이만 공개되고, **그때 연락처가 열려요.**

**거짓이다.** 연락처는 매칭된 상대에게도 나가지 않는다 (ADR-42·47).
`MatchInfo` 가 나르는 건 `realName` 하나이고, 그 필드의 주석은 이렇게 적혀 있었다 —
*"연락 수단이 아니다 — 전화·인스타는 여기에도 없다"*. **코드가 아니라고 적어둔 것을
도움말이 그렇다고 말하고 있었다.**

더 나쁜 건 방향이다. 등록 화면은 *인스타는 운영자 확인용* 이라고 말한다 (ADR-42).
같은 앱의 두 화면이 서로 다른 말을 하면 참가자는 어느 쪽도 못 믿고, 그때 잃는 건
번호가 아니라 **번호를 맡길 이유**다.

### 고친 것 넷

**① 연락처 문장을 지웠다.** 대신 무엇이 나가는지를 분명히 적는다 —
`서로 콕 찌른 사람의 이름이 참가자 탭에 함께 보여요. 연락처는 앱이 전하지 않아요 —
그 자리에서 직접 나누세요.` 지우기만 하면 그 자리가 비고, *그럼 어떻게 연락하지* 가
운영자에게 간다. **없다는 것도 답이라 적어야 한다.**

**② 회차 설정 둘을 답에 넣었다.** 되돌리기(`allowUndoPre`·`allowUndo`)와
알림(`preNotify`·`pokeNotify`)은 라운드마다 따로이고 회차마다 다른데, 도움말이 한마디도
안 했다. 특히 알림이 큰데 —

> 끈 라운드는 알림만 없는 게 아니라 **받은 수 자체가 안 내려간다** (`visibleReceived`).
> 화면 어디에도 그 숫자가 없으므로 참가자는 **"아무도 나를 안 골랐다"** 로 읽는다.
> 그건 이 앱이 없애려는 바로 그 경험이다.

그래서 *알림이 안 와요* 가 아니라 ***알려주지 않아요*** 라고 쓴다.

**③ 중복을 걷었다.** 단계 그림과 문답이 거의 같은 문장을 두 번 하고 있었다 —
`프로필을 보고 마음이 가는 사람에게 투표해요` 와 `만나기 전에, 프로필만 보고 고르는 거예요`.
바로 위아래에 붙어 있어서 두 번 읽히고, 그만큼 **묻는 답이 뒤로 밀렸다.**
이제 **단계 그림은 시점만, 문답은 왜 하는가와 무엇이 다른가**를 말한다.
`결과는 어디서 보나요?` 는 `발표되면 뭐가 보이나요?` 에 흡수했다 — *어디서* 만 답하면
**무엇이** 나가는지는 여전히 안 알려준 것이다.

**④ 화면에 없던 문답을 살리고, 죽은 것은 지웠다.**
`매력 투표는 언제까지인가요?` 는 `copy.ts` 에 있었지만 `Help.tsx` 가 그리지 않았다 —
**아무도 못 읽는 문구였다.** 마감은 단계 그림으로 옮겼고(`파티 직전에 마감돼요 —
남은 시간은 홈에 있어요`), 죽은 키는 지웠다.

### 자리 이야기를 어디까지 하나 — **내 쪽만**

도움말은 *왜 투표를 해야 하나* 에 답한 적이 없었다. `파티에서 다시 고를 기회가 있어요` 는
답이 아니라 미루기다. 진짜 답은 자리인데, ADR-23 이 그걸 금지하고 있었다 —
*같은 테이블에 앉은 사람 중 누가 나를 골랐는지 짐작하게 된다.*

그 걱정은 **여전히 옳다.** 자리 배정은 한쪽만 보낸 표도 센다 (ADR-40). 그래서
*서로 고른 사람끼리 같은 테이블* 이라고 말하면, 내가 고르지 않은 사람과 같은 테이블일 때
**그 사람이 나를 골랐다**로 좁혀진다. 스무 명이 두세 명이 된다.

**그래서 주어를 하나로 묶었다.**

| | |
|---|---|
| 쓴다 | `내가 고른 사람과 첫 자리에서 같은 테이블이 되기 쉬워져요` |
| 쓰지 않는다 | ~~`서로 고른 사람끼리 같은 테이블에 앉아요`~~ |

앞엣것은 **내 선택이 내 자리에 미치는 영향**만 말한다. 고를 이유는 그대로 전해지고,
상대의 선택을 되짚는 문장은 주지 않는다. 대칭을 스스로 추론하는 사람은 여전히 있겠지만,
**앱이 알려주지는 않는다** — 그 선이 이 결정의 전부다.

콕도 같은 꼴이다: `다음 자리부터 내가 찌른 사람과 같은 테이블이 되기 쉬워져요`.

> ⚠️ ADR-23 의 금지는 **좁아졌지 없어지지 않았다.** `서로` 로 시작하는 자리 문장을
> 되살리지 마라. 화면 테스트가 두 답에 `내가` 가 있는지, `서로 고른` 이 없는지 본다.

### 운영자가 보는 범위 — 숫자는 늘, 짝은 매칭만

`운영자에게도 숫자만 보여요. 서로 콕 찌른 쌍이 됐을 때만 짝으로 보여요.`

**숫자가 보인다는 것을 빼면 안 된다.** 받은 콕 순위가 운영자 화면에 실제로 뜬다 (ADR-30).
*매칭된 것만 보여요* 라고만 쓰면 그 순위가 곧 거짓이 된다. 지켜지는 건 **한쪽만 찌른 것**이고,
그건 운영자 응답에도 숫자로만 남는다 (`hostState` 에 `oneWay` 가 없다 — 테스트가 지킨다).

### 따라오는 것

- **`연락처가 열려요` 를 되살리지 마라.** 되살릴 거라면 **내보내는 코드가 먼저**다 (ADR-42).
  `MatchInfo` 에 담을 자리가 없는 것이 그 방어이고, 이 문장이 그 방어를 말로 깨고 있었다
- 회차 설정을 새로 더할 때 **도움말이 그 답을 하는지** 보라. 참가자가 겪는 것이 회차마다
  다른데 도움말이 한 가지로만 말하면, 그 회차에서는 도움말이 틀린 것이다
- 문답을 더할 때는 **단계 그림과 겹치는지** 먼저 본다. 겹치면 둘 중 하나를 지운다

## ADR-53 발표 안내는 **매칭이 있는 사람에게만** 참가자 탭을 가리킨다

**문제** — 발표 뒤 소식이 모두에게 `참가자 탭에서 확인해보세요` 라고 했다.
**매칭이 없는 사람에게는 그 길이 틀렸다.**

- 그 사람의 답은 **이미 홈 카드에 문장으로 다 있다** (`이번엔 서로 닿지 않았네요…`)
- 시킨 대로 참가자 탭에 가면 명단은 있는데 💘 배지가 없다 —
  즉 **없는 것을 찾아 훑는 일**이 된다. 이 앱이 없애려던 경험 그대로다

배너도 같은 값을 썼다. 내 정보 탭에서 배너를 누르면 참가자 탭으로 갔고, 갈 이유가 없는 곳이었다.

**결정 하나 — 안내를 매칭 유무로 가른다.**

| | 소식 몸글 | 누르면 갈 곳 |
|---|---|---|
| 매칭 있음 | `참가자 탭에서 확인해보세요` | 참가자 탭 |
| 매칭 없음 | **없음** | 홈 |

**몸글을 비운 것이 핵심이다.** 여기에 무슨 말을 넣든 홈이 조심스럽게 한 말을
**소식 목록에서 한 번 더** 하는 것이고, 그 목록은 계속 남는다.
일어난 일(`결과가 발표됐어요`)만 적고 길 안내는 하지 않는다.

`tab` 이 배너가 갈 곳도 정한다. 배너는 `tab !== banner.tab` 일 때만 뜨므로 —

- 매칭 있는 사람: 참가자 탭에서 안 뜬다 (결과가 거기 있다). 예전과 같다
- 매칭 없는 사람: **참가자 탭에서 뜬다.** 그 사람의 결과는 거기 없고 홈에 있으니 맞다

⚠️ **빈 몸글은 자리를 먹지 않아야 한다.** 소식 줄도 배너도 `body` 가 있을 때만 그린다 —
빈 칸도 flex 항목이라 `gap` 을 먹는다 (ADR-49 후기 2 에서 빈 `stack` 으로 겪은 것과 같다).

**결정 둘 — 누구인지는 홈에서 바로 안다.**

홈의 `서로 찌른 상대 N명` 아래에 **이름만 한 줄** 세운다 (`이별빛 · 김달빛`).
발표 순간 가장 먼저 궁금한 것이 *누구야* 인데, 지금까지 홈에는 숫자만 있고
이름은 탭을 옮겨야 나왔다.

⚠️ **카드를 홈에 그리는 게 아니다.** 프로필·같은 테이블·💘 배지·`결과 보기` 는 참가자 탭 것이다 (ADR-18).
홈에 있는 건 **그 탭으로 가기 전에 답하는 한 줄**뿐이다.

**왜 결과를 통째로 홈으로 옮기지 않았나**

그 방안(결과를 늘 홈에)도 봤다. 두 가지가 막았다.

- **ADR-18 을 되돌리는 셈이다.** 결과가 `내 정보` 탭에만 있던 것을
  *"파티장에서는 상대를 눈앞에 두고 다른 탭을 뒤져야 했다"* 는 이유로 **사람이 있는 자리**로 옮긴 결정이다.
  그 이유는 지금도 유효하다
- **같은 것이 두 곳에 생긴다.** 매칭 상대는 여럿일 수 있어(ADR-24) 홈이 사실상 참가자 탭을 복제한다.
  중복을 없애려면 참가자 탭에서 결과를 빼야 하는데 그게 ADR-18 을 정면으로 뒤집는 것이다

**남는 길** — 더 나은 방안이 하나 있다. **목적지가 답하게 만드는 것** — 참가자 탭 맨 위에
결과 한 줄(매칭 수 또는 무매칭 문장)을 두면 `참가자 탭에서 확인해보세요` 가 **모두에게 참말**이 되고
이 ADR 의 분기가 통째로 필요 없어진다. 이번에는 안 골랐지만, 발표 화면을 다시 열 때 먼저 볼 것은 그쪽이다.

## ADR-54 파티 시작은 **기본 정보**다 — 예약 스텝에서 뺀다

**문제** — 회차 만들기 2스텝(`예약`)에 시각 넷이 서 있었다.
매력 투표 시작 → 마감 → **파티 시작** → 커플 발표.

**그중 셋만 예약이다.** 파티 시작은 운영자가 현황 탭에서 직접 누른다 (ADR-14).
예약 목록에 끼어 있으니 **넷 다 저절로 넘어가는 줄로 읽혔고**, 그렇게 읽으면
운영자가 아무것도 안 눌러서 파티가 영영 안 열린다.

그걸 막으려고 그 칸에 한 줄을 붙였다 —
`이 시각은 예약되지 않아요 — 현황 탭에서 직접 넘깁니다. 나머지 일정의 기준이에요.`
**문장으로 구조를 고치고 있었다.**

**결정 — 칸을 옮긴다.**

| 스텝 | 무엇 |
|---|---|
| 1 · 기본 정보 | 회차 이름 · 장소 · **파티 시작** |
| 2 · 예약 | 매력 투표 시작 → 마감 → 커플 발표 |

이제 **2스텝에 있는 것은 전부 저절로 넘어간다.** 예외가 없으니 예외를 설명할 줄도 없다.
`partyHint` 가 하던 일을 자리가 한다.

**기준점이라서 더 맞다.** 나머지 일정 기본값이 파티 시각에서 거꾸로 계산되므로(`changeParty`)
**가장 먼저 정하는 것**이 순서상으로도 옳다. 2스텝에 들어가면 뒤에서 셋째 칸을 고쳤을 때
앞의 두 칸이 따라 움직이는데, 그건 읽는 사람에게 뜬금없다.

**결정 둘 — 2스텝의 설명 줄을 전부 걷는다.**

걷은 것 — `이때부터 파티 시작까지 첫 자리를 짭니다` · `이 시각은 예약되지 않아요…` ·
`파티를 시작해야 울려요…` · `등록은 회차를 만들면 바로 열려요`.

**라벨만으로 무엇인지 알 수 있는 칸에는 설명을 붙이지 않는다.** 이 화면은 대부분
**기본값 그대로 `다음` 을 누르는** 자리인데, 칸 넷에 설명 넷이 붙어 화면의 절반이 글이었다.

⚠️ **모든 설명을 걷은 것이 아니다.** 남긴 자리의 기준은 하나다 —
**고른 결과가 라벨에 드러나지 않는가.**

- 3스텝의 토글들은 남는다. `매력 투표 알림` 을 껐을 때 무슨 일이 생기는지는 라벨에 없다
- 1스텝의 장소도 남는다 (`안내문에 들어가요. 참가자 화면에는 안 보입니다`) —
  참가자에게 보인다고 믿으면 안내문에 장소를 안 적고, 그러면 아무도 어디로 갈지 모른다

**설정 탭은 그대로 뒀다.** 거기 `예약` 묶음은 **일정 전체를 읽는 자리**라
잠긴 `등록 시작` 까지 한 줄로 보여준다 — 위저드처럼 "예약된 것만" 이 아니다.
`파티를 시작해야 울려요` 같은 줄도 거기 남아, 위저드에서 걷은 사실을 찾아볼 곳이 있다.

**대가** — 1스텝이 세 칸이 됐고, 시각 하나가 시각 아닌 칸 둘과 나란히 선다.
`장소가 1스텝으로 간 것은 시각 넷 사이에 끼면 안 되기 때문` 이라던 이유의 뒤집힌 꼴인데,
**섞이면 안 되는 것은 시각과 글자가 아니라 예약과 예약 아닌 것**이었다.

### 후기 — 설정 탭도 따라가고, 위저드 설명은 하나만 남는다

**설정 탭의 `파티 시작` 도 `기본 정보` 묶음으로 옮겼다.** 두 화면이 같은 것을 다른 자리에 두면
만들 때 고른 것을 고치러 온 사람이 어디를 눌러야 할지 다시 찾는다. 옮기면서 두 가지가 따라왔다 —

- `예약` 묶음은 이제 **저절로 넘어가는 것 + 지나간 기록(`등록 시작`)** 이다
- **고쳤다는 점도 `기본 정보` 에 붙어야 한다.** `pending()` 이 일정 키를 통째로 `schedule` 로
  세고 있어서, 자리만 옮기면 점이 엉뚱한 알약에 붙는다

**위저드 3스텝의 설명 줄도 걷었다.** 이제 위저드 전체에 설명은 **장소 하나뿐**이다.

앞서 3스텝은 남겼었다 — *고른 결과가 라벨에 드러나지 않는다* 는 이유였다. 맞는 말이지만,
**그 설명이 필요한 순간은 만들 때가 아니라 고칠 때**다. 처음 만드는 사람은 대부분 기본값으로
지나가고, `매력 투표 알림을 꺼야 하나` 를 고민하는 건 한 번 치러보고 나서다.
그때 가는 곳이 설정 탭이고, **거기에는 그대로 있다.**

장소만 남긴 기준은 그대로다 — *참가자에게 보이지 않는다* 는 라벨이 말해주지 않고,
모르면 안내문에 장소를 안 적어서 **아무도 어디로 갈지 모르게 된다.**

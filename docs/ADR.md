# 설계 결정

**바꾸기 전에 반드시 읽는다.** 여기 있는 건 되돌리기 어려운 결정이고, 대부분 사고를 겪고 나온 것이다.
"더 나은 방식"처럼 보이는 게 이미 검토돼 버려진 경우가 많다.

---

## ADR-1 공개 범위는 기능이 아니라 제품의 정체성

**결정** — 일방적으로 받은 콕은 **끝까지 익명**이다. 발표 후에도 상호 매칭만 닉네임이 공개되고,
연락처는 매칭돼도 공개하지 않는다.

**왜** — 이 앱이 없애려는 건 "거절당하는 경험"이다. 누가 나를 안 찔렀는지 알 수 있게 되는 순간
파티의 분위기가 바뀐다.

**따라서** — 설정 가능한 옵션이 아니다. 참가자에게 나가는 응답은 `toPublic()` 한 곳만 거치고,
발표 전에는 콕 발신자(`fromId`)가 응답에 아예 들어가지 않는다.

---

## ADR-2 예약과 수동 진행은 "일회성 알람"으로 공존한다

**문제** — 운영자는 시각을 예약할 수도, 현장에서 버튼으로 진행할 수도 있다. 둘이 섞이면
발표를 되돌렸을 때 지나간 예약 때문에 즉시 다시 튕긴다.

**결정** — 예약 시각은 상태가 아니라 **한 번만 울리는 알람**이다. 실제 전환 시각을 `fired` 에
기록하고, 알람은 `fired` 가 비어 있을 때만 울린다.

```ts
if (phase==="prep"    && schedule.regOpenAt   && !fired.reg   && now >= schedule.regOpenAt)   → "reg"
if (phase==="prevote" && schedule.voteCloseAt && !fired.party && now >= schedule.voteCloseAt) → "party"
if (phase==="party"   && schedule.revealAt    && !fired.done  && now >= schedule.revealAt)    → "done"
```

**따라오는 규칙 3가지**

1. **예약 값을 지우지 않는다** — "예약은 21:00 이었는데 20:45 에 진행했다"를 보여줄 수 있어야 한다
2. **지나온 항목만 잠근다** — `schedLocked()`. 등록이 시작됐어도 발표 시각은 여전히 수정 가능하다
3. **차이를 알려준다** — 수동 진행 확인창에 `schedDiff()` 한 줄

**버린 대안** — "수동 진행 시 예약을 삭제". 기록이 사라져 운영 회고가 불가능해진다.

> ⚠️ 이걸 일반 스케줄러나 cron 으로 "개선" 하지 마라. 되돌리기가 깨진다.

## ADR-3 회차 PIN 을 공통 PIN 보다 먼저 검사한다

**사고** — 두 PIN 이 같은 값일 때 회차 담당자가 자기 PIN 을 넣었는데 master 가 부여됐다.
`{"회차PIN":"0000","공통PIN":"0000","획득권한":"master","전체회차접근":true}`

**결정** — 두 겹으로 막는다.

1. 회차 화면에서는 **회차 PIN 을 먼저** 비교한다
2. PIN 을 만드는 **모든 지점**(위저드·회차 설정·기본 설정·자동 생성기)에서 두 값이 같아지는 걸 막는다

**원칙** — 권한 검사에서 "더 좁은 권한을 먼저 본다". 그리고 **입력 시점 차단과 검사 시점 방어를 둘 다** 둔다.
한쪽만 있으면 기존 데이터나 새 입력 경로로 뚫린다.

## ADR-4 참가자 알림은 저장하지 않고 상태에서 파생시킨다

**결정** — 알림 목록은 `fired` 에서 매번 계산한다. 읽음/안읽음 플래그도, 알림 테이블도 만들지 않는다.

**왜** — 알림을 저장하면 "발표를 되돌렸을 때 이미 보낸 알림을 어떻게 할 것인가"가 곧바로 생긴다.
파생시키면 상태가 하나뿐이라 모순이 없다. 되돌리면 알림도 자동으로 "되돌렸어요"로 바뀐다.

**한계** — "이 알림을 읽었는가"를 알 수 없다. 자리 이동만은 확인이 꼭 필요해서 별도로 `ack` 를 저장한다.

---

## ADR-5 테이블 수는 설정이 아니라 배정 시점의 입력값

**결정** — 회차 설정에 테이블 수를 두지 않는다. **자리 배정을 누를 때마다** 고르고,
각 배정 결과에 그때 쓴 값을 함께 저장한다.

**왜** — 현장에서 결정되는 값이다. 노쇼가 생기고 지각자가 오고 1부·2부 배치가 다르다.
미리 정해두면 반드시 틀린다.

## ADR-6 되돌릴 수 있는 행동에는 확인을 붙이지 않는다

| 행동 | 확인 | 왜 |
|---|---|---|
| 콕 찌르기 `+` | ✅ | 예산이 줄고 상대에게 알림이 간다 |
| 콕 되돌리기 `−` | ❌ | 다시 찌르면 복구된다. 확인은 마찰만 늘린다 |
| 단계 전환 | ✅ | 참가자 전원의 화면이 바뀐다 |
| 참가자 삭제 | ✅ | 콕·자리 이력이 함께 사라진다 (숫자로 명시) |
| 자리 알림 발송 | ✅ | 참가자 화면을 덮는 확인 화면이 뜬다 |
| 자리 초안 생성 | ❌ | 참가자에게 안 보인다. 몇 번이든 다시 만들 수 있다 |

확인창은 "정말 하시겠습니까?"가 아니라 **무엇이 어떻게 바뀌는지**를 항목별·숫자로 보여준다.

## ADR-7 데모 뷰는 별도 코드가 아니라 컨텍스트 파라미터다

**결정** — 참가자 뷰는 한 벌만 유지하고, 컨텍스트로 "지금 어느 화면을 그리는가"를 결정한다.

**왜** — 데모용 화면을 따로 만들면 두 벌이 갈라져 **데모가 거짓말을 하게 된다.**
컨텍스트만 바꾸면 데모에 보이는 것이 실제 그 화면이다.

**대가** — 모든 뷰·핸들러가 컨텍스트를 받아야 한다. 하나라도 빠뜨리면 다른 화면이 반응한다.
화면 독립성을 테스트로 상시 검사한다.

## ADR-8 조용한 실패는 테스트로만 잡힌다

**사고** — `새 회차 만들기` 버튼이 아무 반응이 없었다. 함수 이름이 브라우저 내장과 충돌해
**내장 함수가 조용히 호출**됐고, 에러도 남지 않았다.

**결정** — 이름 충돌을 상시 검사한다. 넓게 보면: **에러를 남기지 않는 실패는 사람 눈으로 못 잡는다.**
기계가 잡게 만든다.

같은 이유로 `npm run check:copy` 가 있다 — 문구를 지어내도 에러가 안 나므로.

## ADR-9 회차 목록은 KV 가 아니라 DO 하나가 들고 있다

**결정** — 입장 코드 → 회차 ID 인덱스, 회차 PIN, 멱등키, 공통 PIN, 기본 설정을 전부
`RegistryDO` 하나에 둔다. KV 는 쓰지 않는다.

**왜** — 이 네 가지는 모두 "동시에 두 번 눌렀을 때 하나만 만들어져야" 하는 값이다.
KV 는 쓰기 직후 읽기가 보장되지 않아서, 새 회차를 만드는 순간 코드 중복 검사와
멱등키 검사가 **직전에 쓴 값을 못 보고 통과**할 수 있다. 회차가 두 개 생기거나
같은 입장 코드가 두 회차에 붙는다 — 파티 당일에 알아채는 종류의 사고다.

**따라오는 것**

1. 회차 생성은 두 걸음이다. 레지스트리가 신원(아이디·코드·PIN)을 먼저 잡고,
   회차 DO 가 상태를 만든다. `init()` 은 멱등이라 두 번째 요청은 이미 만든 걸 돌려준다
2. 참가자 개인정보는 레지스트리에 올라오지 않는다. 이름·전화·콕은 회차 DO 안에만 있다
3. 배포에 KV 네임스페이스 준비가 필요 없어졌다 — 비밀값 두 개면 나간다

**대가** — 회차 목록을 그릴 때 회차 수만큼 DO 를 호출한다. 한 운영자가 다루는 회차 수는
수십 개 규모라 문제가 되지 않는다. 수백 개가 되면 요약을 레지스트리에 캐시할 것.

## ADR-10 '지금 바로'는 순서 검증의 한쪽이 아니다

**결정** — 회차를 만들 때 `voteCloseAt > regOpenAt` 검사는 **운영자가 고른 두 시각 사이에서만** 한다.
등록 시작을 '지금 바로'로 켠 경우에는 마감이 이미 지났더라도 회차를 만든다.

**왜** — '지금 바로'는 시각이 아니라 버튼이다. 서버 시각과 운영자 폰의 시각이 몇 분만 달라도
"방금 고른 마감이 시작보다 앞"이라는 이유로 회차 생성이 막히는데, 운영자는 무엇을 고쳐야 하는지 알 수 없다.

**대신** — 마감이 이미 지난 상태는 사전 투표 시작 확인창의 ⚠️ 경고
(`PREVOTE_ALREADY_CLOSED`)가 맡는다. 그 자리에서 설정으로 보내면 고칠 수 있다.
운영자가 **두 시각을 직접 고른** 경우에는 그대로 거부한다 — 그건 오타이기 때문이다.

## ADR-11 마지막 라운드에서 서로 찌른 쌍은 가중치가 아니라 구조로 지킨다

**사고** — 마지막 라운드의 상호 매칭 보너스(12 × 2.5 = 30)와 나이차 벌점(30)이 정확히 같아서,
가중치 4짜리 I·E 쏠림이 승부를 갈랐다. 서로 찌른 쌍이 갈라져 앉았다 — 동석률 50%.

**결정** — 마지막 라운드에서는 **이미 같은 테이블에 앉은 상호 매칭 쌍을 떼어놓는 맞교환을 시도하지 않는다.**
성비 불변식과 같은 방식이다: 지키려고 노력하는 게 아니라 그렇게 될 방법이 없다.

**원칙** — 어떤 제약이 "가장 중요하다"면 가중치를 키우지 말고 탐색 공간에서 빼라.
가중치는 언제나 다른 가중치의 합에 밀릴 수 있다.

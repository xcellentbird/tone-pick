# 설계 결정

**바꾸기 전에 반드시 읽는다.** 여기 있는 건 되돌리기 어려운 결정이고, 대부분 사고를 겪고 나온 것이다.
"더 나은 방식"처럼 보이는 게 이미 검토돼 버려진 경우가 많다.

---

## ADR-1 공개 범위는 기능이 아니라 제품의 정체성

**결정** — 일방적으로 받은 콕은 **끝까지 익명**이다. 발표 후에도 상호 매칭만 닉네임이 공개되고,
연락처는 매칭돼도 공개하지 않는다.

**왜** — 이 앱이 없애려는 건 "거절당하는 경험"이다. 누가 나를 안 찔렀는지 알 수 있게 되는 순간
파티의 분위기가 바뀐다.

**따라서** — 설정 가능한 옵션이 아니다. 참가자에게 나가는 응답은 `toPublic()` 한 곳만 거치고,
발표 전에는 콕 발신자(`fromId`)가 응답에 아예 들어가지 않는다.

---

## ADR-2 예약과 수동 진행은 "일회성 알람"으로 공존한다

**문제** — 운영자는 시각을 예약할 수도, 현장에서 버튼으로 진행할 수도 있다. 둘이 섞이면
발표를 되돌렸을 때 지나간 예약 때문에 즉시 다시 튕긴다.

**결정** — 예약 시각은 상태가 아니라 **한 번만 울리는 알람**이다. 실제 전환 시각을 `fired` 에
기록하고, 알람은 `fired` 가 비어 있을 때만 울린다.

```ts
if (phase==="prep" && schedule.regOpenAt && !fired.reg     && now >= schedule.regOpenAt) → "reg"
if (phase==="reg"  && schedule.prevoteAt && !fired.prevote && now >= schedule.prevoteAt) → "prevote"
```

예약이 걸리는 전환은 이 **둘뿐**이다. 사전 투표 마감·파티 시작·발표는 운영자가 누른다 (ADR-14).

**따라오는 규칙 3가지**

1. **예약 값을 지우지 않는다** — "예약은 21:00 이었는데 20:45 에 진행했다"를 보여줄 수 있어야 한다
2. **지나온 항목만 잠근다** — `schedLocked()`. 등록이 시작됐어도 사전 투표 시작은 여전히 수정 가능하다
3. **차이를 알려준다** — 수동 진행 확인창에 `schedDiff()` 한 줄

**버린 대안** — "수동 진행 시 예약을 삭제". 기록이 사라져 운영 회고가 불가능해진다.

> ⚠️ 이걸 일반 스케줄러나 cron 으로 "개선" 하지 마라. 되돌리기가 깨진다.

## ADR-3 회차 PIN 을 공통 PIN 보다 먼저 검사한다 — **폐기됨 (ADR-12)**

**사고** — 두 PIN 이 같은 값일 때 회차 담당자가 자기 PIN 을 넣었는데 master 가 부여됐다.
`{"회차PIN":"0000","공통PIN":"0000","획득권한":"master","전체회차접근":true}`

**당시 결정** — 회차 화면에서는 회차 PIN 을 먼저 비교하고, PIN 을 만드는 모든 지점에서
두 값이 같아지는 걸 막는다.

**지금** — 회차 PIN 자체가 없어졌다 (ADR-12). 검사 순서라는 개념이 사라졌으므로 이 결정은 폐기한다.
남는 교훈은 하나다 — **지켜야 할 순서가 있다면, 그 순서가 필요 없게 만드는 쪽이 낫다.**

## ADR-4 참가자 알림은 저장하지 않고 상태에서 파생시킨다

**결정** — 알림 목록은 `fired` 에서 매번 계산한다. 읽음/안읽음 플래그도, 알림 테이블도 만들지 않는다.

**왜** — 알림을 저장하면 "발표를 되돌렸을 때 이미 보낸 알림을 어떻게 할 것인가"가 곧바로 생긴다.
파생시키면 상태가 하나뿐이라 모순이 없다. 되돌리면 알림도 자동으로 "되돌렸어요"로 바뀐다.

**한계** — "이 알림을 읽었는가"를 알 수 없다. 자리 이동만은 확인이 꼭 필요해서 별도로 `ack` 를 저장한다.

## ADR-5 테이블 수는 설정이 아니라 배정 시점의 입력값

**결정** — 회차 설정에 테이블 수를 두지 않는다. **자리 배정을 누를 때마다** 고르고,
각 배정 결과에 그때 쓴 값을 함께 저장한다.

**왜** — 현장에서 결정되는 값이다. 노쇼가 생기고 지각자가 오고 1부·2부 배치가 다르다.
미리 정해두면 반드시 틀린다.

## ADR-6 되돌릴 수 있는 행동에는 확인을 붙이지 않는다

| 행동 | 확인 | 왜 |
|---|---|---|
| 콕 찌르기 `+` | ✅ | 예산이 줄고 상대에게 알림이 간다 |
| 콕 되돌리기 `−` | ❌ | 다시 찌르면 복구된다. 확인은 마찰만 늘린다 |
| 단계 전환 | ✅ | 참가자 전원의 화면이 바뀐다 |
| 참가자 삭제 | ✅ | 콕·자리 이력이 함께 사라진다 (숫자로 명시) |
| 자리 알림 발송 | ✅ | 참가자 화면을 덮는 확인 화면이 뜬다 |
| 자리 초안 생성 | ❌ | 참가자에게 안 보인다. 몇 번이든 다시 만들 수 있다 |

확인창은 "정말 하시겠습니까?"가 아니라 **무엇이 어떻게 바뀌는지**를 항목별·숫자로 보여준다.

## ADR-7 데모 뷰는 별도 코드가 아니라 컨텍스트 파라미터다

**결정** — 참가자 뷰는 한 벌만 유지하고, 컨텍스트로 "지금 어느 화면을 그리는가"를 결정한다.

**왜** — 데모용 화면을 따로 만들면 두 벌이 갈라져 **데모가 거짓말을 하게 된다.**
컨텍스트만 바꾸면 데모에 보이는 것이 실제 그 화면이다.

**대가** — 모든 뷰·핸들러가 컨텍스트를 받아야 한다. 하나라도 빠뜨리면 다른 화면이 반응한다.
화면 독립성을 테스트로 상시 검사한다.

### 후기 — 데모 뷰 자체를 걷어냈다

이 결정("한 벌만 유지한다")은 옳았지만, **데모 뷰를 운영 앱 안에 둔 것**이 문제였다.
서버 시연 라우트는 `ENV_LABEL` 로 막혀 프로덕션에서 404 였는데, **클라이언트 라우트는 안 막혀서
프로덕션 번들에 화면과 문구가 그대로 실렸다.** "존재 자체를 없앤다" 던 약속이 절반만 지켜진 셈이다.

별도 앱으로 떼는 안도 검토했지만 이 ADR 이 막으려던 **두 벌 갈라짐**이 그대로 돌아온다.
그래서 기능을 걷어냈다. 참가자 뷰는 여전히 한 벌이고, 이제 그 한 벌만 남았다.
부하 리허설은 `scripts/rehearsal.mjs` 가 실제 등록 경로로 대신한다.

## ADR-8 조용한 실패는 테스트로만 잡힌다

**사고** — `새 회차 만들기` 버튼이 아무 반응이 없었다. 함수 이름이 브라우저 내장과 충돌해
**내장 함수가 조용히 호출**됐고, 에러도 남지 않았다.

**결정** — 이름 충돌을 상시 검사한다. 넓게 보면: **에러를 남기지 않는 실패는 사람 눈으로 못 잡는다.**
기계가 잡게 만든다.

같은 이유로 `npm run check:copy` 가 있다 — 문구를 지어내도 에러가 안 나므로.

## ADR-9 회차 목록은 KV 가 아니라 DO 하나가 들고 있다

**결정** — 입장 코드 → 회차 ID 인덱스, 멱등키, 운영자 PIN, 기본 설정을 전부
`RegistryDO` 하나에 둔다. KV 는 쓰지 않는다.

**왜** — 이 네 가지는 모두 "동시에 두 번 눌렀을 때 하나만 만들어져야" 하는 값이다.
KV 는 쓰기 직후 읽기가 보장되지 않아서, 새 회차를 만드는 순간 코드 중복 검사와
멱등키 검사가 **직전에 쓴 값을 못 보고 통과**할 수 있다. 회차가 두 개 생기거나
같은 입장 코드가 두 회차에 붙는다 — 파티 당일에 알아채는 종류의 사고다.

**따라오는 것**

1. 회차 생성은 두 걸음이다. 레지스트리가 신원(아이디·코드·PIN)을 먼저 잡고,
   회차 DO 가 상태를 만든다. `init()` 은 멱등이라 두 번째 요청은 이미 만든 걸 돌려준다
2. 참가자 개인정보는 레지스트리에 올라오지 않는다. 이름·전화·콕은 회차 DO 안에만 있다
3. 배포에 KV 네임스페이스 준비가 필요 없어졌다 — 비밀값 두 개면 나간다

**대가** — 회차 목록을 그릴 때 회차 수만큼 DO 를 호출한다. 한 운영자가 다루는 회차 수는
수십 개 규모라 문제가 되지 않는다. 수백 개가 되면 요약을 레지스트리에 캐시할 것.

## ADR-10 '지금 바로'는 순서 검증의 한쪽이 아니다

**결정** — 회차를 만들 때 `prevoteAt > regOpenAt` 검사는 **운영자가 고른 두 시각 사이에서만** 한다.
등록 시작을 '지금 바로'로 켠 경우에는 사전 투표 시작이 이미 지났더라도 회차를 만든다.

**왜** — '지금 바로'는 시각이 아니라 버튼이다. 서버 시각과 운영자 폰의 시각이 몇 분만 달라도
"방금 고른 시각이 시작보다 앞"이라는 이유로 회차 생성이 막히는데, 운영자는 무엇을 고쳐야 하는지 알 수 없다.

**대신** — 사전 투표 시작이 이미 지난 상태에서는 등록과 사전 투표가 곧바로 이어서 열린다.
운영자가 **두 시각을 직접 고른** 경우에는 그대로 거부한다 — 그건 오타이기 때문이다.

## ADR-11 마지막 라운드에서 서로 찌른 쌍은 가중치가 아니라 구조로 지킨다

**사고** — 마지막 라운드의 상호 매칭 보너스(12 × 2.5 = 30)와 나이차 벌점(30)이 정확히 같아서,
가중치 4짜리 I·E 쏠림이 승부를 갈랐다. 서로 찌른 쌍이 갈라져 앉았다 — 동석률 50%.

**결정** — 마지막 라운드에서는 **이미 같은 테이블에 앉은 상호 매칭 쌍을 떼어놓는 맞교환을 시도하지 않는다.**
성비 불변식과 같은 방식이다: 지키려고 노력하는 게 아니라 그렇게 될 방법이 없다.

**원칙** — 어떤 제약이 "가장 중요하다"면 가중치를 키우지 말고 탐색 공간에서 빼라.
가중치는 언제나 다른 가중치의 합에 밀릴 수 있다.

## ADR-12 운영자 PIN 은 하나뿐이다

**배경** — 회차마다 PIN 을 따로 뒀다. 회차 담당자에게 그 회차만 열어주자는 생각이었다.

**실제** — 운영자는 한 명이거나 한 팀이었다. 회차 PIN 을 쓰는 사람이 없었고,
대신 ADR-3 의 사고가 생겼다. **쓰이지 않는 권한 분리가 실제 취약점을 만들었다.**

**결정** — 권한은 `master` 하나다. `AuthScope` 에서 `host` 를 없애고,
회차 PIN·PIN 해시·충돌 검사·자동 생성기를 전부 지웠다.

**따라오는 것**
- `/api/host/pin` 은 `eventId` 를 받아도 무시한다. 회차 단위의 뒷문이 없다는 걸 테스트로 고정했다 (S-A3)
- 회차 설정에서도, 기본 설정에서도 PIN 칸이 사라졌다.
  바꾸는 곳은 배포 시크릿 `MASTER_PIN` **하나뿐**이다 — 바꾸는 자리가 둘이면
  지금 무엇이 맞는 PIN 인지 화면으로는 알 수 없다. 스토리지에 남아 있던 PIN 도 지웠다

**대가** — 회차별로 운영을 나눠 맡길 수 없다. 필요해지면 그때 **역할**로 다시 만든다 —
같은 화면에 번호를 두 개 두는 방식으로는 돌아가지 않는다.

## ADR-13 참가 링크는 회차를 가리킨다 — 문은 따로다

**문제** — 링크에 입장 코드가 들어 있으면(`/j/ABCDEF`) 그 링크가 곧 입장이다.
링크는 단톡방에 돌고 스크린샷으로 퍼진다 — 운영자가 부르지 않은 사람이 명단에 들어온다.

**결정** — 참가 링크는 `/j/<회차id>` 다. 열면 **회차 이름·단계·파티 일시까지만** 보인다.

- `GET /api/events/by-id/:id` 는 인증 없이 열리지만 **입장 코드를 절대 담지 않는다** (S-C2b)
- 문을 여는 방법은 ADR-15 에서 입장 코드 → **초대 명단의 전화번호**로 바뀌었다.
  링크가 문이 아니라는 이 결정은 그대로다

## ADR-14 마감·파티·발표는 예약하지 않는다

**문제** — 사전 투표 마감·파티 시작·발표 시각을 미리 잡아두면, 현장이 그 시각을 따라가야 한다.
사람이 덜 왔는데 마감되고, 이야기가 무르익는 중에 발표가 뜬다.

**결정** — 예약하는 건 **등록 시작과 사전 투표 시작** 둘뿐이다. 파티 당일에 일어나는 세 전환은
운영자가 현황 탭에서 누른다. 시계가 알 수 없는 것(사람이 다 왔는가, 지금 발표해도 되는가)을
시계에게 맡기지 않는다.

**따라오는 것**
- `EventSchedule` 은 `{ partyAt, regOpenAt, prevoteAt }` 이다. `partyAt` 은 **전환을 울리지 않는다** —
  나머지 일정의 기준점이고, 참가자 카운트다운이 향하는 곳이다
- 등록은 발표 전까지 계속 열려 있다. 늦게 온 사람도 파티 중에 합류한다
- 참가자 상단 카운트다운은 **파티 시작**만 센다. 없는 마감을 세어 보여주면 참가자가 그 숫자를 믿는다
- 하루 넘게 남았으면 초를 세지 않는다 (`144:00:00` 은 읽는 사람이 다시 나눠야 한다)

**대가** — 운영자가 제때 누르지 않으면 아무 일도 일어나지 않는다. 그건 사고가 아니라
"아직 안 넘겼다"이고, 현황 탭 맨 위 버튼 하나로 넘어간다.

## ADR-15 파티의 문은 운영자가 미리 받아둔 전화번호다

**문제** — 입장 코드 여섯 자리는 **옮겨 적을 수 있다.** 한 명에게 알려주면 그 사람이
친구에게 알려줄 수 있고, 운영자는 명단에 없는 사람이 들어온 걸 등록이 끝난 뒤에야 안다.

**결정** — 운영자가 회차마다 전화번호 명단을 미리 넣어두고, **그 번호로만** 들어온다.

```
링크(/j/<회차id>) → 전화번호 입력 → 명단에 있으면 통과 → 등록
```

- 통과한 번호는 **서명한 초대 쿠키**에 담는다. 등록 폼은 번호를 받지 않는다 —
  폼에서 받으면 명단에 없는 번호로 바꿔 낼 수 있다 (테스트로 고정)
- **이미 등록한 사람은 명단과 무관하게 통과한다.** 명단은 문이지 자격이 아니다 —
  운영자가 명단을 정리하다 이미 온 사람을 지웠다고 파티 중에 쫓겨나면 안 된다
- 같은 번호로 다시 오면 곧바로 자기 화면으로 간다. 번호가 곧 재접속 키다
- 입장 코드는 남지만 **회차를 가리키는 이름**일 뿐 아무 문도 열지 않는다

#### 후기 2 — **번호를 아는 사람은 그 사람이 될 수 있다** (2026-08-21, 열려 있음)

이 결정이 막는 것은 "명단에 **없는** 사람" 이다. 그건 잘 한다.
막지 못하는 것은 **"명단에 있는 사람이 남의 번호를 쓰는 것"** 이다.

```ts
// participant.ts — 이미 등록을 마친 사람에게는 곧바로 참가자 세션을 준다
const scope = result.registered ? await playerScopeFor(c, id, phone) : ...
```

번호를 아는 것이 곧 **그 사람의 계정 전체**다 — 보낸 콕, 받은 콕 수, 프로필 수정,
그리고 발표 후에는 **그 사람과 서로 찌른 상대의 실명·전화번호·인스타**(`MatchInfo.contact`).
이 앱이 지키기로 한 셋이 한꺼번에 무너진다.

그리고 이건 이론이 아니다 — **같은 파티에 오는 사람들은 서로 번호를 아는 사이다.**
위 결정이 세운 가정("번호는 남이 모른다")이 현실과 어긋나 있었다.

**근본 원인 한 문장: 전화번호는 식별자이지 증명이 아니다.**

살펴본 길과 각각이 포기하는 것 —

| | 막는 것 | 못 막는 것 | 포기하는 것 |
|---|---|---|---|
| **개인별 링크** | 번호만 아는 사람 | 링크를 넘겨받은 사람 | 단톡방에 링크 하나 뿌리기. 1:1 발송 |
| 기기 고정 | 이미 등록한 사람 가로채기 | 피해자보다 먼저 등록하기 | **카톡 인앱 ↔ 크롬 이동** — 국내 기본 동선이라 정상 사용자가 계속 막힌다 |
| 추가 정보(이름 뒤 두 글자 등) | 번호만 아는 남 | **친구** — 문제의 그 사람 | 효과가 거의 없다 |
| **참가자 비밀번호 4자리** | 번호만 아는 사람 **그리고 친구** | 비밀번호를 알려준 사람 · 어깨너머 | 등록 한 단계 · **잊어버린 사람 응대가 파티 당일에 몰린다** |
| IP | — | 전부 | **통신사 CGNAT 뒤에서 수천 명이 한 IP 를 쓴다.** 남과 나를 IP 로는 못 가른다. 게다가 모바일 IP 는 셀·망이 바뀔 때마다 달라져서, 막는 쪽으로 쓰면 정상 사용자가 먼저 걸린다 |
| SMS 인증 | **전부** | — | 문자 비용(파티당 천원 안팎) · 발신번호 사전등록 리드타임 |

**결정 (2026-08-21) — 개인별 링크로 간다. 지금은 아니다.**
SMS 가 유일하게 문제를 닫지만 이 규모의 파티에는 과하다고 봤다.
개인별 링크는 참가자가 할 일이 줄고(번호도 안 친다), 운영자가 1:1 로 보내는 비용만 진다.

**다시 열림 (2026-08-21 저녁) — 비밀번호 줄이 표에 없었다.** 위 결정을 내릴 때
검토한 다섯 줄 중 어느 것도 "참가자가 스스로 정한 비밀번호"가 아니었다. 이건 새 줄이다.

두 길은 **같은 구멍을 막는 서로 다른 답이라 하나만 고른다.** 둘 다 넣으면
개인별 링크가 이미 증명한 신원을 비밀번호로 한 번 더 묻는 셈이다.

| | 개인별 링크 (13) | 참가자 비밀번호 (15) |
|---|---|---|
| 참가자가 할 일 | **없다.** 링크만 연다 | 등록 때 4자리 정하고, 다른 기기에서 친다 |
| **친구를 막나** | 링크가 카톡에 남아 있다 — 폰을 보면 보인다 | **막는다.** 번호를 알아도 못 들어온다 |
| 운영자 부담 | 28명에게 **1:1 발송** | 단톡방에 링크 하나 그대로 |
| 그 부담이 **언제** 오나 | 파티 **전**, 여유 있을 때 | 분실 응대가 **파티 당일**, 가장 바쁠 때 |
| 되돌리기 | 새 링크 뽑아 다시 보낸다 | 운영자가 재설정한다 |

**갈림길은 마지막 두 줄이다** — 막는 힘은 비밀번호가 세지만, 그 비용을 파티 당일에 낸다.

> ⚠️ **그때까지 이 구멍은 열려 있다.** 가장 비싼 유출(연락처)은 **발표 후에만** 열리므로,
> 발표를 현장에서 사람들이 눈앞에 있을 때 누르는 지금 운영이 그나마 완화책이다.
> **표에 없던 줄이 아니면 다시 그리지 마라** — 위 다섯은 이미 검토했다.

**닫혔다 (2026-08-23) → ADR-32.** 개인별 링크(13)로 간다. 15 는 이 결정으로 닫힌다.

#### 후기 — 코드로 회차를 찾는 길까지 닫았다

"아무 문도 열지 않는다" 고 해놓고 **`/api/events/by-code` 가 코드를 회차 아이디로 바꿔주고 있었다.**
그 아이디가 곧 참가 링크다 — 즉 30비트 코드(32^6)를 뚫으면 **64비트 링크(`randomHex(8)`)가
그대로 나왔다.** 링크의 강도가 코드까지 내려가 있던 셈이다.

그래서 셋을 함께 걷었다.

- 뿌리 화면(`/`)의 코드 입력 — 운영자는 보통 링크만 주므로, 링크를 열었다 뒤로 간 참가자가
  **알지도 못하는 코드를 요구받는 막다른 길**이었다. 실제로 겪은 문제다
- `/j/:id` 의 `이전` 버튼 — 그 막다른 길로 보내던 버튼이다. 링크로 온 사람에게는 돌아갈 자리가 없다
- `/api/events/by-code` — 위의 오라클

대신 뿌리 화면은 **세션이 있으면 자기 회차로 보낸다.** 링크를 잃은 사람이 앱 주소만 알아도
자기 파티로 돌아온다 — 다만 **다른 기기에서는 안 되므로**, 링크가 여전히 보편적인 길이다.

**남은 것** — `/ws/:code` 는 여전히 코드로 회차를 찾는다. 다만 그쪽은 아이디를 내주지 않고
"그 코드의 회차가 있는가" 만 새므로 훨씬 약하다. 회차 목록을 훑는 게 걱정되면 그때 닫는다.

**이 문은 인증 없이 열려 있다.** 그래서 제한이 없으면 "이 번호가 이 파티에 있나"를
되묻는 창구가 된다 — 참가 링크를 손에 넣은 사람이 주소록을 통째로 넣어보면
누가 소개팅 파티에 갔는지 알아낼 수 있다. 이 앱이 가장 막아야 하는 유출이다.

- 회차·접속지별로 실패 횟수를 센다 (`ENTRY_TRIES`). 넘으면 잠시 막는다
- 접속지는 **해시로만** 저장한다. 원본 IP 는 어디에도 남기지 않는다
- 실패 문구는 하나뿐이다. "초대되지 않았어요"와 "그런 회차가 없어요"를 구분해 주면
  그 구분 자체가 답을 알려준다

**대가** — 운영자가 번호를 미리 모아야 한다. 명단 편집에는 **더하기와 빼기만** 둔다.

- 한 명씩 — "저도 갈게요" 연락이 파티 전날에 온다
- 붙여넣기 — 처음 명단을 만들 때. 한 명씩으로는 100명을 넣을 수 없다
- **통째로 갈아치우는 길은 없다.** 한 명 추가하려다 손이 미끄러지면 그 파티의 명단이
  전부 날아가고, 되돌릴 방법이 없다. 붙여넣기도 있는 명단에 더한다

**명단이 비어 있으면 아무도 들어올 수 없다.** 그게 기본값이라 운영자가 모르면 파티 당일
문 앞에서 알게 된다 — 참가자 탭 맨 위에서 비어 있음을 경고로 말한다.

## ADR-16 자리 맞교환은 남녀도 바꾼다

**배경** — 좌석 변경을 **같은 성별끼리만** 허용했다. 테이블 성비를 지키기 위해서였다.

**실제** — 현장에서 운영자가 아는 사정(아는 사이라 떼어놔야 한다, 자리를 부탁받았다)은
배정 알고리즘이 모른다. 같은 성별 안에서만 바꿀 수 있으면 그 사정을 못 푼다.

**결정** — 맞교환은 성별을 가리지 않는다. **여전히 맞교환 하나뿐**이다 —
한 명만 옮기는 API 는 만들지 않는다. 그건 테이블 인원이 어긋나는 일이라 성격이 다르다.

바뀐 성비는 자리 화면 테이블 머리의 `남 N / 여 M` 에 곧바로 보인다.
숨기지 않고 보여주는 쪽을 택했다 — 막는 것보다 낫다.

## ADR-17 콕은 성별을 가리지 않는다 (기본값)

**배경** — 처음에는 이성에게만 찌를 수 있었고, 동성 허용은 회차 설정의 선택 항목이었다.

**결정** — 기본이 **모두에게**다. 누구에게 마음이 가는지는 앱이 정할 일이 아니다.
이성만으로 좁히고 싶은 회차에서만 설정에서 좁힌다.

`allowSameGender` 는 그대로 두되 **없으면 모두에게**로 읽는다. 좁혔을 때만 `false` 를 적는다 —
설정을 새 항목으로 갈아엎으면 저장된 옛 모양이 또 화면에 NaN 을 띄운다 (ADR-12 뒤의 사고).

**따라오는 것**
- 참가자 목록의 기본 필터가 '전체'다. 반쪽만 보여주면 찌를 수 있는 사람이 가려진다
- 자리 배정의 남녀 정원은 **어느 쪽이든 그대로**다. 콕과 자리는 다른 규칙이다

## ADR-18 발표 결과는 그 사람이 있는 자리에 나온다

**문제** — 상호 매칭을 '내 정보' 탭에만 보여줬다. 파티장에서는 상대를 눈앞에 두고
다른 탭을 뒤져야 결과를 확인할 수 있었다.

**결정** — 발표 후 참가자 목록에서 **그 사람의 카드가 달라진다.**

- 카드 테두리와 바탕이 강조되고, 매력 자리에 `💘 서로 찔렀어요`가 들어간다
- **색만으로 말하지 않는다.** 글자로 같은 정보를 준다
- 같은 테이블이면 테이블 번호까지 카드에 붙는다
- **목록에서 맨 위로 올라온다.** 스무 명을 훑어 내려가게 두면 다른 탭에 숨긴 것과 같다
- 프로필 시트 맨 위에 매칭 카드가 뜬다
- 홈의 `결과 보기` 는 **참가자 탭**으로 간다
- '내 정보' 탭에는 결과가 없다. 그 탭이 답하는 질문은 "내가 낸 것이 무엇인가" 하나다
- 서로 찌른 상대가 없으면 홈에서 문장으로 말한다. **"0명"이라는 숫자를 꺼내지 않는다**

연락처도 이 자리에서 열린다 (ADR-19).

발표 전에는 `matches` 가 비어 있어서 목록에 아무 표시도 생기지 않는다. 테스트로 고정했다.

## ADR-19 연락처는 서로 찌른 쌍에게, 발표 후에 열린다

**바뀐 것** — 처음에는 "연락처는 매칭돼도 주지 않는다. 앱은 같은 테이블까지만 만든다"였다.
운영자 판단으로 **서로 찌른 쌍에게는 연락처를 연다**로 바꿨다.

**왜 그래도 안전한가** — 이 앱이 없애려는 건 *거절당하는 경험*이지 연락 그 자체가 아니다.
연락처는 **양쪽이 서로를 골랐을 때만** 열린다. 한쪽만 찌른 상대에게는 발표 뒤에도 끝까지 익명이다 —
일방적인 호감이 드러나지 않는다는 첫 번째 기둥은 그대로다.

**통로는 하나뿐이다.** `MatchInfo.contact` 는 `pokeState()` 의 `phase === "done"` 블록,
그것도 `mutual` 에 든 쌍만 지나는 자리에서 채워진다. 세 조건이 구조로 겹쳐 있다.

- 명단(`roster`)은 여전히 `toPublic()` 만 지난다. 예외 없다
- 발표 전에는 `matches` 자체가 비어 있다
- 셋 다 테스트로 고정했다 (발표 후 열림 / 발표 전 없음 / 한쪽만 찌른 경우 없음)

**받을 때 한 약속을 먼저 고쳤다.** 등록 화면은 "연락처는 운영자만 봐요"라고 말하고 있었다.
그 문구를 그대로 둔 채 상대에게 넘기는 건 기능 변경이 아니라 약속을 어기는 일이다.
지금은 등록 전에 이렇게 말한다 — *"연락처는 운영자와, 발표 때 서로 찌른 상대에게만 보여요.
한쪽만 찌른 경우에는 끝까지 공개되지 않고, 파티가 끝나고 3일 뒤에 지워져요."*
(2026-08-16 기본 보관 기간을 7일 → 3일로 줄였고, 회차 설정에서 1~14일로 조정할 수 있게 했다.
등록 화면 문구는 회차의 `retentionDays` 를 그대로 읽는다 — 문구와 파기 판정의 출처가 같다)

**대가** — 한 번 나간 번호는 되돌릴 수 없다. 보관 기간 파기는 우리 쪽 저장소만 지운다.
그래서 공개 범위를 **양쪽 합의**로 좁혀둔 것이고, 이 조건을 넓히는 변경은
등록 화면 문구를 먼저 고치지 않고는 하지 않는다.

## ADR-20 오늘의 연애운 — 점수를 매기지 않고, 한 번 열면 바뀌지 않는다

**무엇** — 파티가 시작되면 참가자 탭 **맨 오른쪽**에 '오늘' 탭이 생긴다.
카드를 뒤집으면 LLM 이 쓴 오늘의 연애운 한 편(세 문단)과 **오늘의 미션**이 나온다.
이 앱에서 유일하게 기능이 아니라 재미인 자리다.

탭은 끝에 붙인다. 도중에 끼어들면 있던 탭들이 밀려서 손가락이 기억한 자리가 어긋난다.

세 문단은 **오늘 그 파티에서 일어날 법한 일**만 말한다 — 오늘의 결 · 잘 통할 흐름 ·
조심하면 좋을 것. 먼 미래나 인생 전체를 말하지 않는다.
미션은 그 세 문단에서 이어지고, **30분 안에 해볼 수 있고 실패해도 티가 나지 않는 것**이다.
"용기를 내세요" 같은 말은 미션이 아니다.

**미션은 두 칸이다 — 왜(`lead`)와 언제·무엇(`mission`).**
한 줄만 던지면 남이 준 숙제로 읽히고, 숙제는 미뤄진다. 오늘의 운세에서 이어지는 이유가
앞에 서야 내 것이 된다. 그리고 미션 문장에는 **언제 할지**가 들어간다 —
누구에게·무엇을 만 정해주면 그 순간이 오지 않는다. 시계 시간이 아니라 상황으로 적는다
("자리를 옮기고 막 앉았을 때", "대화가 잠깐 멎었을 때").

**무게와 압박은 다르다.** `lead` 는 이유만 말하고 **시키지 않는다** — 시키는 건 미션 한 문장뿐이다.
'꼭'·'반드시'·'해야' 를 쓰지 않는다. 같은 이유로 **"했어요" 체크는 만들지 않는다** —
했다/못 했다가 남으면 그게 곧 점수이고, 이 앱이 없애려던 경험을 앱이 다시 만든다.

`lead` 는 **없이 올 수도 있다.** LLM 이 빼먹었을 때 쓸 만한 미션까지 버리는 건 손해가 더 크다 —
그때는 미션 한 줄만 저장되고 화면도 한 줄로 그린다. 이 칸이 생기기 전에 열어 둔 운세도 마찬가지다.

### 점수를 매기지 않는다

연애운 앱의 기본형은 `82점`인데 여기서는 그게 독이다. 이 앱이 없애려는 게
거절당하는 경험인데 `당신의 오늘 연애운 34점`은 앱이 **직접** 그 경험을 만든다.
파티장에서 옆 사람과 비교하는 순간까지 만든다.

그래서 좋고 나쁨이 아니라 **오늘의 결**을 말한다. 모델에게도 못 박아 둔다 —
점수·등급·순위 금지, 외모 금지, 단정 금지. 화면에 숫자가 없는 것까지 테스트로 고정했다.

### 한 번 열면 바뀌지 않는다

회차 DO 에 1인 1행으로 저장하고, 두 번 저장돼도 **먼저 온 하나**가 남는다
(`ON CONFLICT DO NOTHING`). 다시 열 때마다 달라지면 그 순간 전부 거짓말이 된다.
색과 '말이 잘 통할 결'은 닉네임+MBTI 해시로 정해서 LLM 없이도 같은 값이 나온다.

### LLM 에 보내는 것은 두 입력 함수가 만드는 것뿐이다

호출이 둘이라 **재료도 둘로 갈린다.**

| 호출 | 함수 | 보내는 것 |
|---|---|---|
| ① 오늘의 기운 (사주) | `fortuneInput()` | **실명** · 생년월일 · 성별 · **오늘 날짜** |
| ② 오늘의 미션 | `missionInput()` | **실명** · 닉네임 · MBTI · 매력 3가지 · **방금 나온 운세** |

②가 돌려주는 것은 `{lead, mission}` 두 칸이다.

**미션을 두 번째 호출로 뺀 이유** — 한 호출에서 함께 뽑으면 미션이 본문 마지막 문단을
그대로 옮겨 적었다. 다 읽고 나서 "그래서 오늘 뭘 하지" 를 따로 물으면 겹치지 않는다.

그리고 그 호출은 **참가자가 미션 카드를 뒤집을 때** 나간다. 운세 카드를 뒤집는 것과 같은 의식이다 —
미리 만들어 두고 감췄다 보여주면 "여는 동작이 있어야 오늘 것처럼 읽힌다" 는 이 ADR 의 말과 어긋난다.
안 열어 본 사람 몫을 아예 만들지 않는 것은 덤이다.

**저장이 규칙을 지킨다.** `saveFortune` 의 `ON CONFLICT DO NOTHING` 이 곧 "한 번 연 운세는
바뀌지 않는다" 이고, 미션은 그걸 우회하지 않도록 **`saveMission` 이 따로** 채운다 —
이미 있으면 그대로 돌려주고, 운세 본문은 건드리지 않는다.
(`saveFortune` 로 덮어쓰는 길을 만들면 그 규칙이 조용히 무너진다.)
`parseFortune` 은 `FortuneDraft`(미션 없는 모양)를 돌려준다 — **타입으로 갈라두면
한 호출에서 둘 다 뽑으려는 시도가 컴파일에서 막힌다.**

**읽기는 좁게 한다.** 두 경로 모두 `fortuneContext()` 를 쓴다 — 단계·나·저장된 운세 셋만 꺼낸다.
`participantState()` 를 부르면 명단 전체를 `toPublic()` 으로 빚고 콕을 집계하는데,
파티가 시작되면 이 경로가 인원 수만큼 한꺼번에 열린다. 지금 규모(50명)에서는 그것만으로
줄이 서지 않지만, 필요 없는 일을 인원 수만큼 하지 않는 것은 그 자체로 옳다.

> ⚠️ `fortuneContext()` 의 `me` 에는 **실명이 있다.** LLM 입력을 만드는 데만 쓰고,
> 라우트가 돌려주는 건 `Fortune` 하나여야 한다. 그대로 내보내면 참가자 응답에 이름이 실린다.

**오늘 날짜는 파티가 열리는 지역 기준**이다 (`todayIn`). UTC 로 자르면 자정 넘은 파티가
어제 날짜를 읽는다 — 한국 밤 9시는 UTC 로 같은 날 정오지만, 새벽 1시는 UTC 로 어제다.

**전화번호와 인스타는 어느 쪽에도 가지 않는다.** 이건 그대로다.

**생년월일**은 여는 순간 본인이 직접 넣고(진짜 운세 보는 의식) 별자리·띠로 풀려 실린다.
**전송에만 쓰고 어디에도 저장하지 않는다** — 운세와 함께 남기면 전화번호 옆에 놓이는
가장 무거운 신원 정보가 된다. 라우트가 읽고 그 자리에서 버린다.

#### 개정 — 실명을 운세 호출에만 허용한다

원래는 실명도 금지였다("참가자끼리도 안 주는 걸 외부에 보내는 건 더 나쁘다").
바꾼 이유는 **사주의 재료가 이름과 생년월일**이어서다. 닉네임으로 보는 사주는 사주가 아니다.

대신 예외를 **좁게** 두고 셋을 함께 지킨다. 하나라도 빠지면 예외가 아니라 구멍이다.

1. **오늘의 운세 기능(두 호출)에만.** 그 기능 밖으로는 어떤 이유로도 나가지 않는다 —
   경계가 "기능 하나" 라야 "어디까지 보내도 되나" 를 되묻지 않는다
2. **답변에 이름이 나오지 않는다.** 프롬프트가 못 박고 2인칭으로 쓰게 한다.
   보내는 것보다 **남는 것**이 무겁다 — 답변에 이름이 나오면 저장물에도 화면에도 남는다
3. **저장하지 않는다.** 생년월일과 같다. 전송에만 쓴다

세 가지 전부 테스트가 고정한다 (`test/08-fortune.test.ts`) — 특히 ①은
어필 입력에 실명이 섞이는 순간 깨진다.

**같이 걷어낸 것** — '말이 잘 통할 결'(MBTI 궁합)은 없앴다. 운세 재료가 사주로 좁혀지면서
MBTI 를 보낼 이유가 사라졌고, 그 줄만 살리자고 재료를 넓히는 건 앞뒤가 바뀐 일이다.

'오늘의 어필' 카드도 걷어냈다. 미션과 **같은 말을 두 번** 하고 있었다 —
어필에 미션을 참고로 넘겼더니 그대로 받아 적었다. 두 카드가 서로를 알게 하려던 것이
서로를 베끼게 만들었다. 지금은 미션 하나만 남고, 그게 운세를 읽고 나온다.

### 실패는 정상 경로다

키가 없거나 · 모델 이름이 틀렸거나 · 느리거나(6초) · 형식이 어긋나면 **규칙 문구**로 떨어진다.
그래서 그쪽 문장도 읽을 만하게 썼다 — 본인이 쓴 매력 한 줄을 그대로 안아 쓴다.
파티 당일에 탭 하나가 에러를 뿜는 건 사고다.

**호출은 Worker 에서 한다. DO 안에서 부르지 마라** — DO 는 요청을 한 줄로 처리해서,
응답을 기다리는 몇 초 동안 그 회차의 모든 요청이 뒤에 선다. 파티 중에는 그게 곧 정지다.

**읽는 자리는 `readFortune()` 하나다.** 지금은 1.0.0 이 쓴 모양만 들어 있어 할 일이 없지만,
다음에 모양이 바뀌면 고칠 곳이 여기 하나다 — '오늘의 한 걸음'(`step`)이 '오늘의 미션'(`mission`)이
됐을 때 여기가 그 일을 했다. 그 자료는 1.0.0 기준선에서 사라졌다.
`readFortune()` 이 옛 이름을 받아준다. 저장된 자료는 코드보다 오래 산다 (기본값 NaN 사고와 같은 자리).

**모델은 설정이다** — `LLM_MODEL` · `LLM_BASE_URL` · `OPENAI_API_KEY`.
제공자가 바뀌어도 코드가 아니라 변수가 바뀐다. 모델 이름이 틀리면 규칙 문구로 떨어질 뿐 앱은 돈다.

## ADR-21 참가자 명단은 한 번에 다 열리지 않는다

**결정** — 단계마다 보이는 만큼만 보인다.

| 단계 | 보이는 것 |
|---|---|
| 준비 중 · 등록 중 | **아무것도 없다.** 명단도, 인원 수도 |
| 사전 투표 | 닉네임 · 매력 3가지 |
| 파티 시작 후 · 발표 | + 나이 · MBTI |

**왜** — 등록만 하고 기다리는 동안 남의 프로필을 훑는 시간이 길수록,
파티장에서 처음 만나는 순간이 줄어든다. 사전 투표에서 사람을 고를 때 필요한 건
닉네임과 그 사람이 직접 쓴 매력 세 줄이다. 나이와 MBTI 는 그 자리에서 판단을 굳히는 재료라
**눈앞에 사람이 있을 때** 여는 편이 낫다.

**인원 수도 등록 중에는 안 나간다.** 한동안 "기다리는 사람에게 필요한 정보" 라고 보고 내려줬는데,
**인원이 적을수록 그 숫자 하나가 명단만큼 많은 것을 말한다.** 둘이 등록한 회차에서 `2명` 은
"나 말고 한 명" 이고, 그 한 명이 누구인지는 단톡방에서 금방 좁혀진다.

그래서 `ParticipantState.event` 에서 아예 뺐다 — 사전 투표부터는 `roster` 가 대신 말하므로
어느 단계에도 필요 없다. **명단 방송(`roster`)에도 수를 싣지 않는다**: 전원에게 나가는 신호이고,
받는 쪽은 어차피 다시 읽는다 (ADR-26). 화면에서 감추는 것으로는 부족하다 —
개발자 도구를 여는 참가자가 있다.

**성별은 내내 있다.** 이성만 보기와 아바타가 이걸로 그려진다 — 기능이 걸려 있어서 뺄 수 없다.

**화면에서 감추는 게 아니라 응답에 없다.** `toPublic(player, phase)` 한 곳에서 갈린다.
개발자 도구를 여는 참가자가 반드시 있고, 그 사람에게도 없어야 한다.
단계별로 응답 키 목록을 테스트가 고정한다.

**대가** — 등록 직후 참가자 탭이 비어 있다. 왜 비었는지 그 자리에서 말해준다
("사전 투표가 열리면 참가자를 볼 수 있어요"). 아무 말 없이 빈 목록이면
"내 등록이 안 됐나" 싶어진다.

## ADR-22 운영자도 '받은 콕'은 보지 않는다 · 입장 코드는 바꾸지 않는다 · 설정은 확인을 거친다

### 받은 콕을 응답에서 뺀다

현황 탭에서 '아직 콕을 못 받은 사람' 을 뺐던 것과 같은 이유다 —
**알면 그 사람을 다르게 대하게 된다.** 파티를 진행하며 한 사람을 더 챙기거나 덜 챙기게 되고,
그건 이 앱이 없애려던 경험을 운영자 손으로 만드는 일이다.

화면에서 감추는 게 아니라 `HostState` 에서 뺐다. 참가자 삭제 확인창의 숫자에서도 뺐다 —
거기서 새면 감춘 의미가 없다. **사전 투표 1위는 남는다.** 그건 진행 멘트에 실제로 쓴다.

보낸 콕은 남긴다. "누가 아직 아무도 안 찔렀나" 는 운영자가 말을 걸어볼 신호다.

### 입장 코드는 만든 뒤에 바꾸지 않는다

이미 나간 링크·안내와 어긋나고, 바뀐 걸 모르는 사람은 문 앞에서 막힌다.
되돌릴 방법도 없다. 설정 화면에서는 **글자로만** 보여주고, 서버는 `code` 를 받아도 무시한다.
`EventPatch` 에서 아예 지웠다 — 받지 않는 값은 타입에도 두지 않는다.

### 콕 상한은 이미 쓴 횟수 아래로 못 내린다

내리면 그 사람의 남은 횟수가 음수가 되고, 화면은 "−1회 남음" 을 보여준다.
이미 보낸 콕을 되물릴 방법도 없다 — 그래서 **막는 쪽**이 맞다.

두 겹으로 둔다. 화면에서는 `−` 버튼이 그 아래로 내려가지 않고(`pokeUsedMax`),
서버는 같은 규칙으로 409 를 준다. 사람이 고르는 자리와 판정하는 자리를 둘 다 막는다.

### 설정은 확인을 거쳐야 적용된다

이 화면의 저장은 **참가자 전원의 화면**을 바꾼다 — 콕 횟수도, 일정도.
그래서 규칙 4 대로 무엇이 어떻게 바뀌는지 항목으로 보여주고, 바뀐 것만 보여준다.
아무것도 바꾸지 않고 눌렀으면 빈 확인창 대신 그렇다고 말한다.

## ADR-23 커플 자리는 다른 라운드와 화면이 달라야 한다

**배경** — 마지막 라운드는 `buildSeating(final: true)` 로 만든다. 이 라운드의 목적은 하나다 —
**서로 찌른 쌍을 같은 테이블에 앉히는 것.** 떼어놓는 맞교환은 아예 시도하지 않는다 (ADR-11).

그런데 화면에는 그게 **하나도 보이지 않았다.** 이름만 늘어놓여 있어서
배정이 제 일을 했는지 눈으로 확인할 방법이 없었고, 제목 한 줄만 달랐다.

### 이름을 바꿨다

`마지막 자리 배정` → **`💘 커플 자리 배정`**.
'마지막' 은 지킬 수 없는 약속이다 — 그 뒤에 한 번 더 배정할 수 있고, 실제로 그럴 일이 있다.
이름은 그 버튼이 **하는 일**을 말해야 한다.

**참가자에게는 이 라운드가 특별하다고 말하지 않는다.** `${round}라운드` 로만 알린다 —
"커플 자리" 라고 알리면 같은 테이블에 앉은 사람 중 누가 나를 찔렀는지 짐작하게 된다.
"마지막 자리" 도 뺐다. 지킬 수 없는 약속이라서.

### 화면에 더한 것 넷

1. **성적표** — `서로 찌른 8쌍 중 7쌍을 같은 테이블에`. 이 라운드가 제 일을 했는지 한 줄로
2. **떨어진 쌍을 이름으로** — 인원 구성상 100% 가 안 될 수 있다 (SEATING.md 기준 90%).
   못 붙인 쌍이 운영자가 맞교환으로 손볼 수 있는 **유일한 신호**다
3. **자리 위의 💘** — 같은 테이블에서 이어진 사람에게 붙는다. 다른 라운드에는 붙이지 않는다.
   그 라운드들은 쌍을 붙이려 하지도 않아서, 표시가 있으면 오해가 된다
4. **쌍을 깨는 맞교환에 확인** — 막지는 않는다. 현장 사정은 운영자가 안다.
   다만 무엇이 깨지는지는 이름으로 말한다

### 섞기가 쌍을 흩어놓던 것을 고쳤다

`shuffleSeating()` 은 남녀 비율만 지키고 쌍은 보지 않았다.
커플 자리에서 누르면 **버튼 하나로 그 라운드가 무의미해졌다.**

커플 자리에서는 붙어 앉은 쌍이 자리를 지키고 나머지만 섞인다.
성비도 그대로다 — 쌍이 제자리에 있으니 각 테이블의 남녀 수는 애초에 변하지 않는다.
버튼은 숨기지 않는다. "이 조합이 마음에 안 든다" 는 커플 자리에서도 일어나는 일이고,
그때 원하는 건 쌍을 푸는 게 아니라 **나머지를 다시 섞는 것**이다.

### 확정해도 배정은 닫히지 않는다 (ADR-28 에서 바뀜)

처음에는 커플 자리를 확정하면 배정을 닫고 `배정 다시 열기` 를 거치게 했다.
지금은 닫지 않는다 — 확인창에는 성적표만 한 번 더 나온다.

## ADR-24 한 사람이 여러 명과 이어질 수 있다

콕이 1인당 여러 번이므로 A–B 와 A–C 가 동시에 성립한다. 막지 않는다 —
두 사람에게 마음이 가는 건 이상한 일이 아니고, 막으려면 "먼저 온 쌍만 인정" 같은
설명할 수 없는 규칙이 필요해진다.

### 참가자에게 보이는 것

**B 는 A 와 이어졌다는 것만 안다.** A 가 C 와도 이어졌다는 건 어디에도 없다.
`matches` 는 본인 기준으로만 만들어지므로 구조가 이미 그렇다 — 테스트로 고정했다.

같은 테이블에 A·B·C 가 앉아도 B 는 눈치챌 수 없다. 자리는 이유를 말하지 않는다.

### 자리 배정

**불가능한 상황이 아니다.** A 가 앉은 테이블에 B 와 C 가 함께 앉으면 두 쌍 다 성공한다.
`seating.ts` 는 처음부터 짝을 **리스트**(`partners: number[][]`)로 들고 있고
`withPartner()` 가 "짝 중 아무나 이 테이블에 있는가"를 본다 — 알고리즘은 이미 맞았다.

정원이 모자라 못 붙이는 경우에만 떨어진 쌍이 된다. 그건 다른 쌍과 똑같이 다룬다.

### 화면 코드에서 실제로 났던 사고

커플 자리 화면(ADR-23)을 만들며 짝을 `Map<string, string>` 으로 뒀다.
`A→B` 를 넣고 `A→C` 를 넣으면 **앞의 것이 덮인다.** 결과는 조용했다 —
A–B 쌍이 성적표에서 빠지고, 💘 가 엉뚱한 사람에게 붙고, 맞교환 경고가 뜨지 않았다.

지금은 이렇게 한다.
- 짝은 `Map<string, Set<string>>` — 사람마다 **여럿**
- 성적표는 사람→짝 지도가 아니라 **쌍 목록**(`mutual`)을 그대로 센다.
  지도에서 세면 쌍 하나가 통째로 빠진다
- 💘 는 같은 테이블의 짝 수를 센다. 둘이면 `💘×2`
- 맞교환 경고는 **떨어지게 되는 쌍을 전부** 이름으로 보여준다. 한 번에 여럿이 깨질 수 있다

**교훈** — "한 사람에 하나" 로 모델링하기 전에 그게 정말 하나인지 본다.
여기서는 아니었고, 틀렸을 때 에러가 나지 않고 조용히 빠졌다.

## ADR-25 여러 쌍 중에서는 콕을 더 많이 주고받은 쪽을 먼저 붙인다

**문제** — A 가 B·C 둘과 이어졌는데 (ADR-24) 정원이 모자라 한 명하고만 앉힐 수 있다.
지금까지는 **목록에 먼저 온 쌍**이 자리를 가져갔고, 그 순서는 Set 순회 순서라 사실상 임의였다.

**결정** — 주고받은 콕 횟수로 정한다. 많이 오간 쪽이 먼저 앉는다.

두 군데에 같은 기준을 넣었다.

1. **자리를 잡는 순서** — 쌍 목록을 세기 순으로 정렬해 강한 쌍부터 앉힌다.
   `buildSeating` 의 ① 단계는 앞의 쌍이 자리를 가져가는 구조라, 정렬만으로 우선순위가 생긴다
2. **벌점** — 붙여 앉히는 보너스가 세기에 비례한다 (`pairWeight`)

**상한을 둔다** — `pairWeight` 는 2를 넘지 않는다. 없으면 30번 주고받은 한 쌍이
나이차 벌점을 통째로 밀어내고 그 테이블만 이상해진다. 가중치가 다른 가중치의 합을
넘으면 안 된다는 건 마지막 라운드에서 이미 겪었다 (ADR-11).

**왜 이 기준인가** — 세 번 주고받은 쌍과 한 번씩 주고받은 쌍 중 하나를 골라야 한다면,
앞의 것이 더 확실한 신호다. 다른 후보(먼저 찌른 순서, 나이차, 무작위)는 설명할 수 없거나
운영자가 손댈 수 없는 값이다. 주고받은 횟수는 두 사람이 스스로 만든 값이다.

**화면도 같은 순서다** — 운영자의 커플 목록이 세기 순으로 읽힌다. 상단이 가장 확실한 쌍이다.

## ADR-26 실시간은 "다시 읽어라" 신호이고, **끊겼던 것도 신호다**

**측정** — QA 에서 재보니 단계 전환 브로드캐스트 +250ms, 콕 +218ms 로 도착한다.
소켓 자체는 잘 돈다. 문제는 **끊긴 동안**이었다.

서버는 놓친 걸 다시 밀어주지 않는다. 콕은 받은 그 순간 한 번만 나가고,
연결이 없으면 그걸로 끝이다. 상태는 서버에 남아 있으니(`receivedCount`)
**다시 읽기만 하면** 되는데, 다시 읽을 계기가 없었다.

파티장에서 폰을 주머니에 넣었다 꺼낸 사람만 옛 화면을 본다 — 조용한 사고다.

**세 가지를 더했다.**

1. **다시 붙으면 한 번 부른다** — `reconnect` 는 서버가 보내는 게 아니라
   클라이언트가 스스로 만드는 신호다. 화면이 스스로 따라잡는다
2. **주기적으로 두드린다** — 25초마다 ping. 죽은 소켓은 `close` 없이 조용히 멈추기도 한다
   (폰이 잠들거나 통신사가 바뀔 때). 70초 동안 아무 소식이 없으면 끊어서 재연결 경로를 태운다
3. **앱으로 돌아오면 따라잡는다** — `visibilitychange`. 폰을 꺼내는 순간이
   사람이 화면을 가장 믿는 순간이다. 소켓이 죽어 있으면 백오프를 기다리지 않고 바로 붙는다

`pong` 으로는 화면을 다시 그리지 않는다. 살아 있다는 뜻일 뿐이다.

**비용** — ping 은 1인당 파티 세 시간에 400여 번이지만 **메시지는 요청으로 세지 않는다.**
WS 는 연결 1건만 요청이다. 이게 애초에 폴링 대신 WS 를 고른 이유다.

**테스트를 쓰지 않았다** — 가짜 소켓을 세워 재연결을 흉내내는 테스트를 써 봤는데,
규칙이 아니라 배관을 검사하고 있었다. 리팩터링에 깨질 뿐 지켜주는 게 없어서 버렸다.
서버 쪽 절반(ping → pong)은 QA 에서 확인했다 (+173ms).

## ADR-27 매력은 사전 투표가 열리기 전까지만 고칠 수 있다 — **대상이 넓어짐 (ADR-31)**

> 지금은 매력만이 아니라 **등록할 때 낸 것 전부**(전화번호 제외)가 이 규칙을 따른다.
> 경계(`phase === "reg"`)와 그 이유는 아래 그대로다.


**왜 열어주나** — 등록 폼 3스텝의 마지막 칸에서 급히 쓴 세 줄이다.
"세 가지 모두 필요해요" 를 채우려고 아무거나 적고 넘어간 사람이 있고,
그 세 줄이 파티에서 자기를 대신 소개한다. 다듬을 시간은 줘야 한다.

**왜 닫나** — 사전 투표가 시작되면 사람들이 그 세 줄을 **보고** 콕을 찌른다.
그 뒤에 바꾸면 누군가 나를 고른 근거가 조용히 사라진다.
찌른 사람은 자기가 무엇을 보고 찔렀는지 다시 확인할 방법도 없다.

**경계는 `phase === "reg"`** — 등록 중에만 열린다.
`prep` 은 등록 자체가 없고, `prevote` 부터는 명단이 열리는 시점과 정확히 같다 (ADR-21).
명단이 열리는 순간과 매력이 잠기는 순간을 같게 뒀다 — 두 개의 경계를 기억하지 않아도 되게.

닫힌 뒤 시도하면 왜 안 되는지 말한다. "저장되지 않았어요" 로 끝내지 않는다.

## ADR-28 커플 자리를 확정해도 배정은 닫히지 않는다 · 테이블 수는 누를 때 묻는다

### 배정을 닫지 않는다

커플 자리를 확정하면 `seatingClosed` 가 켜지고, 더 배정하려면 `배정 다시 열기` 를 눌러야 했다.
지각자를 막으려는 장치였는데, 실제로는 **한 번 더 자리를 바꾸는 일이 그냥 있다** —
쌍이 떨어졌거나, 테이블이 비었거나, 사람이 더 왔거나.

그때마다 "닫혔습니다 → 다시 열기 → 배정" 세 단계를 지나게 하는 건
막을 이유가 없는 일에 문을 세운 것이다. 플래그·API·화면 분기를 통째로 지웠다.
`자리 재배정`·`커플 자리 배정` 은 발표 전까지 언제나 눌린다.

**발표(`done`)만이 자리를 끝낸다.** 그건 지금도 막혀 있고, 그 하나면 충분하다.

### 테이블 수는 배정을 누를 때 묻는다

`테이블 수` 스테퍼가 화면 맨 위에 상시 떠 있었다. ADR-5 는 **테이블 수는 설정이 아니라
배정 시점의 입력값**이라고 적어뒀는데, 화면은 설정처럼 보였다 — 지금 값이 적용된 건지,
다음에 쓸 값인지 알 수 없다.

이제 배정 버튼을 누르면 시트가 열리고 거기서 고른다. 구조와 화면이 같아진다.

**숫자만 받지 않는다.** 그 숫자가 만드는 자리를 함께 보여준다 —
`테이블당 6명 · 남 3 / 여 3`, 그리고 인원이 모자라거나 넘칠 때의 경고.
없으면 8을 넣어보고 결과를 보고 다시 6으로 되돌리는 일을 반복하게 된다.

- 시작값은 **지난 라운드의 테이블 수**다. 두 번째 라운드에서 같은 수를 다시 고르는 일이 흔하다
- 커플 자리에서는 몇 쌍을 붙이려는 참인지 그 자리에서 말한다
- 시트는 라우트다. 뒤로 가기로 닫힌다 (ROUTES.md)

## ADR-29 참가자를 지워도 그가 보낸 콕은 남는다

**사고가 될 뻔한 것** — 참가자를 지우면서 그 사람이 주고받은 콕을 통째로 지웠다.
그러면 **받은 사람의 숫자가 줄어든다.**

참가자 10명, A 의 받은 콕 3회. 운영자가 C 를 지운다 → A 의 받은 콕이 2회가 된다.
참가자 탭에서 C 가 사라진 것도 **동시에** 보인다. 그 둘을 맞추면 —
**"C 가 나를 찔렀구나."**

받은 콕은 끝까지 익명이어야 한다 (CLAUDE.md 절대 규칙 1). 삭제가 그 문을 열고 있었다.

**결정**
- **보낸 콕은 남긴다.** 받는 쪽 숫자가 흔들리지 않는다.
  남는 건 아무것도 가리키지 않는 아이디뿐이다 — 이름도 번호도 `pokes` 에 없다
- **받은 콕은 지운다.** 보낸 사람의 **예산이 돌아온다**.
  없는 사람에게 쓴 횟수를 물릴 이유가 없다. 새 정보도 아니다 —
  자기가 누구를 찔렀는지는 본인이 알고, 명단이 줄어든 것도 이미 보인다

**따라오는 정리** — 운영자 집계는 **지금 있는 사람만** 센다.
없는 사람의 아이디가 커플 목록에 빈 이름으로 뜨거나, `pokeUsedMax` 를 묶어
콕 상한을 못 내리게 하면 안 된다.

자리 배정과 발표는 이미 방어돼 있었다 — `World` 는 모르는 아이디를 건너뛰고,
`matches` 는 `player()` 가 null 이면 거른다.

**교훈** — "관련된 걸 다 지운다" 는 깔끔해 보이지만, 숫자가 줄어드는 것 자체가 정보다.
지울 것과 남길 것을 **누가 무엇을 알게 되는가**로 갈랐어야 했다.

스무 명 목록에서 같은 이모지가 열두 번 반복되면 눈이 미끄러진다.
첫 글자도 후보였지만 "김" 으로 시작하는 사람이 여럿이면 다시 뭉개진다.
동물은 닉네임 해시로 골라 목록·프로필·자리·현황이 같은 아바타를 쓴다 —
"이 사람 어디 앉았지" 가 눈으로 풀린다.

동물을 고르는 기준 셋 — 귀여울 것(무섭거나 벌레스러운 것은 뺀다. 소개팅 자리의 얼굴이다) ·
같은 종을 두 번 넣지 않을 것(🐶와 🐕가 다른 두 사람이면 구분이라는 목적을 잃는다) ·
사람을 닮은 것·표정이 강한 것은 뺄 것(참가자를 특정 인상으로 대신 말하게 되면 안 된다).

**성별은 링 색이다 (두 번 바뀜).** 처음에는 배경이 해시 색(색=사람), 다음은 성별 그라데이션
채움이었다. 채움은 실제 화면에서 실패했다 — 채도 높은 분홍 위에서 분홍 고래가 뭉개졌다.
이모지는 말풍선 같은 중립 배경용 그림이다. 그래서 바닥은 어두운 틴트로 낮추고
성별의 채도는 **테두리 링**(남 파랑 · 여 분홍, 자리 탭과 같은 단색)이 가져간다.
남녀는 더 또렷해지고 동물은 자기 색으로 뜬다.
역할이 겹치지 않는 게 핵심이다: **동물 = 사람, 링 = 성별.** 하나가 둘을 말하려 하면 둘 다 흐려진다.

동물은 40마리에서 **24마리**로 줄였다 — 전신 동물(🦙🦒🐢🦢)은 21px 에서 형체가 안 읽혔다.
얼굴형 이모지는 작은 크기용 "큰 머리"로 그려져 있어 살아남는다. 겹칠 확률은 올라가지만,
알아볼 수 없는 40마리보다 알아볼 수 있는 24마리가 낫다 — 아바타는 소프트 식별자다.

**매력은 한 줄에서 자른다.** 등록 폼이 "문장으로 써도 좋아요" 라고 권하므로
셋을 다 펼치면 카드 키가 제각각이 되고 목록이 들썩인다. 전문은 프로필 시트에서 본다.

**콕 횟수를 오른쪽으로.** 왼쪽에 두면 찌른 카드만 폭이 좁아져 목록이 들쭉날쭉했다.
오른쪽 자리는 0회일 때도 비워두므로 폭이 흔들리지 않는다.

### 현황 탭 — 받은 콕 순위를 되살린다 (ADR-22 일부 뒤집음)

ADR-22 에서 받은 콕을 운영자에게도 감췄다. 운영자 판단으로 **현황 탭의 순위**로만 되살린다.

**참가자 탭의 개인 행에는 여전히 넣지 않는다.** 두 자리는 성격이 다르다 —
명단은 한 사람씩 훑는 자리고, 현황은 전체 분위기를 읽는 자리다.
목록에서 사람마다 숫자를 달아두면 그 사람을 볼 때마다 숫자가 먼저 읽힌다.

순위는 **TOP 5 다. 5위가 동점이면 그만큼 늘어난다** — 같은 수를 받은 사람을 자르면
순위가 거짓말이 된다. 제목의 N 이 실제로 보여주는 수를 말하고, 동점자는 같은 번호를 단다.

처음에는 0회까지 전원을 보여줬다 — "빼면 빠진 사람이 곧 0회" 라는 이유였다.
TOP 5 로 자른 지금은 반대가 됐다: **빠짐은 "상위권 아님"만 말한다.** 하위권이 오히려 가려진다.
바 길이는 1위 대비 비율이다 — 절대 수보다 "얼마나 몰렸나" 가 눈에 들어온다.

👑 사전 투표 1위는 왕관 카드로, 💘 상호 매칭은 양쪽 아바타 사이에 하트로 바꿨다.
둘 다 진행 중에 가장 자주 보는 것이라 형태가 읽혀야 한다.

**현황 탭의 색** — 왕관은 금색(축하), **매칭은 참가자·운영자 모두 주 색 하나**다
(화면마다 매칭 색이 다르면 색이 뜻을 잃는다). 순위 바는 하트(콕)→주 색(매칭) 그라데이션 —
받은 콕이 쌓여 매칭으로 향한다는 걸 색으로도 말한다. `--heart` 는 콕(보낸 마음)의 색이다.
순위 번호는 **받은 콕이 있는 상위 셋만** 금색 — 전부 칠하면 아무도 돋보이지 않고,
0회에 금색을 주면 금색이 거짓말을 한다.

**MBTI 배지는 네 기질 계열색**이다 (NT 보라 · NF 초록 · SJ 파랑 · SP 노랑 —
16personalities 관행이라 아는 사람에게는 설명 없이 읽힌다). 16가지에 16색을 주면
아무 색도 기억되지 않는다. **참가자용 화면의 명단·프로필 시트에서만** 쓴다 —
운영자 콘솔의 참가자 탭(Players)은 평문 그대로다.
NT 보라가 주 색과 겹치는 건 알고 허용했다: 배지는 글자가 정보를 다 나르고 색은 보조다.

자리 이동 확인율 카드는 현황에서 뺐다 — 자리를 보낸 직후에 보는 숫자라
자리 탭 라운드 카드에 있는 것으로 충분하다. 같은 숫자를 두 곳에 두지 않는다.

### 배경

화면 위 모서리에 아주 옅은 오로라를 깔았다 (`--aurora`).
**옅게** 두는 게 핵심이다 — 진하면 목록을 길게 스크롤할 때 카드 대비가 흔들린다.
스크롤과 함께 흐르지 않도록 화면에 고정한다.

### 가져오지 않은 것

프로토타입 현황에는 `총 콕 26` 같은 집계와 참여율이 있었다.
운영에 쓰이지 않는 숫자라 두고 왔다 — 화면에 있는 숫자는 전부 **누를 이유**가 있어야 한다.

## ADR-31 내 정보는 사전 투표가 열리기 전까지, 한 번에 고친다

**결정** — 등록할 때 낸 것을 참가자가 스스로 고친다. **전화번호만 빼고 전부**,
**사전 투표가 열리기 전까지**, **고치는 버튼 하나로 한꺼번에**.

ADR-27(매력만 고칠 수 있다)의 대상을 넓힌 것이다. 경계는 그대로 `phase === "reg"` 하나다.

### 왜 넓혔나

매력만 고칠 수 있고 닉네임은 못 고치는 상태가 참가자에게 설명되지 않았다.
ADR-27 의 논리는 "남들이 보고 콕을 찔렀으니 근거가 사라지면 안 된다" 인데,
**사전 투표 전에는 어느 필드에도 그게 적용되지 않는다.** 매력만 열려 있던 건
그 필드에 특별한 성질이 있어서가 아니라 그때 그것만 문제로 인식됐기 때문이다.

그리고 복구 경로가 없었다. 오타를 발견한 참가자가 할 수 있는 게 없고
운영자에게도 수정 경로가 없어서(참가자 상세에는 삭제뿐), 유일한 복구가
"운영자가 지우고 참가자가 다시 등록" 이었다. 오타 하나에 그 비용은 과하다.

비용이 가장 큰 오타는 **성별**이다. 토글 하나를 잘못 누르면 자리 배정 풀·`이성만 보기`·
아바타 색이 전부 어긋난다. 못 고치게 두는 건 보수적인 게 아니라 방치다.

### 왜 전화번호만 빼나

파티의 문이 초대 명단의 전화번호다 (ADR-15). 등록 후에 번호를 바꿀 수 있으면
**명단에 없는 번호로 갈아탈 수 있다** — 문을 우회하는 길이 생긴다.

막는 방법은 등록 폼과 같다. **입력 타입(`RegisterInput`)에 phone 키를 두지 않는다.**
들어와도 무시하는 게 아니라 자리가 없고, 저장할 때도 저장돼 있던 값을 그대로 쓴다.
규칙 테스트가 이걸 고정한다.

### 왜 하나로 합쳤나

참가자가 하는 일은 "내가 낸 것을 고친다" 하나다. 버튼이 둘이면
"무엇이 다르길래 둘이지" 를 생각하게 되는데 실제로는 아무 차이도 없다 —
둘 다 사전 투표에 잠기고 둘 다 나만 보는 정보다. 구분할 이유가 없는 걸 화면이 구분하면
사용자는 없는 의미를 찾는다.

잠기는 것도 한 번에 읽힌다. 버튼이 둘이면 잠금 문구를 두 자리에 써야 하고,
한쪽에만 쓰면 어긋난다.

서버도 합치는 쪽이 자연스러웠다. `register()` 의 upsert 가 **매력을 포함해** 전 필드를
갱신하고 있어서, 매력만 따로 UPDATE 하던 `editCharms()` 쪽이 오히려 특수 케이스였다.
지금은 등록과 수정이 `cleanProfile()` → `writeProfile()` 한 길을 같이 지난다.

**저장은 전부 되거나 전부 안 된다.** 닉네임만 실패할 수 있는 필드인데(유일성),
겹치면 같이 보낸 나이도 저장되지 않는다. 화면은 그 칸에 에러를 띄우고 **입력값을 보존한다** —
등록 폼이 `nick_taken` 을 다루는 방식과 같다. 사용자가 잃는 건 저장 버튼 한 번 더다.

### 대가

**늦게 등록한 사람에게는 수정 기회가 처음부터 없다.** 등록은 발표 전까지 열려 있는데
(파티 중 합류) 수정은 사전 투표에서 닫히기 때문이다. 규칙은 어긋나지 않는다 —
그 사람의 정보는 등록 즉시 명단에 보이므로 잠글 이유가 그 순간부터 성립한다.
"등록 후 N분" 같은 개인별 창을 주면 경계가 둘이 되므로 그렇게 하지 않았다.

대신 **화면이 그 사실을 말한다** (`ME.locked`). 버튼만 조용히 사라지면
"내 화면만 이상한가" 가 된다. 매력 하나가 잠길 때는 넘어갔을 수 있지만
내 정보 전체가 잠기면 반드시 눈에 띈다.

**인스타도 함께 잠근다.** 인스타는 발표 전까지 아무도 보지 않으므로 잠글 논리적 근거가
없는 유일한 항목이고, 틀리면 서로 찌른 쌍이 연락할 방법이 사라진다.
그럼에도 함께 잠근 이유는, **이 기능 자체가 그 오타의 완화책**이기 때문이다 —
지금까지는 인스타가 내 정보 탭에서 가려져 있고 고칠 수도 없어 다시 볼 이유가 없었는데,
고치기가 열리면 그 버튼을 누르는 행위가 오타를 발견하는 자리가 된다.
경계를 하나 더 만들 값어치가 그보다 크지 않다.
**실제로 사고가 한 번 나면 인스타만 발표 전까지 여는 것으로 되돌린다.** 그때 이 문단을 지운다.

### 저장 알림은 운영자에게만 간다

처음에는 등록과 똑같이 전원에게 `roster` 를 방송했다. 그런데 고치기가 열려 있는 건
등록 중뿐이고 **그때 참가자에게는 명단이 아예 안 내려간다** (ADR-21). 인원수도 그대로다 —
전원에게 보내면 50명이 **똑같이 그려질 화면**을 다시 읽으려고 줄을 서는 셈이었다.

실시간은 "다시 읽어라" 신호로만 쓰기 때문에(ADR-26) **신호 하나가 곧 N번의 읽기**다.
읽기 자체는 가볍지만 같은 DO 를 지나므로 쓰기 큐가 있으면 그 뒤에 선다 —
50명 리허설에서 재조회 하나가 8초까지 밀린 적이 있다.

그래서 `toHosts()` 로 좁혔다. 참가자 소켓에는 Worker 가 세션 쿠키를 보고 `playerId` 를 붙이므로,
안 붙은 소켓이 운영자 콘솔이다. 바뀐 닉네임이 필요한 건 운영자 명단 하나뿐이다.

> **일반화하지 마라.** 대부분의 변화는 참가자 화면도 바꾸므로 전원에게 가야 한다.
> 이 통로는 "참가자 화면이 똑같이 그려질 변화"에만 쓴다.

### 만들지 않은 것

수정 이력, 운영자에게 가는 수정 알림, 운영자가 참가자 정보를 고치는 길.
사전 투표 전에는 자리도 좌석 칩도 없고 인원·성비 숫자는 어차피 다시 읽히므로
운영자에게 실무상 영향이 없다.

### 후기 — "이렇게 보여요" 는 참가자 탭에 만들었다

처음에는 미리보기도 **만들지 않는 것**에 넣었다. 뒤집은 이유가 둘이다.

**숫자가 이미 어긋나 있었다.** 상단 인원수는 `SELECT COUNT(*)` 라 자기를 포함하는데
명단은 서버에서 자기를 뺀다. 10명인데 9장이었고, 등록 직후 혼자일 때는 "1명" 옆이 빈 화면이었다.

**고칠 수 있게 됐는데 확인할 자리가 없었다.** 매력 세 줄을 다듬고 나서 그게 카드에서
어떻게 읽히는지 볼 방법이 없었고, 단계마다 자기가 어디까지 보이는지도 알 수 없었다.

**내 정보 탭이 아니라 참가자 탭 맨 위**에 뒀다. 다른 카드들 옆에 같은 크기로 있어야
"군중 속의 나" 가 되기 때문이다. 두 탭의 질문은 여전히 갈린다 —
내 정보 탭은 **내가 낸 것**(실명·전화 포함), 이 카드는 **남들이 보는 것**이다.

화면 규칙은 `docs/UI.md`, 범위는 `docs/scenarios/10-my-card.md`.
**서버는 바뀌지 않았다** — 화면이 이미 받은 `me` 를 `toPublic()` 같은 함수로 줄여 그린다.

## ADR-32 참가 링크는 사람마다 다르다 — 번호는 묻지 않는다

**문제** — ADR-15 후기 2 가 연 구멍을 닫는다. **번호를 아는 사람이 그 사람이 될 수 있었다.**
전화번호는 식별자이지 증명이 아닌데, 하필 **같은 파티에 오는 사람들은 서로 번호를 아는 사이다.**

**결정 (2026-08-23)** — 초대 명단의 **한 줄마다 고유 토큰**을 발급한다. 토큰이 곧 신원이고,
**참가자는 전화번호를 치지 않는다.**

```
/j/<회차id>/<토큰>  →  등록 (또는 이미 등록했으면 자기 화면)
```

슬라이스 13 으로 간다. **15(참가자 비밀번호)는 이 결정으로 닫힌다** — 둘은 택일이었다.

### 문은 여전히 초대 명단이다

ADR-15 를 뒤집는 게 아니라 **같은 문의 열쇠를 바꾸는 것**이다. 들어오는 사람은 여전히
운영자가 미리 넣어둔 명단의 그 사람뿐이고, 바뀐 것은 *"명단에 있음"을 무엇으로 보이느냐* 다.

| | 전 (ADR-15) | 후 (여기) |
|---|---|---|
| 참가자가 대는 것 | 전화번호 — **남도 안다** | 링크 토큰 — 그에게만 배달됐다 |
| 링크 | 회차마다 하나, 단톡방에 뿌린다 | **사람마다 하나, 1:1 로 보낸다** |
| 참가자가 할 일 | 번호를 친다 | 없다. 링크를 연다 |

**"이 번호가 이 파티에 있나" 를 되묻는 창구가 사라진다.** ADR-15 가 `ENTRY_TRIES` 로
완화하려던 유출이 구조적으로 없어진다 — 넣어볼 칸 자체가 없다. 제한은 그대로 두되
(문은 여전히 인증 없이 열려 있다), 그것이 막던 일은 이제 일어나지 않는다.

### 왜 `/j/<토큰>` 이 아니라 `/j/<회차id>/<토큰>` 인가

토큰만 담으면 짧아서 당기지만, 그러면 **토큰 → 회차** 를 찾는 색인이 회차 DO 밖에 있어야 한다.
토큰은 **한 사람을 가리키는 값**이라, `metrics.ts` 가 그어둔 선("가리키게 되는 순간
그 보장이 사라진다")을 넘는다. 파기가 DO 하나 지우는 일로 끝나야 한다.

회차 아이디를 앞에 두면 Registry 에 아무것도 쌓이지 않는다. 링크는 길어지지만
**어차피 붙여넣는 것**이라 길이가 비용이 아니다.

**토큰 없는 `/j/<회차id>` 는 없앤다.** 남겨두면 구멍이 그대로다.

**회차 정보 조회도 토큰을 요구한다.** 경로만 없애는 것으로는 모자라다 —
`/api/events/by-id/:id` 가 토큰 없이 파티 이름·일정을 내주면 **회차 아이디만으로 회차가 열린다.**
ADR-15 후기에서 `by-code` 오라클을 걷어낸 것과 같은 종류다. 길을 하나 막으면 옆문도 같이 본다.

### `Join` 화면은 남는다 — 하는 일이 바뀐다

번호 칸이 사라지면 이 화면의 존재 이유가 없어 보이지만, 곧바로 등록 폼으로 넘기지 않는다.

- **등록이 아직 안 열렸을 때 말할 자리가 필요하다.** 안내문은 등록 시작 **전에** 보내므로,
  일찍 연 참가자에게 "언제 열리는지"를 들려주는 화면이 있어야 한다 (지금 하던 일 그대로다)
- 링크를 열자마자 입력 폼이 뜨는 것보다 **파티 이름·일시·장소를 한 번 보여주는 쪽**이 낫다

토큰 검증은 이 화면에 들어올 때 한 번 하고 초대 쿠키를 받는다.
**번호 칸이 있던 자리가 `등록하기` 버튼이 된다.**

### 정한 것

- **토큰은 명단 행에 붙는다** (`invites.token`). 번호를 명단에 넣을 때 `randomHex(16)` 로 만든다.
  회차 아이디가 `randomHex(8)` 인데 토큰이 그보다 약하면 링크의 강도가 거기로 내려간다
- **등록하면 `players` 행에도 복사한다.** 그래야 ADR-15 의 규칙이 살아 있다 —
  운영자가 명단을 정리하다 이미 온 사람을 지워도 그는 자기 링크로 계속 들어온다
- **실패 문구는 여전히 하나뿐이다.** 토큰이 틀렸든, 회차가 없든, 파기됐든 같은 문장.
  구분해 주면 그 구분이 곧 답이 된다
- **번호는 서버가 토큰에서 꺼내 초대 쿠키에 담는다.** `RegisterInput` 에 phone 키를
  두지 않는 방어(ADR-31)는 그대로다 — 이제 폼이 번호를 아예 보지 않는다
- **재발급 경로를 만들지 마라.** 링크를 잃으면 운영자가 안내문을 다시 보내면 된다.
  정 필요하면 명단에서 빼고 다시 넣으면 새 토큰이 나온다.
  "입장 코드는 만든 뒤에 바꾸지 않는다" 와 같은 이유다

### 세션에는 토큰을 담고, 번호를 담지 않는다

세션은 **서명만 하고 암호화하지 않는다** (`auth.ts`) — 서버에 세션 표를 두지 않으려는 선택이고,
그래야 파기가 DO 하나 지우는 일로 끝난다. 대신 **페이로드를 읽을 수 있다.**
HttpOnly 라 JS 로는 못 읽지만 개발자 도구 Application 탭에서는 그대로 보인다.

그래서 초대 쿠키(`tp_inv`)는 **참가 토큰**을 들고, 번호는 회차 DO 안에서만 푼다.
참가자가 번호를 치지 않기로 해놓고 쿠키에 번호를 남기면 그 결정이 브라우저에서 새어 나간다.

**참가자 세션은 30일이다.** 7일이었는데 파티 당일에 딱 걸렸다 —
등록이 파티 6일 전에 열리므로 첫날 등록한 사람은 당일이 7일째다.
끊기면 링크를 다시 찾아야 하고, 그게 하필 파티장에서 일어난다.
늘려도 실질 노출은 안 는다 — **회차 파기(3일)가 진짜 상한**이라 세션이 살아 있어도 열리는 게 없다.

**토큰은 주소창에만 있다.** 쿠키에도 `localStorage` 에도 넣지 않는다 —
넣으면 그 기기에서 링크 없이 계속 들어올 수 있어 편하지만, 남의 기기에 남는 값이 하나 더 생긴다.
재발급 화면을 만들지 않기로 한 것과 같은 자세다.

### 한 기기로 여러 회차

참가자 세션은 브라우저에 **하나뿐**이라 다음 회차에 들어가면 앞의 세션이 덮인다.
쿠키를 회차마다 두지 않았다 — 자료가 섞일 길을 늘리는 대신, **되찾는 비용을 링크가 낸다.**

같은 사람이 A·B 에 모두 초대돼도 각자의 링크만 있으면 한 번 누르는 것으로 오간다.
덮인 회차는 그동안 **401 이어야 한다** (S-A9). 링크는 1:1 로 보내져 대화방에 남으므로
되찾는 재료가 사라지지 않는다 — 번호를 묻던 시절보다 오히려 단계가 하나 줄었다.

### 대가 — **링크를 넘겨받은 사람은 못 막는다**

이 결정이 닫는 것은 "번호만 아는 사람" 이다. 닫지 못하는 것은 **"링크를 본 사람"** 이고,
지인 파티에서 그건 대체로 **친구**다 — 링크가 카톡에 남아 있고, 폰을 보면 보인다.
ADR-15 후기 2 의 표가 이미 이렇게 적어뒀고, 그걸 알고 고른 것이다.

15(비밀번호)만이 그 사람까지 막지만, 그 비용을 **분실 응대로 파티 당일에** 낸다.
13 은 부담을 파티 **전**으로 옮기고 참가자가 할 일을 없앤다. 그 교환을 택했다.

> 가장 비싼 유출(연락처)은 **발표 후에만** 열린다. 발표를 현장에서 사람들이 눈앞에 있을 때
> 누르는 운영이 여기서도 완화책으로 남는다.
>
> **사고가 한 번 나면 15 를 다시 연다.** 그때 이 문단을 지우고 표를 다시 그린다.

### 발송 동선 — 이 결정이 요구하는 것

링크가 사람마다 다르면 **단톡방에 하나 뿌리기가 불가능하다.** 그래서 슬라이스 13 은
발송 동선을 같이 만든다 (`PLAN.md` 13).

- 운영자가 **안내 템플릿**을 한 번 쓴다 — `{장소}` `{일시}` `{링크}` 를 치환한다.
  기본 문구는 `copy.ts`, 운영자가 고친 것은 자료로 저장한다
- 명단 **행마다 복사 버튼**. 미리보기가 버튼 위에 있어 확인 다이얼로그가 필요 없다
- **보냄 체크가 필수다.** 한 명씩 복사하는데 어디까지 보냈는지 모르면 못 한다.
  전체 1회 복사였다면 없어도 됐을 것이 여기서는 없으면 안 된다
- 채널은 가리지 않는다 — 인스타 DM·문자·카톡 어디든 붙여넣는다.
  나중에 문자 자동 발송을 붙이더라도 **같은 템플릿을 쓴다**

**회차에 `place` 를 더한다.** 시간은 `schedule` 에 있는데 장소가 없었다.
참가자 응답에는 싣지 않는다 — 안내문으로만 나간다.
**회차 마법사 2단계(일정)에 둔다** — "언제·어디서" 가 한 화면에 있는 게 자연스럽고,
1단계는 이름만 받아 가볍게 시작하는 지금 구조를 지킨다.

## ADR-33 참석 상태 — 문 앞에서 세는 것

**문제** — 파티 당일 운영자가 하는 일은 **누가 왔는지 세는 것**인데, 앱에 그 자리가 없었다.
운영자 한 명이 사람을 맞으면서 명단을 손으로 훑는 건 문 앞에서 줄을 만든다.

`노쇼 체크` 는 "아직 만들지 않는 것" 에 있었다. **연다.** 이유는 하나 —
운영자가 실제로 파티 당일에 하는 일이고, 앱이 그걸 안 하면 종이로 하게 된다.

**결정 (2026-08-24)** — 참가자에게 **참석 상태** 한 칸을 둔다. 그리고 **문 앞 QR** 로 자동으로 찍는다.

### 상태는 셋이고, 칸은 하나다

`players.attendance` — 없음(안 옴) · `arrived` · `left`.

시각을 두 개 두는 대신 칸 하나를 쓴다. **`나감` 은 도착했던 사람만 될 수 있어서** 순서가 있는
한 축이고, 시각 둘(`arrived_at`·`left_at`)로 두면 "나갔는데 온 적 없음" 같은 불가능한 조합이 생긴다.
도착 시각은 아직 아무도 묻지 않았다 — 물으면 그때 칸을 늘린다.

**라벨은 저장하지 않고 단계와 함께 계산한다.**

| 저장된 값 | 파티 시작 **전** | 파티 시작 **후** |
|---|---|---|
| player 없음 (명단만) | `미등록` | `미등록` |
| 없음 | `등록함` | **`안 옴`** |
| `arrived` | — | `도착` |
| `left` | — | `나감` |

`등록함` 과 `안 옴` 이 **같은 값의 다른 이름**이다. 상태를 하나 더 만들지 않아도 된다.

### 찍는 길은 **하나뿐이다** — 운영자가 누른다

카드 오른쪽의 상태 칩이 곧 버튼이다. 파티가 시작된 뒤에만 눌린다.
되돌릴 수 있어서 확인창이 없다.

**길을 늘리지 않는다.** 참가자가 스스로 누르는 `도착했어요` 버튼도 두지 않는다 —
경로가 둘이면 안내가 둘이 되는데, 애초에 **눌러야 하는지 모르는 참가자**가 있다.
누르지 않은 사람과 안 온 사람이 화면에서 구분되지 않으면 그 숫자는 못 믿는 숫자가 된다.

### 문 앞 QR 을 접었다 — **브라우저가 갈린다**

한동안 "문 앞에 회차 QR 을 붙이고 참가자가 찍으면 자동으로 도착" 으로 설계했다.
찍은 사람이 누구인지는 세션으로 안다고 봤고, 세션이 없으면 체크인 쿠키를 심어
나중에 링크로 들어올 때 반영하기로 했다. **둘 다 통하지 않는다.**

```
등록  :  카톡 링크  →  카카오톡 인앱 브라우저   ← 세션 쿠키가 여기 저장된다
QR    :  기본 카메라 →  Safari / Chrome        ← 여기엔 아무것도 없다
```

QR 스캔은 **폰 기본 브라우저**를 연다. 우리가 고를 수 없다. 그런데 참가자 대부분은
카톡 링크로 등록하므로 세션은 인앱 브라우저에 있다 — 문 앞 QR 은 **세션조차 못 찾는다.**
체크인 쿠키도 같은 이유로 다른 브라우저에 심긴다.

**이 함정은 두 번째다.** ADR-15 후기 2 에서 "기기 고정" 을 버린 이유가 그대로 이것이었다 —
*"카톡 인앱 ↔ 크롬 이동. 국내 기본 동선이라 정상 사용자가 계속 막힌다"*.
표에 적어둔 것을 QR 설계에서 다시 밟았다.

**반쯤 되는 것이 아예 안 되는 것보다 나쁘다.** 통할 때와 안 통할 때가 참가자 눈에
구분되지 않아서, 문 앞에서 "저는 왜 안 돼요" 가 나온다.

**원리적으로 막혀 있다.** 회차 QR 은 찍은 사람이 누구인지 모르고,
개인 QR 은 알지만 참가자가 그걸 **찾아야** 한다 — 찾을 거면 링크를 누르지 QR 을 찍을 이유가 없다.
누구인지 알려면 번호를 물어야 하는데, QR 사진은 단톡방에 도니까
"번호를 아는 사람이 그 사람이 되는" 구멍(ADR-32)이 원격에서 되살아난다.

### 대가

**안 온 사람이 도착으로 남아 있을 수 있다** — 운영자가 안 누른 것과 안 온 것이 같은 값이다.
그래서 파티 시작 **전**에는 그 값을 `안 옴` 이라고 부르지 않고 `등록함` 이라고 부른다.
숫자를 믿을 수 있는 건 운영자가 문 앞에서 실제로 누르고 있을 때뿐이고, 그게 이 기능의 전제다.

**남의 참석 상태는 참가자 응답에 나가지 않는다.** 운영자만 본다 (`HostState`).
명단(`roster`)에도, 자기 자신(`me`)에게도 넣지 않는다 — 참가자가 그 값으로 할 일이 없다.

### 아직 안 만든 것

**개인 QR** — 운영자 화면에서 그 사람의 참가 링크를 QR 로 띄워, 링크를 못 찾는 사람이
그 자리에서 찍게 하는 것. 개인 링크는 토큰을 품고 있어 **어느 브라우저에서 열려도 통한다** —
위에서 접은 회차 QR 과 갈리는 지점이 정확히 여기다. 렌더링 라이브러리가 하나 필요해서,
참석 상태가 QA 에서 도는 걸 보고 정한다.

### 후기 — 한 목록을 다시 둘로 나눴다. **축이 아니라 역할로** (2026-08-24)

이 결정은 참석 상태를 열면서 **명단과 참가자를 한 목록으로 합쳤고**,
필터 칩을 성별에서 상태(전체·등록함·미등록·도착·안 옴)로 바꿨다. 참석은 그대로 두고
**그 두 가지를 되돌린다.** 기능이 틀린 게 아니라 한 목록에 두 가지 일이 겹쳐 있었다.

**칩이 두 질문에 동시에 답하려 했다.** `미등록` 은 *등록 전*의 상태고 `안 옴` 은 *등록 후*의
상태인데, 한 줄에 나란히 서 있으면 같은 축으로 읽힌다. 실제로 두 낱말이 섞였다 —
"아직 안 온 사람"(미등록)과 "안 옴"(등록했지만 파티에 안 옴)이 같은 화면에 있었다.

**그래서 축이 아니라 역할로 나눴다.**

| | 맡는 것 |
|---|---|
| 입장 명단 (위) | 등록 **전/후** — 더하기 · 안내문 · 아직 등록 안 한 사람 · 빼기 |
| 참가자 카드 (아래) | 등록 **후** — 참석 상태 |

**합쳤을 때 얻은 것은 그대로 남는다.** 한 사람은 여전히 한 번만 나온다 —
등록하면 명단 행에서 빠지고 카드로 올라온다. 명단은 파티가 다가올수록 줄고 카드가 그만큼 는다.
합치기 전에 문제였던 "같은 사람이 두 번 나온다" 는 **화면을 갈랐기 때문이 아니라
등록한 사람을 양쪽에 뒀기 때문**이었다.

**칩은 성별로 돌아간다** — 전체 · 남성 · 여성. 칩의 진짜 용도가 "세 숫자를 한 번에 보는 것"
(성비)이었고, 그건 상태 칩으로 대신할 수 없어서 숫자 한 줄로 따로 적어야 했다.
칩이 성비를 도로 나르면 그 줄이 필요 없다 — **같은 숫자를 두 곳에 두지 않는다.**

**참석 상태는 카드 안 맨 오른쪽으로 들어갔다.** 카드 밖 형제 요소로 두니 목록 폭이 들쭉날쭉했고,
누르는 자리가 카드와 따로 놀았다. 안으로 넣으면서 카드가 버튼 하나에서 상자가 됐다 —
버튼 안에 버튼을 넣을 수 없어서 왼쪽(아바타·실명·번호)이 상세를 여는 손잡이,
오른쪽이 참석 칩이다. **한 번 눌러 찍는다는 결정은 그대로다.**

**잃은 것 — 상태별 인원 칩.** `안 옴 4` 를 눌러 그 사람들만 보는 길이 없어졌다.
대신 카드 목록 위에 `도착 8 · 안 옴 4` 한 줄을 둔다. 세는 건 되고 거르는 건 안 된다 —
스무 명 남짓이라 훑으면 보이고, 거를 만큼 길어지면 그때 다시 연다.

## ADR-34 사전 콕을 매력 투표로 가른다 — 만나기 전은 자리, 만난 뒤는 매칭

**문제** — 사전 콕이 **두 일을 겸했다.** 자리 배정의 재료이면서 매칭의 재료였다.
그런데 그 둘은 성격이 다르다 — 앞은 *"프로필만 보고 고른 것"* 이고 뒤는 *"만나보고 고른 것"* 이다.

첫 회차 숫자가 그 어긋남을 보여준다.

| | 콕 | 매칭으로 | 전환율 |
|---|---|---|---|
| 사전 | 17건 | 4건 | **24%** |
| 파티 | 53건 | 6건 | 11% |

**매칭 5쌍 중 4쌍이 사전 콕에서 출발했다.** 얼굴도 모르고 고른 것이 결과의 대부분을 정한 셈이다.

**결정 (2026-08-24)** — 둘을 가른다.

| | 언제 | 무엇에 쓰이나 | 취소 |
|---|---|---|---|
| **매력 투표** | 운영자가 연 날 → **파티 시작에 마감** | **첫 자리 배정**에만 | 된다 |
| **콕** | 파티 시작 후 | **매칭**과 **둘째 라운드부터의 자리** | 된다 |

개수는 둘 다 회차 설정을 따른다. **매력 투표는 매칭에 들어가지 않는다.**

> 저장값은 `pre` 그대로 둔다. `CHECK (round IN ('pre','party'))` 를 고치는 건 SQLite 에서
> 표를 다시 만드는 일이고, **마이그레이션에서 한 번 데인 뒤라**(ADR-32 후기) 뜻만 바꾼다.
> 뜻은 이 문서가 정한다 — `pre` 는 이제 **매력 투표**다.

### 알림을 없앤다 — 취소와 한 몸이다

**매력 투표도 콕도 참가자에게 아무 알림을 주지 않는다.**
받지 못한 사람에게 나쁜 경험이 되고, 그건 다음 파티에 안 나오는 이유가 된다.
첫 회차에서 **받은 콕 0회가 11명(30%)** 이었고 남성은 36% 였다.
지니 0.51 에 상위 5명이 37% 를 가져갔다 — 알림이 있으면 그 쏠림이 실시간으로 체감된다.

**그리고 이것이 취소를 안전하게 만든다.** 취소만 열면 받은 수가 줄어드는 것을 누가 보고
"방금 누가 취소했다" 에서 발신자를 좁힐 수 있다 — ADR-29 가 막던 유출이다.
알림이 없으면 그 창이 닫힌다. **둘은 한 몸이라 나중에 알림만 되살리면 안 된다.**

### 되돌리기와 알림은 **회차 설정**이다

운영자와 합의되지 않은 것이라 회차마다 정한다. 둘 다 `EventConfig` 에 있고,
**기본은 '되돌릴 수 있다' 와 '알리지 않는다'** 다.

| | 기본 | 없을 때 뜻 |
|---|---|---|
| `allowUndoPre` | 없음 | 매력 투표를 되돌릴 수 있다 |
| `allowUndo` | 없음 | 파티 콕을 되돌릴 수 있다 |
| `pokeNotify` | 없음 | 알리지 않는다. `true` 로 적어야 알린다 |

**되돌리기는 라운드마다 따로 정한다.** 한동안 매력 투표는 언제나 무를 수 있게 뒀는데,
회차마다 판단이 갈리는 값이라 운영자에게 넘긴다.

> **운영자 라벨은 짧게 쓴다.** `할 수 있음`·`못 함`·`보냄`·`안 보냄`.
> 설명이 길면 고르는 자리가 읽는 자리가 된다 — 참가자에게 나가는 문장이 아니다.
> 세 줄이 같은 모양이라 `Toggle` 하나로 그린다.

**알림을 끈 회차에서는 발표 전까지 `receivedCount` 를 응답에 싣지 않는다.**
화면에서 감추는 것으로는 부족하다 — 개발자 도구를 여는 참가자가 있고,
그 숫자 하나가 곧 *"지금까지 몇 명이 나를 골랐나"* 다. 발표 단계에서만 나간다.

**되돌리면 알림이 저절로 사라진다.** 알림은 저장되지 않고 `receivedCount` 에서
파생되므로(`noticesOf`, ADR-4), 무르면 그 줄이 없어져 **받지 않았던 상태로 돌아간다.**
지울 메시지가 애초에 없다.

### 매력 투표에서 '콕' 이라는 말을 쓰지 않는다

둘은 쓰임이 아예 다르다 — 매력 투표는 첫 자리 배정의 재료이고, 콕은 매칭의 재료다.
같은 말로 부르면 참가자가 *"아까 찔렀는데 왜 또?"* 가 된다.

라운드별 이름은 `copy.ts` 의 **`ACT` 한 곳**에서 나온다. 문구를 새로 쓸 때 그걸 거친다.

| | 매력 투표 | 파티 |
|---|---|---|
| 이름 | 매력 투표 | 콕 찌르기 |
| 문장 안 | 투표 | 콕 |
| 버튼 | ✨ | 👉 |

**이모지도 가른다.** 같은 👉 를 두 라운드에 쓰면 화면만 보고는 지금 무엇을 하는지 알 수 없다.

> **서버는 라운드를 모른다.** `pokeMessage` 는 실패 사유만 받으므로
> `anyClosed`·`anyNoBudget` 이라는 **중립 문구**를 따로 둔다.
> 화면이 먼저 막으므로 거기까지 오는 건 단계가 방금 바뀐 경우뿐이다.

### 되돌리기는 **확인창 안**에 둔다

목록 행에 버튼을 하나 더 두면 **카드가 화면 밖으로 밀린다.** 그리고 더 나쁜 게 있다 —
되돌리기는 **찌른 사람 옆에만** 나오므로, 어깨너머 가리기(슬라이스 16)를 켠 동안
그 버튼이 보이면 *"이 사람을 골랐다"* 가 그대로 샌다. 그 슬라이스의 유일한 불변식이
버튼 하나로 깨진다.

확인창은 **이미 숫자를 보여주고 있다**(보낸 횟수·남은 횟수). 거기가 제자리다.
`confirm({ second })` 로 받는다. 이미 보낸 적이 있고 되돌릴 수 있을 때만 나온다.

**자리는 실행 버튼 옆이다.** 둘은 같은 축의 반대 방향이라(한 번 더 / 한 번 물리기)
붙어 있어야 무엇을 고르는 자리인지 읽힌다. **취소는 아래 줄로 내린다** —
아무것도 하지 않고 닫는 것이라 성격이 다르다.

```
[ 되돌리기 ]  [ 매력 투표 ]
[        취소        ]
```

### 보류한 것

첫 기획에는 있었으나 **운영자와 합의되지 않아 이번에 만들지 않는다.**

| | 상태 |
|---|---|
| **둘째 라운드부터의 함께 점수** (50 · 동석 −10 · 콕 +10 · 나이차 −5) | **보류.** 실제 파티에서 재보고 확정한다 |
| **커플 자리 폐지** (ADR-23·28) | **보류.** 지금 규칙 그대로 둔다 |
| 같은 테이블 · 지나온 테이블 보기 | `PLAN.md` 23 |
| 운영자 투표 화면 | `PLAN.md` 24 (서버는 이미 있다) |

자리 배정은 **지금 알고리즘 그대로**다. 매력 투표가 `pre` 라운드에 그대로 들어가므로
첫 자리 배정에 자연히 반영된다 — 바꾼 것은 **매칭이 그것을 세지 않는다**는 한 줄뿐이다.

> **`MatchKind` 를 걷어냈다.** 매칭이 파티 콕만 세므로 `pre`·`crossed` 는 나올 수 없다.
> 남는 길은 *"이 쌍은 매력 투표도 서로 했다"* 로 다시 정의하는 것뿐이었는데,
> **그건 붙일 의미가 없는 사실이다** — 프로필만 보고 서로 골랐다는 게 만나본 뒤의 결과를
> 더 설명해 주지 않는다. 죽은 값을 그리느니 지웠다 (운영자 현황의 네 갈래 카드와 줄마다 붙던 배지).

### 대가

**매칭이 줄어들 수 있다.** 위 표대로면 사전 콕이 만들던 4쌍이 사라진다.
**운영자가 콕 개수를 늘려 맞춘다** — 다음 회차 설정에서, 또는 파티 도중에.
콕이 자리 배정에도 쓰이므로 개수가 늘면 자리도 같이 좋아진다.

**앱을 열 이유가 얇아진다.** 알림이 없어지면 파티 중에 앱을 볼 이유가 콕 하나뿐이다.
같은 테이블 보기와 **운영자 투표**(슬라이스 14 — 서버는 있고 화면이 없다)가 그 자리를 맡는다.
부족하면 테이블 대화 카드·라운드 미션이 대기 중이다 (`PLAN.md` 20·22).

**나이차 −5 는 약한 손잡이다.** 지금은 10살 이상이 한 단이고 콕 하나(+10)가 그것을 덮는다.
`SEATING.md` 에 *3라운드에서 나이차 위반 26쌍* 이 났던 기록이 있으므로,
표본을 재보고 모자라면 값을 올린다. `buildSeating` 은 순수 함수라 숫자를 바꿔가며 잴 수 있다.

| | 어떻게 |
|---|---|
| **ADR-21** 명단은 사전 투표부터 열린다 | 기준이 **매력 투표 시작**으로 이름만 바뀐다 |
| **ADR-27·31** 사전 투표 전까지 고칠 수 있다 | 같음 — 경계는 그대로 한 곳이다 |
| **ADR-22·30** 받은 콕 순위 | 운영자 화면은 그대로. 참가자 알림만 사라진다 |

| **ADR-25** 여러 쌍 중 콕이 많은 쪽 | **함께 점수에 흡수된다** — 콕 개수가 곧 점수다 |
| **ADR-26** 실시간은 "다시 읽어라" 신호 | 그대로. 콕 알림만 빠진다 |
| **ADR-29** 지운 사람의 콕은 남긴다 | 그대로. 취소가 열려도 알림이 없어 안전하다 |

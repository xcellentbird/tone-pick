# 화면 요구사항

화면을 만들 때 지켜야 할 것. 문구는 전부 `src/shared/copy.ts` 에서 가져온다.
URL·히스토리 규칙은 `ROUTES.md`, 도메인 규칙은 `DOMAIN.md`.

---

## 전역 원칙

| 원칙 | 내용 |
|---|---|
| **되돌릴 수 없는 것만 확인을 받는다** | 콕 `+` · 단계 전환 · 참가자 삭제 · 자리 발송은 확인. 콕 `−`(되돌리기)와 자리 초안 생성은 즉시 |
| **확인창은 무엇이 어떻게 바뀌는지 숫자로** | "정말 하시겠습니까?"만 있는 다이얼로그는 만들지 않는다 |
| **문구가 버튼 이름과 겹치지 않게** | 본문에 "취소"를 쓰면 옆의 취소 버튼과 헷갈린다 → "되돌리기" |
| **에러는 그 값을 입력한 자리에** | 닉네임 중복이면 3스텝이 아니라 1스텝으로 되돌려 표시. 입력값은 보존 |
| **참가자에게 "0"을 들이대지 않는다** | 받은 콕 0회는 숫자 대신 별도 문구 (`REVEAL.noMutual`) |
| **일정은 30분 단위** | 파티 일정은 21:00 / 21:30 으로 잡힌다. 21:07 을 고를 수 있게 두면 고를 것만 많아지고 안내 문구에도 어중간한 시각이 나간다. `step` 은 피커만 붙잡으므로 **받은 값을 코드에서 맞춘다** (`snapSchedule`) |
| **"지금 바로"는 시각이 아니라 토글** | `datetime-local` 이 초를 버려서, "지금"을 시각으로 넣으면 매번 몇 초씩 어긋난다 |

## 화면별 요구사항

### 입장 `/`

링크 없이 **코드만 아는 사람**이 들어오는 문이다.

- 입장 코드 6자리 입력 + `운영자로 들어가기`
- 코드가 틀리면 **입력값을 지우지 않고** 인라인 에러만 (`ENTRY.notFound`)
- 맞으면 그 회차의 확인 화면(`/j/:id`)으로 바로 넘긴다 — **코드를 두 번 묻지 않는다**

### 회차 확인 `/j/:id` — 참가 링크가 여는 곳

- 보이는 것: 단계 · 회차 이름 · 파티 일시. **입장 코드는 응답에도 화면에도 없다**
- **전화번호**를 넣어야 등록으로 넘어간다 (ADR-15). 명단에 있는 번호만 통과한다
- 실패 문구는 하나뿐이다 (`ENTRY.notInvited`) — 왜 안 되는지 말하지 않는다
- 번호가 틀려도 **입력값을 지우지 않는다**
- 이미 등록한 사람은 번호만 넣으면 곧바로 자기 화면으로 간다 — 링크를 다시 여는 게 기본 동작이다
- 준비 중 회차면 언제 열리는지 알린다 (`ENTRY.notOpenYet`)

### 참가자 등록 `/j/:id/register/1..3`

| 스텝 | 항목 |
|---|---|
| 1 기본 정보 | 닉네임 · 실명 · 나이 · 성별(토글 2개) |
| 2 연락처 | 인스타(선택) — **전화번호는 묻지 않는다.** 입장할 때 확인했다 |
| 3 나를 소개 | MBTI 4문항 토글 · 매력 3가지 |

- **MBTI 는 16지선다 드롭다운이 아니라 4문항 토글** (`MBTI_AXES`). 모르는 사람도 답할 수 있어야 한다
- 선택 토글은 **입력값을 날리지 않는다.** 폼 전체를 다시 그리면 아직 저장 안 된 입력이 사라진다
- 닉네임 중복은 `REGISTER.err.nickTaken` + 1스텝으로 되돌림
- 이탈 시 `useDraftGuard` (`REGISTER.draftGuard`)

### 참가자 메인 `/e/:code`

3탭: **🏠 홈 / 👥 참가자 / 🙋 내 정보** (`TABS_PARTICIPANT`)

**탭마다 답하는 질문이 하나씩이고, 겹치지 않는다.** 같은 정보가 두 탭에 있으면
어느 쪽이 맞는지 눈이 한 번 더 확인하게 된다.

| 탭 | 질문 | 여기에만 있는 것 |
|---|---|---|
| 홈 | 지금 무슨 일이고 내가 뭘 하면 되나 | 단계별 **할 일 문장**, **내 자리**, 결과 요약(몇 명인지), **지금까지의 소식** |
| 참가자 | 누가 왔나 · 누굴 찌를까 | 목록·필터·프로필 시트·콕, 남은 콕 |
| 내 정보 | 내가 낸 것 · 내 결과 | 내 프로필, **매칭 상세**(누구인지), 회차 이름·코드 |

**알림을 탭으로 두지 않는 이유** — `fired` 에서 파생되는 것뿐이라 파티 한 번에 많아야 네 개다.
읽음 상태도 없어서(ADR-4) 받은편지함이 아니라 타임라인이고, 그건 "지금 무슨 일인가"의 과거형이다.
탭바의 자리는 그보다 비싸다.

- **단계 이름은 운영자 용어다.** 참가자에게는 할 일을 문장으로 준다 (`HOME.todo`)
- 결과는 홈에 **숫자만**, 상대가 누구인지는 내 정보에서 — 홈이 결과 화면이 되면 알림·내 정보가 빈다

**상단 한 줄** — 화면 맨 위에 `단계 · 남은 콕 · 카운트다운` 을 한 줄로 두고, 스크롤해도 남긴다.
참가자가 반복해서 확인하는 건 이 셋뿐이다. 단계와 무관한 카운트다운은 띄우지 않는다.

| 단계 | 표시 |
|---|---|
| 등록 중 | 인원 수 |
| 사전 투표 | 남은 콕 + 마감까지 `01:10:45` |
| 파티 진행 | 남은 콕 + 발표까지 (없으면 `revealSoon`) |
| 발표 완료 | `STATUS.done` |

- **카운트다운은 초까지 움직인다.** 분 단위면 멈춘 화면처럼 보인다. 폭이 흔들리지 않게 고정폭 숫자로
- **단계는 색으로도 구분한다** — 등록=회색 / 사전 투표=핑크 / 파티=골드 / 발표=완료색
- **회차 이름은 상단에 두지 않는다.** 입장·등록에서 이미 확인했고 파티 중에 다시 볼 일이 없다 →
  '내 정보' 탭. 상단은 세로 공간이 가장 비싼 자리다

**배너** — 최근 3분 이내의 단계 변화만 배너로 띄운다. 그보다 오래된 건 알림 탭에만.

- 단계 배너 → 누르면 홈. **홈에서는 띄우지 않는다** — 소식 목록이 이미 있다. 발표 되돌림은 `warn` 변형
- 자리 배너 → 누르면 내 정보 탭
- **자리 이동 확인**은 전체 화면을 덮는다. 단, **발표가 끝났으면 띄우지 않는다**

**참가자 탭**

- 카드 높이 **74px 고정**. 매력은 한 줄 말줄임 — 문장형 입력이 들어와도 카드 높이가 흔들리면 안 된다
- 프로필 시트에서는 매력 **전문**을 보여준다
- `이성만 보기` 토글
- 👉 버튼 = 콕 확인 다이얼로그 (`POKE.confirm`)

**소식 (홈 안)**

- `ev.fired` 에서 파생한다. 읽음 상태를 저장하지 않는다 (ADR-4)
- 익명 콕이 쌓이면 정보량 0인 카드가 반복된다 — 카운터로 합칠 것

**내 정보 탭**

- 실명·전화번호는 기본 가림. 파티장에서 어깨너머로 보인다
- 발표 후 상호 매칭은 **숫자만**. 이름과 힌트는 참가자 탭에 있다 (ADR-18)

### 운영자 콘솔 `/host/:id`

4탭: **현황 / 참가자 / 자리 / 설정** (`TABS_HOST`)

헤더에 `회차 목록` 버튼이 있다. 회차 하나에 갇히지 않는다 — 파티가 여러 개면 오가는 게 기본 동작이다.
회차 이름 아래에 코드 · 단계 · 등록 인원.

**현황** — 단계 컨트롤이 맨 위. 각 전환은 `phaseAction()` 의 항목을 보여주는 확인창을 거친다.
예약이 있는 전환(등록 시작·사전 투표 시작)은 `schedDiff()` 한 줄이 자동으로 붙는다.

그 아래는 **둘뿐**이다: 서로 찌른 커플(실시간) · 사전 투표 남녀 1위. 그리고 자리 확인율.
**공동 1위는 함께 보여준다** — 한 명만 집으면 나머지가 조용히 가려진다.

일부러 두지 않은 것 —
- **성비** · **등록 명단** — 참가자 탭에 있다. 같은 숫자를 두 곳에 두면 어느 쪽이 맞는지 눈이 한 번 더 확인한다
- **아직 콕을 못 받은 사람** — 알면 그 사람을 다르게 대하게 된다. 이 앱이 없애려던 경험이다
- **콕 총 횟수** — 운영 판단에 쓰이지 않는다

**참가자** — 맨 위가 **입장 명단**이다 (ADR-15). 비어 있으면 아무도 못 들어오므로 그때 가장 크게 말한다.
명단 편집은 시트에서 **더하기와 빼기만** 한다. 한 명씩 넣는 칸과 여러 명 붙여넣는 칸이 함께 있고,
붙여넣기도 있는 명단에 **더한다** — 통째로 갈아치우는 길은 두지 않는다 (ADR-15).

그 아래 전체 / 남성 / 여성 필터와 등록한 사람 목록. 셋 중 하나가 항상 켜져 있다.
목록 → 상세 시트. **삭제는 상세에서만**, `DELETE_PLAYER` 로 사라지는 데이터를 숫자로.

**자리** — 테이블 수 선택 → 초안 → 검토 → 발송. 상세는 `SEATING.md`.
초안은 참가자에게 렌더링하지 않는다.

테이블마다 `남 3 / 여 3` 을 적고, 좌석 칩을 성별로 칠한다(`--male` / `--female`) —
어두운 파티장에서 성비가 깨진 테이블을 색으로 먼저 찾는다.
**색만으로 구분하지 않는다**: ♂/♀ 기호와 숫자가 같은 정보를 함께 준다.
고른 칩의 보라 테두리가 성별 색보다 세다 — 지금 하는 일이 맞교환이라서.
**남녀도 맞바꿀 수 있다** (ADR-16). 바뀐 성비는 그 숫자에 바로 보인다.

**설정** — 이름·PIN·코드·콕 횟수·일정. **지나온 일정 항목은 잠근다** (`schedLocked`).
순서가 역전되는 값은 저장을 거부한다.

### 회차 위저드 `/host/new/1..3`

| 스텝 | 입력 | 검증 |
|---|---|---|
| 1 기본 정보 | 이름 · 입장 코드 | 코드 중복 불가 (비우면 자동) |
| 2 일정 | **파티 일시** · 등록 시작(`지금 바로` 토글) · 사전 투표 시작 | 사전 투표 시작 > 등록 시작 · 30분 단위 |
| 3 규칙 | 사전 콕 1~5 · 파티 콕 1~10 | 예상 매칭 안내를 함께 표시 |

### 회차 기본 설정 `/host/defaults`

콕 횟수 둘 · 일정 오프셋 둘. **운영자 PIN 칸은 없다** — 배포 시크릿 `MASTER_PIN` 하나가 유일한 출처다.
저장된 옛 모양은 읽을 때 지금 모양으로 맞춘다. 없는 항목이 그대로 올라오면 숫자 칸이 NaN 이 된다.

**파티 일시가 먼저다.** 나머지 두 시각은 거기서 거꾸로 계산된다 —
등록은 `regOpenBeforeD`(기본 6)일 전, 사전 투표는 `prevoteBeforeH`(기본 24)시간 전.

```
파티 일시를 옮기면  → 아직 손대지 않은 값만 따라 움직인다
직접 고친 값은      → 그대로 둔다. 고쳐놓은 걸 되돌리는 건 사고다
```

**예약하는 건 이 둘뿐이다.** 사전 투표 마감·파티 시작·발표는 현황 탭에서 운영자가 누른다 (ADR-14).
설정 화면에서 그 칸을 찾지 않도록, 일정 섹션 아래에 없는 이유를 적어둔다.

**콕 횟수 선택에는 예상 매칭을 함께 보여준다.** 기대 상호 매칭 쌍 수는 파티 규모와 무관하게
`k²` 에 수렴한다 (`pokeEstimate`, `pokeEstimateLabel`).

### 데모 뷰 `/demo/:id`

참가자 화면 1~3개를 나란히 띄우는 시연 도구.

- 각 화면은 **완전히 독립**적으로 동작한다 (탭·시트·확인창 전부 별개)
- **참가자 뷰를 따로 만들지 마라.** 같은 컴포넌트에 컨텍스트만 다르게 준다.
  두 벌로 갈라지면 데모가 거짓말을 하게 된다 (ADR-7)
- 폰 상태는 URL 에 담지 않는다

## 시트와 확인창

동작은 Radix Dialog 에서 빌려 쓰고 **모양은 우리 CSS 변수 그대로**다 (`src/client/ui/Sheet.tsx`).
손으로 만들었을 때 없던 것: 포커스 트랩·포커스 복원·**스크롤 잠금**·Escape·배경 비활성화.

- 재본 값: gzip **12KB**. 같은 자리를 antd 로 채우면 215KB 였다
- **히스토리는 여전히 우리가 쥔다.** 뒤로 가기로 닫히고 실행 **전에** 히스토리를 정리하는 규칙은
  라이브러리가 모른다 — 열림 상태를 밖에서 주고 닫힘 요청만 받는다
- Escape 는 **취소와 같다.** 닫히기만 하고 행동은 실행되지 않는다
- 데모 뷰에서는 포털 대상을 폰 요소로 준다. 기본값(document.body)이면 시트가 폰 밖에 뜬다

## 모바일 체크리스트

- `<meta name="viewport" ... viewport-fit=cover>`
- 높이는 `100dvh` — iOS 주소창 때문에 `100vh` 는 어긋난다
- 하단 탭바에 `padding-bottom: env(safe-area-inset-bottom)`
- 터치 타겟 최소 **44×44px**
- 입력 폰트 **16px 이상** — 미만이면 iOS 가 자동 확대한다
- 색·간격·모서리는 **CSS 변수로만**. 하드코딩 금지 (테마 교체의 토대)

- Rausch 는 예약 버튼의 색이다. 여기 버튼은 조심스럽게 누르는 콕이라 결이 다르다
- 소개팅 앱의 분홍·빨강은 가장 예상 가능한 선택이라 기억에 남지 않는다
- 앰버(파티)·청록(발표)과 색상환에서 가장 멀어 **단계 구분이 제일 또렷하다**

이 색은 버튼만이 아니라 **사전 투표 단계의 색**이다. 콕을 찌르는 시간의 색이라
경고처럼 튀지 않으면서 온기는 있어야 한다.

**밝은 쪽과 짙은 쪽을 나눠 쓴다.** 어두운 바탕 위의 글씨·테두리는 밝은 쪽(대비 5.9:1),
흰 글씨를 얹는 버튼은 짙은 쪽(5.7:1). 어두운 파티장에서 읽어야 하는 화면이라
대비에서 타협하지 않는다.

테마를 통째로 바꾸면서 **컴포넌트는 한 줄도 건드리지 않았다.** 색을 변수로만 쓰기로 한 규칙이
값을 한 자리에 모아둔 덕이다. 다음 테마도 같은 방식으로 갈아끼운다.
